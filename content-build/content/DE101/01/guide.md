**The big idea**: A relational table makes a promise a document store never makes — every row carries exactly the declared columns, with the declared types, and is identified by a key the engine itself guarantees. Three consequences are this lesson. The contract (schema, primary keys, foreign keys) is enforced at *write* time, so bad data is refused at the door rather than discovered by a query months later. A query's clauses *mean* things in a fixed logical order that is not the order you type them, which is why an alias works in `ORDER BY` and fails in `WHERE`. And the contract has one deliberate hole — `NULL`, the marker for "no value" — which drags SQL's logic from two truth values to three and silently drops rows from filters that look exhaustive. Nearly every "this query returned the wrong rows" bug in your first year of SQL is one of those three.

**Key concepts**

- **A table is an unordered set of rows over a fixed, typed schema.** *Mechanism:* you declare the columns and their types once; every row then supplies a value — or `NULL` — for every one of them, and the engine validates on write (schema-on-write). *Why it matters:* the alternative is what you already live with in Firestore and in a data lake: schema-on-read, where `'abc'` in a numeric field is stored cheerfully and discovered by whichever consumer touches it first. *Example:* given `users(user_id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE, country TEXT)`, an insert of `'abc'` as `user_id` is rejected, a row with no `email` is rejected, a duplicate `email` is rejected — and `country = NULL` is accepted, because nullability was a decision you made on that one column.

- **Rows are identified by keys, not by position, and a table has no intrinsic order.** *Mechanism:* a **primary key** is a column or column set the engine guarantees unique and non-`NULL`; several columns may qualify (*candidate keys* — both `user_id` and `email` here), and you designate one. *Why it matters:* any row order you observe without an `ORDER BY` is an accident of storage that can change after a data reorganisation, an engine upgrade, or a new plan. Code that depends on it breaks with no warning and no error. *Example:* `SELECT * FROM orders LIMIT 3` may return orders 1, 2, 3 today and 91, 4, 60 tomorrow, both correct.

- **A foreign key makes a dangling reference impossible, in the storage layer.** *Mechanism:* declare `user_id INTEGER NOT NULL REFERENCES users(user_id)` on `orders` and the engine refuses an order for user 999 when no such user exists, and refuses to delete user 7 while orders still point at them. *Why it matters:* this is **referential integrity**, and in Firestore you maintain the same discipline in application code, where it rots silently. *Judgment:* every constraint costs a check per write, so teams under heavy write load sometimes drop FK enforcement deliberately. That is a real tradeoff, not a free win.

- **Natural keys carry meaning; surrogate keys stay still.** An email is a *natural* key: readable, and it changes when a person changes address — and changing a primary key ripples through every foreign key pointing at it. A generated integer or UUID is a *surrogate*: meaningless, stable, cheap to index. Production systems overwhelmingly use surrogates for identity and add a `UNIQUE` constraint on the natural candidate to keep it honest.

- **The logical evaluation order is `FROM` → `WHERE` → `SELECT` → `ORDER BY` → `LIMIT`.** *Mechanism:* you write `SELECT` first, but it evaluates *third* — projection happens after filtering, so `WHERE` sees stored column values and never sees an alias. `ORDER BY` runs after projection, so it *can* see one. *Example:* over `orders` rows `(1, 40)`, `(2, 250)`, `(3, 120)`, `(4, 250)`, `(5, 95)`, the query `SELECT order_id, amount*2 AS a2 FROM orders WHERE amount > 100 ORDER BY a2 DESC, order_id LIMIT 2` keeps orders 2, 3 and 4, computes `a2` = 500, 240, 500, sorts to (2, 500), (4, 500), (3, 240), and returns the first two. Order 1's doubling never happens at all. Write `WHERE a2 > 100` instead and most engines raise *column "a2" does not exist* — the alias has not been created yet.

- **SQL is declarative, so the logical order is a reasoning tool and not a description of execution.** The optimiser may physically filter through an index before touching most rows, or push a predicate under a join, as long as the answer matches what the logical order specifies. When a result surprises you, replay the query in logical order; that resolves it most of the time.

- **Sorting is the only source of order, and only a *total* order is reproducible.** *Mechanism:* `ORDER BY` applies its sort keys lexicographically, each independently `ASC` (default) or `DESC`. If the key list does not uniquely determine a sequence, rows inside a tie group may come back in a different arrangement on every execution. *Example:* 30 rows share `amount = 100` and you sort by `amount` alone. Page 1 (`LIMIT 10`) and page 2 (`LIMIT 10 OFFSET 10`) are two separate queries, so a row can land on both pages or on neither. Appending the primary key — `ORDER BY amount DESC, order_id` — makes the order total and the paging reproducible.

- **`LIMIT`/`OFFSET` truncate the result set; limiting the output is not the same as limiting the work.** To serve `OFFSET 100000 LIMIT 10` the engine must still produce and discard 100,000 ordered rows, so cost grows linearly with page depth. **Keyset pagination** is the fix: remember the last row's sort-key values and ask for `WHERE (amount, order_id) < (100, 3117) ORDER BY amount DESC, order_id DESC LIMIT 10` — a seek instead of a scan-and-discard, and stable when rows are inserted between fetches. `ORDER BY score DESC LIMIT 10` is the same top-k your reranker performs, and a good engine implements it the way you would: a bounded heap of size k, not a full sort.

- **`NULL` is a marker for "no value", usually read as *unknown*, and it forces three-valued logic.** *Mechanism:* any comparison involving `NULL` returns `UNKNOWN` — including `NULL = NULL`, because two unknown quantities cannot be asserted equal. The connectives follow from asking whether the unknown could still change the outcome: `FALSE AND UNKNOWN` is `FALSE` (one false conjunct dooms the conjunction either way), `TRUE OR UNKNOWN` is `TRUE`, and everything else involving `UNKNOWN` stays `UNKNOWN`. `NOT UNKNOWN` is `UNKNOWN`. This is interval reasoning over {0,1} — the same move as bounding a probability you know only lies strictly between 0 and 1.

- **`WHERE` keeps a row only when the predicate is `TRUE`.** `FALSE` and `UNKNOWN` are both discarded, and that single rule is what makes `NULL` bite. *Example:* over `users` rows `(1,'PH')`, `(2,NULL)`, `(3,'SG')`, the filter `country = 'PH'` returns user 1, and `country <> 'PH'` returns user 3 — **not** users 2 and 3. The two filters together do not cover the table, because row 2 evaluates `UNKNOWN` in both directions. The membership tests that do work are `IS NULL` and `IS NOT NULL`, special predicates that return only `TRUE` or `FALSE`.

- **Deliberate tools for `NULL`.** `COALESCE(x, fallback)` returns the first non-`NULL` argument, mapping unknown to a sentinel *at projection time* (`COALESCE(country,'unknown')`). `IS DISTINCT FROM` is a null-safe inequality: `NULL IS DISTINCT FROM 'PH'` is `TRUE`, and `NULL IS NOT DISTINCT FROM NULL` is `TRUE`. It restores two-valued logic where you genuinely want "different, treating NULL as a comparable value".

**Rules to remember**

- Logical order: `FROM` → `WHERE` → `SELECT` → `ORDER BY` → `LIMIT`. `WHERE` cannot see an alias; `ORDER BY` can.
- A table is a set. No `ORDER BY`, no promised order — at any size, on any engine.
- Every `LIMIT` deserves an `ORDER BY`, and every paging `ORDER BY` deserves a unique tiebreaker.
- `OFFSET n` produces and throws away `n` rows. Deep paging wants keyset, not `OFFSET`.
- Comparisons with `NULL` return `UNKNOWN`, and `WHERE` keeps only `TRUE`. Use `IS NULL` / `IS NOT NULL`.
- `WHERE x NOT IN ('PH', NULL)` returns **zero rows, always** — it expands to `x <> 'PH' AND x <> NULL`, and the second conjunct is `UNKNOWN` for every row.
- `SELECT DISTINCT` deduplicates whole output rows *after* projection. It is not a per-column operation.

**Common pitfalls**

- **Trusting an unordered result that happens to look ordered.** Small tables often come back in insertion order, which trains the habit; it breaks in production after a reorganisation, with no error.
- **Assuming `= 'x'` and `<> 'x'` partition a nullable column.** They cover it only where the column is non-`NULL`. This is the single most common cause of silently missing rows in a filter — and it does not raise anything, so nothing tells you.
- **Encoding "unknown" as `0` or `''` to dodge three-valued logic.** Those collide with legitimate values and can never be told apart afterwards. `NULL` at least declares itself. The real fix is upstream: declare `NOT NULL` wherever the domain guarantees a value, and reserve nullable columns for facts that are genuinely optional.
- **Believing the optimiser's freedom changes the meaning.** It may reorder work physically; it may never return a different answer than the logical order specifies. If the answer changed, something else did.
- **`SELECT *` in production code.** It drags wide columns across the network and silently changes your output shape the day someone adds a column. Fine for exploration; brittle everywhere else.
- **Paging with `OFFSET` over a live table.** Rows inserted between page 1 and page 2 shift every subsequent page down, so a row you already showed reappears. Keyset paging is immune, because it anchors on values rather than on a count.

**How to approach the questions**

1. For anything about clause behaviour, replay the query in logical order and ask *what exists yet*. An alias in `WHERE` is an error; an alias in `ORDER BY` is fine — the same rule answers both.
2. When a scenario says rows are missing, duplicated across pages, or inconsistent between runs, there are only two suspects: a `NULL` falling through a comparison, or a sort that is not a total order. Decide which before reading the options.
3. For any `NULL` question, evaluate the predicate *per row* to `TRUE`/`FALSE`/`UNKNOWN` and then apply the gate: only `TRUE` survives. Do not shortcut to "it's true-ish".
4. For key questions, ask what the engine *guarantees* versus what the modeller *intended*. `PRIMARY KEY` and `UNIQUE` are guarantees; "this should be unique" is not, and distractors trade on the difference.
5. Watch for cost claims about `LIMIT`. Truncating the output is not the same as skipping the work, and `OFFSET` is the case where that gap is visible.

**Where this leads**: keys are what make a join meaningful, and the *uniqueness* of a key is what makes a join's row count predictable. The next lesson, **Joins**, is where a key you only believed was unique starts multiplying rows downstream — and where `NULL`'s three-valued logic returns with real force in the difference between `NOT IN` and `NOT EXISTS`.
