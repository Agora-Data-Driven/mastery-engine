1. The Contract Desk

You already store data in a document store, where a write is accepted first and judged later. A relational table judges it at the door. Send each proposed write through both and watch where the disagreement is. Like a bouncer with the guest list versus one who lets everyone in and sorts it out inside.

2. Logical Order Machine

You type SELECT first. It runs third. Step a query through the order it actually means things in and the alias bug stops being a mystery. Like a recipe: you name the dish at the top, but you still chop before you plate.

The optimiser is free to do this work in a different physical order — filter through an index before touching most rows, for instance. It is never free to return a different answer than this order specifies. That is why the ladder is a reasoning tool, not a description of execution.

3. Pagination Roulette

Six orders tie at 300. Page 1 and page 2 are two separate queries, so the engine is free to arrange that tie group differently in each. Hit re-run and watch rows appear twice or vanish. Like shuffling a deck between dealing hand one and hand two.

Two separate lessons, one clause. A sort that is not a total order is not reproducible, so paging over it is a lottery. And OFFSET truncates the output without saving the work — which is why deep paging uses keyset: WHERE (amount, order_id) < (300, 106), a seek instead of a scan-and-discard, and immune to rows inserted between fetches.

4. Three-Valued Gate

NULL means unknown, so a comparison against it is neither true nor false. Set the two operands and read off what SQL concludes — then watch the WHERE gate, which keeps a row only when the answer is exactly TRUE. Like a witness who says "I don't know": not a yes, and not a no either.

Derive it rather than memorise it: treat UNKNOWN as "could be either" and ask whether that freedom can still change the answer. FALSE AND anything is FALSE because one false conjunct dooms the conjunction whichever way the unknown lands. TRUE OR anything is TRUE for the mirror reason. Everywhere else the unknown survives — and a surviving unknown is a dropped row.

5. Where NULL Hides

Five users, two of them with an unknown country. Run each predicate and read the per-row verdict. The tally at the bottom is the point: two filters that look like opposites do not cover the table between them. Like a survey where "did not answer" is neither a yes nor a no, so both bar charts are short.

The fix at query time is IS NULL / IS NOT NULL, which never return UNKNOWN, or COALESCE to map unknown onto a sentinel at projection time. The fix at design time is better: declare NOT NULL wherever the domain guarantees a value. Every nullable column taxes every future query that touches it.
