**The big idea**: Two things you already have decide almost everything in this lesson. From **Tables, Rows, and Keys: The Relational Contract**, a key is either unique on a side or it is not — and that single fact determines how many rows a join emits. From **NULL Semantics and Three-Valued Logic**, a comparison against `NULL` is `UNKNOWN` and only `TRUE` survives a filter — which is why a row with a `NULL` join key matches nothing, and why a `LEFT JOIN` can be silently demoted to an inner one by a line in `WHERE`. Joins go wrong in exactly two directions: rows silently **vanishing** and rows silently **multiplying**. Neither raises an error. This lesson is the vocabulary plus the row-count discipline that catches both.

**Key concepts**

- **Every join means: form the Cartesian product, then keep the pairs where `ON` is `TRUE`.** *Mechanism:* no engine literally builds the product — it hashes, or walks an index — but the *meaning* is exactly that, and reasoning from it never lies. *Example:* 3 users × 3 orders is a 9-cell grid; `ON o.user_id = u.user_id` marks 3 cells `TRUE` and an inner join returns those 3 rows. *Why it matters:* the product view makes both failure modes visible in advance. A left row with no `TRUE` cell in its row of the grid disappears; a left row with three `TRUE` cells comes back three times.
- **An inner join's output size is the number of matching pairs — which can be smaller *or* larger than either input.** Over `users` (1,'PH'), (2,'SG'), (3,'PH') and `orders` (10→1, 40), (11→1, 250), (12→3, 120), the inner join returns 3 rows: user 1 twice, once per order, and user 2 not at all. Both are definitional, not bugs.
- **A `NULL` join key matches nothing, ever — not even another `NULL`.** `NULL = NULL` is `UNKNOWN`, and a join keeps only `TRUE`. That is lesson 01's rule arriving in a new place, and it is why an unmatched-looking row is sometimes a `NULL` key rather than missing data.
- **The join happens inside `FROM`, so it is first in logical order:** `FROM`+`JOIN` build the combined rows, then `WHERE` filters them, then `SELECT` projects. For an **inner** join, a condition in `ON` and the same condition in `WHERE` give identical results. Experts still put join keys in `ON` and business filters in `WHERE`, purely as habit — because that equivalence is about to break.
- **Outer joins preserve unmatched rows and pad the other side with `NULL`.** `LEFT JOIN` keeps every left row (unmatched ones appear once with every right column `NULL`); `RIGHT JOIN` is its mirror and is rarely written, since `a RIGHT JOIN b` is `b LEFT JOIN a` with the tables swapped and pipelines read better with the preserved table first; `FULL JOIN` keeps both sides, whose canonical use is **reconciliation** — full-join yesterday's export to today's on the key and the `NULL`-on-one-side rows are precisely the adds and the deletes. On the data above, `users u LEFT JOIN orders o` returns 4 rows: the 3 inner rows plus `(2,'SG',NULL,NULL)`.
- **For an outer join, `ON` and `WHERE` are not interchangeable, and this is the weekly trap.** *Mechanism:* a condition in `ON` decides *what counts as a match* — failing it leaves the left row unmatched but still preserved. A condition in `WHERE` filters *the joined result* — failing it deletes the row. *Example:* `LEFT JOIN orders o ON o.user_id = u.user_id WHERE o.amount > 100` evaluates `NULL > 100` for user 2, gets `UNKNOWN`, and drops them. Every unmatched left row dies the same way, so the `LEFT` accomplished nothing at all and you have written an inner join in four extra characters. Move the predicate into `ON` to keep all users and join only their big orders, or write `WHERE o.amount > 100 OR o.order_id IS NULL` to let the padding through explicitly — or, if you really did want only matched rows, write `JOIN` and say so.
- **`LEFT JOIN … WHERE right.pk IS NULL` is the "childless parents" idiom** — it returns exactly user 2. Test a column that is `NOT NULL` in the base table; the primary key is ideal. Testing a naturally nullable column cannot tell "no match" apart from "matched, and that field is `NULL`".
- **A semi-join asks *does a match exist*, and returns each left row at most once.** *Mechanism:* `WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.user_id)` probes for at least one row and stops at the first hit. The `SELECT 1` is not read; only the existence of a row matters. *Why it matters:* output grain is exactly the grain of `users` — never multiplied, no `DISTINCT` needed — and the early stop is a real win when a user has thousands of orders. Result: users 1 and 3, once each.
- **The anti-join is its negation, `NOT EXISTS`** — left rows with no match, here user 2. Semantically the same question as left-join-then-`IS NULL`, and optimisers usually execute both identically; `NOT EXISTS` just states the intent directly.
- **`NOT IN` against a nullable column is a defect, not a style choice.** `u.user_id NOT IN (SELECT user_id FROM orders)` looks equivalent, and it is lesson 01's trap wearing a subquery: one `NULL` anywhere in that column puts a `<> NULL` conjunct in the expansion, every row evaluates `UNKNOWN`, and the query returns **zero rows** silently. `NOT EXISTS` has no such mode — a probe comparison that comes out `UNKNOWN` simply means that probe row is not a match. `IN` is tolerable; `NOT IN` should be `NOT EXISTS`.
- **Fan-out is the counting rule: a key value appearing $m$ times on the left and $n$ times on the right emits $m \times n$ rows.** FK→PK is the safe case, because $n$ is at most 1. Many-to-many is the dangerous one. *Example:* join `users` to `orders` **and** to `logins`, both one-to-many, and a user with 3 orders and 4 logins produces $3 \times 4 = 12$ rows — every order repeated 4 times, every login 3 times. Nothing errors. `SUM(amount)` over that result counts each order four times, so a revenue report overstates that user by 4× and another user by a *different* factor, which is what makes the error so hard to spot: no single scale factor explains the total.
- **Fan-out is a defect only when the consumer assumes the old grain.** "One row per order with user attributes attached" is often exactly the goal. The bug is the silent change from "one row per user" to "one row per user-order pair" while something downstream still counts as if nothing moved.

**Rules to remember**

- Join = product, then keep `ON` = `TRUE`. Output rows = number of matching pairs.
- `NULL` never matches, on either side, under any join type.
- Inner join: `ON` and `WHERE` are interchangeable. Outer join: they are not, and the difference is preserved-vs-deleted.
- A predicate on the nullable side in `WHERE` converts a `LEFT JOIN` into an inner join. Every time.
- Need columns, or one row per match? Join. Need each left row at most once? Semi-joins (`EXISTS`) and anti-joins (`NOT EXISTS`).
- `m` on the left × `n` on the right = `m × n` rows for that key value. One-to-one multiplies nothing; one-to-many multiplies the one side; many-to-many multiplies both.
- To combine two one-to-many relationships, aggregate each to one row per key **first**, then join those results.

**Common pitfalls**

- **Reaching for `DISTINCT` to fix a row count.** It hides the duplication rather than removing its cause, costs a sort or hash, and can mask a *second* fan-out elsewhere in the query. A `DISTINCT` that "fixed" a count is a flag that the grain went wrong upstream, not a fix.
- **Trusting a naming convention as a uniqueness guarantee.** `UNIQUE` and `PRIMARY KEY` are machine-checked; a column called `..._id` is a hope. Fan-out arrives the day the hope turns out to be false, and by then the report has been trusted for months.
- **Using `LEFT JOIN` everywhere "to be safe".** It changes nothing when the key is a real FK, and when it does matter you have usually already destroyed it with a `WHERE` predicate on the right side. Say which rows you want to preserve, deliberately.
- **Diagnosing "missing rows" without checking for `NULL` keys.** A row with a `NULL` foreign key looks identical to a row whose parent was deleted, and only one of those is a referential-integrity problem.
- **Reconciling two exports with a `LEFT JOIN`.** It only ever finds the deletes. The adds live on the other side, which is exactly what `FULL JOIN` exists for.
- **Aggregating after a many-to-many join and sanity-checking only the grand total.** The inflation factor differs per key, so the total can look plausible while every individual row is wrong.

**How to approach the questions**

1. For any join question, first count: how many times does the key value appear on each side? Multiply. That single number answers most "how many rows are returned" questions before you read the options.
2. When a scenario says a `LEFT JOIN` "did not work", look for a predicate on the right-hand table in `WHERE`. That is the answer far more often than anything else.
3. For `NOT IN` versus `NOT EXISTS`, the deciding question is always whether the subquery column can be `NULL`. If it can, `NOT IN` returns nothing at all — not "fewer rows", nothing.
4. When a total is inflated, do not look for a factor. Look for a second one-to-many join in the same query, and check whether the factor is even constant across keys.
5. Distinguish *what counts as a match* (`ON`) from *what survives the join* (`WHERE`). Distractors are built almost entirely out of confusing those two.
6. When a question describes an existence test rather than a combination, name it: semi-joins return matching left rows once, anti-joins return the non-matching ones once. Any option that multiplies rows is answering a different question.

**Where this leads**: the cure for fan-out is to reduce each side to the grain you want *before* joining, and that means aggregation.
