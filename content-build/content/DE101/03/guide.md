**The big idea**: Aggregation changes the **grain** of a result — millions of rows become one row per customer, per day, per model version. Two things you already have decide whether that collapse tells the truth. From **Join Fan-out: Row Duplication When Keys Are Not Unique**, a total computed over duplicated rows is inflated, and no aggregate can undo that afterwards: `GROUP BY` sums whatever rows it is handed. From **NULL Semantics and Three-Valued Logic**, `NULL` behaves differently here than it did in a join — `NULL = NULL` still is not `TRUE`, yet all the `NULL`s form one group together, and the aggregate functions each treat them their own way. Write the intended output grain in words first, then trace how each clause reaches it. Almost every aggregation bug is a clause acting on the wrong side of the collapse.

**Key concepts**

- **`GROUP BY` partitions rows into equivalence classes and emits one row per class.** *Mechanism:* rows land in the same group when their grouping expressions compare equal; the aggregate functions then consume all rows of a group and return one value each. *Example:* over `retrieval_runs` rows `(factoid,120)`, `(factoid,180)`, `(research,900)`, `(factoid,NULL)`, grouping by `query_class` gives the factoid group `COUNT(*)=3`, `COUNT(latency_ms)=2`, `SUM=300`, `AVG=150`. With several grouping columns the grain is their **combination**: `GROUP BY run_date, model_version` means one row per date-version pair.
- **No `GROUP BY` at all means one implicit group over the whole filtered input.** `SELECT COUNT(*) FROM retrieval_runs` emits exactly one row, and it emits one even when the table is empty.
- **`NULL` grouping values form a single group together** — deliberately unlike an equality join, where `NULL = NULL` is `UNKNOWN` and matches nothing. Rows with an unknown `model_version` are still counted, in one `NULL` bucket. This exception exists because the alternative is losing them entirely.
- **The aggregates disagree about `NULL`, and the differences are load-bearing.** `COUNT(*)` counts **rows**, including rows full of `NULL`. `COUNT(expr)` counts only rows where `expr` is non-`NULL`. `SUM`, `AVG`, `MIN` and `MAX` all skip `NULL`s — so `AVG(x)` is `SUM(x)/COUNT(x)`, **not** `SUM(x)/COUNT(*)`. Over the factoid group that is `300/2 = 150`, not `300/3 = 100`. When every input value in a group is `NULL`, the value aggregates return `NULL` while the counts return `0`.
- **The logical order gains two rungs:** `FROM`+`JOIN` → `WHERE` → `GROUP BY` → aggregates computed → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. Everything about this lesson follows from where a clause sits relative to the grouping step.
- **`WHERE` filters rows before groups exist; `HAVING` filters completed groups after aggregate values exist.** *Mechanism:* `WHERE` cannot reference an aggregate, because none has been computed yet; `HAVING` cannot reference an ungrouped, unaggregated column, because a group has many values for it. *Example:* version A has successful latencies 100 and 300 plus a failure at 2,000; version B has successes at 700 and 900. `WHERE status='success'` then `HAVING AVG(latency_ms) > 500` gives averages A=200, B=800 and returns **B only**. Let the failure into the population and A averages 800 and qualifies too. The clause placement is what decided which population the metric described.
- **A predicate on a *grouping key* may legally sit in either clause, and belongs in `WHERE`.** `WHERE model_version='v3'` and `HAVING model_version='v3'` return the same groups, but `WHERE` discards rows before grouping — less shuffle, less aggregate state — and it says the condition is about source rows rather than about a computed group. Optimisers often push a safe `HAVING` predicate down anyway; clear SQL should not depend on that rewrite.
- **`HAVING COUNT(*) >= 100` is the standard evidence gate**: keep only groups with enough observations before you believe their rate. For conditional evidence, the portable form is `SUM(CASE WHEN relevant THEN 1 ELSE 0 END)`; dialect helpers like `COUNTIF` do the same thing.
- **`COUNT(DISTINCT expr)` counts unique **non-`NULL`** values within each group,** and is a third, different number. *Example:* for `q1` with `document_id` values `d7, d7, d9, NULL`: `COUNT(*)=4`, `COUNT(document_id)=3`, `COUNT(DISTINCT document_id)=2`.
- **`COUNT DISTINCT` is not a slightly slower count — it is a set-construction problem.** *Mechanism:* the engine must maintain or derive the set of values seen. A hash aggregate is expected $O(n)$ work but holds memory proportional to *distinct cardinality*; a sort-based plan is $O(n\log n)$ comparisons but spills and merges predictably. In a distributed warehouse, rows sharing a distinct key must usually be shuffled to the same worker, so network movement dominates. *Example:* one billion events with 200 million unique user IDs. `COUNT(*)` needs one integer counter per partial aggregate. Exact `COUNT(DISTINCT user_id)` needs state representing 200 million IDs, plus repartitioning and a merge. One word of SQL changed the physical problem.
- **Distinct counts are non-additive across overlapping groups.** Summing daily distinct users does *not* give monthly distinct users — a person active on three days is counted three times. The monthly number must deduplicate at month grain. This is the single most common wrong dashboard number in the industry.
- **Approximate cardinality is a real answer for the right question.** HyperLogLog keeps a compact sketch and estimates with known relative error: appropriate for dashboards and capacity trends, never for billing, uniqueness enforcement, or an exact evaluation denominator. Pre-aggregation is the other lever — deduplicate `(day, user_id)` near ingestion and count a far smaller table — but it is still not summable across months.
- **Every selected column must have a one-value-per-group explanation.** *Mechanism:* after grouping, a group holds many source rows, so a selected expression must be a grouping expression, an aggregate, or a value the dialect can prove functionally determined. *Example:* `SELECT customer_id, order_id, SUM(amount) FROM orders GROUP BY customer_id` is invalid in standard SQL — which `order_id`? Strict engines reject it; permissive modes pick an arbitrary member, and that choice can change with the plan, the storage order, or the parallelism.
- **Aggregates operate independently, so a `MAX` and a bare column are not from the same row.** `SELECT query_id, document_id, MAX(score) FROM ranked_results GROUP BY query_id` does **not** return the top-scoring document. For q1 rows `(d1, 0.9)` and `(d2, 0.7)`, the answer you wanted is `(d1, 0.9)` and a permissive engine may emit `(d2, 0.9)` — a pair that never existed in the data. Adding `document_id` to the `GROUP BY` makes it legal and changes the grain to one row per query-document, which is not the summary you asked for.

**Rules to remember**

- Logical order: `FROM` → `WHERE` → `GROUP BY` → aggregates → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`.
- `WHERE` = row filter, before grouping. `HAVING` = group filter, after aggregates exist. Neither can do the other's job.
- `COUNT(*)` counts rows; `COUNT(x)` counts non-`NULL` values of `x`; `COUNT(DISTINCT x)` counts unique non-`NULL` values.
- `AVG(x) = SUM(x)/COUNT(x)`. Missing values are excluded from the denominator, not treated as zero.
- All-`NULL` group: counts are `0`, `SUM`/`AVG`/`MIN`/`MAX` are `NULL`.
- `NULL`s group together under `GROUP BY`, even though they match nothing under a join.
- Distinct counts never sum across overlapping groups. Deduplicate at the grain you want to report.
- A selected column must be grouped, aggregated, or provably determined. "It happens to look constant" is not an explanation.

**Common pitfalls**

- **Aggregating after a fan-out and trusting the total.** `GROUP BY` faithfully sums the rows it is handed, so a query that joined orders to both line items *and* logins multiplies every amount before the `SUM` ever runs. Aggregate each one-to-many source to the target grain first, then join. No amount of `DISTINCT` fixes it — and `COUNT(DISTINCT query_id)` can look right while `SUM(cost)` beside it stays wrong, which is how these survive review.
- **`COALESCE`-ing missing measurements to zero without deciding what missing means.** If `NULL` latency means "not measured", turning it into `0` fabricates a fast request and drags the average down. If it genuinely means zero, say so deliberately. `AVG` already excludes unknowns; that default is usually the honest one.
- **Summing daily distinct counts into a monthly figure.** It is always an overcount, by exactly the amount of repeat activity you were probably trying to measure.
- **Adding a column to `GROUP BY` to silence an error.** It makes the query legal by changing the grain, which means it now answers a different question — and usually the one you were aggregating to avoid.
- **Relying on a permissive engine's arbitrary pick.** It is not a documented value, it is whatever fell out of this plan, and distributed execution is free to choose differently tomorrow. If any representative truly suffices, write `ANY_VALUE(...)` and document the nondeterminism.
- **Assuming a functional dependency survives a join.** `customer_name` is determined by a `customer_id` primary key — until a dimension join duplicates that key, at which point the "constant" column has several values in one group.

**How to approach the questions**

1. Say the output grain out loud before anything else — "one row per X". Then check each clause against it. Most wrong answers are grains, not syntax.
2. For a `WHERE`-versus-`HAVING` question, ask which **population** the aggregate should describe. A filter that changes the population belongs in `WHERE`; a test of a computed group value belongs in `HAVING`.
3. For any counting question with a `NULL` in the data, compute all three counts. The distractors are almost always the other two numbers.
4. When a total looks inflated, look upstream for a second one-to-many join, not for a bug in the aggregate.
5. Treat "select a non-aggregated column" as a correctness defect even when an engine allows it, and prefer the repair that keeps the grain: aggregate at key grain, then join the one-row-per-key dimension.

**Where this leads**: `GROUP BY` gets you a per-group value at the cost of the rows themselves — you cannot see the individual order beside its customer total.
