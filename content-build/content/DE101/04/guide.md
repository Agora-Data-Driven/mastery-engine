**The big idea**: **GROUP BY Mechanics and Aggregate Functions** bought you a per-group number by destroying the rows — you get the customer total, and the individual order is gone. A window function computes over a related set of rows and **attaches the answer to every row**, so the grain survives. That one change unlocks the questions grouping could not answer: rank documents inside each query, compare today with yesterday, attach a rolling average to every request, and finally return *the document with the maximum score* rather than the arbitrary pairing **GROUP BY Pitfalls: Non-Aggregated Columns** warned you about. The whole subject is three independent choices that must never be blurred: which rows share a **partition**, how those rows are **ordered**, and which ordered rows are inside the current **frame**.

**Key concepts**

- **`OVER (...)` defines the set of rows a function sees, without collapsing anything.** *Mechanism:* the function is evaluated per row against its window; the row itself is still emitted. *Example:* over `(q1,d1,0.90)`, `(q1,d2,0.70)`, `(q2,d3,0.80)`, the query `SELECT query_id, document_id, score, AVG(score) OVER (PARTITION BY query_id) AS query_avg` returns **three** rows — both q1 rows carrying 0.80, q2 carrying 0.80. `GROUP BY query_id` would have returned two rows and thrown the documents away.
- **`PARTITION BY` divides rows into independent windows; omit it and the partition is everything.** With no `PARTITION BY`, every row after `FROM`/joins/`WHERE` shares one window and receives the global value. That is legal, occasionally right, and a scalability trap — a global window funnels all state into one logical partition.
- **Windows are evaluated after `GROUP BY` and `HAVING`, but before the final `ORDER BY`.** So a window can operate on grouped output: `SELECT run_date, COUNT(*) AS requests, SUM(COUNT(*)) OVER () AS all_requests … GROUP BY run_date` first makes one count per date, then the windowed `SUM` adds those grouped rows without collapsing them further. Everything about the placement rules follows from that position in the order.
- **A window result cannot go in `WHERE`, because `WHERE` runs earlier.** Wrap the query in a subquery and filter outside it, or use `QUALIFY` where the dialect has it: `QUALIFY ROW_NUMBER() OVER (PARTITION BY query_id ORDER BY score DESC, document_id) <= 10` keeps the top ten **per query**. A global `LIMIT 10` keeps ten rows in total — a completely different grain, and a very common wrong answer.
- **Ranking functions require an `ORDER BY` inside `OVER`, and they differ only on ties.** For scores 100, 90, 90, 70 descending: `ROW_NUMBER` gives 1, 2, 3, 4 — unique, so the two 90s get different numbers and *which one gets 2 is nondeterministic* without a tie-breaker. `RANK` gives 1, 2, 2, 4 — equal values tie, then the count of preceding rows creates a gap. `DENSE_RANK` gives 1, 2, 2, 3 — ties with no gap, so it numbers *distinct values*.
- **Choose the ranking function by the sentence you would say out loud.** "Exactly one latest row per entity" is `ROW_NUMBER` with deterministic tie-breakers, keeping row 1. "Competition position" is `RANK`: two entrants tied for second means the next is fourth. "The first three distinct score tiers" is `DENSE_RANK <= 3`, and it may return more than three rows.
- **Deduplication is the workhorse pattern.** `QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY updated_at DESC, ingest_id DESC) = 1` keeps one row per `event_id`: latest timestamp, then largest stable ingestion id. Drop `ingest_id` and equal-timestamp duplicates become nondeterministic; use `RANK = 1` instead and tied rows all survive, so it does not deduplicate at all.
- **Adding `ORDER BY` to an *aggregate* window makes it order-sensitive and introduces a frame.** *Mechanism:* the frame says which ordered rows contribute to the current row's answer. `SUM(cost) OVER (PARTITION BY project_id ORDER BY event_time, event_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` is a running total — costs 10, 20, 5 give 10, 30, 35. `AVG(latency_ms) OVER (ORDER BY event_time, event_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` is a three-row moving average — latencies 10, 20, 30, 80 give 10, 15, 20, and $(20+30+80)/3 = 43.33$. Early rows simply use the smaller frame available; SQL does not invent missing predecessors.
- **`ROWS` counts physical rows; `RANGE` groups *peers* that share the same ordering value.** *Why it matters:* many engines default an ordered aggregate window to the equivalent of `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, so tied ordering values change the answer. *Example:* amounts 10 and 20 both at 09:00, then 5 at 10:00. Under `ROWS` with a deterministic tie-break the running totals are 10, 30, 35. Under peer-inclusive `RANGE` both 09:00 rows read 30, then 35. Neither is wrong — `ROWS` answers "through this physical event", `RANGE` answers "through this ordering value" — but only one of them is what you meant, and the default picked for you.
- **`LAG(expr, offset, default)` reads an earlier row; `LEAD` reads a later one; default offset is 1.** They do not join anything — `PARTITION BY` and `ORDER BY` are what define "previous" and "next". *Example:* error rates 0.02, 0.03, 0.01 for one service give previous values `NULL`, 0.02, 0.03 and changes `NULL`, +0.01, −0.02. The first row has no predecessor, which is a fact worth preserving.
- **`LAG` compares *rows*, not time periods.** If Tuesday is missing from the data, Wednesday's `LAG` is Monday, and the query cheerfully reports a day-over-day change that spans two days. `LAG(value, 7)` means seven rows earlier, not seven calendar days. When the requirement is genuinely calendar-based, join to a calendar table to materialise the missing rows first, or use a date-keyed self-join.
- **`FIRST_VALUE` / `LAST_VALUE` read the window's boundary values,** and are the natural way to normalise within a group: `score / FIRST_VALUE(score) OVER (PARTITION BY query_id ORDER BY score DESC)` turns absolute scores into within-query relative ones. The frame caution bites hardest here — with the default frame, `LAST_VALUE` sees only rows up to the current one, so it returns "the value so far" rather than the partition's final value unless you declare the full frame explicitly.

**Rules to remember**

- `GROUP BY` changes the grain; `PARTITION BY` does not. Same partitioning idea, opposite effect on row count.
- Windows run after `GROUP BY`/`HAVING` and before the final `ORDER BY`. They cannot appear in `WHERE`; use a subquery or `QUALIFY`.
- `ROW_NUMBER` = unique, `RANK` = ties with gaps, `DENSE_RANK` = ties without gaps.
- Give `ROW_NUMBER` a full tie-breaker. Give `RANK`/`DENSE_RANK` only attributes that define a *real* tie — an arbitrary tie-breaker destroys the tie by making the ordered tuple distinct.
- `ORDER BY` inside `OVER` decides rank. The query's final `ORDER BY` decides display. Never assume one controls the other.
- State the frame explicitly in production analytics. `ROWS` = physical rows, `RANGE` = peers sharing the ordering value.
- "Last 100 requests" is inherently a `ROWS` question. "Previous 24 hours" is not — a fixed row count is wrong whenever the event rate varies.
- `LAG` returns `NULL` for the first row of a partition. That `NULL` means "no comparison exists"; a default of 0 means "compare against zero", which is a different claim.

**Common pitfalls**

- **`ROW_NUMBER` with an incomplete `ORDER BY`.** It runs, it looks deterministic, and it silently picks a different survivor after a plan change — which turns a deduplication job into a source of drift. Add a stable unique key.
- **Trusting the default frame.** An ordered aggregate window without an explicit frame is `RANGE`-flavoured on most engines, so duplicate ordering values make several rows jump to the same running total together. It looks like a data bug and is a specification gap.
- **Assuming `LAST_VALUE` means "the last value".** With the default frame it means "the last value up to here", which is just the current row.
- **Rounding before ranking.** Truncating a similarity score to two decimals manufactures ties that the data does not contain. Rank on the full precision and round for display only.
- **Adding a tie-breaker to `RANK` to make it "cleaner".** That is `ROW_NUMBER` with extra steps, and it destroys exactly the tie semantics you chose `RANK` for.
- **Letting a window paper over a join defect.** If an upstream join duplicated each chunk, both the row count *and* the `COUNT(*) OVER (...)` are wrong together, and they agree with each other, which is what makes it convincing. Fix the base grain before adding analytic context.
- **Using a global unpartitioned window on a large table.** It imposes one total order and colocates all state in one logical partition. Partition on the real analytical unit, and filter before you window.

**How to approach the questions**

1. For any window question, name the three choices separately — partition, order, frame — before reading the options. Most distractors change exactly one of them.
2. Ranking questions with ties are almost always testing which of the three functions produces the given number sequence. Write out 1,2,3,4 / 1,2,2,4 / 1,2,2,3 and match.
3. If a question puts a window in `WHERE`, the answer is that it cannot be there. Look for the subquery or `QUALIFY` option.
4. For running totals, ask whether the ordering column can have duplicates. If it can, `ROWS` versus `RANGE` is the whole question.
5. For `LAG`/`LEAD`, check whether the data is guaranteed one row per period. Missing periods and duplicate periods are the two ways "previous" stops meaning what the query author assumed.
6. When a question distinguishes "top 10 per group" from "top 10 overall", the grain is the answer: `QUALIFY … <= 10` versus `LIMIT 10`.
