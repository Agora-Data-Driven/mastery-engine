**The big idea**: You now have four operations that each move the grain — **Join Fan-out** multiplies it, **GROUP BY Mechanics** collapses it, **OVER and PARTITION BY** preserves it, and a filter narrows it. Real queries chain several of those together, and this lesson is how you chain them without losing track. A CTE gives each stage a **name and an inspectable contract**. A subquery answers a question inside a query, and whether it is *correlated* decides whether it is one cheap computation or a million. `UNION` versus `UNION ALL` is the same distinction `COUNT` versus `COUNT DISTINCT` already taught you, applied to whole rows. None of the three absolves you from saying what one row represents at every stage — that is still the job.

**Key concepts**

- **A common table expression (CTE) names a query result for the length of one statement.** *Mechanism:* `WITH name AS (…)` creates a stage that later stages — and the final `SELECT` — can reference; a CTE may reference earlier CTEs in the same `WITH` list, so a chain of common table expressions forms an acyclic, readable query pipeline. *Example:* `valid_runs` filters to judged rows and keeps query-run grain; `per_model` groups it to one row per model version; the final query filters those summaries with `WHERE queries >= 100`. Three stages, three named grains, each one readable on its own.
- **A CTE is not a table, a view, or a temp table.** It lasts for the statement. A **view** is a catalog object reusable across statements; a **temporary table** materialises data for a session, can be indexed, and can be read by several statements. Choosing between them is a real decision, not a style preference.
- **Optimisers may *inline* a CTE or *materialise* it, and behaviour varies by engine and query shape.** So both "CTEs make queries faster" and "CTEs are optimisation fences" are unreliable folklore. A CTE referenced twice may be computed once, or its logic may simply run twice. If a costly, stable intermediate must be computed **exactly** once, reused across statements, or audited independently, materialise it explicitly — and know that materialising costs a write and a later read, so it is not free either.
- **Name a stage after what its rows mean.** `latest_event_per_id` tells the reader the grain; `cte2` tells them nothing. A useful stage does one meaningful thing: filter a population, deduplicate, aggregate, enrich, or project. A pile of tiny aliases with no semantic boundary is worse than one nested expression, because it looks organised.
- **Column selection is part of the contract.** Passing `SELECT *` through every stage hides which attributes are still valid after a grain change and pushes unnecessary bytes through shuffles. Project the stable keys and the measures you need.
- **CTEs make a long statement testable.** During development, temporarily make each stage the final `SELECT` and check its row count and key uniqueness. That converts one opaque result into a sequence of verified transformations — and it is where you catch a fan-out, at the boundary where it happened.
- **An *uncorrelated* subquery references nothing from the outer query, so it is computed once.** *Example:* `WHERE score > (SELECT AVG(score) FROM ranked_results)`. With scores 0.9, 0.6, 0.3, the average is 0.6 and only 0.9 qualifies. One inner evaluation, whatever the outer row count.
- **A *correlated* subquery references the current outer row, so logically it is re-evaluated per row.** *Example:* `WHERE r.score > (SELECT AVG(r2.score) FROM ranked_results r2 WHERE r2.query_id = r.query_id)` compares each row against **its own query's** average. For q1 scores 0.9 and 0.5 the average is 0.7 and 0.9 survives; for q2 scores 0.8, 0.7, 0.6 the average is 0.7 and 0.8 survives. Same inner SQL, different input per outer row — that is the entire difference.
- **The per-row model explains *semantics*, not necessarily execution.** A capable optimiser will often **decorrelate** the subquery into a join plus an aggregate. But correlation can block that: complex limits, volatile functions, inequality conditions, and engine-specific constructs inside the subquery all make decorrelation unsafe, and then it really does run per row.
- **When decorrelation fails, the cost is a product.** *Example:* 1,000,000 documents each asking for `MAX(updated_at)` over 10,000,000 chunks, with no useful index, approaches an impossible number of row touches. The pre-aggregate rewrite scans chunks **once** — `WITH latest AS (SELECT document_id, MAX(updated_at) … GROUP BY document_id)` then `LEFT JOIN` — and is the general cure. A composite index on `(document_id, updated_at)` is the other cure, and it is the better one when the outer set is small.
- **Correlation is not automatically bad.** Ten indexed probes beat aggregating a billion-row table. The risk profile is: large outer set × inner work that is not a cheap keyed probe.
- **A scalar subquery must return at most one row, or the statement errors.** An aggregate without grouping guarantees one row — though that value may be `NULL`, and then `score > NULL` is `UNKNOWN` and **every** row is filtered out. `EXISTS` never interprets a value at all; it tests only whether a qualifying row exists, which is why correlated `NOT EXISTS` remains the safest exclusion form when nullable keys are involved.
- **`UNION ALL` concatenates and keeps every row; `UNION` concatenates and then removes duplicates across the *complete* selected tuple.** *Example:* `current` = `(q1,d1)`, `(q2,d2)`; `archive` = `(q2,d2)`, `(q3,d3)`. `UNION ALL` returns 4 rows including `(q2,d2)` twice; `UNION` returns 3.
- **Duplicate identity covers every selected column, which is rarely the business identity.** If the branches also select `score`, then `(q2,d2,0.8)` and `(q2,d2,0.7)` are **not** duplicates, and `UNION` cannot decide which score should survive — it was never asked to. Keyed precedence needs an explicit stage: `ROW_NUMBER()` ordered by source priority and update time, then keep row 1.
- **`UNION` costs what `COUNT DISTINCT` costs, for the same reason.** Deduplication means hashing or sorting, memory, possible spill, and usually a distributed shuffle; `UNION ALL` can stream or concatenate branches with far less coordination. Default to `UNION ALL` when duplicates are impossible by construction or are meaningful, and reach for `UNION` only when set semantics are part of correctness.
- **Set operators align columns by *position*, not by name.** `SELECT document_id, score … UNION ALL SELECT score, document_id …` is a defect even when type coercion lets it run: values cross semantic columns and the output column names come from the first branch, so nothing looks wrong. Use identical explicit column order, cast deliberately, and never `SELECT *` in a branch — schema evolution on one side silently changes positions.
- **Neither operator promises output order.** `ORDER BY` belongs once, at the end of the compound query. Ordering a branch does not define final order, and is often rejected unless paired with a branch-local `LIMIT` inside a subquery. A `LIMIT` after a union applies to the combined result.

**Rules to remember**

- A CTE is statement-scoped. A view is a catalog object; a temp table is materialised and indexable. Pick deliberately.
- Inline versus materialise is the engine's choice unless you force it. Read the plan before claiming a CTE saved work.
- Uncorrelated = evaluated once. Correlated = logically once per outer row.
- Scalar subquery: at most one row, or error. A `NULL` from one makes every comparison `UNKNOWN`.
- `UNION ALL` = concatenate. `UNION` = concatenate then dedupe on the whole tuple.
- `UNION` also removes duplicates **within** a branch, not only across branches.
- Set operators match by position. `ORDER BY` goes once, at the end.
- Adding a `'current' AS source` provenance column makes otherwise-equal rows distinct to `UNION` — which is a reason to do keyed deduplication explicitly rather than relying on set semantics.

**Common pitfalls**

- **Using `UNION` as a cleanup for duplicates you did not expect.** It is `DISTINCT` wearing a different hat: it hides an upstream defect, costs a shuffle, and can mask a second source of duplication. If duplicates are a surprise, assert branch uniqueness and go find out why.
- **Deduplicating partitions that are disjoint by construction.** Combining July 24 and July 25 with `UNION` spends real resources proving an invariant the partition constraint already guarantees. Use `UNION ALL`.
- **Assuming `UNION` can resolve conflicting rows.** It can only remove *identical* ones. Retry exports with different ingestion timestamps are not identical, so `UNION` keeps both and the "deduplicated" table still has two rows per key.
- **Writing a correlated subquery over a large outer set without checking the plan.** The SQL is short and the semantics are clear; the execution can be a nested loop over a million rows. Check whether the optimiser decorrelated it, and if not, pre-aggregate or index.
- **`COALESCE`-ing a scalar subquery's `NULL` reflexively.** Decide first whether an empty inner result means unknown, zero, or a fallback. Only then choose, and only if the fallback matches the domain.
- **Building a CTE chain with no grain boundaries.** Ten stages named `step1`…`step10` are not more readable than one nested query; they just spread one unclear idea over more lines.
- **Trusting a branch's `ORDER BY` to order the union.** It does not, and the plan is free to ignore it entirely.

**How to approach the questions**

1. Correlated and uncorrelated subqueries are told apart by one test: does the inner query reference an outer column? That answers most of the question before you read the options.
2. For `UNION` versus `UNION ALL`, ask what the *complete selected tuple* is — not what the key is. Distractors nearly always assume dedup happens on the business key.
3. When a query is described as slow, look for a correlated subquery whose inner work is a scan rather than a keyed probe, and expect the fix to be "aggregate once, then join".
4. For CTE questions, be suspicious of any absolute claim about performance. The defensible statements are about scope, readability, and grain; the performance ones depend on the plan.
5. Watch for column-order swaps in set-operation code. It runs, it returns rows, and it is wrong — which makes it a favourite for a challenge question.
