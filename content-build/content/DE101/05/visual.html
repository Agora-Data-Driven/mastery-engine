1. The Grain Pipeline

You already have four ways to move the grain: Join Fan-out multiplies it, GROUP BY Mechanics collapses it, OVER and PARTITION BY preserves it, and a filter narrows it. A CTE gives each move a name. Tap a stage to make it the final SELECT and inspect what one of its rows means. Like a factory line with a labelled bin between every machine.

This is not decoration. During development, temporarily make each stage the final SELECT and check its row count and key uniqueness — exactly what the buttons above simulate. That turns one opaque statement into a sequence of verified transformations, and it is where you catch a fan-out: at the boundary where it happened, not four stages later in a total that looks slightly high.

2. Naming A Result

Three constructs put a name on a query result, and they differ in scope, in whether the data is written down, and in whether the engine may compute it twice. Pick one and see what you actually bought. Like a sticky note, a printed form, and a filing cabinet.

The question people actually get wrong: referenced twice

Both "CTEs make queries faster" and "CTEs are optimisation fences" are folklore. The behaviour depends on the engine, the query shape, and any hints — so read the plan before claiming a CTE saved work. What a CTE reliably buys is scope, a name, and a visible grain, and those are worth it on their own.

3. Correlated Or Not

One word changes how many times the inner query runs. Tap an outer row to watch its own evaluation — and count the evaluations at the bottom. Like one exam pass mark for the whole school versus a pass mark computed per class.

The per-row model explains the semantics, not necessarily the execution: a capable optimiser often decorrelates this into a join plus an aggregate and runs it once. Correlation blocks that when the subquery contains complex limits, volatile functions, inequality conditions, or engine-specific constructs — and then it really does run per row.

4. The Cost Of Per-Row

Every document wants MAX(updated_at) from its chunks. Three ways to get it, and which one wins flips as the outer set grows. Drag the document count. Like phoning ten people versus mailing everyone: the cheap option depends entirely on how many.

WITH latest AS ( SELECT document_id, MAX(updated_at) AS latest_at FROM chunks GROUP BY document_id ) SELECT d.document_id, l.latest_at FROM documents d LEFT JOIN latest l USING (document_id);

Scan chunks once, build one row per document, then join. This is the general cure for a correlated subquery that would not decorrelate — and it is just the pre-aggregate-then-join move that fixed fan-out, arriving from the other direction.

Correlation is not automatically bad. The risk profile is specific: a large outer set multiplied by inner work that is not a cheap keyed probe. State the logical intent cleanly first, then check whether the optimiser decorrelated it or the index made repeated probes affordable.

5. Duplicate Semantics

Two exports overlap by one row. UNION ALL keeps everything; UNION removes duplicates — but only rows that are identical across every selected column. Add the score column and watch the "duplicate" stop being one. Like merging two guest lists where one person wrote their name slightly differently.

Two more things about set operators

Three questions settle every case: are duplicate rows valid events or redundant copies; which columns define business identity; and which row should win when the non-key attributes disagree? UNION ALL answers only the first. UNION answers exact-tuple set membership. Anything involving keyed precedence, freshness, or source trust needs an explicit deduplication stage after the concatenation.
