**The big idea**: Everything so far was about what a query *means* — **SELECT-FROM-WHERE and Logical Evaluation Order** for correctness, **Join Fan-out** and **GROUP BY Mechanics** for grain. This lesson is about what the engine actually *does*. The optimiser turns your declarative SQL into a tree of physical operators, and reading that tree is the skill that separates "the query is correct" from "the query returns in 40 ms". Around it sit three decisions of the same kind: whether your index's key grain matches your predicate (and why the B-tree in your database is not the inverted index in your retriever), which multi-write states a transaction forbids, and whether the workload is transactional or analytical — because a system tuned for one is actively bad at the other.

**Key concepts**

- **A plan is a tree of physical operators; read it from the leaves upward.** *Mechanism:* leaves read tables or indexes, operators filter/join/aggregate/sort/exchange, the root returns rows. `EXPLAIN` shows the planned tree; `EXPLAIN ANALYZE` (or the engine's equivalent) runs it and reports observed rows, time, memory and I/O. Labels differ per engine; the reading method does not.
- **Four questions per operator:** how many rows enter and leave, which algorithm runs, where do rows move, and are the estimates close to reality? *Why it matters:* a filter cutting ten million rows to ten thousand is valuable **near the scan**. The same filter sitting above a join means the join processed rows that were always going to be discarded.
- **The three scan shapes.** A **sequential/table scan** reads the eligible table or partitions — correct, and often fastest when you need a large fraction of it. An **index scan/seek** navigates to matching keys and may then fetch base rows; it wins on selective predicates and loses to random fetches when many rows match. A **partition-pruned scan** reads only the partitions whose metadata can satisfy the predicate.
- **The three join algorithms are the cost models you already met.** A **nested loop** reads outer rows and probes the inner side — excellent for a small outer set with an indexed inner key, and dangerous as two large scans (this is the correlated-subquery cost from the last lesson, wearing an operator name). A **hash join** builds a hash table on one input and probes with the other: typically $O(m+n)$, memory-hungry, and it can spill. A **merge join** walks two sorted inputs and is linear *once the ordering exists* — but the sort can dominate if it does not.
- **Estimated-versus-actual row divergence is the single most useful signal in a plan.** *Example:* `orders` has 100M rows, `customers` 1M, and a date filter should keep 1%. The good plan prunes partitions or filters orders to 1M, hash-joins against customers, then aggregates. If the optimiser estimated 10,000 filtered rows and observed 10,000,000, it may have chosen a nested loop and be performing millions of probes. That gap points at stale statistics, correlated predicates, data skew, or a non-sargable expression.
- **A predicate is *sargable* when it can become an index search argument.** `WHERE created_at >= '2026-07-01'` can seek a timestamp index. `WHERE DATE(created_at) = '2026-07-01'` wraps the column in a function and generally forces evaluation per row, unless the engine rewrites it or an expression index exists. The fix is the half-open range: `created_at >= '2026-07-01' AND created_at < '2026-07-02'`.
- **Other things to look for in a plan:** sorts and shuffles/exchanges, spills to disk (inadequate memory or too much input), repeated subplans, and unexpectedly wide rows. A distributed shuffle can dominate the arithmetic entirely, because matching keys have to cross workers. `SELECT *` increases moved bytes and can prevent an index-only scan.
- **A B-tree index stores ordered *row keys*; an inverted index stores *terms*.** *Mechanism:* a B-tree on `(tenant_id, created_at)` supports exact tenant lookup, time ranges within a tenant, ordered retrieval, and prefix use of the leading column. An inverted index analyses text into terms and maps each term to a **postings list** — `retrieval -> [(doc 2, positions 4,19), (doc 8, position 7)]` — over which Boolean intersection, phrase matching and BM25 operate.
- **The grain is the difference, and it decides which predicates are possible.** *Example:* `documents(body TEXT)` with one million articles. A B-tree on `body` orders complete body strings, so it can serve `body = 'exact full contents'` and perhaps a left-anchored prefix under a suitable collation — but `body LIKE '%retrieval%'` cannot navigate to an interior token and will usually scan. An inverted index opens the `retrieval` postings directly. Conversely, an inverted text index is not the tool for `created_at BETWEEN …` or a primary-key lookup, which is why search systems keep separate structures for structured fields.
- **Key order matters in a B-tree, and analysis choices matter in an inverted index.** `(tenant_id, created_at)` serves tenant-equality-plus-date-range well and serves a `created_at`-only query poorly. The inverted analogue is analyzer, token normalisation, positions and stored frequencies — and changing tokenisation changes which keys exist, so it forces a reindex exactly as a new key expression or collation forces a B-tree rebuild.
- **Both pay write amplification, differently.** A B-tree insert modifies leaf pages and may split nodes; an inverted index buffers occurrences, writes sorted immutable segments, and merges them later.
- **ACID names four guarantees, and each constrains a different failure.** **Atomicity**: all of a transaction's writes commit or none become visible — a crash after the debit and before the credit rolls back. **Consistency**: a commit moves the database from one state satisfying its declared invariants to another; constraints do the enforcing, and if your application transfers the wrong amount while satisfying every constraint, ACID faithfully commits the wrong decision. **Isolation**: an isolation level restricts which intermediate effects concurrent transactions can observe — without enough of it, two workers both read stock 1, both decide to sell, both write 0, and you have oversold. **Durability**: after a successful commit the result survives process or machine failure, per the system's contract, usually via write-ahead logs and replicated storage.
- **A client timeout does not prove a rollback.** The server may have committed and lost the acknowledgement. That is precisely why external requests still need idempotency keys — the uncertainty is structural, not a bug.
- **Transaction boundaries are a design decision, and broad is not better.** *Example:* creating a document row, 20 chunk rows and a counter increment in one transaction is right if readers must never see the document without its chunks. A full index rebuild in one transaction is not: build a versioned index separately, validate it, then atomically switch a small alias. **ACID protects the cutover, not every byte of a long-running computation.** And never hold locks while calling an LLM or a remote API — do the external work outside, then open a short transaction to validate current state and commit deterministic writes.
- **ACID applies within one datastore's documented boundary.** It creates no atomicity across Firestore, GCS, Pub/Sub and an external API. Cross-system workflows need idempotency, outbox patterns, state machines and reconciliation. Firestore's own transactions rerun optimistically when a read document changes, so the code inside must be safe to execute several times.
- **OLTP is many short selective operations; OLAP is few heavy scans.** *Mechanism:* OLTP is latency-sensitive and write-heavy relative to analytics, commonly normalised, and served well by row-oriented storage plus B-tree indexes — fetching or changing a whole row by key is cheap. OLAP is throughput-oriented and mostly read, served by columnar storage that reads only the referenced columns, compresses repeated values and vectorises computation, often over denormalised stars or nested tables.
- **Workload shape, not the data's name, decides placement.** *Example:* `GET /jobs/abc` needs one row in under 20 ms and may update its status immediately — a transactional database with a primary-key B-tree. A report computing weekly success rate over five billion events needs three columns and none of the rest — a columnar warehouse scanning them in parallel; five billion indexed point probes would be absurd. The same `orders` domain legitimately lives in both, with a change pipeline keeping the derived copy fresh.
- **Mixed workloads interfere in both directions.** A full-table dashboard scan on an OLTP primary evicts hot pages, burns CPU, holds snapshots open and slows customer writes; heavy point-update traffic fragments analytical files and defeats compression. Hence replicas, exports and storage-compute separation, rather than one engine optimising contradictory access patterns.

**Rules to remember**

- Read plans leaves-upward. Compare **estimated** rows against **actual** rows first; a large gap explains most bad plans.
- Filters belong as close to the scan as possible. A filter above a join means the join did wasted work.
- Wrapping a column in a function usually kills index use. Rewrite as a half-open range.
- No operator name is inherently bad: a full scan of a small dimension is healthy, an index probe returning half a table is not.
- B-tree = ordered row keys. Inverted index = terms → postings. Calling both "indexes" does not make them interchangeable.
- Leading-column order in a composite index decides which queries it can serve.
- Consistency means *declared invariants*, not business correctness.
- A timeout is not a rollback. Use idempotency keys for anything external.
- ACID stops at one datastore's boundary. Cross-system needs outbox/reconciliation.
- OLTP: selective, latency-bound, row-oriented, normalised. OLAP: scan-heavy, throughput-bound, columnar, denormalised.

**Common pitfalls**

- **Treating cost numbers as truth.** They are not time units and are not comparable between optimisers — rank alternatives *within* one engine, then confirm with actual runtime and bytes read. And never judge a plan on one parameter value: cached pages and data skew both distort the result.
- **Treating a nested loop as the villain.** It is the right operator for a small outer set with an indexed inner key. It is catastrophic as two large scans — and it is often *chosen* because an estimate was wrong, which is the thing to fix.
- **Adding a text index for a `LIKE '%…%'` query and expecting a seek.** A B-tree cannot enter a string in the middle. That predicate needs an inverted index or a trigram-style structure, not a bigger B-tree.
- **Letting authorization ride on relevance.** Tenant and status constraints must be enforced as constraints alongside term postings, never inferred from text scoring.
- **Believing ACID protects a long job.** A multi-hour rebuild inside a transaction is impractical and often impossible. Version, validate, then swap.
- **Running the dashboard against the OLTP primary "just for now".** It is the classic way to make customer writes slow, and the interference is invisible in the dashboard's own timing.

**How to approach the questions**

1. For plan questions, ask what should have been eliminated and *when*. Most wrong plans are correct operators applied at the wrong point in the tree.
2. Whenever a question mentions a wrong or surprising algorithm choice, look for a row-estimate error behind it before blaming the operator.
3. For index questions, name the lookup key out loud. An ordered scalar or tuple attached to a row is a B-tree question; a token appearing across many documents is an inverted-index question.
4. For ACID questions, identify which of the four letters is actually at stake. Overselling stock is isolation; money vanishing mid-transfer is atomicity; committing a wrong-but-legal amount is neither.
5. For OLTP-versus-OLAP, ignore what the data is called and count: how selective, how many rows scanned, how fresh, how concurrent, how latency-sensitive. Hybrids exist, so the labels are tendencies rather than prohibitions.
6. Watch for absolute claims — "always use an index", "scans are bad", "always one transaction". Each has a counter-example in this lesson, which is usually why it is an option.

**Where this leads**: you can now read what an engine did and say why. That is the foundation for the rest of the track — storage layouts and table formats that decide how much a scan actually costs, and the pipeline patterns that move data between an OLTP authority and its analytical copies without losing or duplicating a row.
