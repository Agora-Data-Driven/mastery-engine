1. The Plan Tree

SELECT-FROM-WHERE and Logical Evaluation Order told you what a query means. The plan tells you what the engine did — and the engine is free to reorder, as long as the answer matches. Same SQL, two plans. Read from the leaves upward and tap any operator. Like a recipe versus the order the kitchen actually cooks it in.

SELECT c.region, COUNT(*), SUM(o.amount) FROM orders o JOIN customers c ON c.customer_id = o.customer_id WHERE o.created_at >= '2026-07-01' AND o.created_at < '2026-07-02' GROUP BY c.region; -- orders: 100,000,000 rows · customers: 1,000,000 rows · the date keeps 1%

No operator name is inherently bad. A full scan of a small dimension is healthy; an index probe returning half a table is not. And never read cost numbers across different database products as time units — use them to rank alternatives inside one optimiser, then confirm with actual runtime and bytes read.

2. Sargable Or Not

An index is a sorted structure, so the engine can only jump into it if the predicate names the column. Wrap that column in anything and the index has nothing to seek on. Tap a predicate. Like a phone book: you can find "Reyes" instantly, and you cannot find "everyone whose surname has seven letters" without reading all of it.

The word is "sargable" — Search ARGument-able. The test is mechanical: is the indexed column sitting bare on one side of the comparison? If it is wrapped in a function, a cast, or arithmetic, the engine must compute that expression for every row before it can compare anything, and a sorted structure over the raw values cannot help.

3. Two Kinds Of Index

Both are called indexes and they store different things. A B-tree stores ordered row keys; an inverted index stores terms pointing at documents. Send four queries at both and watch which one can answer. Like a book's page numbers versus its back-of-book index.

The judgment test is one question: what is the lookup key? An ordered scalar or tuple attached to a row is a B-tree question. A token appearing across many documents is an inverted-index question. A query that combines both needs both access paths, and the engine intersects the candidates — but authorization must be a constraint, never something inferred from text relevance.

4. Four Letters

ACID is four separate promises, and most confusion comes from attributing a failure to the wrong one. Pick a scenario and see which letter is actually at stake — including one where all four hold and the outcome is still wrong. Like blaming the lock when the problem was the person you gave the key to.

ACID applies inside one datastore's documented boundary. It creates no atomicity across Firestore, GCS, Pub/Sub and an external API — cross-system workflows need idempotency keys, outbox patterns, state machines and reconciliation. And Firestore's own transactions rerun optimistically when a read document changes, so the code inside has to be safe to execute several times.
