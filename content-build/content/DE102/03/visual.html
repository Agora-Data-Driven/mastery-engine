1. Overwrite Or Version

Star Schema vs Snowflake ended on a failure both shapes share: update a dimension row in place and last year's report changes with it. Drag the report date and watch what each strategy says about February. Like correcting an old diary entry instead of writing a new one.

Not every attribute deserves Type 2. Classify them: Type 1 overwrite for values whose old form should never be reported (a misspelled name), Type 2 version for historically meaningful changes (contractual tier, sales territory), and fixed for attributes that should not change at all without someone opening an incident.

2. The Boundary Instant

Two versions meet at one instant. Whether an event at exactly that instant matches once, twice, or not at all is decided by a single convention — and the bug only ever shows up on boundary days. Like a shift handover: if both shifts claim 14:00, everything at 14:00 gets logged twice.

Four invariants, per business key — all four are tests

Applying a change is close-then-insert inside one transaction: set the old row's end to T and the new row's start to T. The transaction is what prevents a moment with two current rows or none. Append-oriented warehouses do the same thing by rebuilding the affected keys in a staged model and atomically replacing a partition.

3. Early Or Late Binding

How a fact connects to a versioned dimension decides what happens when history is corrected. On April 1 you learn the region actually changed on March 15 — after March facts have already loaded. Like stamping the address on every envelope versus looking it up when you post it.

Neither is the right answer on its own — some systems keep both, using early-bound keys for fast serving and late-bound resolution for audit and controlled restatement. What matters is that the design explicitly states whether history is corrected retroactively, because the two produce different numbers for the same month and both look correct in isolation.

4. The Same Shape, Twice

A document is a business identity with versions and validity intervals. That is not an analogy to SCD Type 2 — it is the same design with different column names. Tap a row to see both sides. Like a contract: one agreement, numbered amendments, each valid between two dates.

Three questions a single "latest version" helper cannot answer

A parser defect is not source history. If V7 was wrong because your pipeline was wrong rather than because the document said that, create a new derived artifact under a new parser version and preserve the source version — otherwise content history and processing history become conflated and nobody can say which one changed.

5. Sufficient History

More history is not automatically safer. Every version you keep is storage, query complexity, breach exposure and legal-discovery scope. Pick an attribute and decide what it actually owes you. Like keeping receipts: some for seven years, some until the warranty ends, most not at all.

The rule people forget

Ownership is what stops a Type 2 table becoming an unbounded archive nobody trusts: source teams define when a change is effective, data teams implement capture and intervals, governance defines retention and erasure, consumers define which historical questions must be answerable. The sound decision is not maximum history — it is sufficient, governed history.
