**The big idea**: This is the whole course arriving at your own system. **Grain: What One Row Represents** and **Document Versioning as SCD Type 2** already gave you the tools; a retrieval corpus is just four of them chained together. It is not one table of text — it is versioned source documents, parsed representations, chunks, and model-specific embeddings, each with its own precise grain and its own identity. Get those right and corpus processing becomes ordinary data engineering: you can rebuild an answer, invalidate exactly the stale artifacts, and cite the original source at a real offset. Get them wrong and one upgrade overwrites unrelated work, a citation points at text that is no longer there, and nothing tells you.

**Key concepts**

- **Four grains, and each row must have one unambiguous meaning.** A `document` row is stable source identity and ownership. A `document_version` row is one immutable state — content, source timestamps, parser version, permissions. A `chunk` row is one retrieval unit derived from **one document version under one chunking configuration**, with text, ordinal, boundaries and chunker config. An `embedding` row is one model-specific vector for one embeddable input, with model id, dimensionality, normalisation policy and creation time.
- **The cardinalities are load-bearing.** One document has many versions; one version has many chunks; **one chunk can have many embeddings** when several models, dimensionalities, or preprocessing policies coexist. A uniqueness rule on `(chunk_id, embedding_model_version)` prevents duplicate vectors while still permitting a controlled migration where two model versions live side by side.
- **Embedding grain is not always chunk grain, so name the input unit explicitly.** A multimodal embedding may combine text and an image region. A late-interaction model produces *many token vectors* per chunk. A document-level vector may drive broad candidate retrieval before chunk reranking. If an embedding row sometimes means a chunk and sometimes a whole document with no type and no parent, its scores and its lineage cannot be interpreted at all.
- **Do not put vectors on the document row.** One document produces many chunks, so that is repeated state you cannot update independently. The mirror case is legitimate: a vector database may denormalise title, permission filter and source URI into each vector record for serving speed — fine **because the normalised catalog remains the authority and the serving copy is reconstructable**. Same discipline as any derived table.
- **Lifecycle differs by grain, which is the point of separating them.** A metadata correction creates a new document version without changing normalised text. A parser upgrade creates new parsed content and new chunks. An embedding-model upgrade regenerates embeddings and **must not invent new source documents**. Independent identities are what let a pipeline invalidate only the affected descendants.
- **Processing runs deserve their own grain too.** An ingestion run, parse attempt, chunking run or embedding batch records status, configuration, errors and counts. Storing `processed = true` on the document loses every retry and makes partial failure invisible; a run-to-artifact relationship is what supports audit and idempotent recovery.
- **Access control must follow the source version into the serving artifacts.** A chunk retrievable without its document's current permission context is a content leak. Store immutable permission snapshots where historical reconstruction is required, and propagate revocations promptly to vector and cache layers.
- **Chunking chooses what one retrieval row means — it is a grain decision, not preprocessing.** The choice determines recall, context coherence, citation precision, vector count, and the unit a ranker scores. *Example:* a 2,000-token policy chapter can contain the answer plus a dozen distracting clauses; a 50-token fragment can omit the condition that changes the answer entirely.
- **Overlap trades duplication for boundary safety.** Window 400 tokens with stride 300 overlaps by 100, so a statement spanning a boundary appears intact in at least one chunk. The cost is roughly $\lceil (L - \text{window})/\text{stride} \rceil + 1$ chunks for a document of $L$ tokens, and overlapping passages crowd the result list.
- **Structure-aware chunking respects headings, paragraphs, sentences, code blocks and table rows,** assembling neighbouring units until a token budget is reached. A hard maximum is still required, because one malformed paragraph or minified file will exceed the embedding model's context limit.
- **Chunk identity must incorporate the chunking decision.** If `chunk_7` means "ordinal seven", inserting text near the beginning shifts every later ordinal and makes unchanged chunks look changed. Derive identity from **document version, chunker version, boundaries, and optionally normalised content** — the exact recipe depends on whether identity should represent occurrence, content, or both.
- **Store the configuration, not just the number.** Tokenizer, target size, maximum size, overlap, boundary rules, table handling, normalisation version. "400 tokens" is ambiguous across tokenizer versions, and a **configuration hash** makes two chunk sets comparable or reproducible during an experiment.
- **Chunking can be hierarchical.** Small child chunks for precise retrieval, parent sections for context expansion: the ranker retrieves a child, the answer builder loads its parent or ordered neighbours within a budget. Parent-child ids and ordered adjacency are what make that deterministic.
- **Changing chunk grain is a schema migration.** Build the new chunk set under a new version, embed it, validate coverage, switch the serving alias, keep rollback. **Never update rows in place** while a live index mixes incompatible boundaries and ids.
- **Content addressing derives identity from bytes, under an explicit canonicalisation rule.** A cryptographic hash of canonical content is stable across identical inputs and changes when the content does — which buys idempotency, cache lookup, corruption detection and reuse. It is **evidence of equality under that rule**, not a replacement for source identity.
- **Canonicalisation choices are semantic.** Normalising line endings prevents meaningless version churn. Collapsing all whitespace merges code and tables where whitespace carries meaning. Lowercasing destroys case-sensitive identifiers. Record the canonicalisation version **in the hash domain**, so a future change to the recipe cannot silently collide with the old one.
- **Domain-separate every derived id.** Hash a structured input: `embedding_id = hash("embedding-v1", chunk_id, model_id, preprocessing_hash)`. Re-running the same work yields the same id, so an upsert is idempotent; changing the model or the preprocessing yields a different id, so both versions coexist during migration. Length-prefixed fields or canonical structured serialisation prevent concatenation ambiguity.
- **Mutable pointers still have a job.** A serving alias points from logical document to current version, or from model family to active index. The immutable ids preserve history; the pointer carries current behaviour. **Updating a pointer is safer than rewriting every artifact's identity.**
- **Lineage is the path back: embedding → chunk → document version → source document,** plus links to the processing runs that carry parser, chunker and embedding configuration. That path is what turns a retrieved chunk into a citation with a source URI, title, version, page or section, and an exact span you can verify the quoted text against.
- **Offsets need a declared coordinate system.** Character offsets are intuitive and depend on Unicode representation; byte offsets are exact and awkward to display; token offsets depend on a tokenizer. Most systems store normalised-text character offsets plus source-mapping metadata — and **always state whether the end is exclusive**.
- **When normalised text differs from source HTML or PDF, an offset alone cannot locate the passage.** Parsers must retain page numbers, block ids, bounding boxes, DOM paths, or a mapping from normalised spans to source spans. **Citation requirements shape parser outputs, and they have to do so before chunking begins.**
- **Lineage enables targeted repair.** Parser version P3 has a bug: query lineage for every chunk it produced, rebuild only those descendants, compare counts. A source document is deleted: traverse the descendants into vector indexes and caches. A plain text blob with no parent supports none of this.
- **Lineage is an explanation boundary, not a truth claim.** It can prove which source and which transformation produced an artifact. It cannot prove the source is true or the answer correct. That needs relevance evaluation, source-quality policy and runtime grounding checks alongside it.

**Rules to remember**

- Four grains: document, document_version, chunk, embedding. One row, one unambiguous meaning.
- A chunk belongs to a document **version** under a **named chunker configuration**. Both are part of its identity.
- `(chunk_id, embedding_model_version)` unique — one vector per chunk per model, and migrations stay possible.
- Never derive chunk identity from ordinal alone; an insertion at the top renumbers the whole document.
- Store the chunker configuration and hash it. "400 tokens" is not a specification.
- Domain-separate derived ids: type tag, parent id, config hash, content hash.
- Canonicalisation version belongs inside the hash domain.
- Serving copies may be denormalised; the catalog stays the authority and the copy stays reconstructable.
- Permissions follow the version into every serving artifact, and revocations propagate to caches and indexes.
- Every active embedding resolves to an active chunk and a permitted source version. Orphan count is zero.

**Common pitfalls**

- **Treating chunking as preprocessing.** It sets the retrieval grain, the citation precision, the token cost and the unit your ranker scores. It is the single most consequential modelling decision in the corpus, and it is usually made in a config file by whoever wrote the loader.
- **Chunk ids that mean "the seventh chunk".** Insert a sentence into the introduction and every downstream artifact looks changed, so embeddings are regenerated for text nobody touched.
- **Updating chunks in place to change the policy.** A live index holding two incompatible boundary schemes returns overlapping and missing passages at once, which reads as a relevance problem and is a migration problem.
- **`processed = true` on the document.** It cannot express a retry, a partial failure, or which configuration produced what.
- **Hashing without recording the canonicalisation.** Two recipes eventually produce the same hash for different content, or different hashes for identical content, and no evidence survives to say which happened.
- **Exposing raw hashes of low-entropy inputs.** If the input space is guessable, a hash is not a secret — an attacker enumerates candidates and compares.
- **Citing the current version.** Without lineage the link points at whatever the document says today, which may no longer contain the evidence the answer was built from — a plausible-looking citation that is simply wrong.
- **Character offsets against a PDF.** Normalised text and source layout are different coordinate systems, and only a parser that retained page numbers, block ids or bounding boxes can bridge them.
- **Confusing provenance with correctness.** Perfect lineage proves where a claim came from. It says nothing at all about whether the claim is true.

**How to approach the questions**

1. For any corpus question, name the grain of every row involved first. Most defects in these scenarios are two grains sharing a table or one grain missing a parent.
2. When something "regenerated unnecessarily", look at what the identity was derived from. Ordinal-based or configuration-blind ids are the usual cause.
3. For chunk-size questions, ask which failure the scenario is describing: a missing surrounding definition (chunks too small) or a diluted key term and wasted tokens (chunks too large). Overlap addresses boundaries only.
4. For hashing questions, check for domain separation and a recorded canonicalisation version. A bare `hash(content)` is almost always the wrong option.
5. For lineage questions, trace the full path — embedding, chunk, version, document — and check whether the answer preserves it under deletion and under a parser upgrade.
6. Be suspicious of any option claiming provenance establishes correctness. It establishes origin, and the distinction is usually what the question is testing.

**Where this leads**: you now have a corpus model whose rows have meanings, identities that survive change, and a path back to the source. What it does not have yet is a physical home — how those rows are laid out on storage so a scan is cheap, how partitioning and file layout shape query cost, and what an open table format adds on top of object storage.
