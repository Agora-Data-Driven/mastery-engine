Storage layout is where most of the compute money in an analytics or retrieval stack is won or lost. The evaluation logs of your hybrid retriever, the embedding pipelines you run on GCP, the clickstream you join against relevance judgments: all of it eventually gets scanned by queries, and the physical arrangement of bytes decides whether such a scan reads 40 GB or 400 MB. This lesson establishes the row-versus-column decision, then opens up Parquet, the columnar file format that is the de facto standard of the modern data lake, down to the structures that make cheap scans possible.

## Row vs Columnar Layout: Which Workload Wins

A **row-oriented** layout stores every field of one record contiguously, then the next record, and so on. CSV, JSON Lines, Avro data files, a Postgres heap page, and a Firestore document are all row-oriented: the unit of storage is the record. A **columnar** layout transposes this. All values of column 1 across many rows are stored contiguously, then all values of column 2, and so on. The unit of storage is the column (or a column's slice over a batch of rows).

The mechanism that makes this matter is I/O granularity. Storage, whether an SSD block or an object-store GET, hands you contiguous byte ranges; you pay for every byte you read whether or not you use it. In a row layout, reading one field of a row drags the whole row through the I/O path, because the row is the contiguous unit. In a columnar layout, reading one column of a million rows touches only that column's bytes.

Which layout wins is therefore a property of the workload, not of the data:

- **Transactional (OLTP-style) access**: fetch one complete record by key, update a couple of fields, write it back. Row layout wins. The record is one contiguous read; a columnar layout would have to reassemble the record from one location per column.
- **Analytical (OLAP-style) access**: aggregate or filter a few columns across millions or billions of rows. Columnar wins, roughly in proportion to the fraction of columns touched.

Worked example. An `events` table has 100 million rows and 50 columns averaging 4 bytes per value: 200 bytes per row, 20 GB total. The query `SELECT AVG(latency_ms) FROM events WHERE tenant_id = 'acme'` touches exactly two columns. A row-oriented scan must read all 20 GB, because every row's 200 bytes are interleaved. A columnar scan reads two columns of 400 MB each, about 0.8 GB, a 25x reduction before any compression is applied. And compression amplifies the gap: a column stores values of one type with similar magnitudes and repeated members side by side, which compresses far better than interleaved heterogeneous rows (the specific encodings that exploit this are the next lesson's subject).

Columnar layouts also enable **vectorized execution**: the engine processes a column as a dense array of one type, which is friendly to CPU caches and SIMD instructions, instead of interpreting one heterogeneous record at a time.

The judgment layer. Columnar loses, sometimes badly, when the access pattern is record-shaped. `SELECT *` on a 200-column table to fetch one row by ID forces 200 separate column reads to rebuild a single record that a row store returns in one seek. High-rate single-record inserts and in-place updates are equally hostile: columnar formats are batch-oriented, laying out a large group of rows at once, so they want writes accumulated into big batches. This is why the same business runs both: Firestore (row/document-oriented) serves your application's point reads and writes, while exports to a columnar format serve the analytical scans. Choosing columnar for a key-value serving workload, or row storage for a scan-heavy warehouse, is the canonical mistake this lesson exists to prevent.

## Parquet Row Groups and Column Chunks

Parquet is a self-describing binary file format that implements columnar layout with a two-level structure. A file begins and ends with the 4-byte magic `PAR1`. At the very end, just before the trailing magic, sits a 4-byte length followed by the **footer**: Thrift-encoded metadata containing the schema, the number of rows, and, for every column of every row group, the byte offset, sizes, encodings, and statistics of that column's data.

The body of the file is divided horizontally into **row groups**: self-contained slices of the table, typically targeted at 128 MB to 1 GB of data (or a fixed row count such as one million rows). Within a row group, each column's values are stored contiguously as a **column chunk**, one chunk per column per row group. Each chunk is further divided into **pages** (data pages around 1 MB by default), which are the smallest units of encoding, compression, and reading.

The read path follows the metadata. A reader fetches the tail of the file, reads the footer length, then the footer. From the footer alone it knows every column chunk's exact byte range. To answer a query needing 2 of 50 columns, it issues byte-range reads for just those chunks in each row group it needs, coalescing adjacent ranges. On object storage this is a handful of range GETs per row group rather than a full-file download.

Why two levels instead of storing each column once for the whole file? Because row groups are the unit of **parallelism and memory bounding**. Each row group is independently readable: a distributed engine assigns different row groups of the same file to different tasks. The writer, symmetrically, buffers one row group in memory, flushes it, and starts the next, so its memory footprint is bounded by the row group size rather than the file size. A pure whole-file-per-column layout would make both splitting and bounded-memory writing awkward. Column chunks inside the row group then deliver the columnar I/O benefit.

Worked example. Our 100-million-row table written with 1-million-row row groups yields 100 row groups; with 50 columns that is 5,000 column chunks, each described in the footer. The two-column query reads the footer plus 200 column chunks. If each needed chunk is about 4 MB, the scan reads roughly 800 MB out of a multi-gigabyte file, and 100 independent row groups mean up to 100-way parallelism.

The judgment layer is the row group size dial. Too small (say, 5,000 rows): footer metadata balloons with entries, per-chunk request overhead multiplies, and each chunk is too small to encode or compress effectively. Too large (say, one row group per 2 GB file): the file has one split, so one task processes it while the rest of the cluster idles, and both writer and reader need memory proportional to the group. The historical 128 MB default matched HDFS blocks; on object stores, groups of 256 MB to 1 GB are common because per-request latency, not block locality, dominates. Page size is a smaller dial: smaller pages give finer-grained reads and pruning at the cost of per-page overhead.

## Column Statistics and Predicate Pushdown

Skipping data you can prove irrelevant is the cheapest optimization in a query engine, and Parquet is built to make that proof possible. Alongside each column chunk's location, the footer stores **column statistics**: the minimum value, maximum value, and null count for that chunk (newer Parquet versions add page-level min/max in a column index, plus optional Bloom filters for equality tests on high-cardinality columns).

**Predicate pushdown** is the engine behavior that exploits them. Instead of reading all data and filtering afterward, the engine pushes `WHERE` predicates down into the scan. Before reading a row group, it evaluates the predicate against the chunk statistics. For a filter `event_ts >= '2026-07-01'`, any row group whose `max(event_ts)` is below that literal provably contains no matching row and is skipped without reading a single data byte. Only the footer was ever read. (A sibling optimization, projection pushdown, prunes columns; predicate pushdown prunes rows. Keep the two distinct.)

The semantics are deliberately conservative. Statistics can prove absence, never presence. A row group whose min/max range overlaps the predicate might still contain zero matching rows, so it survives pruning, gets read, and the engine re-applies the filter to its rows, which then all drop out. That is a wasted read, but never a wrong answer: correct stats yield false positives but no false negatives.

Worked example. Write the 100 row groups sorted by `event_ts`, so each group covers roughly a disjoint 15-minute window. The query `WHERE event_ts BETWEEN '2026-07-01 00:00' AND '2026-07-01 01:00'` overlaps about 4 groups; 96 are skipped, a 96% I/O reduction from metadata alone. Now shuffle the same rows randomly before writing. Every row group's min is near the global minimum and its max near the global maximum; every group overlaps every predicate; zero groups are skipped. Identical data, identical statistics machinery, and the entire benefit was created or destroyed by physical layout.

That is the central judgment: **statistics are only as good as your clustering**. Sort or cluster data on the columns your queries filter by most, and min/max pruning approaches partition-level power at row-group granularity. For a uniformly distributed high-cardinality column like a UUID, min/max is useless unless the data is sorted by it; equality lookups there are what Bloom filters are for.

Know the edge cases experts check. Floating-point `NaN` does not order cleanly, so writers historically produced unusable min/max for such columns and engines may ignore those stats. Very long strings get truncated in statistics (min truncated downward, max padded upward) to keep footers small, which remains safe but weakens pruning. And predicate shape matters: `col != x` can prune a chunk only in the degenerate case where min = max = x; `IS NULL` prunes via null_count = 0; range and equality predicates on well-clustered columns are where pushdown pays.
