**The big idea**: **OLTP vs OLAP Workloads** told you the two shapes of work want different storage. This lesson is the *inside* of that claim. Storage layout is where most of the compute money in an analytics or retrieval stack is won or lost, because every query eventually scans bytes and the physical arrangement decides whether a scan reads 40 GB or 400 MB. Three ideas do all the work: **row versus columnar** is a property of the workload, never of the data; **Parquet's two-level structure** (row groups holding column chunks) is what makes selective, parallel, bounded-memory reads possible; and **column statistics plus predicate pushdown** let an engine skip data it can *prove* irrelevant — but only as well as your physical clustering allows.

**Key concepts**

- **Row-oriented stores a whole record contiguously; columnar transposes it.** CSV, JSON Lines, Avro data files, a Postgres heap page and a Firestore document are all row-oriented — the unit of storage is the record. In a columnar layout all values of column 1 across many rows sit together, then all of column 2. The unit of storage is the column, or a column's slice over a batch of rows.
- **The mechanism is I/O granularity, and it is unforgiving.** Storage — an SSD block, an object-store GET — hands you contiguous byte ranges, and you pay for every byte you read whether you use it or not. Reading one field of a row therefore drags the whole row through the I/O path, because the row is the contiguous unit. Reading one column of a million rows touches only that column's bytes.
- **Worked numbers.** An `events` table of 100 million rows × 50 columns at ~4 bytes per value is 200 bytes per row, **20 GB**. `SELECT AVG(latency_ms) FROM events WHERE tenant_id = 'acme'` touches two columns. A row scan must read all 20 GB. A columnar scan reads two columns of ~400 MB, about **0.8 GB — a 25× reduction before compression**. And compression amplifies it: a column holds one type with similar magnitudes and repeated members side by side, which compresses far better than interleaved heterogeneous rows.
- **Columnar also enables vectorized execution.** The engine processes a column as a dense array of one type — cache-friendly and SIMD-friendly — instead of interpreting one heterogeneous record at a time.
- **Columnar loses, badly, when the access is record-shaped.** `SELECT *` on a 200-column table to fetch one row by id forces 200 separate column reads to rebuild what a row store returns in one seek. High-rate single-record inserts and in-place updates are equally hostile, because columnar formats are batch-oriented — they lay out a large group of rows at once and want writes accumulated. This is why one business runs both: Firestore serves the point reads and writes, exports to a columnar format serve the analytical scans.
- **Parquet is self-describing, with the metadata at the end.** The file opens and closes with the 4-byte magic `PAR1`; just before the trailing magic sit a 4-byte length and the **footer** — Thrift-encoded schema, row count, and for every column of every row group its byte offset, sizes, encodings and statistics.
- **Two levels: row groups, then column chunks.** The body is divided horizontally into **row groups** — self-contained slices, typically 128 MB–1 GB or a fixed row count such as one million rows. Within a row group each column's values are one contiguous **column chunk** (one per column per row group), and each chunk divides into **pages** (~1 MB by default), which are the smallest units of encoding, compression and reading.
- **The read path follows the metadata.** Fetch the tail, read the footer length, read the footer. From the footer alone the reader knows every column chunk's exact byte range, so a query needing 2 of 50 columns issues byte-range reads for just those chunks, coalescing adjacent ranges. On object storage that is a handful of range GETs per row group instead of a full-file download.
- **Why two levels rather than one column per file?** Row groups are the unit of **parallelism and memory bounding**. Each is independently readable, so a distributed engine assigns different row groups of the same file to different tasks; symmetrically the writer buffers one row group, flushes it, and starts the next, so its memory is bounded by the group size rather than the file size. Column chunks inside the group then deliver the columnar I/O benefit.
- **Worked numbers again.** 100M rows with 1M-row row groups gives 100 row groups; 50 columns makes 5,000 column chunks, each described in the footer. The two-column query reads the footer plus 200 chunks — roughly **800 MB** out of a multi-gigabyte file — with up to 100-way parallelism.
- **Row group size is the main dial, and it is wrong in both directions.** *Too small* (5,000 rows): footer metadata balloons, per-chunk request overhead multiplies, and each chunk is too small to encode or compress effectively. *Too large* (one group per 2 GB file): the file has one split, so one task processes it while the cluster idles, and both writer and reader need memory proportional to the group. The 128 MB default matched HDFS blocks; on object stores 256 MB–1 GB is common, because per-request latency rather than block locality dominates. Page size is the smaller dial: finer reads and pruning against per-page overhead.
- **Column statistics live in the footer: min, max and null count per column chunk.** Newer Parquet versions add page-level min/max in a column index, plus optional **Bloom filters** for equality tests on high-cardinality columns.
- **Predicate pushdown evaluates the filter against those statistics before reading data.** For `event_ts >= '2026-07-01'`, any row group whose `max(event_ts)` is below the literal provably contains no matching row and is skipped without reading a single data byte — only the footer was ever read. Keep it distinct from **projection pushdown**, which prunes *columns*; predicate pushdown prunes *rows*.
- **Statistics can prove absence, never presence.** A row group whose min/max overlaps the predicate might still contain zero matches, so it survives pruning, gets read, and the filter re-applies and drops everything. That is a wasted read and never a wrong answer: correct statistics yield **false positives but no false negatives**.
- **Clustering is what makes statistics valuable — the same data can be 96% skippable or 0%.** Write the 100 row groups sorted by `event_ts` so each covers a disjoint ~15-minute window: `WHERE event_ts BETWEEN 00:00 AND 01:00` overlaps about 4 groups and skips 96, a 96% I/O reduction from metadata alone. Shuffle the same rows randomly first and every group's min is near the global minimum and its max near the global maximum, so every group overlaps every predicate and **zero** are skipped. Identical data, identical machinery; the entire benefit was created or destroyed by physical layout.
- **Predicate shape matters too.** Range and equality predicates on well-clustered columns are where pushdown pays. `col != x` can prune a chunk only in the degenerate case where `min = max = x`. `IS NULL` prunes via `null_count = 0`. A uniformly distributed high-cardinality column like a UUID has useless min/max unless sorted by it — equality lookups there are what Bloom filters exist for.
- **Two edge cases experts check.** Floating-point `NaN` does not order cleanly, so writers historically produced unusable min/max for such columns and engines may ignore those statistics. Very long strings are **truncated** in statistics (min truncated downward, max padded upward) to keep footers small — still safe, but weaker pruning.

**Rules to remember**

- The layout question is about the *workload*: record-shaped access wants rows, scan-shaped access wants columns.
- Columnar saving is roughly proportional to the fraction of columns you touch. Touch all of them and it saves nothing.
- Parquet: file → row groups → column chunks → pages. The footer describes every chunk's byte range.
- Row groups are the unit of parallelism and of bounded writer memory.
- Statistics prove absence only. False positives are expected; false negatives would be a bug.
- Predicate pushdown prunes rows; projection pushdown prunes columns. Different optimisations, often confused.
- Sort or cluster on what you filter by, or min/max pruning does nothing at all.
- `!=` prunes only when min = max. Bloom filters serve equality on high-cardinality columns.

**Common pitfalls**

- **Choosing the layout from the data rather than the access pattern.** "It's analytics data" is not the argument; "queries touch 3 of 60 columns over billions of rows" is.
- **`SELECT *` on a columnar table.** It reads every column chunk and discards the columnar advantage entirely — and it also defeats an index-only-style read path in engines that have one.
- **Tiny row groups.** Common when a job writes one file per small batch: the footer grows, request overhead multiplies, and compression never gets enough data to work with.
- **One giant row group.** The file becomes one split, so parallelism collapses to one task and both writer and reader need memory proportional to it.
- **Expecting statistics to help on unsorted data.** The machinery runs perfectly and prunes nothing. The fix is the write path, not the query.
- **Assuming pruning means the predicate is satisfied.** Surviving row groups are still filtered row by row; skipping is an optimisation, not the filter.
- **Relying on min/max for a UUID or hash column.** Uniform high-cardinality values make every range overlap. That is a Bloom filter question.
- **Forgetting that statistics on long strings are truncated.** Pruning quietly weakens as values get longer, with nothing in the query plan to say so.

**How to approach the questions**

1. For layout questions, count columns touched and rows scanned. That ratio decides the answer more often than any other consideration.
2. When a scenario says "a query got slower after a change to the writer", suspect row group size or clustering, not the query.
3. For pushdown questions, ask whether the statistics can *prove absence*. If the answer is "maybe there's a match", the group is read — and that is correct behaviour.
4. Distinguish predicate pushdown from projection pushdown explicitly; distractors swap them.
5. For any pruning claim, check the sort order of the write. Identical data with a different physical order gives opposite answers, and the question usually hides the ordering in one clause.
6. Watch for absolute claims like "columnar is faster". It is faster per column touched, and slower to reassemble a record.
