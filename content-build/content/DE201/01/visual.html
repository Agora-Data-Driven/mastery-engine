1. Bytes You Pay For

OLTP vs OLAP Workloads said the two shapes of work want different storage. Here is the inside of that claim: storage hands you contiguous byte ranges and you pay for every byte, used or not. Drag the columns a query touches. Like a newspaper: reading one column down every page versus reading one whole page.

Columnar also enables vectorized execution: the engine processes a column as a dense array of one type — cache-friendly and SIMD-friendly — instead of interpreting one heterogeneous record at a time. That is a second, independent win on top of the bytes.

2. Inside A Parquet File

Parquet is self-describing and puts its map at the end. Follow the read path: tail first, then the footer, then exactly the byte ranges you need. Tap each step. Like a book whose index is the last page — you read that first, then jump straight to two chapters.

Why two levels rather than one column per file? Row groups are the unit of parallelism and of bounded writer memory. Each is independently readable, so a distributed engine hands different row groups of the same file to different tasks; the writer buffers one group, flushes it, and starts the next, so its memory is bounded by the group rather than the file. Column chunks inside the group then deliver the columnar I/O benefit.

3. The Row Group Dial

One number, wrong in both directions. Drag it and watch parallelism, metadata size and writer memory move against each other. Like choosing how many boxes to pack a house into: a thousand tiny ones or two enormous ones both make moving day worse.

The historical 128 MB default matched HDFS block size. On object stores, 256 MB to 1 GB is common — because per-request latency, not block locality, dominates there. The dial is not a constant to memorise; it is a consequence of what your storage charges you for.

4. Proving Absence

Statistics can prove a row group contains no match. They can never prove it contains one. Pick a predicate and watch which groups are skipped from the footer alone — and which are read and then throw everything away. Like a library catalogue that lists each shelf's first and last title: you can rule shelves out, never rule one in.

Two edge cases experts check. Floating-point NaN does not order cleanly, so writers historically produced unusable min/max for such columns and engines may ignore those statistics entirely. And very long strings are truncated in statistics — min truncated downward, max padded upward — which stays safe and quietly weakens pruning as values get longer.

5. Sorted Or Shuffled

Identical rows, identical statistics machinery, identical query. The only difference is the order they were written in — and it decides whether you skip 96% of the file or none of it. Like a filing cabinet: alphabetised, you open one drawer; shuffled, you open all of them.

This is the central judgment of the whole lesson: statistics are only as good as your clustering. Sort or cluster on the columns your queries filter by most and min/max pruning approaches partition-level power at row-group granularity. Do nothing, and the machinery runs perfectly and prunes nothing — with no error and nothing in the plan to say why.
