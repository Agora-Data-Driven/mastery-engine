Columnar layout buys you the right to read only the columns you need; encodings and compression decide how few bytes those columns cost. In a cloud warehouse or a Cloud Run job scanning Parquet on GCS, you are billed for bytes scanned, stored, and shipped over the network, so a 10x size reduction is close to a 10x cost reduction on the I/O-bound part of every query. This lesson opens the compression stack inside a Parquet page, then connects it to something you already know deeply: the postings compression that makes an inverted index fit in memory.

## Dictionary and Run-Length Encoding

First, a distinction the rest of the lesson depends on. An **encoding** is a type-aware, reversible transformation applied to a column's values before any byte-level compression: it exploits what the values *are*. A **compression codec** (next section) is a general-purpose byte-stream compressor applied afterward, per page, that exploits residual redundancy in whatever bytes it is given. Encodings do the intelligent work; codecs mop up.

**Dictionary encoding** targets repetition of whole values. The writer builds a dictionary of the distinct values seen in a column chunk and stores it once (in a dictionary page); the data pages then store only small integer indexes into that dictionary. The indexes are bit-packed to the minimum width needed: a column with $k$ distinct values needs only $\lceil \log_2 k \rceil$ bits per row. A `country` column with 200 distinct names needs 8 bits per value; storing the strings raw at an average 10 bytes would cost 80 bits. That is a 10x reduction before the codec touches anything.

**Run-length encoding (RLE)** targets consecutive repetition. Instead of storing a value once per row, store the value once with a count: a million-row chunk of `status` values that is 600,000 `ok` followed by 400,000 `error` becomes two (value, run-length) pairs, bytes instead of megabytes. Parquet's workhorse is a hybrid, RLE/bit-packing: long runs are run-length encoded, and stretches without runs fall back to bit-packed literal values. Crucially, Parquet applies this hybrid *to the dictionary indexes themselves* (and to the definition/repetition levels that track nulls and nesting). So a low-cardinality column that is also sorted gets both wins multiplied: tiny indexes, and long runs of the same index collapse to almost nothing.

Worked example. A 1,000,000-row column chunk of `status` strings averaging 8 bytes each is 8 MB raw. Dictionary encoding with 4 distinct values needs 2-bit indexes: the data drops to about 250 KB plus a 32-byte dictionary. If the chunk happens to be sorted so the values form 4 runs, RLE represents it in a few dozen bytes. Same information, five orders of magnitude apart, purely from exploiting structure.

The judgment layer is cardinality. Dictionary encoding pays off when the number of distinct values is small relative to the row count; it fails when cardinality is high. Parquet writers cap the dictionary page size (on the order of 1 MB by default), and when a chunk's dictionary overflows that cap the writer *falls back* to plain encoding mid-chunk. A UUID or free-text column therefore gains nothing from dictionary encoding and bloats files that expected it, and a sudden jump in file size after a schema change is often exactly this fallback triggering. For sorted numeric data (timestamps, auto-incrementing IDs), delta encodings such as `DELTA_BINARY_PACKED` store successive differences instead of absolute values, which shrinks magnitudes dramatically; hold that thought for the postings section. Finally, remember from the last lesson that write-time sorting was what made min/max statistics useful; here it makes RLE useful too. Sort order is a single decision that pays twice.

One structural note ties encodings to schema design. Parquet represents nulls through definition levels rather than sentinel values, and those levels are themselves RLE/bit-packed, so a nullable low-cardinality column compresses nearly as well as a required one. Sentinel values such as empty strings or zeroes, by contrast, become ordinary frequent entries in the dictionary and blur the line between "absent" and "zero" in the data itself. Honest nulls keep both the semantics and the compression profile clean.

## Compression Codecs: Ratio vs Speed

After encoding, each page is optionally compressed with a general-purpose codec. The codec sees only bytes, not types. The practical menu, as of early 2026:

| Codec | Ratio | Compression speed | Decompression speed | Typical role |
|---|---|---|---|---|
| Uncompressed | 1x | n/a | n/a | Already-tiny or incompressible data |
| Snappy | Modest | Very fast | Very fast | Long-time default for hot data |
| LZ4 | Modest | Very fast | Fastest | Same niche as Snappy |
| Zstd | Good, tunable levels | Fast at low levels | Fast | The modern default at low levels; archival at high levels |
| Gzip | Good | Slow | Slow | Legacy compatibility, cold data |

The fundamental trade is CPU time against bytes moved and stored. Every byte saved is a byte not stored, not shipped over the network, and not billed; every byte saved costs CPU cycles to compress once and decompress on *every* read. That asymmetry is the key judgment input: analytical data is write-once, read-many. A file compressed once may be decompressed thousands of times, so **decompression speed matters more than compression speed**, and codecs like Zstd that decompress fast even at high compression levels dominate codecs like Gzip that are slow in both directions at similar ratios.

Whether heavier compression helps a given query depends on where the bottleneck is. Worked example: a scan must move 10 GB of encoded page data from object storage over an effective 200 MB/s per-worker network path. Snappy at 2.0x ratio ships 5 GB in 25 s; Zstd level 3 at 2.5x ships 4 GB in 20 s. If one core decompresses Zstd output at 800 MB/s or better, decompression overlaps the network transfer and the heavier codec is a straight win: the scan is I/O-bound, so buying bytes with CPU is cheap. Flip the scenario to data already on local NVMe at 3 GB/s and the scan becomes CPU-bound; now the lighter codec (or a lower Zstd level) wins because decompression, not I/O, is the critical path.

Two expert-level cautions. First, codecs compress *encoded* pages, so measured ratios depend on what encoding left behind: a well-dictionary-encoded, RLE-compressed column is already near its entropy floor, and a heavy codec may add CPU cost for a few percent of extra ratio. If a benchmark shows Zstd level 19 barely beating Snappy on some column, the encoding already did the work; do not pay level-19 CPU for it. Second, choose per temperature: hot, interactively queried tables want Snappy or Zstd at low levels; cold archival partitions tolerate high Zstd levels where the one-time compression cost amortizes against years of storage. Parquet permits setting the codec per column, which matters when one bulky text column deserves heavier treatment than the numeric columns beside it.

## Parquet Encodings vs Postings Compression

Recall from IR 101 how an inverted index compresses postings lists. A term's postings are document IDs in sorted ascending order. Sorted ascending integers are transformed into **gaps** (deltas between consecutive IDs), which are small positive integers, and small integers are stored in few bits using variable-byte coding or bit-packing schemes. The worked shape: doc IDs `[1000, 1003, 1007, 1012]` become gaps `[1000, 3, 4, 5]`; after the first, each fits in 3 bits instead of the 32 a raw ID would take.

Set that beside what this lesson built. Parquet's `DELTA_BINARY_PACKED` encoding on a sorted timestamp column does *literally the same thing*: store the differences between consecutive values, then bit-pack the small residuals. Dictionary encoding maps unbounded values into a dense integer space and bit-packs the indexes; RLE collapses consecutive repetition. Different names, one principle: **apply a cheap, reversible transform that exposes the data's low entropy, then spend only as many bits as the transformed values need**. Sortedness is the common fuel. Postings compress because doc IDs are sorted; Parquet columns prune and compress because you sorted them at write time. When you sorted a table by `event_ts` and both the min/max pruning and the file size improved, you were re-running the postings playbook on tabular data.

The parallel extends to a distribution-level insight from IR 101: a frequent term's postings list is *dense* in doc-ID space, so its gaps are small and it costs few bits per document, while a rare term's sparse postings have large gaps and cost more bits per entry. The tabular analog is exact: a low-cardinality column (values recur constantly, like a dense postings list) compresses to almost nothing, while a high-cardinality column (every value distinct, like maximally sparse postings) resists every trick in this lesson.

Where the two worlds genuinely differ is access pattern, and the difference explains each side's engineering choices. A search engine decodes postings *during query scoring*: BM25 traversal walks a postings list sequentially, intersecting and skipping via skip pointers, and every nanosecond of decode latency sits directly on the query's critical path. So postings formats favor schemes that decode at RAM speed and support jumping into the middle of a list. Parquet readers instead decompress a whole page at a time into a vectorized batch and hand it to the engine; random access within a page is not a goal, and per-page decompression cost is amortized over thousands of values. Both, however, converge on the same macro-judgment you saw in the codecs section: because decoding sits on the read path, both ecosystems favor light, fast codecs over maximum-ratio ones for anything queried frequently. An index that decompresses slowly is a slow search engine; a lake that decompresses slowly is an expensive warehouse.

Carry this bridge forward. When a later lesson shows many small files being merged into large ones, you will recognize LSM-style segment merging from the IR side. The storage layer of a search engine and the storage layer of a data lake are the same discipline wearing different clothes, and every encoding idea you meet in one will eventually greet you in the other.
