1. Pruning Two Scales

Column Statistics and Predicate Pushdown skipped row groups inside a file. The same idea works one level up, before a file is ever opened. Watch a one-day query eliminate data at both scales. Like finding a receipt: the right box, then the right folder, then the right page.

The two mechanisms are independent and they multiply. Partitioning eliminates files from the plan before any are opened; row-group statistics then eliminate groups inside the files that survive. A table can be perfectly partitioned and still scan badly if the data inside each partition is unsorted.

2. The Granularity Curve

Finer partitions prune more and cost more to plan. The curve has a bottom, and both sides of it are real failures. Drag the granularity. Like drawer dividers: a few help, one per sock means you spend the morning reading labels.

Two things that break pruning even when the layout is right

Choose with measurements, not intuition: bytes per partition, files per partition, filter frequency, pruning ratio, planning latency, skew, late-write frequency. The goal is not maximum partition count — it is to skip large irrelevant regions while keeping each selected region efficient to plan and scan.

3. Cost Per Object

Same bytes, different object counts. Every object costs a list, an open, a round trip, a footer parse, a task and a teardown — before any row is read. Drag the file size. Like moving house in ten thousand shopping bags.

Two things people confuse

The operational signal is end-to-end: planning time, object requests, task count, scan throughput, query latency, compaction cost. A file-size threshold is a means, not the goal. A layout is healthy when reads use compute efficiently and maintenance does not consume disproportionate resources.

4. Swap, Never Mutate

A compactor must merge 1,000 files into 16 while queries are reading them. Step through the safe workflow, then try the unsafe one and watch a reader double count. Like renovating a shop: build the new counter in the back, then move it in overnight.

Compaction is successful when readers see a consistent snapshot throughout: either the old set of small files or the new compacted set, never an accidental mixture. That guarantee matters more than hitting an exact target size — physical maintenance should improve performance without changing the table's logical history.

5. When Compaction Fails

The job dies. What you do next depends entirely on whether the atomic commit landed — and a lost acknowledgement makes that genuinely ambiguous. Pick a failure point. Like posting a letter and losing the receipt: did it arrive, or not?

What makes recovery possible at all

Sorting during compaction is the bonus round: clustering events by tenant within a date partition narrows the ranges a tenant filter touches, improving row-group statistics for free while the rewrite is happening anyway. Weigh it against rewrite CPU and skew — and note that repeatedly compacting already-healthy files just burns resources and churns storage.
