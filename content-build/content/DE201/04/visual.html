1. Not A File System

Compaction: Merging Files Without Breaking Readers assumed something could swap a pointer atomically. First, what the storage underneath actually offers. Tap an operation and compare what each system does. Like a post office box versus a filing cabinet: same-looking labels, very different rules about what you can reach inside.

The reliable mental model is an immutable key-value namespace with whole-object operations and prefix enumeration. Libraries may expose a familiar file API on top, and engineering decisions still have to account for copy-based renames, paginated listings, request costs and explicit dataset metadata.

2. Listing Is Not Membership

A batch is writing 1,000 objects. Drag the moment a reader lists the prefix and watch what it decides the table contains — then switch to a manifest. Like counting people arriving at a party to decide who was invited.

Costs are part of the semantics in practice. Object stores charge or throttle requests, retrieval, egress, and sometimes early deletion from archive tiers — so an algorithm issuing millions of HEAD or LIST calls can be expensive while reading almost no bytes. Measure request count alongside bytes scanned.

3. One Key, Many Keys

The whole lesson in one sentence: strong consistency for individual keys does not imply atomicity across a dataset. Watch a compactor replace A and B with C three different ways. Like swapping a two-page document for a one-page one while someone is reading it.

Multi-object atomicity needs a metadata layer. A table snapshot records the exact file set and the commit atomically changes one authoritative reference, while the large data objects stay immutable. That is the foundation of open table formats: object storage holds the files; table metadata supplies transactions, conflict detection, snapshots and garbage-collection reachability.

4. Moving A Pointer Safely

Two writers, one current.json. With an unconditional overwrite the store behaves perfectly and one writer's work vanishes. Press run. Like two people editing the same shared note: whoever saves last is the only one who did anything.

Two things that look like solutions and are not

Checksums guard a different boundary from consistency. A reader can consistently retrieve the wrong artifact because the metadata references an incorrect key — so validate object length and checksum against the manifest before accepting critical data, and quarantine mismatches rather than retrying forever against a bad reference.

5. Five Places To Crash

Consistency claims are only trustworthy when the multi-step protocol has been tested at every window. Pick a crash point and check three things: what readers see, whether recovery is idempotent, and whether cleanup could eat live data. Like fire drills: the point is the doors you have not tried.

Local development conceals all of this: an emulator or mounted adapter answers listings cheaply and makes rename appear native. Integration tests should run against the real API behaviour — pagination, conditional requests, multipart completion, credentials and realistic object counts. Performance and correctness assumptions belong in those tests.
