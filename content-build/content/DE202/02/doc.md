Idempotency is the center of gravity of pipeline engineering. Every layer of a modern data platform — message delivery, task schedulers, distributed workers, your own retry loops — will eventually execute the same work more than once, and the only sane response is to design so that re-execution is harmless. For an AI stack this is existential: if re-running the job that builds your retriever's document store or aggregates evaluation metrics changes the answer, you can never trust a rebuilt index or a backfilled dashboard again. This lesson builds the three pillars that make pipelines *replayable*: idempotent writes, deterministic partitioning, and a deliberate choice between incremental and full refresh.

## Idempotent Writes: Same Input, Same Result

An operation is **idempotent** when applying it more than once leaves the system in the same state as applying it once: $f(f(x)) = f(x)$. For pipelines, the operative form is: *running a job N times over the same input produces exactly the same target state as running it once.* Note what is being promised — not that the job never re-runs (it will), but that re-runs are indistinguishable from single runs.

**Why you have no choice.** Duplicated execution is not an edge case; it is the steady state of distributed systems. Message queues deliver at-least-once, so consumers see repeats. Orchestrators retry failed tasks, and "failed" often means "the write succeeded but the acknowledgment was lost", so the retry re-writes. Workers crash after committing partial output. Humans re-run yesterday's job after fixing a bug. If your write path is a blind `INSERT INTO curated.orders SELECT ...` append, every one of those events silently doubles rows: the classic symptom is a nightly job that re-ran after an outage and doubled downstream revenue counts. Nothing errored — the data is simply wrong, and appends give you no way to tell which copy is legitimate.

**The mechanisms.** Idempotent writes come in a small number of shapes, all reducible to "make the write's effect a function of the data, not of how many times it ran":

1. **Overwrite a deterministic target.** Delete-then-insert or truncate-then-write scoped to exactly the slice the job owns. In BigQuery: write partition `curated.orders$20260724` with `WRITE_TRUNCATE`, or run `DELETE FROM curated.orders WHERE day = '2026-07-24'` followed by the insert, inside the same job. Run it once or five times: the partition ends up identical.
2. **Merge/upsert keyed on a business key.** `MERGE INTO curated.orders t USING batch b ON t.order_id = b.order_id WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...`. The key makes rows converge instead of accumulate.
3. **Stage-and-swap.** Write results to a temporary table, validate, then atomically replace the target (or repoint a view). Re-runs just rebuild the temp table.
4. **Deduplication windows.** Attach a stable unique ID to each record and have the sink drop repeats. BigQuery's legacy streaming `insertId` works this way but is *best-effort* over a short window — treat it as duplicate reduction, not a guarantee; strict correctness still needs a key-based `MERGE` or downstream `QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY ingest_time DESC) = 1` dedup.

**Worked example.** A nightly job aggregates `raw.order_events` into `curated.revenue_daily`. Append version: July 24 runs, times out on the final commit acknowledgment, the orchestrator retries, and July 24 now has two copies — revenue reads $214,882 instead of $107,441. Idempotent version: the job computes the July 24 aggregate and writes it to partition `revenue_daily$20260724` with `WRITE_TRUNCATE`. The retry recomputes the identical aggregate and truncate-writes the identical partition. State after one run and after five runs: byte-for-byte the same.

**Judgment layer.** Idempotent *write modes* are necessary but not sufficient — the *transform* must also be deterministic. A job that stamps rows with `CURRENT_TIMESTAMP()`, samples with `RAND()`, reads mutable reference data "as of now", or calls an LLM (whose outputs vary run to run) produces different content each execution; overwriting with it is still a changed table. Either make such fields derive from the input (use `event_time`, seed the sampler, snapshot reference data, cache model outputs by input hash) or accept and document the drift. Cost is the other axis: `MERGE` against a multi-terabyte target rescans expensive data per run, so high-volume pipelines prefer partition overwrite, which touches only the slice being rewritten. Finally, watch the scope of your delete: `DELETE WHERE day = X` is idempotent only if the job writes *all* of day X — a job that owns half a partition and truncates all of it destroys its neighbor's data on every run.

## Deterministic Partitioning for Replayable Jobs

Idempotent writes answer *how* to write; deterministic partitioning answers *where*. A partitioning scheme is **deterministic** when the partition an element belongs to is a pure function of the element's own data — `DATE(event_time)`, `ABS(FARM_FINGERPRINT(user_id)) % 64` — and never a function of processing context: wall-clock time at load, arrival order, worker identity, or an auto-incrementing batch number.

**Why it is the other half of replayability.** Overwrite-style idempotent writes only work if a re-run targets *the same slice* the original run wrote. Combine the two and you get the property this whole course leans on: *re-running the job for input slice X rewrites exactly the partitions X maps to, and touches nothing else.* That is what makes a job replayable — you can re-execute any historical day with surgical, predictable effect.

The canonical violation is **ingestion-time partitioning** for event data: partitioning by "the date the row was loaded". On the happy path it looks identical to event-date partitioning. But replay Monday's failed load on Wednesday and the rows land in Wednesday's partition: Monday's partition stays wrong, Wednesday's is polluted, and the overwrite mechanism from the previous section has no correct slice to truncate. The job is now *unreplayable* — the output depends on when it ran.

**Worked example.** Events carry `event_time`. The job partitions by `DATE(event_time, 'UTC')` and writes with per-partition truncate. On July 23 the source was down; on July 25 you backfill July 20–23. Each day's input maps to exactly its own partition: the backfill rewrites `$20260720` through `$20260723` and cannot touch July 24–25. Compare hash bucketing for a keyed store: `bucket = ABS(FARM_FINGERPRINT(user_id)) % 64` assigns every occurrence of a user to the same bucket on every run on every machine — `FARM_FINGERPRINT` is a stable hash of the value, unlike in-memory hashes that vary per process. A rebuild of bucket 17 affects exactly the users that hash to 17.

**Judgment layer.** The subtle failure modes are all about the "pure function" clause. *Timezones:* `DATE(event_time)` in one job and `DATE(event_time, 'Asia/Manila')` in another silently assign boundary events (a purchase at 23:30 UTC) to different days — pick one convention (UTC is the default choice) and enforce it in the contract. *Late data:* an event for July 20 arriving July 25 still maps to `$20260720`; the replayable design handles it by re-running recent partitions on a schedule (a lookback window — see the next section) rather than by dumping stragglers into today. *Skew:* deterministic does not mean balanced — one whale user can make bucket 17 ten times larger than its peers; you fix skew by choosing a better key or higher bucket count, never by assigning overflow "wherever there is room", which would reintroduce nondeterminism. *Mutable attributes:* partitioning by a value that can change (the user's current country) makes history move between partitions across runs; partition by immutable event facts instead.

## Incremental vs Full Refresh

Given replayable slices, the remaining decision is how much to recompute each run. A **full refresh** rebuilds the entire target from all input every time. An **incremental refresh** processes only the new or changed slice and folds it into the existing target.

**Mechanisms.** Full refresh is `CREATE OR REPLACE TABLE curated.x AS SELECT ... FROM raw.y` — brutally simple and *self-healing*: whatever was wrong yesterday, today's run rebuilds from scratch, so errors do not persist. Incremental refresh needs bookkeeping: a **high-water mark**. The job records the maximum `updated_at` (or partition date, or log position) it has processed; the next run selects `WHERE updated_at > @last_high_water_mark`, transforms just that delta, and applies it with an idempotent write — `MERGE` for keyed upserts, partition overwrite for date slices. The two previous sections are what make incremental *safe*: without idempotent, deterministically-targeted writes, an incremental pipeline that retries corrupts its target and its watermark.

**The arithmetic that forces the choice.** Suppose `raw.order_events` holds 2 TB of history and grows 5 GB/day. A daily full refresh scans 2 TB × 365 ≈ 730 TB/year, and the scan grows as history grows. The incremental version scans ~5 GB/day plus the merge overhead — roughly 400× less data, with runtime to match. At warehouse on-demand pricing of a few dollars per TB scanned, that is the difference between a rounding error and a five-figure annual bill for one table. This is why incremental is the default for large fact tables.

**Where incremental silently rots.** Every incremental design inherits the weaknesses of its watermark:

- **Unreliable `updated_at`.** A backend path that writes rows without touching `updated_at` (bulk fixes, direct SQL) makes changes invisible to `WHERE updated_at > wm` — permanently skipped.
- **Clock skew and in-flight transactions.** A row committed with `updated_at = 10:00:00` can become visible *after* a run that already advanced the watermark past 10:00:00; the row falls in the gap. Standard insurance is a **lookback window**: each run reprocesses the trailing N hours/days below the watermark (cheap, because the writes are idempotent — reprocessing overlap is harmless by construction).
- **Deletes are invisible.** A deleted row simply stops appearing in the source; no `updated_at` filter will ever select it, so the target keeps a ghost. You need soft deletes (a `deleted_at` column that updates the watermark column) or change data capture, covered in a later lesson.
- **Drift accumulates.** Missed rows, ghosts, and logic changes compound over months. Mature pipelines therefore run *hybrid*: incremental daily for cost, plus a periodic (weekly/monthly) full refresh or reconciliation diff that bounds how wrong the table can silently become.

**Judgment layer.** Choose full refresh when the data is small (a full rebuild costing seconds needs no watermark machinery), when correctness must be self-healing, or when the logic is not incrementalizable — global deduplication, window functions over all history, or "top-K over all time" cannot be computed from a delta alone without maintaining auxiliary state. Choose incremental when volume makes full scans unaffordable and the source offers a trustworthy change signal. And treat the hybrid as the professional default for large, important tables: incremental for the daily 99%, scheduled full reconciliation as the audit. The unifying test for any design you propose: *if this job re-ran twice for the same slice, or re-ran for last Tuesday, would the target be byte-identical to the single-run, on-time world?* If yes, you have a replayable pipeline; if no, you have a latent incident.
