Every model you train and every retrieval system you operate is downstream of a data pipeline, and prediction quality is capped by the correctness of the values that pipeline delivers. Your hybrid retriever already lives this pattern: BM25 statistics, document embeddings, and reranker inputs are all values some job computed from raw documents and interaction logs. Feature pipelines are the general form of that work, turning immutable raw events into model inputs; feature stores are the storage pattern that lets one set of feature definitions serve two very different consumers, training jobs that scan months of history in bulk and serving paths that must answer for a single entity in milliseconds.

## Feature Pipelines: From Raw Events to Model Inputs

**The raw material.** A raw event is an immutable, append-only record of a fact: something happened, involving some entity, at some time. `{"user_id":"u42","event":"click","doc_id":"d9","ts":"2026-07-01T08:14:03Z"}` is an event; so is an order row, a page view, a payment, a sensor reading. Events are never updated in place. If a click was logged incorrectly, you append a correction event; the log stays append-only. This immutability is the property that makes everything downstream recomputable: any derived value can be rebuilt from the log, for any point in the past, as many times as you need.

**What a feature is.** A feature is a named, typed, derived value that describes an entity as of a point in time: `user_ctr_7d(u42, as_of=2026-07-08) = 0.214`. Three parts carry equal weight: the entity key (which user, which document, which card), the value, and the as-of timestamp. A feature "without" a timestamp is a latent bug, because the same feature name takes different values on different days, and a consumer that cannot say *which* day's value it wants will eventually get the wrong one. Model inputs are then just a fixed-order vector of feature values for one entity at one as-of time, exactly the design matrix rows you know from training linear and logistic models.

**The stages.** Production pipelines decompose into five stages, each with a contract:

1. **Ingestion** lands events from producers (application logs, message queues, database change streams) into durable, partitioned storage, typically keyed by arrival date.
2. **Validation** checks each event against a schema and sanity ranges: required keys present, timestamps parseable and not in the future, enumerations legal, numeric fields within plausible bounds. Failing events are routed to a quarantine location (a dead-letter table) with the reason attached, and the *rate* of failures is monitored. Quarantining beats silent dropping because you can inspect, fix, and replay; it beats letting bad rows through because one malformed producer deploy can otherwise poison every aggregate computed after it.
3. **Transformation** applies stateless, per-event cleaning: parse and normalize timestamps to UTC, canonicalize categorical values, cast types, derive simple per-event fields. Stateless means each output row depends only on its input row, which makes this stage trivially parallel and trivially re-runnable.
4. **Aggregation** is where features are born: windowed reductions grouped by entity key. Counts, sums, rates, distinct counts, most-recent values, over windows like 1 day, 7 days, 30 days. This stage is stateful across events and is where most of the correctness risk lives.
5. **Materialization** writes the resulting feature rows to the storage that consumers read, which the next section covers.

**Worked example.** Compute `user_ctr_7d` for u42 as of 2026-07-08. The window is `2026-07-01 <= ts < 2026-07-08`. In that range u42 has 14 `impression` events and 3 `click` events, so the value is 3/14 ≈ 0.214. The output row is `(entity=u42, feature=user_ctr_7d, value=0.214, as_of=2026-07-08)`. Run the same job as of 2026-07-09 and the window slides: two impressions fall out, one new click enters, and the value becomes 4/12 ≈ 0.333. Both rows are kept; history accumulates one row per entity per day.

**Idempotence and re-runs.** Jobs crash, get retried by schedulers, and get re-run by humans after bugfixes. The design rule that survives all of this: a run *owns* a deterministic output partition (say, `feature=user_ctr_7d/as_of=2026-07-08`) and **overwrites** it, so re-running produces byte-identical state instead of duplicates. Pipelines that append on each run double their counts on the first retry after a mid-job crash, and the corruption propagates to every downstream consumer before anyone notices. Idempotence is cheap to design in and brutal to retrofit.

**Event time vs processing time.** Event time is when the fact happened; processing time is when your pipeline observed it. Mobile clients batch uploads, queues back up, and regions fail over, so events routinely arrive minutes to days late. If you window on processing time, a re-run assigns events to entirely different windows than the original run did, so outputs are unstable by construction. The stable design windows on event time, waits out a declared lateness horizon (say 48 hours), then closes the window and treats its partition as immutable; events arriving after the horizon are counted in a correction process or consciously dropped, but the closed partition never silently changes.

**Judgment.** Batch pipelines recompute windows on a schedule: simple, cheap, reproducible, with freshness equal to the schedule. Streaming pipelines update aggregates per event: fresh within seconds, but state management, out-of-order events, and exactly-once accounting make them materially harder to build and to trust. Choose the *slowest* freshness the model measurably needs; a weekly-retrained model scored nightly gains nothing from a streaming 30-day aggregate. The same logic governs precompute vs compute-at-request: features derivable from the request payload alone (the query text your retriever tokenizes) are computed inline; features over history (a 90-day aggregate) must be precomputed, because no request-time budget survives scanning 90 days of events. Most teams run batch for everything, then move individual features to streaming only when their staleness is shown to cost accuracy, as with a 10-minute transaction count in fraud detection.

## Feature Stores: Offline Training vs Online Serving

**Two consumers, two access patterns.** Training assembles a design matrix: millions of (entity, as-of time) rows joined to feature values, read as a bulk scan over months of history. Serving does the opposite: fetch the *latest* values of a handful of features for *one* entity, inside a request budget of a few milliseconds. These access patterns want physically different storage layouts. Bulk scans want columnar files, compressed, partitioned by date, where reading one feature column across a billion rows is sequential I/O. Point reads want a key-value engine where one entity's values sit under one key in memory or on a fast index. No single engine is optimal at both, for the same reason no single index served both your BM25 term lookups and your bulk analytics: layout is a commitment.

**The offline store** is the columnar, historical side: a warehouse table (BigQuery) or Parquet files on object storage (GCS), partitioned by as-of date, holding the *full history* of feature values with their timestamps. Consumers are training-set assembly, backfills, and analysis. Latency of seconds to minutes is fine; the costs that matter are storage and per-scan compute.

**The online store** is the serving side: a key-value system (Redis, Bigtable, Firestore) mapping entity key to the *latest* feature values, often with a TTL. `GET features:u42` returns `{"user_ctr_7d":0.214,"spend_30d":112.50,"updated_at":"2026-07-08T02:10:00Z"}` in single-digit milliseconds at p99. It holds no history; it is a materialized cache of "current truth" per entity.

**Materialization and sync.** One pipeline computes the feature values, then writes twice: the full dated history to the offline store, and the latest values to the online store. The two stores are two *projections of one computation*, never two computations. That sentence is the entire point of the architecture: the moment training reads values produced by one code path and serving reads values produced by another, the definitions drift and the model silently degrades. The full mechanics of that failure class are the subject of the next lesson; here it is enough to see the structural prevention.

**The registry.** A feature store also keeps a registry: each feature's definition as code and metadata, its name, entity type, source events, transformation, refresh schedule, TTL, and owner. The registry is what makes "one definition, two destinations" enforceable, enables discovery and reuse across models, and gives you somewhere to hang lineage and monitoring.

**Worked example.** Training a click model on 90 days of data for 1M users scans roughly 90M offline rows of `user_ctr_7d` history in a minutes-long batch job that costs cents. At serving time, the model server does one point read for u42 (about 3 ms), assembles the feature vector in code, and calls the model, comfortably inside a 20 ms budget even with 40 features, because all 40 live under one key.

**What breaks without each half.** Serve from the warehouse and each request runs aggregation queries that take hundreds of milliseconds to seconds: the latency budget dies. Train from the online store and only *latest* values exist, so you join today's features to last month's labels, a temporal mismatch this course treats in depth next lesson. Skip the shared pipeline and you get two divergent implementations of every feature.

**TTL and staleness.** Online values refreshed nightly usually carry a TTL near the refresh interval. If the pipeline misses a run, values expire and serving reads come back empty, so the serving code's *default policy* becomes model input: an unnoticed default of 0 for `spend_30d` looks like "brand-new customer" to the model. Decide defaults deliberately, and monitor the online store's null-read rate as a first-class alert.

**When you do not need one.** If all scoring is a nightly batch (score 200k customers, write results to a table an app reads), there is no online read path, so a feature store adds machinery without value: compute features and scores in the same batch job. If every feature derives from the request payload alone, there is nothing to store. And at small scale, a Firestore document per user refreshed by one scheduled job *is* a perfectly good minimal online store; the pattern matters, not the product. Managed and open options exist when you outgrow that (as of early 2026: Feast in open source; Vertex AI Feature Store on your own stack; SageMaker Feature Store; Tecton), and the adoption triggers are concrete: multiple models sharing features, request-time inference with tight budgets, or a training/serving divergence incident you never want to repeat. Note the shape transfers to retrieval directly: your document embeddings and term statistics are features of documents, computed offline in batch and materialized into a low-latency index for serving.
