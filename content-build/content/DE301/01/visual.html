1. Events To Inputs

You already run this pipeline — BM25 statistics and document embeddings are values a job computed from raw documents and logs. Here is the general shape, with a contract at every stage. Tap one. Like a kitchen: deliveries, inspection, prep, cooking, plating — and only one of those stages can ruin the whole service.

A model input is just a fixed-order vector of feature values for one entity at one as-of time — the design-matrix rows you already know from training linear and logistic models. Nothing about the destination is exotic; all the difficulty is in getting honest values into it.

2. The Sliding Window

A feature is three things: an entity, a value, and an as-of timestamp. Drag the as-of date and watch the same feature name take a different value — which is exactly why the third part is not decoration. Like a bank balance: meaningless without saying when.

Re-run the same job. What should happen?

History accumulates one row per entity per day, and every row is kept. That is what lets a training job ask for the value as it was on any past date — the mechanism the next lesson is built on.

3. Which Clock

Events arrive late — mobile clients batch uploads, queues back up, regions fail over. Which timestamp you window on decides whether a re-run reproduces the original answer. Like postmarks versus the day the postman happened to deliver.

Batch or streaming is the other half of this decision, and the rule is the same shape: choose the slowest freshness the model measurably needs. Most teams run batch for everything and move individual features to streaming only when staleness is shown to cost accuracy — a 10-minute transaction count in fraud detection is the canonical exception, not the template.

4. Two Projections

One computation, two consumers with opposite access patterns. Switch consumer and watch which layout survives the requirement. Like a library that needs both a reading room and a vending machine.

And you may not need one at all. If all scoring is a nightly batch — score 200k customers, write results to a table an app reads — there is no online read path, so compute features and scores in the same job. At small scale a document per user refreshed by one scheduled job is a perfectly good minimal online store: the pattern matters, not the product.

5. When The Run Is Missed

The nightly job fails. Values expire, serving reads come back empty, and whatever your code substitutes becomes a model input. Choose the default and read what the model concludes. Like a form where a blank box gets filled in for you by someone who was not there.

Monitor the online store's null-read rate as a first-class alert. A missed pipeline run is not visible in serving latency, error rates or model accuracy on the day it happens — the request succeeds, the model returns a confident score, and the only trace is a rate of empty reads that nobody is watching.
