1. The As-Of Join

Feature Pipelines insisted every feature carries an as-of timestamp. Here is what it is for: a join that answers what did we know then, not what do we know now. Switch the join and watch a March example get July's answer. Like asking what the weather was on the day of the picnic, not what it is outside right now.

The same rule reaches reference data. Currency conversion must use the rate available at prediction time; taxonomies, risk lists, model-derived embeddings and business rules all need versioned snapshots. A single unversioned lookup table leaks even when every event feature is correct — which is why a leakage audit that only covers features finds nothing.

2. Two Clocks Again

A fact can be about 09:00 and only reach you at 14:00. A prediction at 11:00 could not have used it, however early its event time. Drag the prediction moment. Like a letter dated Monday that arrives Thursday: it was true on Monday and you did not know it.

And the policy this forces on late arrivals

Bitemporal sources make this explicit: valid time is when a fact was true in the world, system time is when you learned it. To reproduce a February prediction, use the system-known timeline — training on later-corrected truth is a different experiment, legitimate to run and dishonest to deploy against.

3. Leakage Audit

Run each feature through one question: could the production system obtain this exact value, with this freshness and this logic, before making the prediction? Tap a feature. Like checking whether a witness could actually have seen what they described.

Checks that expose common shortcuts

These tests do not prove the absence of leakage — they expose the usual shapes. The governing test stays counterfactual, and it can rule a feature out even when it is genuinely causally related and sitting in today's warehouse.

4. Splitting Honestly

A random split assumes rows are independent. Repeated customers and near-duplicate sessions make that false, and the optimism it buys survives every review. Switch the split. Like testing a student on questions they have already seen with the numbers changed.

The two strategies answer different questions and are not alternatives. Temporal asks "will this work on next month's data", which is the deployment question. Group asks "will this work on a customer it has never seen", which is the memorisation question. Where both risks exist, you need both constraints.

5. Same Number, Different Truth

Offline says 100. Online says 100. That is not parity. Tap each kind of skew and see what shared code does and does not fix. Like two clocks showing the same time, one of which stopped three days ago.

And when exact parity is genuinely impossible, train for the serving reality: simulate the online delay, the missingness, the quantisation or the approximation in the historical features. A slightly less accurate model trained on deployable signals is worth more than a high-scoring one that depends on truth production cannot obtain.
