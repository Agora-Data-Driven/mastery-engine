**The big idea**: **Versioning Datasets Alongside Models** and **Reproducible Training Data: Snapshots over Live Queries** established that an artifact is only trustworthy when you can name the exact input version behind it. **Parsing and Extraction as Pipeline Stages**, **MinHash and SimHash for Near-Duplicate Detection**, **LSH: Finding Near-Duplicates Without All-Pairs Comparison** and **Language ID and Quality Filtering** turned raw documents into a clean, deduplicated, versioned corpus of chunks. This lesson is the last hop: translating those versioned chunks into vector artifacts that retrieval can serve — and remarkably little of it is about calling a model. Correctness rests on four things: deterministic identity, bounded batching, metadata lineage, and filtering semantics. A reliable design can resume after failure, coexist across model versions, and prove that every returned vector still belongs to an eligible source.

**Key concepts**

- **A chunk-and-embed job is a selective, resumable batch job, not a loop over documents.** The mechanism is fixed: read an immutable corpus version, select the chunks missing the target embedding version, batch their text, invoke a pinned model, validate the vectors, write results under deterministic keys. Without the "select what is missing" step, a re-run duplicates everything it already made; with it, re-running converges to the same logical output. A job killed after 60% of a generation is written retries only the remaining 40%.
- **Embedding identity must include every input that affects the vector.** A useful recipe: `embedding_id = hash(chunk_id, model_id, model_revision, preprocessing_version)`. Change the text normalization, the instruction prefix, the truncation rule or the pooling strategy and the preprocessing version changes, minting a *new* identity rather than overwriting the old vector. Without that, two numerically incompatible vectors compete for one key.
- **Do not identify a vector by document ID — and not by content hash alone either.** One document version has many chunks and one chunk can have many embeddings, so a document ID is far too coarse. A content hash deduplicates identical text, but two occurrences of the same passage may need distinct metadata and permissions. If cross-document deduplication is genuinely valuable, separate the reusable vector bytes from the occurrence records.
- **Pin the inputs before any work begins.** Resolve the corpus snapshot and the chunker version up front. If chunks change while a batch runs, the result mixes generations and orphans vectors. The run manifest records corpus version, chunk manifest, model endpoint and revision, code artifact, parameters and expected item count.
- **Batch size is a token budget, not a chunk count.** Suppose the endpoint accepts at most 20,000 tokens and a batch holds chunks of 600, 900 and 1,100 tokens. Token-aware packing beats a fixed count of 50 chunks: fifty 1,100-token chunks is 55,000 tokens and is rejected, while fifty short ones waste the call. Reserve space for model-specific prefixes, and use the exact tokenizer version.
- **Retries need stable request items and stable outputs.** If a timeout fires *after* the service already processed a batch, repeating it must upsert the same embedding IDs — never increment a counter or append an unnamed vector as a side effect. Record attempt status separately from committed artifact identity.
- **Transient and permanent failures need different machinery.** Rate limits and transient errors get exponential backoff, jitter and bounded concurrency. Permanent errors — input too long, invalid encoding, unsupported language — enter a quarantine carrying chunk ID, error class and model version. Retrying malformed input forever wastes quota and blocks progress.
- **Validate before commit, and check the ORDER.** Vector count equals accepted input count; dimensionality matches the model contract; values are finite; norms fall in expected bounds; and response ordering maps back to request IDs. A batch API that returns results in a changed order silently attaches vectors to the wrong chunks whenever the client trusts position alone.
- **Completion is a published fact, not an assumption.** Partial publication is safe when each upsert is individually idempotent and the index supports mixed completion, but serving must know whether a corpus generation is complete. A readiness manifest tracks expected, succeeded, quarantined and missing counts; the serving alias switches only after policy thresholds pass, and committed vector IDs are reconciled against the chunk manifest so silent omissions cannot masquerade as completion.
- **Model upgrades build BESIDE the current generation.** Embed with the new version, populate its own index, compare recall, latency and distributions, then switch routing — and keep the previous generation for rollback. Updating vectors in place removes the ability to reproduce old scores, which is exactly the versioning discipline you already met, applied to retrieval.
- **Caches need the same identity discipline as the store.** Key by canonical model revision, preprocessing hash and exact text hash, then verify the returned dimension and checksum. A cache keyed only by text silently reuses vectors from an older model whose numeric space is incompatible; track its provenance and invalidate on an audited retention policy.
- **Storing vectors beside metadata is what makes a vector filterable, citable, invalidatable and explainable.** A vector without metadata can do none of those. Each record needs at least embedding ID, chunk ID, document-version ID, model version, dimension, creation time and state; retrieval usually also wants source, language, tenant, permissions, timestamps, content type and quality attributes.
- **"Beside" has two legitimate readings, and you often want both.** Co-located fields inside the vector index give low-latency filtering and result display. A normalized relational catalog joined by stable ID stays the source of truth for full lineage and for attributes too large or too mutable to copy onto every vector record.
- **Denormalized filter fields must be synchronized, and that sync has a risk window.** When document permissions change, every affected vector must become inaccessible promptly — by updating index payloads, by delete-and-rebuild, or by an external authorization service consulted after retrieval. Store immutable attributes with the vector generation (chunk parent, language at processing, model version, corpus version, content hash); reference mutable ones through a versioned metadata stream, and record a metadata version so stale payloads are detectable.
- **Dimensionality and distance semantics belong in the schema.** A 768-dimensional cosine-normalized vector cannot blindly share a field with a 1,536-dimensional inner-product vector. Index namespaces or typed collections should bind model, dimension, normalization and metric together.
- **Lineage is what makes deletion actually work.** Deleting document version V must enumerate every chunk and embedding descendant across models and indexes. Moving the logical document's current pointer removes nothing if the serving query still searches the old vectors. Maintain state — active, superseded, deleted, quarantined — and monitor orphan vectors, stale metadata versions, dimension mismatches and inactive hits.
- **Pre-filter applies eligibility before or during the ANN traversal; post-filter retrieves neighbours from the broader index and removes ineligible results afterwards.** Placement changes recall, cost and security. Concretely: top 10 results for tenant A, which owns 1 percent of a shared index. A post-filter search asking for 10 global neighbours may return zero tenant-A items. Raising the candidate count to 1,000 lifts the expected eligible count to about 10 under uniform assumptions — and neither relevance nor tenant distribution is uniform.
- **Post-filtering needs oversampling, and `k/p` is a starting point, not a guarantee.** With eligible fraction $p = 0.05$ and $k = 20$, the rule suggests 400 candidates. Skew, correlation with similarity, and ANN misses mean you must measure and cap, not trust the arithmetic.
- **Pre-filtering guarantees the search runs over eligible vectors — when the index truly implements the predicate.** It can improve recall inside a tenant because ineligible nodes never consume the top-k budget. But restrictive filters can fragment an ANN graph or leave too few candidates, and some engines implement "filtering" by oversampling internally rather than genuinely restricting traversal.
- **Authorization is not a relevance filter.** An ineligible vector must never be returned, logged as visible content, or handed to a reranker that exposes it to an unauthorized service. Post-filtering is secure only when removal happens inside a trusted boundary before any prohibited disclosure — logs and traces included.
- **Small eligible sets are an argument for exact search.** If an eligible subset holds 500 vectors, brute-force cosine may beat navigating a massive ANN index. Adaptive candidate sizing estimates selectivity from metadata statistics and requests more neighbours for rare filters, bounded to protect latency.

**Rules to remember**

- Identity is a hash of chunk plus every input that changes the numbers. Anything less duplicates or collides.
- Re-running a correct job is free and safe. If a re-run creates rows, the job is not idempotent.
- Pin the corpus snapshot and chunker version before work starts, and record them in the run manifest.
- Pack batches by tokens, not by count, reserving room for prefixes; map responses by request ID, never by position.
- Quarantine permanent errors; back off on transient ones. Never retry malformed input forever.
- Build a new model generation beside the old one, compare, then switch routing. Keep rollback.
- A vector's dimension, normalization and metric are schema, not convention.
- Deletion follows lineage down to every embedding descendant, in every index.
- Pre-filter or partition for mandatory security constraints; post-filter only for cheap, non-sensitive refinement.

**Common pitfalls**

- **Keying vectors by document ID.** One document version is many chunks and many embeddings. The key collides the moment a second chunk or a second model appears.
- **Re-embedding everything on every run** because selection was skipped. Expensive, and it produces duplicate vectors that both look valid.
- **A fixed chunk count per batch.** It blows the token limit on long chunks and wastes the call on short ones.
- **Trusting response order.** The vectors land on the wrong chunks and nothing errors — retrieval simply degrades in a way no test catches.
- **Publishing a partial generation as complete.** Without a readiness manifest, "the job finished" and "every chunk has a vector" are different claims.
- **Updating vectors in place on a model upgrade.** Old scores become irreproducible and there is no rollback.
- **A cache keyed on text alone.** It serves vectors from an incompatible numeric space with total confidence.
- **Treating post-filtering as an access control.** If an ineligible vector reached a reranker or a log, the exposure already happened.
- **Assuming "pre-filter" means one thing.** Some engines restrict traversal, some oversample internally, some traverse through ineligible nodes. Read the implementation.
- **Correct pre-filter, stale payload.** A revoked group that has not propagated passes the filter cleanly. The filter was right; the metadata was old.
- **Judging filtered behaviour by unfiltered recall.** Global recall says nothing about a 1 percent slice.

**How to approach the questions**

1. For any "the job ran twice" scenario, ask what the key is. If the answer is a document ID, a position, or an autogenerated ID, the job is not idempotent.
2. When a change is described (new normalization, new prefix, new pooling), decide whether it changes the *numbers*. If it does, it changes the identity, and old vectors must be superseded rather than overwritten.
3. For batching questions, do the token arithmetic explicitly against the 20,000-token ceiling. Counts are distractors.
4. For metadata questions, ask which of filter, cite, invalidate or explain breaks without the field in question.
5. For filter-placement questions, first ask whether the predicate is *security* or *relevance*. Security constraints push you to pre-filtering or physical partitioning; relevance refinements can live in a post-filter.
6. Whenever a selectivity is quoted, compute $k/p$ before answering — then remember it is a floor, not a promise, and that a very small eligible set may be better served by exact scanning.
