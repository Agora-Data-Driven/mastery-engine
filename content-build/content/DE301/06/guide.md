**The big idea**: **Chunk-and-Embed as an Idempotent Batch Job**, **Storing Vectors Beside Metadata** and **Pre-Filter vs Post-Filter in ANN Search** built the thing that *produces* vectors and the query shape that *consumes* them. This lesson is about the system that serves them — and whether you need a specialised one at all. A vector database is an operational system for indexing vectors, applying metadata constraints, updating state, and serving similarity queries under latency and availability goals: a product category, not a data structure. Three ideas decide everything in it. An index is chosen by its **operational profile**, not its benchmark recall. The vector store is a *derived serving projection* and never the truth itself — the discipline **Versioning Datasets Alongside Models** and **Reproducible Training Data: Snapshots over Live Queries** imposed on training data, now applied to serving. And exact search is the baseline you have to beat, not the step you skip.

**Key concepts**

- **An operational profile is nine dimensions, and benchmark recall is one of them.** They are recall, latency, build time, memory, disk, update behaviour, filtering, concurrency and recovery. Two indexes with similar benchmark recall can have very different profiles, so a leaderboard says almost nothing about behaviour during an incident. ANN indexes trade exactness for speed at scale; *which* exactness and *which* costs is the whole question.
- **HNSW builds a multilayer proximity graph.** Search enters at sparse upper layers, navigates toward the query, then explores more candidates in a dense lower layer; `efSearch` controls that exploration, and larger values usually improve recall and cost latency. Strong low-latency recall and incremental insertion — but graph edges consume substantial memory, deletion may be **tombstoned** until maintenance or rebuild, and heavy churn degrades the structure or leaves dead nodes. Metadata pre-filter behaviour is implementation-dependent, because restricting traversal can *disconnect eligible regions* — last lesson's pre-filter question, returning as a graph-connectivity question.
- **IVF trains centroids and probes a few coarse clusters.** Vectors are assigned to lists; at query time only a selected number are searched. With **10,000 lists and `nprobe=20`, roughly 0.2 percent of clusters are probed** before further candidate scoring, though cluster sizes and distribution vary. Raising `nprobe` raises recall and raises work. IVF needs representative training data: poor centroids or distribution drift create unbalanced lists and missed neighbours. Appends are natural after training, but a major distribution change may warrant retraining and rebuilding the quantizer.
- **Two ways to shrink memory, each with a bill.** Product quantization (PQ) compresses vectors into short codes by splitting them into subspaces and storing codebook assignments; IVF-PQ combines coarse cluster pruning with compressed approximate distance, so very large collections become feasible — but quantization loses accuracy and requires training, and you rerank a shortlist with the original vectors to recover quality. **Disk-oriented graph indexes** instead keep more state on SSD and cache critical regions in memory, trading some latency for a smaller RAM footprint with careful I/O, cache and tail-latency planning.
- **Flat exact search computes distance to every eligible vector.** Linear in collection size, yet optimized matrix operations make it excellent for small collections, large batches or GPU workloads, with no index-build complexity. Keep it in evaluation *even after adopting ANN*: it is the exact recall reference that separates a regression caused by embeddings and relevance from one caused by approximate candidate-generation recall loss.
- **Updates are either immutable generations or online mutations.** Rebuild-and-swap gives predictable quality and rollback; online insertion gives freshness. Many systems run a large stable base index beside a small mutable delta and search both until compaction. That hybrid needs score compatibility and deduplication — the same source item can sit in both after an update, so select the newest version before returning — and the delta must be watched, because a structure designed for freshness becomes a second full index and degrades latency if rebuilds stall.
- **Benchmark with real dimensions, filters, concurrency, update rate and hardware,** and report a *curve*, not one default: recall against exact top k, p50 and tail latency, memory, disk, build time, insertion lag, deletion visibility, cost. Capacity tests must include failure and recovery — replica rebuild, index loading, cache warmup, node loss, compaction while serving. An index that meets steady-state latency but takes **twelve hours to restore** may violate availability goals.
- **Keeping the vector store in sync starts by naming the source of truth.** That is the authoritative corpus or feature catalog, not the ANN index; the vector store is a derived serving projection that can be rebuilt. Every record therefore needs stable source identity, source version, chunk version, embedding version, metadata version and lifecycle state. Without those fields, current and stale look identical and reconciliation has nothing to compare.
- **The change classes are not interchangeable.** A content update creates a new document and chunk generation plus new embeddings. A metadata-only change updates payload fields *without* re-embedding. A delete must remove or make descendants ineligible **across every index generation and cache**, not just the live one. Inserts and permission revocations complete the set, and most sync answers turn on which class you are in.
- **Drive synchronization from a change stream or manifest diff, and make the consumer idempotent.** Each event carries source key, new version, operation and ordering position; the consumer upserts deterministically and stores the last applied version per key, so redelivery is harmless and stale versions are rejected — the chunk-and-embed job's idempotency contract, moved into a streaming consumer.
- **Dual-write from the application to both stores is unsafe without a shared transaction.** One write succeeds while the other fails, and nothing detects it. Commit to the source first, then project asynchronously through an outbox, CDC stream or durable job. Serving then exposes a freshness *lag*, which reconciliation can repair; silent divergence cannot be repaired, because you never learn it happened.
- **Permissions need a stricter service level than embedding freshness.** A new article may tolerate minutes before it is searchable; a revoked permission may need immediate denial. A trusted authorization check *after* retrieval can fail closed while index metadata catches up. Track freshness and revocation as separate objectives.
- **Reconciliation diffs IDs, not counts.** Compare expected artifacts from the source manifest against actual index records to detect missing vectors, orphans, stale source versions, wrong model versions, dimension mismatches, deleted-but-searchable records and metadata divergence. **Counts alone cannot find one missing item paired with one orphan** — the totals agree and both records are wrong. Use a periodic full ID diff plus continuous samples and targeted scans over recent changes and failed partitions, and store discrepancies as tracked repair tasks.
- **Index generation manifests make completeness explicit.** A generation declares corpus snapshot, embedding model, expected record count and IDs, filtering schema, index parameters, build artifact and validation, and only a *ready* generation receives the read alias; later updates replay through a recorded sequence. Recovery is then idempotent — repeat the same ID and version after a timeout, read the authoritative alias state when a swap is ambiguous, rebuild rather than patch when corruption is broad.
- **Exact search is cheaper than most teams assume.** One hundred thousand vectors of dimension 384 contain 38.4 million scalar values; in 32-bit floats that is about **154 MB** before metadata — $N \times d \times 4$ bytes. A single process or an existing analytical engine may scan that efficiently, especially for batch queries or modest request rates.
- **Four situations where you do not need a vector database at all.** *Existing storage*: if the product already needs relational filters, transactions and joins, vectors beside authoritative rows simplify consistency — measure that database's vector performance under real selectivity. *Offline similarity joins*: daily training-data deduplication needs no highly available service; a file-backed library builds a local index inside the job and discards it. *Lexical retrieval*: exact error codes, names, legal phrases and identifiers want an inverted index. *Precomputed recommendations*: with a bounded query set — related items per catalog product — compute neighbours offline into a key-value table.

**Rules to remember**

- Choose an index by operational profile, never by a single benchmark recall number.
- Recall is a curve. Publish `efSearch` and `nprobe` as curves, not defaults.
- The ANN index is never the source of truth. It is a derived projection, rebuildable from a manifest.
- Never dual-write to source and vector store. Commit to the source, then project.
- Idempotent upserts keyed by source key plus version: redelivery harmless, stale versions rejected.
- Revocation gets its own objective and fails closed at query time. Freshness lag is not an answer for permissions.
- Reconciliation compares IDs, because counts hide a missing item paired with an orphan.
- Only a validated, complete generation receives the read alias.
- Estimate the exact baseline first: $N \times d \times 4$ bytes. If it meets the objective with headroom, approximation is unnecessary — and keep flat exact search in evaluation permanently as the recall reference.

**Common pitfalls**

- **Adopting a vector database merely because embeddings exist.** Embeddings feed clustering, classification, reranking, anomaly detection and offline analysis with no online ANN in sight. Start from the user interaction and the service level.
- **Comparing indexes on recall while ignoring lifecycle cost.** Tombstoned deletes, memory per edge, pre-filter behaviour and a twelve-hour restore are invisible on a recall chart and decide the outcome.
- **Benchmarking without filters, concurrency, updates or real dimensions.** Single-threaded steady-state numbers do not predict production, and one default hides the curve.
- **Re-embedding on a metadata-only change, or not re-embedding on a content change.** One wastes money; the other serves stale meaning with a fresh-looking payload.
- **Deleting from the live index only.** Descendants stay searchable in another generation or a cache — a correctness *and* a permissions failure.
- **Trusting reconciliation counts, or trusting index metadata for authorization.** The first nets a missing item against an orphan to zero; the second serves revoked content until sync catches up.
- **Costing only the per-query benchmark price.** Always-on replicas, full rebuilds, re-embedding, backups, synchronization and on-call labour dominate the real total — and so does exit cost, which you pay by keeping vectors, metadata, stable IDs, model versions and evaluation sets in an open format behind a narrow retrieval interface.

**How to approach the questions**

1. When a scenario names an index, ask which *operational* dimension is under test — memory, deletion, filtering, recovery — not which index has the better recall.
2. If a question moves a parameter, state both directions: raising `nprobe` or `efSearch` improves recall *and* increases work. Answers that move only one way are distractors.
3. For any sync question, identify the source of truth and the direction of the write first. If the application writes to both stores, that is the planted flaw.
4. Name the change class — insert, content update, metadata-only, revocation, delete — before answering. Most sync answers turn on which one it is.
5. For "did we detect it?" questions, ask what reconciliation compared. If the answer is counts, it cannot detect the described failure.
6. For adoption questions, compute the exact baseline first, then compare against the simplest credible alternative over expected growth rather than today's demo.
7. Distrust absolutes. "HNSW is faster" is false on memory and deletion; "embeddings require a vector database" is false whenever the collection is small, the query set is bounded, or the work is offline.
