1. From Pipeline To Product

Chunk-and-Embed as an Idempotent Batch Job, Storing Vectors Beside Metadata and Pre-Filter vs Post-Filter in ANN Search built the thing that produces vectors. A vector database is what serves them. Tap a stage, then flip who owns the truth. Like a printed catalogue: useful, reprintable, and never the shop's actual stock ledger.

A vector database is an operational system for indexing vectors, applying metadata constraints, updating state, and serving similarity queries under latency and availability goals. That is a product category, not a data structure — which is why the rest of this lesson is about operational profile, synchronization and cost rather than about distance functions.

2. Probing IVF Lists

An inverted-file index trains centroids, assigns every vector to a coarse cluster, and at query time searches only a few of them. Drag nprobe — then let the distribution drift and watch the same knob stop meaning what it meant. Like searching a warehouse by aisle: fine until someone crams half the stock into three aisles.

Report this as a curve, not a default. The same discipline applies to HNSW's efSearch, which controls how many candidates the graph traversal explores: larger values usually improve recall and cost latency. A single tuned number in a benchmark table hides the only thing a reviewer needs — the shape of the trade.

3. Five Index Profiles

Two indexes with similar benchmark recall can have very different operational profiles. Turn on the constraints your workload actually has and read the verdict column — the words, not the colours. Like hiring for a job: the CV headline is recall, and everything that decides the outcome is further down the page.

Capacity tests must include failure and recovery: replica rebuild time, index loading, cache warmup, node loss, compaction while serving traffic. An index that meets steady-state latency but takes twelve hours to restore may violate availability goals — and none of the five rows above differs on that in a way any recall benchmark would show you.

4. Sync Without Dual Writes

Keeping the vector store in sync with the source of truth is the genuinely hard problem in this product category. Pick a change, pick a transport, then try to break it. Like posting a letter versus telling two people something and hoping they both remember it the same way.

Reconciliation is what closes the loop: diff the source manifest against actual index records for missing vectors, orphans, stale source versions, wrong model versions, dimension mismatches, deleted-but-searchable records and metadata divergence. Counts alone cannot find one missing item paired with one orphan — the totals agree and both records are wrong. Store every discrepancy as a repair task with source evidence, never as an untracked ad hoc update.

5. Exact Search First

A vector database adds infrastructure, indexing delay, memory or disk cost, backup, security and synchronization work. Size the exact baseline before you buy any of it — then tick what your product actually needs. Like pricing a van before you have checked whether the thing fits in the car.

Build a total-cost model: compute, index replicas, storage, network, backups, re-embedding, synchronization, on-call labour and vendor limits. A low per-query benchmark price hides always-on replicas and frequent full rebuilds. And preserve the exit: vectors and metadata in an open format, stable IDs, model versions and exact evaluation sets, with product-specific APIs behind a narrow retrieval interface. A system you can credibly leave is a system you can negotiate with.
