Every AI system you build sits on top of a storage decision someone made, and the wrong one becomes the permanent tax on every feature after it: a retriever that re-embeds documents because the store cannot express incremental change, a feature pipeline that times out because an analytical query is hammering a transactional database. The Professional Data Engineer exam tests exactly one skill here, repeated in a dozen costumes: read a workload description and map it onto the one GCP service whose design center matches it. This lesson builds that mapping as an explicit decision matrix, then walks the relational family, the NoSQL family, object storage, and the services that move data between all of them.

## The Workload-Driven Storage Decision Matrix

The mechanism is a decision procedure, not a memorized list. Every storage question decomposes into five workload axes, and each GCP product is an engineered point in that five-dimensional space:

1. **Structure** — relational rows with joins and constraints, semi-structured documents/key-value, wide sparse tables, or unstructured blobs (images, PDFs, model checkpoints).
2. **Access pattern** — OLTP (many small point reads/writes by key, transactional) versus OLAP (few large scans and aggregations over billions of rows) versus object access (write once, read whole).
3. **Scale and growth** — gigabytes that fit one machine, or petabytes that must shard horizontally.
4. **Latency** — sub-millisecond (cache), single-digit millisecond (serving), seconds-to-minutes (analytics).
5. **Consistency and distribution** — is a single region fine, or do you need strongly consistent writes across continents?

Applying the axes yields the canonical matrix: relational + OLTP + fits-a-region → **Cloud SQL** (or **AlloyDB** when Postgres needs more); relational + OLTP + global/horizontal scale → **Spanner**; documents with mobile/web sync and per-entity access → **Firestore**; wide-column, huge write throughput, low-latency key lookups → **Bigtable**; sub-millisecond ephemeral state → **Memorystore**; unstructured objects → **Cloud Storage (GCS)**; OLAP over structured data → **BigQuery** (the entire next two lessons).

Worked micro-example. "An IoT fleet writes 500,000 sensor readings per second; dashboards need the latest reading per device in under 10 ms; analysts run daily aggregates." Decompose: semi-structured, keyed by device+timestamp (axis 1), massive sequential writes plus point reads (axis 2), petabyte growth (axis 3), single-digit ms (axis 4). That is Bigtable's design center for serving, with an export or Datastream-style feed into BigQuery for the analysts. Neither service alone satisfies both halves — the matrix frequently outputs *two* services connected by a pipeline, and the exam rewards noticing that.

The why: violating the matrix does not fail loudly; it degrades. Analytics on Cloud SQL saturates the primary and starves OLTP traffic. Point lookups on BigQuery cost a full column scan and hundreds of milliseconds. Blobs in a relational database bloat backups and replication. The judgment layer: when a workload straddles axes, experts split it (transactional store + analytical copy) rather than buying the most general product — Spanner can technically hold your 10 GB app database, but you would pay a multi-node minimum for distribution you do not need. Default to the cheapest service whose design center you are inside, and escalate only on a demonstrated axis violation.

## Relational Options: Cloud SQL vs AlloyDB vs Spanner

All three speak SQL with ACID transactions; they differ in how far they scale writes and how they achieve availability.

**Cloud SQL** is managed MySQL, PostgreSQL, or SQL Server on a single primary instance with optional read replicas and a high-availability (HA) configuration that keeps a standby in a second zone, promoted automatically on failure. Writes scale only *vertically* — a bigger machine — because there is exactly one primary. Its mechanism is the lift-and-shift value proposition: the same engine your application already targets, with Google handling patching, backups, and failover. It is the default answer for "existing application, relational schema, regional scale."

**AlloyDB** is Google's re-architected PostgreSQL: fully wire-compatible, but the storage layer is disaggregated (compute nodes write log records to an intelligent regional storage service, similar in spirit to the storage-compute separation you will see in BigQuery) and it adds an in-memory **columnar engine** that vectorizes analytical scans over hot data. The result is markedly faster transactional throughput than stock Postgres and the ability to serve moderate analytics on the operational data without a separate warehouse — the hybrid pattern (HTAP). Choose it when the workload is Postgres, demands more performance than Cloud SQL delivers, or mixes OLTP with real-time analytical reads. It still scales writes vertically within a region — it is not a horizontally sharded system.

**Spanner** is the qualitatively different one: a globally distributed relational database that shards data across nodes automatically ("splits"), replicates each shard with the Paxos consensus protocol, and uses **TrueTime** — GCP's GPS-and-atomic-clock time API that returns a bounded uncertainty interval — to timestamp transactions so that *external consistency* (strict serializability) holds even across continents: if transaction B starts after A commits, B sees A. Writes scale *horizontally* by adding nodes, and availability reaches 99.999% in multi-region configurations because failover is not an event, it is the steady state of consensus. The costs: a price floor far above Cloud SQL, and schema discipline — a sequentially increasing primary key (timestamps, auto-increment IDs) funnels all inserts to the last split and hotspots one server, so keys must be hashed, reversed, or UUIDs.

Worked example: a payments ledger must survive a regional outage with zero data loss and accept writes from the EU and US concurrently. Cloud SQL HA is zonal-failover within a region — insufficient. AlloyDB is regional — insufficient. Spanner multi-region is the only fit. Flip the scenario to "a 50 GB inventory database for one warehouse in Belgium" and Spanner is over-engineering; Cloud SQL wins on cost and familiarity. The exam's tell for Spanner is the co-occurrence of *relational + global + strong consistency*; any two alone are usually cheaper elsewhere.

## NoSQL Options: Firestore vs Bigtable vs Memorystore

These three drop relational joins to buy different superpowers, and they are not interchangeable.

**Firestore** is a serverless document database: data lives in documents (JSON-like maps) grouped into collections, every query must be served by an index (all single fields are auto-indexed; composite queries need declared composite indexes), and reads are strongly consistent. Its distinctive mechanism is the client-facing sync model — mobile/web SDKs subscribe to queries and receive real-time snapshots, with offline persistence — plus per-document ACID transactions. Pricing is per document read/write/delete, which shapes design: a query returning 10,000 documents bills 10,000 reads. You already run it behind Cloud Run; note the operational consequence you have lived with — queries that are not index-expressible (arbitrary aggregations, full scans) do not belong there. Design center: user-facing application state, hierarchical entities, thousands-to-millions of small documents, strong consistency without capacity planning.

**Bigtable** is a wide-column store: a single table of rows sorted lexicographically by row key, each row holding sparse cells under column families, each cell versioned by timestamp. There are no secondary indexes and no joins — *the row key is the query*. Scans are efficient only over contiguous key ranges, so schema design is key design: `device#1234#2026-07-25T10:00` clusters one device's readings for range scans, while a timestamp-prefixed key would hotspot the tablet currently holding "now," exactly like Spanner's sequential-key problem. Throughput scales linearly with nodes, latency stays single-digit milliseconds at petabyte scale, and replication across clusters is *eventually consistent*. Design center: time series, telemetry, personalization/feature lookups — in ML terms, the online feature store serving a model at request time.

**Memorystore** is managed in-memory Redis (or Valkey/Memcached): microsecond-to-sub-millisecond reads, data held in RAM, richer structures (sorted sets, streams) but durability only via optional snapshots/AOF — it is a cache and ephemeral-state tier, not a system of record. Sessions, leaderboards, rate counters, hot-key caching in front of any database above.

Worked example — a RAG chat product: conversation documents and per-user settings in Firestore (hierarchical, synced, strongly consistent); clickstream events and per-user embedding-feature vectors keyed `user#region` in Bigtable (billions of rows, key-addressed, ms reads); the last N turns of the active session cached in Memorystore. Judgment: Firestore's per-operation pricing punishes scan-heavy workloads that Bigtable serves cheaply; Bigtable's minimum node cost and key-design burden are wasted on a 100k-document app Firestore runs serverlessly; and anything you cannot afford to lose does not live in Memorystore.

## GCS Storage Classes and Lifecycle Management

GCS stores immutable objects in buckets under a flat namespace (slashes in names merely simulate folders), with 11 nines of durability at every class — durability is how safe bytes are; *classes trade retrieval economics against storage price*, not durability. Objects are replicated across zones (regional), or across regions (dual/multi-region) for higher availability and geo-redundant reads.

The four classes form a temperature ladder. **Standard**: no retrieval fee, no minimum duration — data read frequently. **Nearline**: cheaper per GB, retrieval fee per GB read, 30-day minimum storage duration — access about monthly. **Coldline**: cheaper still, higher retrieval fee, 90-day minimum — access about quarterly. **Archive**: cheapest per GB, highest retrieval fee, 365-day minimum, yet still *milliseconds to first byte* (unlike tape-style offerings elsewhere that take hours). The minimums are early-deletion charges: delete or transition a Coldline object after 10 days and you are billed as if it lived 90.

The arithmetic that decides class placement: Nearline saves roughly half of Standard's storage price but charges about $0.01/GB retrieved (early-2026 magnitudes; treat as illustrative). For 10 TB of embeddings snapshots, Standard ≈ $200/month. In Nearline ≈ $100/month + $100 per full re-read. Re-read monthly and you have saved nothing; re-read quarterly and you save ~$250 per quarter. The break-even is a function of read frequency — which is precisely why the class axis is "access frequency," not "importance."

**Lifecycle management** automates the ladder: JSON rules per bucket, each rule = condition (age, createdBefore, number of newer versions, class) + action (`SetStorageClass` or `Delete`). Typical policy: age 30 → Nearline, age 90 → Coldline, age 365 → Delete; with object versioning on, "keep 3 newest versions, delete older" caps the cost of accidental-overwrite protection. **Autoclass** inverts the approach: the bucket observes each object's access pattern and moves it between classes automatically, charging no retrieval fees but a small per-object management fee — the right default when access patterns are unpredictable or per-prefix rules would sprawl.

Judgment layer: lifecycle transitions are one-way economics (you can transition colder automatically, but frequent reads from Archive are ruinous), so misclassifying *hot* data cold is the expensive mistake, not the reverse. For an AI stack, GCS is also the staging substrate everything else reads: raw documents awaiting embedding, Dataflow temp files, BigQuery load/export files, model artifacts — keep those Standard, and lifecycle-manage the historical tail.

## Migration Services: Datastream, DMS, BigQuery Data Transfer, Transfer Appliance

Four movers, distinguished by what they move, whether movement is continuous, and where it lands.

**Database Migration Service (DMS)** performs *homogeneous database migrations* — MySQL→Cloud SQL for MySQL, Postgres→Cloud SQL/AlloyDB — by doing an initial dump plus continuous replication from the source, letting the destination trail the source by seconds until you schedule a cutover. Minimal-downtime lift-and-shift of the *system of record itself*. (Heterogeneous paths, such as Oracle→Postgres, additionally involve schema conversion tooling.)

**Datastream** is serverless *change data capture (CDC)*: it tails the source database's transaction log — MySQL binlog, Postgres WAL via logical replication, Oracle redo — and emits every insert/update/delete as an ordered event stream into BigQuery, GCS, or onward via Dataflow. The source keeps serving; the destination is a continuously fresh *copy for analytics*. The distinction from DMS is intent: DMS ends with the source retired; Datastream runs forever, keeping a warehouse or lake synchronized. Log-based CDC also avoids the load of repeated SELECT-based polling and captures deletes, which polling misses. Worked example: your Cloud SQL orders table feeds a nightly batch export today; replacing it with Datastream→BigQuery gives analysts minutes-fresh data with no query load on the primary.

**BigQuery Data Transfer Service (DTS)** is scheduled, managed *batch ingestion into BigQuery specifically*: SaaS sources (Google Ads, YouTube, and similar), GCS files, Amazon S3, Redshift, Teradata — configured declaratively, run on a schedule, no pipeline code. If the destination is not BigQuery, DTS is the wrong tool by definition.

**Transfer Appliance** is physical: Google ships you a ruggedized storage device, you load it (tens of TB to ~1 PB) on-premises, ship it back, and Google uploads to GCS. Its niche is bandwidth arithmetic. 1 PB over a dedicated 1 Gbps link ≈ 10^15 × 8 / 10^9 ≈ 8 × 10^6 seconds ≈ 93 days of saturated line — appliance round-trip wins by months. Complementary online tool: **Storage Transfer Service** moves data over the network into GCS from S3, Azure, HTTP endpoints, or other buckets, on schedules — right when bandwidth is adequate.

Judgment matrix: migrating the database itself → DMS. Continuously replicating operational changes into analytics → Datastream. Scheduled SaaS/warehouse batch loads into BigQuery → DTS. Petabyte-scale one-time moves against thin pipes → Transfer Appliance; network-feasible bulk object copies → Storage Transfer Service. The exam pattern is a scenario naming volume, network capacity, freshness requirement, and destination — those four facts select the service mechanically.
