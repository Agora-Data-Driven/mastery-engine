**The big idea**: **The Workload-Driven Storage Decision Matrix** sent every OLAP branch to one destination, and **Relational Options: Cloud SQL vs AlloyDB vs Spanner**, **NoSQL Options: Firestore vs Bigtable vs Memorystore**, **GCS Storage Classes and Lifecycle Management** and **Migration Services: Datastream, DMS, BigQuery Data Transfer, Transfer Appliance** all end up feeding it. That destination is BigQuery, and this lesson is the inside of the box. Three ideas do the work. It is **two independent planes joined by a network**, so storage and compute never contend. The **columnar engine plus partition and block pruning** decide how many bytes a query touches, and bytes are simultaneously the latency, the parallelism and, under one pricing model, the invoice. And the two **pricing models monetize different things** — bytes processed versus slot-time provisioned — so the same query can cost $12.50 or nothing marginal at all.

**Key concepts**

- **Storage-compute separation: two planes, not a server.** The storage plane keeps table data in Colossus, Google's distributed file system, encoded in a proprietary columnar format called Capacitor. The compute plane is Dremel, a multi-tenant pool of workers whose unit of capacity is the **slot** — roughly one virtual CPU's worth of compute with attached memory. Running a query rents you slots for its duration, workers read what they need from Colossus over Google's petabit-scale Jupiter network, and the slots return to the pool at the end. Nothing is provisioned per table. This is AlloyDB's disaggregated storage taken to its extreme, and the consequences are the behaviour: storage is cheap and passive (hold petabytes, pay no compute until someone queries), loading carries no compute charge, there are no indexes to build or vacuum, and ETL, dashboards and ad-hoc analysis hit the same tables with *separate* compute allocations, so an analyst's runaway query need not starve the nightly pipeline.
- **The columnar engine explains the read path.** Capacitor stores each column's values contiguously, with run-length and dictionary encoding squeezing repetitive values, rather than storing rows contiguously the way an OLTP engine does. `SELECT user_id, amount FROM orders` therefore reads exactly two columns' bytes and skips the other thirty, and similar values sitting side by side compress far better than interleaved rows do. This is why `SELECT *` is the cardinal sin: it forces every column off disk and, on-demand, bills for all of them.
- **Execution is a tree of stages joined by shuffle.** A query decomposes into stages, each run by many parallel workers, with intermediate results passed through a distributed in-memory shuffle tier. `GROUP BY user_id` over 10 billion rows means stage one scans and partially aggregates, the shuffle redistributes partials by key, and stage two merges — map-reduce style parallelism with slots reassigned dynamically between stages. The failure mode to know is **skew**: one user holding half the events concentrates a single worker's shuffle partition, and the query slows or spills however many slots you own. The same separation that makes BigQuery brilliant at huge scans and joins makes it structurally wrong for OLTP-style single-row updates — DML exists, but each statement is a distributed job, not an indexed write.
- **Partitioning splits a table into physically separate segments so the planner can skip them.** One criterion only: a `DATE`/`TIMESTAMP`/`DATETIME` column at hourly, daily, monthly or yearly granularity, an integer-range column, or ingestion time via the `_PARTITIONTIME` pseudo-column. A filter on that column lets the planner **prune** whole partitions before a slot reads a byte. Worked numbers: a 730 GB events table partitioned daily over two years holds about 1 GB per day, so `WHERE event_date BETWEEN '2026-07-01' AND '2026-07-07'` scans roughly 7 GB instead of 730 GB — a 99% cut in both on-demand cost and slot-time.
- **Pruning only happens if the filter resolves at planning time.** Comparing the partition column to a constant or a query parameter prunes. Wrapping it in a function of other columns, or joining it to values from another table, generally does not — the planner cannot know the range before it runs. Two operational levers ride on partitions: `require_partition_filter` rejects any query that omits the filter, protecting the budget from an accidental full scan, and **partition expiration** auto-deletes partitions older than N days — lifecycle management inside the warehouse, exactly analogous to the GCS lifecycle rules of Lesson 01. Tables cap out near 10,000 partitions, which is why partitioning by a high-cardinality column such as `user_id` is wrong by construction.
- **Clustering sorts data *within* the table or within each partition, by up to four columns.** Data lands in blocks whose min/max metadata the engine consults to skip blocks that cannot match. It handles what partitioning cannot: high-cardinality columns like `customer_id`, several columns at once, and prefix patterns — filters benefit in cluster-key order, like a phone book sorted by last name then first name, so the first key prunes well and the second alone helps far less. BigQuery re-clusters automatically and free in the background as loads and streaming inserts dirty the sort order. One billing nuance: because block pruning is decided at run time, the dry-run byte estimate for a clustered table is an **upper bound** — you may be billed less — whereas partition pruning is reflected in the estimate up front.
- **The standard design stacks them:** `PARTITION BY DATE(event_ts) CLUSTER BY customer_id, event_type`. Partition when you need guaranteed, estimable pruning, per-segment lifecycle or filter enforcement; cluster when cardinality is high or several filter columns matter; skip both under roughly 1 GB, where metadata overhead outweighs the skipping.
- **Editions are three tiers of the same engine.** **Standard** for basic ad-hoc analytics with no commitments; **Enterprise** as the production tier (materialized-view smart tuning, BigQuery ML, fine-grained security); **Enterprise Plus** adding the compliance ceiling — multi-region disaster recovery and higher assurance controls. The exam tests tier-matching at that granularity, not feature-list recall.
- **Reservations, commitments and slot autoscaling are three separate things.** A **reservation** is a named pool of slots created in an admin project and **assigned** to projects, folders or the org; queries from assigned projects draw from it instead of going on-demand. A **commitment** is optional prepayment, one or three years, for slots at a discount. **Autoscaling** makes a reservation elastic: you set a **baseline** (always allocated, always billed) and a **max**, and BigQuery adds slots in increments as queued work demands, billing autoscaled slots per second only while provisioned. Baseline 0 with max 400 is legitimate — nothing at idle, burst on arrival.
- **Reservations are how you isolate workloads from each other.** Worked example: `etl-reservation` at baseline 500 for the SLA-bound nightly pipelines, `bi-reservation` at baseline 100 / max 300 for dashboards, `adhoc-reservation` at baseline 0 / max 200 for data scientists. The scientists' runaway Monday queries exhaust their own 200 slots and queue; the ETL pipelines never notice. Idle slots are not wasted: **idle-slot sharing** lets other reservations in the same admin project borrow unused baseline or committed slots, reclaimed instantly.
- **On-demand bills bytes processed; capacity bills slot-time.** On-demand runs about $6.25 per TiB scanned (early-2026 list, first 1 TiB per month free) with a 10 MB minimum per table referenced; "processed" means the referenced columns in the partitions and blocks actually read, so the columnar engine and pruning are literally your pricing controls. Compute arrives as a transient pool, historically up to about 2,000 slots per project, with no guarantee. Capacity bills per **slot-hour** through your reservations, so a query scanning 50 TB costs nothing marginal beyond the slots it occupies.
- **Estimating on-demand cost is mechanical, and the exam loves it.** The **dry run** (`bq query --dry_run`, or the console estimate) returns bytes that would be processed without executing. Take a 2 TB table of 40 equal columns: selecting 4 columns over a daily-partitioned table filtered to 30 of 365 days processes about $2\ \text{TB} \times \frac{4}{40} \times \frac{30}{365} \approx 16.4\ \text{GB}$, which is 0.016 TiB at $6.25 ≈ **$0.10**. The same query written as `SELECT *` with no date filter reads 2 TiB → **$12.50**, a 125× ratio produced entirely by column selection and pruning.
- **Choosing the model is a break-even calculation.** At roughly $0.04–0.06 per slot-hour, 100 baseline slots is about $3,000–4,500 a month. Scanning 400 TiB a month on-demand is about $2,500 — stay on-demand. At 5 PiB a month, about $32,000 on-demand, a reservation wins decisively. Storage is the quieter half: active storage around $0.02/GB/month logical drops to long-term (about half price) automatically for any table or partition untouched by *writes* for 90 consecutive days, and a physical-bytes billing model charges on compressed size.

**Rules to remember**

- Storage and compute scale independently and never contend; slots are the unit of compute, bytes the unit of storage.
- Bytes read is the master variable: it drives latency, slot-time and, on-demand, the bill.
- `SELECT *` defeats the columnar engine. Name your columns.
- Partition pruning needs a filter resolvable at planning time — a constant or a parameter, not a function of other columns or a join.
- Partition for date-shaped, low-cardinality, lifecycle-managed segmentation; cluster for high cardinality and multi-column filters, prefix-first; ~10,000 partitions is the ceiling and four the cluster-key limit.
- Baseline slots are always billed; autoscaled slots bill per second only while provisioned.
- On-demand for spiky, low-volume, unpredictable usage; capacity for sustained, heavy or budget-capped usage.
- On-demand's risk is a runaway scan (`maximum_bytes_billed`, `require_partition_filter`, custom quotas); capacity's risk is queueing (autoscaling headroom, isolated reservations).

**Common pitfalls**

- **Believing `LIMIT 10` makes a query cheap.** The scan happens before the limit; bytes processed are unchanged.
- **Trusting a clustered table's dry-run number as the price.** It is an upper bound, decided at run time. Partition pruning is the one reflected up front.
- **Partitioning by a high-cardinality column.** `user_id` blows through the ~10,000-partition ceiling; that column belongs in `CLUSTER BY`.
- **Writing a filter the planner cannot use.** `WHERE DATE(TIMESTAMP_ADD(other_col, …)) = event_date` reads everything, silently and at full price.
- **Assuming more slots fix a skewed query.** One hot key concentrates a shuffle partition; extra slots sit idle.
- **Confusing an Edition with a reservation.** The Edition is the feature tier; the reservation is the slot pool; the commitment is the prepayment.
- **Reading baseline 0 as "no capacity".** It means no idle spend, with autoscale providing burst.
- **Forgetting that reads do not reset the 90-day long-term storage clock.** Only writes do.

**How to approach the questions**

1. Decide first whether the scenario is about **bytes** or about **slots**. That single split tells you whether the answer lives in pruning and column selection or in reservations and autoscaling.
2. For a cost estimate, do the arithmetic explicitly: fraction of columns × fraction of partitions × table size, then TiB × $6.25. Distractors are usually the un-pruned or un-projected variant of the same number.
3. For any "the query is expensive" scenario, check in order: `SELECT *`, a missing or unusable partition filter, then whether the filter column is a cluster key.
4. When you see "isolate the nightly pipeline from ad-hoc users", the answer is separate reservations with assignments, not more slots.
5. Read the usage shape for pricing questions. Spiky and small → on-demand. Sustained, heavy, or "predictable monthly bill" → capacity.
6. Match the guardrail to the model: `maximum_bytes_billed` fails a query rather than over-billing on-demand; autoscaling headroom answers queueing under capacity.
7. For attribution questions, the answer is `INFORMATION_SCHEMA.JOBS` — `total_bytes_processed` and `total_slot_ms` name the query, user or pipeline that is spending.
