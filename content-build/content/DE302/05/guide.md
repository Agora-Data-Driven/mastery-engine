**The big idea**: **Pub/Sub: Topics, Subscriptions, and Delivery Guarantees**, **Dataflow in Production: Autoscaling and Streaming Jobs** and **Datastream for Managed CDC** got data *into* the platform; **Storage-Compute Separation and the Columnar Engine**, **Partitioning and Clustering in BigQuery** and **Materialized Views and BI Engine** made it cheap to query once it was there. This lesson is the middle: repeatable transformations, dependable integration paths, and an orchestrator suited to the work. Google Cloud offers several services here and they solve **different layers**, not the same layer differently. Dataform owns SQL transformation inside BigQuery. Cloud Data Fusion owns visual, connector-rich integration. Managed Service for Apache Airflow — the service long presented under the Cloud Composer name — and Workflows own coordination. The skill being tested is selecting from workload requirements rather than treating every pipeline as the same kind of DAG.

**Key concepts**

- **Dataform is the transform stage of an ELT design, with Git wrapped around it.** Source data has already been extracted and loaded; analysts now turn it into tested, documented tables and views. A *repository* stores the workflow code, *development workspaces* give each contributor an isolated place to edit, compile and test, and Git integration supplies the review and release path expected of production software. Without that wrapper a project degenerates into unrelated query files nobody reviews and nobody can reproduce.
- **The unit of work is an *action*, and there are six shapes of it.** An action can declare a source, build a table, build a view, update an incremental table, run a custom SQL operation, or evaluate an assertion. Most definitions use **SQLX** — SQL plus a configuration block — and Dataform Core can reuse JavaScript for repeated logic.
- **`ref` does two jobs in one call, which is why the dependency graph is never out of date.** Calling `ref` on an upstream object returns a correctly qualified relation name *and* declares that this action depends on that object. Explicit dependency lists exist for the cases where a SQL reference does not naturally express the execution relationship. Because the edge is a by-product of the code you had to write anyway, it cannot drift from the SQL.
- **Compilation turns the project into an ordered graph, and the graph buys parallelism.** Take the doc's example: raw orders and customers are declared; `cleaned_orders` and `cleaned_customers` build from them; `daily_sales` references both, so both must finish first; a **revenue assertion** depends on `daily_sales` and checks that revenue is nonnegative. Add a model that depends only on `cleaned_customers` and it runs independently of the orders branch. Now compare that to a hand-maintained list — *query one, query two, query three*. The list creates **false dependencies**: the customer-only model waits behind the orders branch for no reason. With five build steps of 4, 2, 3, 5 and 1 minutes, the serial list takes 15 minutes and the graph takes 10, because two independent branches run at once. Dataform also checks for missing or circular dependencies while compiling.
- **Compilation and execution are separate phases, and triage starts by naming which one broke.** Compilation resolves project configuration, references, JavaScript and action metadata into a deterministic **compilation result**; it is **hermetic** — it cannot call arbitrary internet services, and identical inputs are intended to produce identical Standard SQL. Execution sends the selected compiled actions to BigQuery in dependency order. A missing `ref` target or a circular dependency is a compilation problem and never reaches BigQuery. An IAM denial on the target dataset, or invalid source data, is an execution problem.
- **Assertions put quality checks inside the graph, as data contracts.** Built-in checks enforce uniqueness, non-null values or accepted row conditions; custom assertions express domain-specific SQL tests. An assertion failure is a **failed data contract**, not a cosmetic warning: place the check next to the model whose promise it protects, name it usefully, and route the failure to an operational owner. The revenue-nonnegative assertion above is exactly this shape.
- **Incremental tables trade cost for correctness risk, so the predicate is the whole design.** The incremental predicate must capture every new *or changed* record belonging in the target. A late-arriving event defeats a strict "greater than the last timestamp" filter, so a **rolling lookback** is often required. A stable unique key supports merge behaviour, and partitioning or clustering reduce the BigQuery work. Keep periodic full reconciliation, because an efficient incremental job can consistently produce the wrong answer and never fail.
- **Promotion to production is configuration, never hand-editing model names.** Workspace **compilation overrides** isolate each developer's output by changing project, schema, prefix or suffix. **Release configurations** define repeatable production compilation settings and variables. **Workflow configurations** select actions and schedule the compiled result. Separate service accounts and projects give stronger environment boundaries. Reviewed code plus controlled configuration determines production output.
- **Cloud Data Fusion, at awareness level, is the visual integration option.** A pipeline is drawn as a directed flow of sources, transformations and sinks; **plugins** supply connectors and processing stages so a team assembles batch or real-time patterns without writing every adapter. It is powered by the open-source **CDAP** project, which explains the vocabulary: an *instance* holds services for design, metadata, lifecycle and coordination; **Studio** is the data-plane interface where pipelines are built and operated; **namespaces** partition applications and metadata inside an instance; a *node* is a source, transform, sink, action or related extension.
- **Design and execution split here too: the logical pipeline versus the compute profile.** The pipeline says *what* should happen; the compute profile says *where and with what resources* it runs. For supported batch execution, Cloud Data Fusion can provision an **ephemeral Managed Service for Apache Spark cluster** in the customer project, run the pipeline and delete the cluster afterwards; it can also target an existing managed Spark environment when an organisation wants tighter control. **Preview runs on a subset of data** — a green preview is not proof that production volume, permissions or malformed edge cases will work.
- **"Managed" does not mean unattended.** Network routes, private connectivity, firewall rules, source credentials, service accounts, plugin versions, schema drift and sink behaviour all still break runs. Instance services are long-running and execution environments cost money, so operators watch both pipeline outcomes and the underlying execution logs, control secrets through supported mechanisms, and test upgrades before promoting them.
- **Managed Airflow is a control plane with an ecosystem; Workflows is a sequence of service calls.** Managed Service for Apache Airflow gives managed Apache Airflow environments where workflows are Python **DAGs** of operators and tasks, with logical run dates, catchup, task instances, pools and trigger rules — plus a provider library that reaches many databases, clouds and processing systems. **Workflows** is fully managed, written in YAML or JSON, and calls Google Cloud APIs, HTTP endpoints and subworkflows while expressing conditions, loops, parallel branches, retries and error handling. There is no Airflow environment to operate, and billing is around executions and steps.
- **Composer versus Workflows is decided by operating model, not by Python versus YAML.** A nightly warehouse process with hundreds of task dependencies, dataset schedules, sensors, historical reruns and cross-DAG conventions wants Managed Airflow. A file-arrival event that calls a validation function, launches a Dataflow job, waits for completion, invokes a Dataform workflow and posts an HTTP notification — five steps that mostly wait on managed services — wants Workflows. Either service can sometimes implement the other example; **implementation possibility is weaker evidence than operational fit.**
- **Idempotency is the rule that survives whichever orchestrator you choose.** A retry can occur after a remote action succeeded but before the orchestrator recorded that success. Pass stable operation IDs, check existing state, make create-or-update behaviour explicit. Keep large data outside orchestration variables, grant the runtime identity only what it needs, bound retries for transient failures, and route permanent failures to an actionable alert.

**Rules to remember**

- Dataform is for BigQuery SQL transformations with dependency graphs, tests, documentation and version control — it is not a general extraction engine.
- `ref` both qualifies the name and declares the edge; the compiled graph, not a hand-written list, is the execution order.
- Missing or circular reference ⇒ compilation. IAM denial or bad source data ⇒ execution. Name the phase before you debug.
- Compilation is hermetic and deterministic: same inputs, same SQL, no internet calls.
- An assertion failure is a broken data contract with an owner, not a warning.
- Incremental correctness lives in the predicate: rolling lookback for late arrivals, a stable unique key for merges, periodic full reconciliation.
- Production output comes from release and workflow configurations, not from renamed models.
- Cloud Data Fusion = visual, plugin-rich integration on CDAP; the compute profile is separate from the pipeline, and preview is not production.
- Choose Managed Airflow for scheduled, dependency-rich, backfill-heavy data DAGs; choose Workflows for event-driven chains of managed API calls with no environment to run.
- Make every orchestrated step idempotent, and keep transformations in the processing service rather than in orchestration code.

**Common pitfalls**

- **Treating a serial list as a dependency graph.** It invents dependencies that the data does not have and slows every run; the graph should communicate real relationships.
- **Debugging an execution failure as if it were a compilation failure** (or the reverse). The two phases fail for entirely different reasons and the fix lives in a different place.
- **Treating an assertion failure as a warning.** Downstream consumers are then served data whose contract is known to be broken.
- **A strict "greater than last timestamp" incremental predicate.** Late-arriving events are silently dropped and the job never errors — this is the classic wrong-answer-forever bug.
- **Hand-editing model names to promote to production.** Overrides, release configurations and workflow configurations exist precisely so promotion is reviewable.
- **Believing a successful Cloud Data Fusion preview proves the pipeline.** Preview uses a subset; volume, permissions and malformed edge cases are untested.
- **Assuming "managed" removes networking, credentials, plugin versions and schema drift.** It removes cluster babysitting, not engineering responsibility.
- **Choosing the orchestrator by language, by what is already on the architecture diagram, or by proving a service *can* do it.** The decision is operating model and accepted operational burden.
- **Putting transformations inside orchestration code.** Let BigQuery and Dataform run SQL, Dataflow process distributed data, and Cloud Data Fusion run its pipeline; the orchestrator starts work, passes parameters, observes status and records outcomes.

**How to approach the questions**

1. First ask which **layer** the scenario is about — transformation, integration, or coordination. Most distractors are correct services from the wrong layer.
2. If the work is SQL that stays in BigQuery and needs dependencies, tests and version control, the answer is Dataform. If it is moving data between systems with connectors and a visual builder, it is Cloud Data Fusion. If it is starting and watching other services, it is an orchestrator.
3. For a Dataform failure, decide compilation versus execution before choosing a fix; the wording ("missing reference", "permission denied") usually gives it away.
4. For incremental questions, look for the words *late-arriving* or *updated*. They point at a lookback window or a merge key, not at a bigger cluster.
5. For orchestrator questions, count the scheduled DAGs, backfills and Airflow-specific features on one side and event-driven API calls on the other — then state the accepted burden (an environment to operate, or none).
6. Beware answers that are technically possible. Both orchestrators can implement most examples; the question is asking which one *fits*.
