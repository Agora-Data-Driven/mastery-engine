A modern lakehouse separates physical storage from several concerns that used to be bundled together: query access, metadata, governance, and distribution. Google Cloud provides distinct services for those concerns, so good architecture begins by naming which problem each component solves. This lesson covers BigLake for governed external access, Dataplex and its current catalog experience for organization and metadata, and Analytics Hub, now surfaced as BigQuery sharing, for publishing governed data products to subscribers.

## BigLake: External Tables with Native Performance

BigQuery native tables store data in BigQuery-managed storage. External tables instead expose data that remains in another system, such as Cloud Storage. BigLake tables are a governed form of external table: analysts query them with GoogleSQL while the underlying structured files remain outside BigQuery-managed storage. Supported designs include Cloud Storage and, through BigQuery Omni, supported Amazon S3 and Azure Blob Storage scenarios.

The defining security capability is access delegation. A BigLake table uses an external connection whose service account accesses the underlying object store. Consumers receive permission on the table rather than direct permission to every storage object. This decouples warehouse access from file access and reduces the risk that an analyst bypasses table controls by reading files directly. It also enables table-level governance features, including supported row-level security, column-level security, and dynamic data masking for applicable Cloud Storage tables.

The trust boundary must still be designed carefully. Administrators grant the connection identity only the object permissions it needs, protect who can use or modify the connection, and grant consumers appropriate BigQuery permissions. If a user retains broad direct Cloud Storage access, BigLake cannot prevent that user from bypassing a policy enforced only at the table layer. Governance depends on both sides of the delegation model.

External storage introduces metadata work. Before scanning records, a query may need to list files, inspect partitions, and read file metadata. A table backed by millions of objects can spend significant time discovering what exists. BigLake metadata caching stores information such as file names, partition information, and physical file metadata so BigQuery can avoid repeated listings and prune files sooner. Caching is especially useful for many files and Hive-partitioned layouts.

Metadata caching has a freshness contract. Maximum staleness expresses how old the cached metadata may be. Automatic refresh is convenient when objects arrive unpredictably, while manual refresh is useful when a pipeline knows exactly when a new partition becomes ready. With manual mode, an orchestrator can complete the write, verify the partition, call the metadata refresh procedure, and only then publish readiness. Cached queries can otherwise observe the object versions represented in the cache rather than newly replaced versions.

File design remains important even with caching. Prefer analytics-friendly columnar formats such as Parquet, use stable schemas, avoid floods of tiny files, and partition according to common selective filters. For Cloud Storage BigLake tables over Parquet, statistics gathered during metadata refresh can improve query planning. A materialized view over a supported metadata cache-enabled BigLake table can further accelerate repeated patterns. None of these features makes a poor physical layout free.

BigLake is valuable when data must remain in open object storage, when multiple engines share the same lake data, or when copying everything into managed warehouse storage would violate cost or ownership requirements. Native BigQuery tables often remain simpler for repeatedly queried, warehouse-owned data requiring the tightest performance and feature integration. A hybrid architecture can expose raw or interoperable lake data through BigLake and materialize refined, heavily used products into native tables.

Troubleshoot BigLake layer by layer. A permission error may originate from the querying principal, the connection, or the connection service account's object permissions. Missing new files may indicate a stale metadata cache rather than a failed query. Slow planning may indicate excessive file counts or disabled caching, while slow scanning may indicate weak partition pruning or unsuitable file formats. Distinguishing metadata discovery from data scanning avoids random configuration changes.

The phrase native performance should be interpreted as a goal supported by optimizations, not a guarantee that every external query equals a native table. Object-store latency, file layout, region alignment, cache freshness, and workload shape still matter. Benchmark representative queries and include freshness expectations in the design.

## Dataplex and Dataplex Catalog: Lakes, Zones, Metadata

Dataplex provides organization and governance capabilities across distributed data. Its lake and zone resources offer a logical management structure over assets without requiring every asset to move into one storage system. A lake commonly represents a domain or broad data estate. A zone groups related assets and can reflect a readiness stage, ownership boundary, or organizational subdivision.

Raw zones generally contain externally sourced data that still needs processing and may use varied formats. Curated zones hold data prepared for consumption, usually with stronger schema and layout expectations. This raw-to-curated distinction communicates a contract: raw data prioritizes faithful landing and replay, while curated data prioritizes trusted use. Additional zones may be appropriate for domain boundaries or published products, but creating many zones without distinct policies produces taxonomy rather than governance.

Assets connect physical resources, such as Cloud Storage buckets and BigQuery datasets, to the logical structure. The lake does not replace those storage systems. Instead, it supplies a place to apply common management behavior and make domain ownership visible. Location compatibility, IAM, and the lifecycle of the underlying resource still require deliberate design.

The catalog side provides a searchable inventory and contextual metadata. Product naming has evolved: Dataplex Universal Catalog is now called Knowledge Catalog in current Google Cloud documentation and console experiences. Existing Dataplex APIs, `gcloud dataplex` commands, metadata, and configurations continue to operate. Certification material or older diagrams may still say Dataplex Catalog or Dataplex Universal Catalog, so recognize these names as stages in the same product evolution rather than unrelated systems.

An entry represents a cataloged resource or concept. An entry type defines the kind of entry and its required metadata structure. Aspects hold related metadata fields attached to entries or entry links; an aspect type is their reusable template. System-discovered metadata can describe a BigQuery table's schema, while a custom aspect can record a sensitivity class, owner, data contract status, or retention tier. This structured approach is more useful than putting every fact into an unsearchable paragraph.

A business glossary gives shared meaning to terms such as active customer, net revenue, or shipment date. Categories organize the vocabulary, and terms can link to physical assets. A glossary does not automatically resolve disagreement: accountable owners must define formulas, exclusions, effective dates, and stewardship. Once governed, these links help users search by business concepts instead of guessing table names.

Catalog metadata includes technical, operational, and business context. Technical metadata covers schema, format, and location. Operational metadata can include freshness, quality outcomes, and lineage. Business metadata includes definitions, ownership, certification, and sensitivity. Strong discovery needs all three. A perfectly documented schema is still hard to trust if nobody knows whether the table refreshed or who approves a definition.

Lineage explains how data moves and changes across systems. It supports impact analysis before a schema change and root-cause investigation after a quality incident. Profiling and data quality capabilities reveal distributions and test conformance. These are complementary: lineage identifies affected consumers, profiling describes observed data, and quality rules decide whether observations meet expectations.

Treat catalog enrichment as an operating process. Automate technical metadata where possible, require owners and classifications during product onboarding, and define reviews for facts that expire. Use IAM so stewards can edit the context they own without becoming infrastructure administrators. Measure usefulness through search success, ownership coverage, freshness of descriptions, and time to identify upstream causes, not merely the number of entries.

## Analytics Hub: Publishing and Subscribing to Shared Data

Analytics Hub is now presented as BigQuery sharing in current documentation, though the API and IAM role names still use Analytics Hub terminology. It implements a publish-and-subscribe model for governed data and streaming resources across teams or organizations. The core objects are a data exchange, a listing, a shared resource, and a subscription.

A data exchange is a curated collection and access boundary for listings. A listing is the discoverable description and reference that a publisher places in the exchange. It can include documentation, contacts, sample queries, and terms that help consumers evaluate the product. For BigQuery sharing, the shared dataset remains in the publisher's project. A listing can expose supported objects such as tables, views, materialized views, routines, models, and external tables, subject to current limitations.

When a consumer subscribes to a dataset listing, BigQuery creates a linked dataset in the subscriber's project. The linked dataset provides read-only access to the shared resource without making a separate full copy for every subscriber. Queries return current shared data under the platform's consistency and replication behavior. The publisher continues to pay for its stored data, while subscribers generally pay for the queries they run according to their BigQuery pricing arrangement.

Zero-copy sharing reduces data sprawl but does not remove governance. The publisher controls who can discover or subscribe through exchange and listing IAM. Row-level and column-level controls on supported shared datasets can restrict what consumers see. Subscribers still need permissions to create and query the linked dataset. Audit and shared-dataset usage information can help publishers understand consumption.

Public and private sharing have different risk profiles. A private exchange can serve approved teams or partners. A public exchange makes listings discoverable to authenticated Google Cloud users and may support free or commercial distribution. Before publishing, classify the data, review privacy and contractual obligations, provide a support contact, and state schema and freshness commitments. A technically valid listing can still be an unsafe or unusable data product.

Sharing also supports Pub/Sub topics. Subscribing to a shared-topic listing creates a linked Pub/Sub subscription in the consumer project rather than copying the topic. This is useful for governed streaming distribution, but publishers and subscribers must understand throughput, retention, delivery behavior, and their respective charges. Do not confuse a linked dataset, which is queried, with a linked Pub/Sub subscription, which delivers messages.

Region and perimeter design require early attention. A linked dataset has a location, queries and joins have location constraints, and cross-region replication choices affect latency and cost. VPC Service Controls can require deliberate ingress and egress rules for publishers, exchanges, and subscribers. Validate the complete producer-to-consumer path in a nonproduction exchange before promising broad availability.

A durable data product includes more than access. The listing should state purpose, owner, schema, semantics, freshness, quality expectations, allowed uses, and change policy. Publishers should make compatible changes where possible and communicate breaking changes before they occur. Subscribers should avoid building critical dependencies on an undocumented field merely because it is visible.

Choose BigQuery sharing when consumers need governed, discoverable access to live shared assets without pipelines that copy a dataset per consumer. Choose scheduled exports or replication when a consumer requires independent retention, offline access, incompatible regions, or strong isolation from publisher changes. The architecture decision is about ownership and lifecycle as much as transfer efficiency.
