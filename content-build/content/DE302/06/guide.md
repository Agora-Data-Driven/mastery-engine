**The big idea**: **Storage-Compute Separation and the Columnar Engine** taught you that BigQuery's compute does not own the bytes it reads, and **GCS Storage Classes and Lifecycle Management** taught you where bytes live before anyone claims them. This lesson removes the last assumption tying those two together. A modern lakehouse separates physical storage from four concerns that used to travel with it — **query access**, **metadata**, **governance** and **distribution** — and Google Cloud ships a distinct service for each: **BigLake** for governed external access, **Dataplex** and its current catalog experience for organisation and metadata, and **Analytics Hub**, now surfaced as BigQuery sharing, for publishing governed data products. Architecture here begins by naming which problem a component solves, because most distractors in this domain are the correct service for a *different* one of the four.

**Key concepts**

- **A BigLake table is an external table with a governance layer attached.** A native table stores data in BigQuery-managed storage; an external table exposes data that stays elsewhere. A BigLake table is the governed form: analysts query it with GoogleSQL while the structured files remain outside BigQuery-managed storage. Supported designs include Cloud Storage and, through BigQuery Omni, supported Amazon S3 and Azure Blob Storage scenarios.
- **Access delegation is the defining capability, and it inverts who holds the storage permission.** The table uses an **external connection** whose service account reads the underlying objects; consumers get permission on the *table*, not on every object. Instead of handing 40 analysts an object-viewer role on the bucket, you grant one connection identity that role and give the 40 table-level access. That decoupling makes table-layer controls real — row-level security, column-level security and dynamic data masking for applicable Cloud Storage tables — because nobody can step around them by reading files directly.
- **The trust boundary has two sides, and BigLake only owns one.** Administrators grant the connection identity only the object permissions it needs, protect who may use or modify the connection, and grant consumers appropriate BigQuery permissions. If one of those 40 analysts keeps a broad direct Cloud Storage role, BigLake cannot stop them bypassing a policy enforced only at the table layer — the masking still renders and the raw file is still readable, with no error anywhere.
- **External storage makes metadata a cost, not a given.** Before scanning any record a query may have to list files, inspect partitions and read file metadata; a table backed by millions of objects spends real time discovering what exists. **BigLake metadata caching** stores file names, partition information and physical file metadata so BigQuery avoids repeated listings and prunes sooner. Picture a Hive-partitioned table over two million Parquet objects: uncached, every query re-discovers all two million before touching a byte of data.
- **The cache has a freshness contract, expressed as maximum staleness** — how old the cached metadata may be. **Automatic refresh** suits objects arriving unpredictably; **manual refresh** suits a pipeline that knows exactly when a partition is ready. In manual mode the orchestrator runs four steps in order: complete the write, verify the partition, call the metadata refresh procedure, then publish readiness. Skip the refresh and queries answer from the object versions the cache represents rather than the newly replaced ones — current-looking results, quietly stale.
- **Caching does not rescue a bad physical layout.** Prefer columnar formats such as Parquet, keep schemas stable, avoid floods of tiny files, and partition on the filters people actually use. For Cloud Storage BigLake tables over Parquet, statistics gathered during metadata refresh improve query planning, and a materialized view over a metadata cache-enabled table accelerates repeated patterns — the same machinery from earlier in this course, pointed at lake data.
- **Choose BigLake for a reason about ownership, not about speed.** It earns its place when data must remain in open object storage, when several engines share the same lake data, or when copying everything into managed warehouse storage would violate cost or ownership requirements. Native tables stay simpler for repeatedly queried, warehouse-owned data; hybrids are legitimate — raw lake data through BigLake, refined products in native tables.
- **Troubleshoot BigLake layer by layer, because three layers produce the same message.** A permission error may originate from the querying principal, from the connection, or from the connection service account's object permissions. Missing new files usually means a stale cache, not a failed query. Slow *planning* points at file counts or disabled caching; slow *scanning* points at weak pruning or unsuitable formats. Read "native performance" as a goal supported by optimizations, never a guarantee.
- **Dataplex organises distributed data without moving it: lakes, zones, assets.** A **lake** commonly represents a domain or broad data estate; a **zone** groups related assets and can reflect a readiness stage, an ownership boundary or an organisational subdivision; an **asset** connects a physical resource — a bucket, a BigQuery dataset — to that logical structure. The lake replaces no storage system; it supplies one place to apply common management behaviour and make domain ownership visible. Location compatibility, IAM and resource lifecycle stay your design problem.
- **Raw versus curated zones communicate a contract, and zones without policies are decoration.** Raw zones hold externally sourced data still needing processing, in varied formats, prioritising faithful landing and replay. Curated zones hold data prepared for consumption with stronger schema and layout expectations, prioritising trusted use. Extra zones for domain boundaries or published products can be right — but eight zones carrying three distinct policies produce taxonomy, not governance.
- **The catalog side is a searchable inventory, and its name has moved.** Dataplex Universal Catalog is now called **Knowledge Catalog** in current documentation and console experiences, while existing Dataplex APIs, `gcloud dataplex` commands, metadata and configurations continue to operate. Certification material and older diagrams may still say Dataplex Catalog — recognise these as stages of one product evolution, not unrelated systems.
- **Entries, entry types, aspects and aspect types make metadata searchable instead of prose.** An **entry** represents a cataloged resource or concept; an **entry type** defines its kind and required metadata structure; **aspects** hold related metadata fields attached to entries or entry links, and an **aspect type** is their reusable template. System-discovered metadata describes a table's schema while a custom aspect records sensitivity class, owner, contract status or retention tier. A **business glossary** gives shared meaning to terms such as *active customer* or *net revenue* — though it resolves no disagreement by itself; owners must define formulas, exclusions and effective dates.
- **Discovery needs three kinds of metadata together, and lineage, profiling and quality are three different jobs.** Technical metadata covers schema, format and location; operational covers freshness, quality outcomes and lineage; business covers definitions, ownership, certification and sensitivity. A perfectly documented schema is untrustworthy if nobody knows whether the table refreshed or who approves the definition. Lineage identifies affected consumers before a schema change and upstream causes after an incident; profiling describes the observed data; quality rules decide whether observations meet expectations.
- **Analytics Hub is publish-and-subscribe for governed data, built from four objects.** A **data exchange** is a curated collection and access boundary; a **listing** is the discoverable description a publisher places in it, carrying documentation, contacts, sample queries and terms; a **shared resource** is what it points at — tables, views, materialized views, routines, models and external tables; a **subscription** is the consumer taking it. The shared dataset stays in the publisher's project.
- **Subscribing creates a linked dataset, and that is the whole cost story.** The subscriber gets read-only access in their own project with no separate full copy per consumer. For 40 consumers: scheduled exports mean 40 copies and 40 pipelines to age out; a listing means one stored dataset and 40 linked datasets. The publisher keeps paying for stored data; subscribers generally pay for their own queries. **Sharing also supports Pub/Sub topics** — subscribing to a shared-topic listing creates a *linked Pub/Sub subscription*, which delivers messages, not a linked dataset, which is queried.
- **Zero-copy is not zero-governance, and public and private exchanges carry different risk.** Publishers control discovery and subscription through exchange and listing IAM; row-level and column-level controls on supported shared datasets restrict what consumers see; subscribers still need permissions to create and query the linked dataset. A private exchange serves approved teams or partners; a public one makes listings discoverable to authenticated Google Cloud users. Region and perimeter matter early too — a linked dataset has a location, and VPC Service Controls demand deliberate ingress and egress rules.

**Rules to remember**

- Name the concern first: query access is BigLake, metadata and organisation are Dataplex, distribution is Analytics Hub.
- BigLake delegates object access to a connection service account; consumers get table permissions, never object permissions — and a broad direct Cloud Storage role defeats the whole table layer.
- Metadata caching solves *discovery* time; partitioning and file format solve *scan* time. Maximum staleness is a contract, and manual refresh belongs inside the pipeline, before readiness is published.
- A Dataplex lake or zone is logical structure over assets; it moves nothing and replaces no storage system.
- Raw prioritises faithful landing and replay; curated prioritises trusted use. A zone without a distinct policy is taxonomy.
- Aspects and aspect types carry structured, searchable metadata; a glossary carries shared meaning, not agreement.
- Subscribing to a dataset listing creates a read-only linked dataset; to a topic listing, a linked Pub/Sub subscription.
- Publisher pays storage, subscriber generally pays query. Zero-copy removes duplication, not IAM.

**Common pitfalls**

- **Believing BigLake makes files private.** It governs the table path only. Audit direct bucket roles or the masking is theatre.
- **Treating "external table" and "BigLake table" as synonyms.** The connection and its delegation are the difference.
- **Blaming the query when new files do not appear.** Suspect the metadata cache and its staleness setting first.
- **Enabling caching and expecting scan performance.** Millions of tiny files remain millions of tiny files.
- **Building a zone hierarchy before the policies exist.** Structure without differing behaviour communicates nothing.
- **Assuming the catalog rename is a new product.** Knowledge Catalog is the same lineage as Dataplex Universal Catalog, and the APIs continue to operate.
- **Cataloguing schema only.** Without freshness, lineage and ownership, nobody can decide whether to trust the table.
- **Publishing a listing with no owner, semantics, freshness or change policy.** Technically valid, and an unusable data product.
- **Confusing a linked dataset with a linked Pub/Sub subscription**, or assuming a linked dataset copies data.

**How to approach the questions**

1. Sort the scenario into query access, metadata, governance or distribution before reading the options. That step alone eliminates most distractors.
2. If the requirement is "data stays in Cloud Storage but analysts must not read files directly", the answer is BigLake with a connection — then check for the analyst who still holds a bucket role.
3. If a query "does not see" data that was written, look for staleness, refresh mode and whether the pipeline called the refresh procedure.
4. Separate slow planning from slow scanning: file counts and caching versus partitioning, formats and pruning.
5. For Dataplex wording, decide whether the scenario needs *structure* (lake, zone, asset), *description* (entry, aspect, glossary) or *evidence* (lineage, profiling, quality).
6. For sharing questions, ask who pays, what gets created in the subscriber's project, and whether the resource is a dataset or a topic. If the consumer needs independent retention, offline access, an incompatible region or isolation from publisher changes, scheduled exports beat sharing.
