**The big idea**: **Dataplex and Dataplex Catalog: Lakes, Zones, Metadata** described the data, **Analytics Hub: Publishing and Subscribing to Shared Data** handed it to someone else, **BigLake: External Tables with Native Performance** put one access layer over storage whose format you do not own, and **Dataflow in Production: Autoscaling and Streaming Jobs** filled all of it. Every one assumed an answer to a question none of them asked: who may act, under which key the bytes sit encrypted, which fields are visible to whom, where the resources live, and inside which administrative boundary. Security and governance are **architectural properties, not a checklist added after a pipeline works**. Five mechanisms do the work and the exam tests whether you keep them apart: IAM decides whether a principal is authorized to *request* an action; Organization Policy can still reject the resulting *configuration*; Cloud KMS controls the *key*; Sensitive Data Protection controls the *values*; and the project-and-dataset hierarchy decides how few times you have to say any of it.

**Key concepts**

- **IAM evaluates what a principal may do on a resource, and the attachment point is half the answer.** A *role* is a named collection of permissions; an *allow policy* binds a principal to a role at a resource — organization, folder, project, dataset, bucket, or a service account. Because grants inherit to descendants, one role means wildly different things at different levels: BigQuery Data Viewer bound at the `prod` folder reaches every dataset in every project beneath it, including the raw one holding PII; bound at the `curated` dataset it reaches that dataset's tables alone. "Read access to one table" becomes read access to the estate if you attach it too high.
- **Basic, predefined, custom — in that order of badness as a default.** Basic roles such as Owner and Editor are broad and poor defaults for production; predefined roles supply service-specific permission sets; custom roles fill a genuine gap. Least privilege is a procedure: identify the exact operations, pick the narrowest role, attach it at the smallest practical scope — then **validate with real workflow tests**, because a role sufficient by name may omit a required permission.
- **Service accounts have two faces, and confusing them is the classic hole.** A service account is a non-human identity for a workload, *and* a resource other principals can use or administer. Granting the service account Storage Object Viewer lets the workload read objects; granting a *user* Service Account User or Token Creator **on that identity** lets them attach or impersonate it — an access path to every resource that identity can reach, so one "small" grant can outrank every direct grant in the project. Prefer one service account per workload or trust boundary — a Dataflow job reading one bucket and writing one dataset should not share an organization-wide identity with an unrelated deployment system — and avoid downloadable keys where workload identity or short-lived impersonation exists.
- **Organization Policy is a different question from IAM, and it answers second.** Constraints restrict resource *configuration* — resource locations, domain membership, external IP use, key creation — and inherit through the hierarchy, stopping a project administrator from building what the organization prohibited. IAM answers "is this principal authorized to request this?"; Organization Policy can still reject an authorized action because the configuration violates a guardrail. Deny policies add explicit denials and IAM Conditions make grants depend on attributes such as time or resource name — but a condition nobody can explain may be less safe than a narrower binding. Keep policy as code and **test negative cases**, not just successful access.
- **Default encryption is real encryption; CMEK is about control.** Google Cloud encrypts customer data at rest by default with Google-owned and Google-managed keys, no configuration required. Customer-managed encryption keys (CMEK) are Cloud KMS keys used by compatible services for **envelope encryption**: the service encrypts data with a data encryption key, then wraps that key with your key-encryption key. You then control the key's location, protection level, IAM, rotation schedule, disabling and destruction. Choose CMEK for a customer-specific cryptographic boundary, key-usage auditability, separation of duties or a central disable switch — and record the requirement, because it adds an operational dependency.
- **The key hierarchy is where CMEK questions actually live.** A **key ring** is a regional container, a **crypto key** expresses purpose and policy, and **key versions** hold the material. Rotation creates a new primary version for *new* encryption while old versions remain necessary to decrypt earlier data: rotate monthly for a year and those twelve months are each readable only through the version primary when they were written. Destroy a still-required version and that data is gone — crypto-shredding is powerful precisely because recovery may be impossible. Operationally: a dedicated key project when separation of duties justifies it, the service's encryption identity granted only encrypt and decrypt, key location compatible with the protected resources. Autokey, Cloud HSM and Cloud EKM each add cost and failure modes, so **the best key architecture is the least complex one that meets the real control objectives**.
- **Cloud DLP — now documented under Sensitive Data Protection — is detection first.** It inspects text and supported repositories using detectors called **infoTypes**: email addresses, phone numbers, credentials, government identifiers, or organization-specific values. An inspection configuration names infoTypes, likelihood thresholds, limits and optional custom detectors. Context affects precision — a digit pattern may resemble an identifier without being one — so tune on representative data with custom dictionaries or regex and review both error directions. And **findings are themselves sensitive** (location, type, likelihood, sometimes context): restrict access and choose output destinations deliberately. Discovery locates risk; it neither remediates it nor proves every sensitive value was found.
- **De-identification is a menu, and the analytical purpose picks the item.** Redaction removes values; replacement substitutes a label; masking hides some or all characters; bucketing reduces precision; date shifting changes dates while retaining useful relationships; tokenization substitutes controlled values. Masking a number to its **last four characters** may suit customer service and remain unsuitable for public release. Reversible tokenization permits controlled re-identification and so demands key management; deterministic transforms preserve equality for joins, yet repeated tokens reveal frequency patterns. Judge risk across the resulting dataset, and run a loop — discover, classify, transform or restrict, verify, monitor — because schema drift reintroduces PII.
- **Residency is a location fact; sovereignty is a legal and operational regime.** Residency specifies where data is stored or processed within a defined geographic boundary; sovereignty asks which laws, authorities, operational controls and organizational obligations govern it. Picking a region is necessary and nowhere near sufficient. Start from a data classification and a documented location requirement, then choose supported locations for storage, processing, logs, backups, metadata and keys, colocating services to limit accidental cross-boundary movement. Multi-region labels are defined geographic scopes and must be checked against the exact policy, never assumed compliant.
- **Trace the complete data path, or the claim is not provable.** Ingestion may originate outside the boundary, a pipeline may stage temporary files elsewhere, an orchestrator may call an external API, a disaster-recovery copy may cross regions; monitoring exports and human access count too. A residency diagram covers primary data, derived data, caches, backups, logs, metadata, keys and administrative access. Location constraints prevent *creation* of unsupported resources — they do not move existing data or validate external destinations — so VPC Service Controls, IAM, network design and audit evidence carry the rest.
- **Project and dataset architecture stops all of this from being a thousand ad hoc grants.** The hierarchy is organization, folders, projects, service resources. Projects bound APIs, quotas, billing association, many IAM grants and lifecycle; folders group projects so policy inherits by environment or control regime. Separate production from development to shrink blast radius, and centralise shared networking, security logging and key management. There is no universal project count — derive boundaries from trust, lifecycle, quota, cost attribution and ownership.
- **BigQuery datasets are the finer boundary, and usually the right one.** A dataset bounds location, access, table defaults and ownership. Separate raw, curated and published datasets when consumers and controls differ: raw grants read only to the pipeline identity while analysts get de-identified curated outputs. Authorized views, row policies, column policy tags and sharing refine access without one table per project. Use groups for humans and service accounts for workloads, and remember **labels are not security boundaries**. A sound governance architecture answers five questions fast: who owns the data, which identity writes it, who reads it, which policies and keys protect it, and how it is retired.

**Rules to remember**

- The attachment point matters as much as the role; inherited grants are the usual accident.
- IAM authorizes the request; Organization Policy can still reject the configuration.
- Impersonation (Service Account User / Token Creator) reaches everything that identity can reach; use one service account per trust boundary and prefer short-lived credentials over downloadable keys.
- Default encryption is not "unencrypted": CMEK buys control, auditability and a disable switch, at the price of an operational dependency.
- Rotation creates a new primary version; older versions stay required to decrypt older data, and destroying one is irreversible.
- Findings from a PII scan are sensitive data themselves, and the transform follows the analytical purpose.
- Residency is a location; sovereignty is the legal and operational regime around it.
- A dataset-level grant beats a project-level role granted to solve one dataset's need.

**Common pitfalls**

- **Treating a service account only as an identity.** The grants *on* it are often the widest permission in the project.
- **Assuming IAM approval means the action succeeds.** A location or key constraint rejects authorized requests all day.
- **Choosing CMEK with no stated requirement**, then destroying a key version "no longer in use". Old versions decrypt old data; this is how a dataset becomes permanently unreadable.
- **Trusting built-in infoTypes untuned.** A digit pattern resembling an identifier is a false positive; a domain value with no detector is a false negative.
- **Calling a deterministically tokenized column anonymous.** Joins still work, so frequency patterns still leak.
- **Believing region selection satisfies residency**, or that a location constraint fixes existing resources — it blocks creation going forward and moves nothing.
- **Granting a broad project role to solve one dataset problem.** Labels will not save you — they are inventory, not a boundary.

**How to approach the questions**

1. Name the mechanism first. Who may act → IAM. Configuration forbidden → Organization Policy. Keys → Cloud KMS. Field values → Sensitive Data Protection. Where it lives → residency. How little you repeat yourself → the hierarchy. Most distractors are a correct mechanism aimed at the wrong question.
2. For access scenarios, ask **which principal, which role, at which resource** — the stem usually hides the scope in a subordinate clause.
3. When a scenario mentions a workload identity, look for impersonation grants before direct grants; if an authorized user still cannot create something, suspect a constraint rather than a missing permission.
4. For CMEK scenarios, ask what the requirement is: none stated → default encryption; control, audit or a central disable switch → CMEK.
5. For masking questions, read the downstream *use*: customer service, analytical joins and public release want different transforms from the same menu.
6. For residency, enumerate the path — primary, derived, caches, backups, logs, metadata, keys, admin access — and close the gap the scenario names; for governance architecture, prefer the smallest boundary that still answers the five ownership questions.
