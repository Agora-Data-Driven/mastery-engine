**The big idea**: **The Workload-Driven Storage Decision Matrix** chose where data lives, **Pub/Sub: Topics, Subscriptions, and Delivery Guarantees** and **Dataflow in Production: Autoscaling and Streaming Jobs** moved it, **On-Demand vs Capacity Pricing: Estimating Cost** priced it, and **IAM: Roles, Service Accounts, and Organization Policies** with **Encryption and Key Management: Google-Managed vs CMEK** decided who could touch it. Those are *design* decisions. This lesson makes the opposite claim: a design is incomplete until engineers can **detect failure, explain cost, recover data, and show how every component satisfies a requirement**. Four disciplines — observability, cost and quota control, cluster ownership, recovery — then collapse into one drawing skill, because an architecture that cannot answer *"what happens when a key is disabled"* is a logo collage.

**Key concepts**

- **Observability begins with outcomes, not implementation signals.** A pipeline is healthy when the expected data arrives within its service objective, complete, correct and usable by consumers; a green virtual machine is only an implementation signal, and a job can succeed while publishing nothing. So the indicators are data-shaped: freshness lag, input and output counts, rejected records, duplicate rate, latency, backlog age, quality failures, publication time. *"Ready by 07:00"* is monitorable; *"the Dataflow job is RUNNING"* is not.
- **On GCP, monitoring, logging and audit answer different questions — and the dashboard layers them.** Cloud Monitoring collects metrics, dashboards and alerting policies; Cloud Logging centralises structured logs to search, route, retain or convert into log-based metrics; audit logs answer who changed or accessed a resource; the Dataflow monitoring view adds the job graph and system lag. Layer one reports consumer objectives (the sales table by 07:00), layer two pipeline health (run state, throughput, backlog, watermark, retries, error rate), layer three resource pressure and dependencies (worker CPU, BigQuery job failures, Pub/Sub oldest-unacked-message age, quota consumption) — the order that carries a responder from impact to cause. Structured logs then carry a stable run ID, pipeline and stage name, severity, attempt, duration and record counts — never credentials — with correlation IDs crossing orchestration and processing.
- **An alert is a request for human action, and noise destroys it.** Alert on sustained user impact or a strong precursor, never on every transient retry, and carry the resource, current value, threshold, runbook, dashboard and owner; route late data, partial degradation and outage with different urgency. A stage retrying 40 times an hour and always recovering should page nobody; that pipeline still 400,000 rows short at 06:50 against an 07:00 objective should page once.
- **Data quality monitoring belongs beside infrastructure monitoring.** Check schema, uniqueness, null rates, accepted ranges, referential integrity and reconciled totals where the contract requires them, and withhold publication when a failed rule makes output unsafe. Recorded as time series, a null rate drifting 0.2% → 1.8% → 4.1% over three weeks is visible long before it trips a threshold.
- **Quotas come in three shapes, and the failing project is often not the one you are looking at.** Rate quotas limit operations over time, allocation quotas cap provisioned resources, some limits are fixed; failure appears as HTTP 429 or a resource-exhausted error, and the quota belongs to the consumer or quota project rather than the one storing the resource. Plan them as capacity and raise limits before launch, and bound retries: 200 clients on one fixed 5-second timer reconverge into a storm that backoff with jitter would have drained.
- **Billing needs labels, budgets and detailed export — and budgets only notify.** A budget does not stop spend, so a runaway job finishes the month. Export billing to BigQuery, relate cost to a useful unit such as per published dataset, then split any change into **volume, unit price and efficiency**. A month scanning 8,000 TB at $5/TB costs $40,000; the next bill is $64,000. Volume up 60% means the design is fine; flat volume with bytes scanned per output row up 1.6× is a regressed partition filter; neither moving means cost with no workload behind it, such as an idle cluster.
- **Troubleshooting runs from symptom to dependency, and evidence is perishable.** Confirm scope and start time, inspect the orchestrator, find the first failed stage, read the service error, check recent changes — only then test hypotheses (IAM, Organization Policy, quota, region, schema, network, downstream) against evidence, preserving run IDs and logs *before* any rerun. Retry transient exhaustion with bounded backoff, never an invalid schema, denied permission or bad record: those go to a dead-letter path, which unblocks the stream and keeps the record.
- **Dataproc's persistent versus ephemeral choice is about utilization and startup latency.** Dataproc runs managed open source frameworks such as Apache Spark and Hadoop; ephemeral clusters are created for a workflow and deleted afterwards, persistent clusters stay up across many jobs. Four scheduled batch jobs a day at 40 minutes each is 2.7 busy hours against 24 paid hours — about 11% utilization, so ephemeral wins. Sixty three-minute interactive jobs invert it: at 90 seconds of creation per job, startup is half the useful work again.
- **Ephemeral is only real if the data lifecycle survives deletion.** Ephemeral clusters give workload-specific sizing, image versions, initialization, network settings and service accounts, cutting idle compute and configuration drift; selection also weighs isolation and operational ownership. But durable inputs, outputs, checkpoints, code and metadata must live in Cloud Storage, BigQuery or an external metastore — if deleting the cluster removes the only useful copy, the workflow was never disposable.
- **Persistent clusters buy warm capacity and bill you in ownership.** They suit continuously running workloads, interactive users needing low startup latency, and short-job streams where repeated creation dominates useful work; in return teams own idle cost, multi-tenancy, upgrades, patching, dependency conflicts and contention. Autoscaling cures neither a skewed Spark stage nor an unbounded driver, Spot capacity is cheaper but can disappear, and upgrades go blue-green: new cluster, route new jobs, drain, delete.
- **Replication is not a backup, and RPO is not RTO — that is where backup-DR basics start.** Replication keeps extra current copies and may hold service up through an infrastructure failure; a backup preserves a recoverable point in time against deletion, corruption or malicious change, and replicating corrupted data quickly is just faster corruption. RPO is the maximum acceptable data loss in time, RTO the target time to restore service: 15-minute snapshots against 3,000 events per minute mean an RPO of up to 45,000 events. Near-zero RPO demands synchronous replication and short RTO warm capacity with automated failover, both of which cost money, so classify workloads instead of giving everything the strictest target.
- **Failover is per-service, and a backup success event proves only that bytes were written.** Some managed regional or multi-regional services fail over automatically, others need an application, operator or orchestrator, and a regional name does not guarantee resilience to a full regional outage; afterwards, prevent split brain and reconcile records written during the event. Backups need retention, immutability, encryption, access separation, restore testing, and instructions stored outside the failed component. Corruption is a separate design from outage — point-in-time recovery, versioned objects, immutable exports — and only a restore exercise measures the real RPO and RTO, under the recovery location's residency and CMEK rules.
- **Drawing the certification-ready reference architecture is telling a requirements story.** Arrange producers → ingestion → storage → processing → serving → consumers, draw batch and streaming paths distinctly, and surround them with cross-cutting control planes for identity, keys, catalog, monitoring, orchestration and recovery, labelling projects, regions and trust boundaries that matter. Begin from workload facts — volume, velocity, formats, consumers, latency objective, retention, quality contract, security classification, residency, RPO, RTO — and let every box answer one of them.
- **Draw identities and operations, never a logo collage.** Show permissions at transitions: a source identity publishes to a topic, a Dataflow service account writes only its permitted destinations, and a CMEK arrow names *which service identity uses which KMS key* rather than parking a lock icon. Make operations visible — dead-letter destinations, quality gates, the orchestrator, deduplication at retry boundaries, backups annotated with RPO and RTO — and let every arrow mean a flow, a call, a dependency or a permission. Then ask the failure questions: a message delivered twice, a schema change, a region unavailable, a key disabled, a quota exhausted. If the drawing cannot say who is alerted, what is replayed and which data stays authoritative, revise it.

**Rules to remember**

- Monitor the data contract, not the machine: freshness, completeness, usability, publication time.
- Three dashboard layers: consumer objective, pipeline health, resource and dependency pressure.
- Quota failure ⇒ 429 or resource-exhausted; check the consumer or quota project, not just the one holding the resource.
- Budgets notify; they do not stop spend. Bound retries and add jitter, or you build a retry storm.
- Cost change = volume × unit price × efficiency. Name which one moved before proposing a fix.
- Ephemeral Dataproc suits scheduled batch, persistent suits interactive and short-job streams; durable state lives off the cluster.
- Replication ≠ backup. RPO is data loss in time, RTO is time to restore, and a backup is unproven until a restore exercise measured both.
- Every box answers a workload fact; every arrow means one thing the legend names.

**Common pitfalls**

- **Monitoring implementation signals.** "The job is running" says nothing about whether the sales table exists at 07:00.
- **Alerting on every transient retry.** The page that fires 40 times a day is the one nobody reads during the real outage.
- **Explaining a cost rise with one factor.** More input raises spend on a healthy design; a lost partition filter raises it on flat data; an idle cluster raises it with no workload.
- **Retrying a permission denial, an invalid schema or a bad record.** They fail identically forever; the fix is a corrective action plus a dead-letter path.
- **Keeping the only copy of intermediate or recovery state on ephemeral cluster disks.** Deletion becomes data loss.
- **Assuming replication protects against deletion or corruption**, or that a regional service survives a regional outage.
- **Product-logo collages.** Services added because they appeared in study material, with arrows no legend explains.

**How to approach the questions**

1. Separate an implementation signal from a consumer outcome: the right option usually measures the contract — freshness, completeness, publication time — not a machine.
2. For cost questions, decompose into volume, unit price and efficiency and find which the stem changed; flat volume with a bigger bill is an efficiency or idle-resource question. For quota errors, ask which project owns the quota and whether retries are worsening it.
3. For Dataproc, count utilization and startup overhead. "Interactive", "low startup latency" and "short jobs" point at persistent; "scheduled batch", "isolation" and "different library versions per team" at ephemeral.
4. For recovery questions, read the failure type first: outage ⇒ replication and failover; deletion or corruption ⇒ backup, point-in-time recovery, versioning, immutability. Then check whether the number given is an RPO or an RTO — swapping them is the distractor.
5. For architecture, answer with requirement + product + configuration + consequence: *a metadata cache-enabled BigLake table with access delegation, because analysts need governed SQL over Parquet that stays in Cloud Storage, accepting a freshness window.*
6. Beware answers that are merely possible: the skill tested across this course is operational fit, and a failure question exposes it.
