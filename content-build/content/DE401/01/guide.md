**The big idea**: you already own every component in this lesson. **The lake from DE 201** gave you bronze, silver, gold and snapshot publication; **the streaming machinery from DE 202** gave you event time, watermarks and log-based capture; **the feature and embedding pipelines from DE 301** gave you the projection pattern; **the inverted and vector indexes from IR 101 and IR 201**, **the ranking funnel from IR 202** and **the RAG endpoint from IR 301** gave you retrieval and serving. What is new here is the *assembly*. This lesson names every stage and its owner, decides which hops run batch and which run streaming, fixes the contracts that keep components replaceable, and settles the question that determines whether you can ever recover from a failure: where the truth lives.

**Key concepts**

- **The source-to-serving data flow has six stages, and walking one document through them IS the architecture.** Sources (the application database arriving as change events, user uploads, crawled pages, SaaS exports) → ingestion (raw events and files landing immutably in cloud storage) → the lake (bronze raw landing, silver normalized documents, gold serving artifacts, in an open table format with snapshot publication) → pipelines (parsing, deduplication, chunking, embedding — this is the feature store layer of the topic name, the place DE 301's feature and embedding pipelines produce the derived artifacts serving reads) → indexes (the inverted index and the vector index) → serving (the hybrid funnel behind a RAG endpoint that answers with citations).
- **The walk, with real numbers.** A 40-page PDF lands at 14:00 in the raw zone with an upload event. The parse job normalizes it into a silver document record: `doc_id`, `source_uri`, a monotonic version, the text, MIME type, ACL, and tenant. A chunking pass emits 12 chunks with deterministic IDs derived from document, version, span and chunker version. The embedding stage encodes all 12 with model v3. Upserts publish to the vector namespace and the inverted index, and by 14:07 the document is visible to the funnel. At 14:32 a support answer cites chunk 7, and the citation resolves back through the chunk to the silver document to the original `source_uri`.
- **Each stage carries four labels: the storage system it lives in, the transform that produces it, the team that owns it, and its freshness SLA.** This is not bureaucracy — the observability lesson measures this path, the cost lesson prices it, and the backfill lesson replays it. *You cannot monitor, price, or rebuild a stage you cannot name.*
- **Medallion discipline supplies the property everything else rests on.** Bronze and silver hold the corpus of record; gold — the chunks, embeddings and indexes — is recomputable from silver **by definition**.
- **The backbone deliberately runs at two speeds.** The batch path carries full and scheduled passes: crawls, bulk re-parses, compaction, full re-embedding, index rebuilds — high throughput, low cost per record, latencies of minutes to hours. The streaming path carries what cannot wait: change-data-capture events from the source database flowing through log-based capture, queue and streaming pipeline, plus upload events, at seconds-to-minutes freshness and a higher per-record price.
- **The per-hop decision rule is freshness requirement × volume × cost, and one worked split makes it concrete.** A support product ingests 8,000 document edits a day, 40 ACL-or-deletion events, and 300 price-sheet updates. The edits flow through a 15-minute micro-batch at essentially batch prices; most corpora show no user-visible difference. The 40 security events and the 300 price updates ride streaming, where their tiny volume makes the per-record premium irrelevant while their freshness requirement is absolute. Running everything streaming multiplies the ingestion bill for zero visible gain; running everything batch leaves a revoked document answerable for a quarter of an hour, **which is a breach window, not a latency number**. Evaluation datasets and analytics are batch, full stop.
- **Both paths write the same silver tables and the same indexes, so convergence must be deterministic.** A slow batch backfill must not overwrite a newer streaming update. Every upsert carries a monotonic version, and writers apply last-writer-wins on `(doc_id, version)` rather than on arrival order — so a replayed batch event loses to a newer streamed one, every time, regardless of who lands last.
- **Never let batch and streaming become two codebases.** The Beam model exists precisely so the same transforms run in both modes. Teams that fork the logic discover the drift during an incident, when the streaming parse and the batch parse produce different chunks from the same document and nobody can say which one the index should contain.
- **Every arrow in the diagram is a contract with four parts: schema, semantics, SLA, failure behavior.** Components stay replaceable only because the contracts stay stable, and the set is small enough to memorize: *raw event* (`source_uri`, `ingested_at`, immutable payload, content hash, append-only); *silver document* (`doc_id`, `source_uri`, monotonic version, content hash, text, MIME type, ACL, tenant, `updated_at`, upserted by `(doc_id, version)`); *chunk* (`chunk_id` as a deterministic hash of document, version, span and chunker version, plus text, offsets, ACL, tenant); *embedding* (`chunk_id`, `model_id`, vector, `embedded_at`); *index* (postings and vector rows keyed by `chunk_id`, tagged with model and index generation); *query API* (query plus tenant context plus filters in, candidates with chunk IDs and provenance out); *answer API* (question in, answer with citations and a trace ID out).
- **The semantics prevent whole bug classes.** Deterministic, version-tagged identity means reprocessing the same input yields the same IDs — that is what makes replay idempotent when a pipeline is rerun after an outage. Every artifact carries the version of the code or model that produced it (chunker version, `model_id`, index generation), so mixed populations are visible rather than silent. Every record carries tenant and ACL. Every timestamp exists twice, event time and ingestion time, so watermark logic has something to work with. And each contract names its failure behavior: output that fails validation is **quarantined, never silently dropped**, and consumers read only validated, published snapshots.
- **SLAs attach per contract:** ingestion lag, parse success rate, chunk coverage, embedding freshness, index visibility lag, query p95, answer p95. A contract without an SLA is a hope.
- **Component boundaries pay the first time something is swapped.** When this system replaced its embedding model, the only things that changed were the embedding stage and the index generation tag, because the chunk contract upstream and the index contract downstream never learned that a new model existed. The counter-example that taught the discipline: an early version let the serving API read the parser's *internal row format* directly; a parser upgrade renamed one field and broke answers in production at 02:00, with every schema still technically valid. The serving layer had coupled to an implementation, not to an interface.
- **Single source of truth, in one sentence: for each entity exactly one system holds the truth, and everything else is a derived, recomputable, disposable copy.** Here the lake's silver documents table is the source of truth for documents and their ACLs. Chunks, embeddings, inverted-index postings, vector rows and every cache are derived copies. The operational test is ruthless: **any derived store may be wiped and rebuilt from truth without information loss.** A store that cannot survive that test has secretly become a source of truth and must be given truth-grade care — backups, schema governance, change control — whether or not that was the plan.
- **Synchronization is the projection pattern plus reconciliation.** Derived stores subscribe to truth's events and versions; reconciliation jobs continuously count documents in silver against live chunks against live vectors per model generation, and alert when the counts diverge beyond a threshold. Deletes and ACL tightenings propagate to every copy within the revocation SLA — tombstones in truth, hard deletes in the copies, *verified* by reconciliation rather than assumed.
- **The failure story that justifies all of it.** A team's parser was lossy, dropping tables from PDFs, and nobody noticed for months because the index looked fine. When they fixed the parser and rebuilt, the table text was gone — it had never existed anywhere but the index. The index had quietly become the only place some content lived. If you cannot rebuild every index from the lake tonight, you have already lost the truth; you just have not needed it yet.

**Rules to remember**

- Six stages in order: sources → ingestion → lake → pipelines → indexes → serving. Name the stage before you diagnose anything.
- Four labels per stage: storage, transform, owner, freshness SLA. Four parts per contract: schema, semantics, SLA, failure behavior.
- Bronze and silver are the corpus of record. Gold — chunks, embeddings, indexes — is recomputable from silver by definition.
- Choose the path per hop by freshness × volume × cost. Security properties (revocation, deletion) are not freshness preferences and always ride streaming.
- Convergence is settled by monotonic version, on `(doc_id, version)` — never by arrival order.
- One codebase for both modes. Same transforms, two runners.
- Exactly one source of truth per entity; everything else is derived, recomputable and disposable.
- The wipe test decides what a store really is, not the architecture diagram.
- Backfills read from truth, never from another copy. Nobody hand-edits the vector database.

**Common pitfalls**

- **Diagnosing without naming the stage.** "Retrieval is bad" is not a location; "index visibility lag is 40 minutes" is.
- **Running everything on one path.** All-streaming buys freshness nobody perceives at a bill everybody notices; all-batch turns a revocation SLA into a fifteen-minute breach window.
- **Letting arrival order decide the winner.** Without `(doc_id, version)`, a replayed batch backfill silently reinstates stale text — or a deleted document's content.
- **Forking batch and streaming logic.** The drift is invisible until an incident, when the two parses disagree about the same document's chunks.
- **Coupling a consumer to a producer's internals.** Reading the parser's row format is not a contract, and no schema check will catch it.
- **Contracts with no failure behavior.** Silently dropping records that fail validation destroys the coverage numbers the observability lesson depends on; quarantine instead.
- **Hand-editing a derived store.** The edit is invisible to the next rebuild and will silently revert.
- **Backfilling from another copy.** Errors photocopy; the rebuild inherits exactly the corruption you were fixing.
- **Confusing "expensive to recompute" with "truth".** Old embedding generations are kept for cost reasons, not because they hold anything the lake does not.

**How to approach the questions**

1. Locate the stage first. Map the symptom onto sources / ingestion / lake / pipelines / indexes / serving before considering any fix; most distractors are correct actions applied at the wrong stage.
2. For a batch-versus-streaming question, do the arithmetic: volume × price against the freshness requirement. Then ask whether the requirement is a *security property*. If it is, volume decides nothing — it goes streaming.
3. When two writers race, look for the version field. Any answer that depends on which write arrived last is wrong.
4. For "what changes when we swap X", trace contracts, not code. If a downstream component must change, either the contract was wrong or someone bypassed it.
5. For any recovery question, apply the wipe test store by store. The answer is usually that one store is not as disposable as the diagram claims.
6. Prefer answers that make a gap *visible* — quarantine, reconciliation alert, generation tag — over answers that make it disappear.
