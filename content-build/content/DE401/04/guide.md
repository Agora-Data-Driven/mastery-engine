**The big idea**: **Re-embedding Cadence: When Quality Gains Justify Rebuilds** decided *whether* a rebuild is worth paying for. This lesson is *how you land one without an incident*. Every improvement to the retrieval layer — a new embedding model, a new chunker, a new quantization level — is a rebuild, and rebuilds are where backbones get hurt. Four earlier ideas are spent at once: **Single Source of Truth vs Derived Copies: Documents, Chunks, Embeddings** says which copy a rebuild may read from; **Freshness SLAs and Lag Metrics for Ingestion and Index Builds** says the snapshot-to-publish gap must be closed; **Golden Query Sets and Regression Canaries for Index Changes** supplies the go/no-go instruments; **Component Boundaries and Interface Contracts** supplies the deterministic IDs and upsert semantics that make replay safe. The playbook is four sentences long: build beside, never in place; validate against live traffic before anyone is exposed; backfill only what the change actually touches; and make rollback a rehearsed drill measured in minutes, not an improvisation measured in hours.

**Key concepts**

- **Rebuild-and-swap is the primitive, and a versioned alias is what makes it atomic.** A complete new index is built beside the serving one under a new generation tag, validated, and then an alias moves from old to new in one metadata operation. Consumers address only the alias, never a physical index, so there is no window in which half the fleet serves v3 and half v4. *Why it matters:* an in-place mutation has no "before" to return to; with an alias, rollback is the same operation reversed.
- **The build reads from the source of truth, never from the old index.** It reads the lake's silver layer, because errors photocopy — a defect in v3 re-enters v4 as ground truth. It runs the same transform code as the streaming path in bulk mode, because a forked build path is the drift trap from lesson one.
- **A rebuild has a staleness gap, and the replay closes it.** The build records its snapshot timestamp and replays every event since, before the swap. Skip it and the index publishes already behind — the staleness-at-publish the freshness lesson measures.
- **A generation is the whole tuple, not just an index.** Embedding model, chunker version, quantization config and index build are tagged together, so every metric attributes to exactly one system state. Builds are also rate-shaped like any backfill: scavenger capacity against the serving path, large enough to finish on schedule, small enough that a mid-build traffic spike never turns a rebuild into a serving incident.
- **Cutover is a procedure, not a command.** Pre-warm the new index into serving memory with the golden set and a replay of recent production queries so caches and autoscaling are hot; swap at low traffic with dashboards up; keep the old generation hot for the rollback window. *A clean run:* the v4 build finishes Tuesday 23:40, the replay catches it up to 23:55, the golden gate passes Wednesday, shadowing runs twenty-four hours, the alias moves Thursday 08:00 in thirty seconds, v3 stays hot until Friday. User-visible change: none.
- **Shadow index validation before cutover runs as four ordered gates.** Structural: per-tenant counts of documents, chunks and vectors, schema conformance, ACL fields present, all from reconciliation. Golden-set: per-class metrics paired against the old index, no class past its threshold. Shadow traffic: live queries mirrored to the new index, logged and never served. Canary soak: production canaries pointed at it for hours or days.
- **Shadow traffic catches what an offline set cannot.** Tail queries nobody imagined, cache interactions that only appear under a real query mix, latency under concurrent load, rare ACL shapes. A two percent shadow for a day surfaces more truth than a week of offline benchmarking.
- **Sizing the shadow is its own discipline.** The sample must contain the classes you fear. If the exact-ID class is three percent of traffic, a one percent shadow shows it only a few hundred times a day — too thin to trust — so the shadow is raised or stratified to oversample rare classes. Duration must cover the traffic cycle: an hour of Tuesday morning misses the batch-window load profile entirely. And results are compared continuously, not merely collected, so a degradation visible at hour three stops the soak then.
- **Top-10 overlap is the subtle instrument.** Overlap will not be one hundred percent, and should not be: improvement means different answers. A few percent of queries changing is a healthy upgrade; sixty percent means either a broken build or a change far larger than advertised — and in both cases a human reads a sample of the changed queries before the swap.
- **Sign-off is written.** Each gate has an owner, a threshold and a recorded result, so the cutover meeting is a formality when the data is green and a no-go when it is not. *Scenario:* shadowing shows 0.9 percent of queries timing out under load despite a green golden set, traced to cold caches on long-tail tenants and fixed by per-tenant pre-warming. Without the shadow, those are nine hundred failures a day discovered by users instead of by a dashboard.
- **Backfill type follows the blast radius of the change.** Full backfill when the change alters every artifact: a new embedding model changes every vector, a new chunker changes every chunk ID, a new analyzer changes every posting, a new quantization config changes every stored code. Incremental when it alters a subset: a parser bug in PDF tables reprocesses only PDFs, a new enrichment field re-runs metadata while reusing embeddings, an ACL schema change rewrites metadata under a revocation clock. The trigger table is written *before* the work starts: the type determines schedule, cost and rollback plan.
- **Replay is idempotent or it is a hazard.** Deterministic IDs, upsert semantics by ID and version, no side effects outside the target generation — so running the backfill twice is safe and a failed one resumes rather than restarts. Checkpoints record partition-level progress; completion is a verified count match from reconciliation, not a job exit code, because `finished` is a state of the data, not of the scheduler.
- **The incremental win is concrete.** A parser fix touches 180,000 PDFs in a 2.1 million document corpus — nine percent, reprocessed in three hours at a quarter of capacity with zero serving impact. The full rebuild costs a day and four times the compute for the identical outcome.
- **Rollback is a designed, rehearsed path.** The alias moves back to the previous generation, which stayed hot for this purpose; generation-keyed caches are invalidated; and a verification pass — canaries plus the golden set — runs against the rolled-back state, because it kept receiving live updates and is not byte-identical to what you left.
- **The rollback window is an economic dial.** Long enough for weekly traffic patterns to reveal a regression, short enough that a second hot generation does not eat the savings. Past it, rollback becomes a rebuild from truth — hours, not seconds — and everyone should know which world they are in before they need it.
- **Mixed-version serving has two dominant risks.** *Incomparable scores:* vectors from different models live in different spaces, so a fused or reranked list mixing them compares incommensurables. *Identity skew:* a chunker change alters chunk IDs, so a corpus mid-backfill can return both the v3 and the v4 chunk of the same passage, or neither — a user asks about the refund policy and gets two near-identical citations, crowding a genuinely different source off the answer. Dedup must key on document identity. **The safe rule:** metadata-only backfills may mix, because vectors and scores are untouched; model and chunker changes go full-generation dual-run behind one alias, and metrics collected during any mix are contaminated and flagged as such.
- **The rehearsed incident.** Thursday 10:20 the alias moves to v4; 11:05 canaries show the exact-ID class down nine percent; 11:10 the pre-agreed threshold makes the decision; 11:12 the alias is back on v3 and caches are invalidated; 11:20 verification is green. Forty-two minutes of degradation instead of a day of it, and the post-mortem adds an exact-ID shadow gate for v5.

**Rules to remember**

- Build beside, never in place. Consumers address the alias; the alias is the only thing that moves.
- Read from the source of truth. Building from the old index photocopies its defects forward.
- Record the snapshot, replay the gap, then swap. Otherwise the new index publishes stale.
- A generation is embedding model + chunker version + quantization config + index build, tagged as one.
- Four gates, in order: structural, golden set, shadow traffic, canary soak — each with an owner, a threshold and a recorded result.
- Overlap is not supposed to be one hundred percent, but every delta must be explained.
- Full backfill when every artifact changes; incremental when a subset does. Decide in writing first.
- Idempotent replay means deterministic IDs, upsert by ID and version, partition checkpoints, no side effects outside the target generation — and completion is a verified count match.
- Keep the old generation hot for the whole rollback window, and rehearse the rollback.
- Metadata-only backfills may mix versions. Model and chunker changes never do.

**Common pitfalls**

- **Building the new index from the old one.** It is faster, and it launders every defect in v3 into v4 as though it were truth.
- **Swapping without the staleness replay.** The golden set passes and the index publishes hours behind from the moment it is live.
- **A cold cutover.** No pre-warm, so the first real traffic meets cold caches and un-scaled capacity — it looks like a quality regression and is a warm-up problem.
- **Trusting a green golden set on its own.** Three hundred adjudicated queries cannot show tail latency, cache interaction or a rare ACL shape — that is the 0.9 percent timeout scenario.
- **A shadow too small or too short to see the class you fear**, or one whose results are collected rather than compared.
- **Assuming an "obviously incremental" fix is incremental.** If it touches chunk IDs, every downstream artifact changes and the plan was wrong before the first worker started.
- **Treating a job exit code as completion.** The scheduler finished; the data may not have.
- **Letting the rollback window lapse quietly.** Once the old generation is dropped, recovery goes from seconds to hours.
- **Mixing generations during a model or chunker change.** Incomparable scores, duplicate citations, contaminated metrics.

**How to approach the questions**

1. Ask what the change touches first. Every vector, chunk ID, posting or stored code means full; a subset means incremental. Most trigger questions fall to that classification.
2. Green golden set but degraded production? Look for what only live traffic reveals — load, caches, tail queries, ACL shapes. That is a shadow-sizing or pre-warm answer.
3. For "should we swap", check the gates ran *in order* and each had a pre-agreed threshold. A decision made in the meeting rather than by the threshold is itself the defect.
4. For rollback, first establish whether you are inside the window. Inside is an alias move in seconds; outside is a rebuild from truth in hours — different answers to the same symptom.
5. When two versions coexist, ask whether the vectors changed. Untouched vectors mean mixing is safe; changed vectors or chunk IDs mean a full-generation dual-run behind one alias.
6. Watch for absolutes. Overlap need not be one hundred percent, and a rolled-back index is never byte-identical to the one you left.
