Search systems are cost models made concrete: every query chooses between scanning, probing, intersecting, and moving bytes through a memory hierarchy. An asymptotically elegant algorithm can still lose when its access pattern fights the hardware, while a simple linear loop can saturate memory bandwidth and win. These distinctions govern inverted-index lookup, metadata filtering, vector search, and every top-k stage built later in the track.

## Time Complexity of Linear Scan vs Binary Search vs Hash Probe

Let $n$ be the number of searchable items. A **linear scan** examines items in sequence until it finds the target or exhausts the input. Its worst-case and unsuccessful-search cost is $n$ comparisons, so it is $O(n)$; a successful search for a uniformly distributed target averages $(n+1)/2$ comparisons, still $\Theta(n)$. Its requirements are minimal: the data need not be sorted, and the algorithm uses $O(1)$ auxiliary space.

**Binary search** requires a sorted, random-access array. Compare the target with the middle item, discard the impossible half, and repeat. After $k$ comparisons, at most $n/2^k$ candidates remain. Requiring this to be at most one gives $n/2^k \le 1$, hence $2^k \ge n$ and $k \ge \log_2 n$. The worst-case cost is therefore $\lceil\log_2 n\rceil$ comparisons, or $O(\log n)$. For one million sorted document IDs, binary search needs at most about 20 comparisons because $2^{20}=1{,}048{,}576$; a failed linear scan needs one million.

A **hash table probe** computes a hash of a key, maps it to a bucket, then checks the candidate entries in that bucket. With a well-distributed hash and a controlled load factor, the expected bucket population is constant, so lookup is expected $O(1)$. This is not a worst-case guarantee. If many keys collide, a bucket can hold $n$ entries and lookup degrades to $O(n)$. Hashing the key also costs time proportional to the key length: probing a cached 64-bit identifier is not the same physical operation as hashing a 2 MB string.

Consider 1,000,000 chunk records and a request for chunk ID `734921`. An unsorted array scan may perform 734,922 equality checks. A sorted ID array needs at most 20 binary-search steps. A hash map at load factor 0.75 normally computes one hash and inspects roughly one or a few entries. But each structure answers a different contract. A scan supports any predicate, such as `language = 'en' AND token_count < 300`, without prior indexing. Binary search supports point lookup and ordered questions such as finding the first ID at least `734921`. A hash table supports fast point lookup but destroys order: it cannot directly answer “all IDs from 700000 through 800000.”

Construction changes the judgment. If there is one lookup against unsorted data, sorting first costs $O(n\log n)$ and then searching costs $O(\log n)$, which is more total work than one $O(n)$ scan. For $q$ repeated lookups, sorting costs $O(n\log n + q\log n)$, while repeated scans cost $O(qn)$; the upfront index becomes worthwhile as $q$ grows. A hash table costs expected $O(n)$ to build and extra memory for buckets, then expected $O(1)$ per point lookup. Persistent search systems pay construction cost because one index serves many queries.

Big-O omits constants, preprocessing, memory, and access locality. For a tiny array, a branchless linear scan can beat binary search because it has no unpredictable branches and reads consecutive memory. Hash lookup can lose when hashing and pointer chasing cost more than checking a few values. Experts therefore use asymptotics to rule out designs that cannot scale, then benchmark realistic sizes and hardware. They also state expected versus worst-case guarantees precisely: calling a hash probe simply “$O(1)$” hides its collision assumptions.

## Big-O of Intersecting Two Sorted Lists

An inverted index represents each term by a sorted postings list of document IDs. An AND query such as `vector AND database` must find IDs present in both lists. If lists $A$ and $B$ have lengths $m$ and $n$, the canonical algorithm uses two cursors:

1. If $A[i]=B[j]$, emit the ID and advance both.
2. If $A[i]<B[j]$, advance $i$.
3. Otherwise advance $j$.
4. Stop when either list ends.

Every step advances at least one cursor, and neither cursor moves backward. Cursor $i$ advances at most $m$ times and $j$ at most $n$ times, so the total work is $O(m+n)$ and auxiliary space is $O(1)$ besides the output. This is a proof by accounting, not an intuition: charge each loop iteration to a cursor advance; there are at most $m+n$ charges.

Worked example: $A=[2,4,8,16,32]$ and $B=[1,2,8,9,32,40]$. Compare 2 with 1 and advance $B$; match 2; compare 4 with 8 and advance $A$; match 8; compare 16 with 9 and advance $B$; compare 16 with 32 and advance $A$; match 32 after advancing through the remaining comparison. The output is $[2,8,32]$. No document ID is revisited.

An alternative is to iterate the shorter list and binary-search every item in the longer list, costing $O(\min(m,n)\log\max(m,n))$. Which bound is better depends on skew. For $m=n=1{,}000{,}000$, the merge costs about 2,000,000 cursor advances, while repeated binary search performs about 20,000,000 comparisons and jumps around memory. For $m=10$ and $n=10{,}000{,}000$, merge can traverse nearly ten million entries, while ten binary searches take about $10\log_2 10{,}000{,}000 \approx 233$ comparisons. The skewed case favors probing the long list.

For more than two terms, query order matters. Intersect the rarest postings first because an intersection cannot be larger than its smallest input. Suppose postings lengths are 20, 50,000, and 2,000,000. Intersecting the two long lists first can scan roughly 2,050,000 entries and produce a large intermediate result. Starting with the 20-entry list yields at most 20 candidates; subsequent membership checks or intersections operate on that tiny set. This is the algorithmic reason document frequency is a query-planning statistic.

The $O(m+n)$ merge bound is an upper bound, not a demand to decode both lists fully. If one cursor is far behind, **galloping** or exponential search can jump forward and then binary-search the bracketed range. Skip data can support similar jumps. Those optimizations matter for highly unequal or clustered lists, but they do not change the fundamental requirements: sorted order enables monotone progress, and the best strategy depends on list lengths and value distribution.

Intersection cost is also not output cost. If both lists contain the same ten million IDs, producing or scoring ten million matches costs at least $\Omega(10{,}000{,}000)$ because every result must be handled. No skipping technique can avoid work proportional to a required output. Experts separate input traversal, output materialization, and downstream scoring rather than quoting one bound for the whole query.

## Memory Hierarchy: Why Sequential Access Beats Random Access

The processor does not read “memory” at one uniform speed. Registers are closest, then small CPU caches, then larger caches, main RAM, local SSD, and remote or object storage. Capacity increases down the hierarchy while latency rises dramatically. Hardware moves data in blocks: a cache miss fetches an entire cache line, commonly 64 bytes, and storage reads pages or larger extents. Performance therefore depends not only on how many values an algorithm touches, but on whether nearby touches reuse the block already fetched.

A **sequential scan** has spatial locality. Reading one array element makes neighboring elements arrive in the same cache line, and hardware prefetchers recognize the pattern and fetch future lines before they are requested. The CPU can pipeline comparisons and vectorize work across several values. A **random access** to unrelated addresses defeats these mechanisms: each lookup may wait for a new cache line, translation, page, or storage request, while most bytes in the fetched block go unused.

Worked example: scan 100 million 32-bit document IDs, 400 MB total. At 20 GB/s effective memory bandwidth, the byte-transfer floor is $0.4/20=0.02$ seconds, before comparison overhead. Now perform 100 million random probes whose working set does not fit cache. Even assuming only 80 ns per RAM miss, serialized latency totals $100{,}000{,}000 \times 80$ ns $=8$ seconds. Real processors overlap some misses, but the roughly 400-fold gap explains why a linear scan can beat an algorithm with fewer, scattered accesses.

This changes the interpretation of the earlier algorithms. Binary search uses only $O(\log n)$ comparisons, but its middle-of-subrange jumps touch distant cache lines; for small arrays a sequential scan can win. A hash table offers expected constant probes, yet buckets and collision chains may require pointer chasing. The two-cursor postings intersection is exceptionally hardware-friendly: compact arrays are read forward once, so asymptotic $O(m+n)$ work is delivered near memory bandwidth.

Data representation controls locality. An array stores equal-sized items contiguously; one cache line carries many useful IDs. A linked list stores nodes wherever the allocator placed them, and each node contains a pointer that must be resolved before the next address is known, preventing effective prefetch. Object-heavy JavaScript records add indirection compared with typed arrays. Compression can improve speed as well as size: if gap encoding halves postings bytes and decoding is cheap, fewer cache lines and storage pages must move, so the CPU may finish sooner despite extra arithmetic.

Storage magnifies the judgment. Reading a 128 MB contiguous range from GCS or SSD amortizes request setup and reaches high throughput. Issuing thousands of tiny random reads pays latency and request overhead repeatedly. Database B-trees use wide, page-sized nodes partly to reduce the number of storage accesses, and external sorting converts random work into sequential runs. Those structures arrive later; the governing rule is already visible: arrange computation so each expensive block fetched supplies as much useful work as possible.

Sequential is not automatically best. A scan that reads 400 MB to find one key loses to a hash index whose few random pages are cached. The choice is the product of access count, access pattern, working-set size, and reuse. Experts estimate bytes moved and likely cache or storage misses alongside Big-O. For retrieval, compact sorted postings win not merely because merge intersection is linear, but because their layout turns that linear work into predictable sequential bandwidth rather than a chain of latency stalls.
