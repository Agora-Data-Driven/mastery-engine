**The big idea**: DE 401 closed on three judgment calls — **Precompute vs Compute-on-Read: The Decision Framework**, **Hot vs Cold Storage Tiering for Corpora and Indexes**, and **Latency Budget Breakdown: Retrieval, Rerank, Generation**. Each assumed you could price the alternatives. This lesson is that pricing, and it opens the Information Retrieval track. Search systems are cost models made concrete: every query chooses between scanning, probing, intersecting, and moving bytes through a memory hierarchy. An asymptotically elegant algorithm can still lose when its access pattern fights the hardware, while a simple linear loop can saturate memory bandwidth and win. Three ideas carry the whole lesson: the **time complexity of linear scan vs binary search vs hash probe**, and the different *contract* each one buys; the accounting proof that **intersecting two sorted lists** costs $O(m+n)$, which is the engine under every AND query in the rest of the track; and the roughly 400-fold gap that makes **sequential access beat random access**, which frequently decides which of the first three actually wins.

**Key concepts**

- **Linear scan is the algorithm with no requirements.** It examines items in sequence until it finds the target or exhausts the input. Worst case and unsuccessful search cost $n$ comparisons, so it is $O(n)$; a successful search for a uniformly distributed target averages $(n+1)/2$ comparisons, still $\Theta(n)$. The data need not be sorted and auxiliary space is $O(1)$. What you buy for that cost is generality: a scan supports *any* predicate, such as `language = 'en' AND token_count < 300`, with no prior indexing at all.
- **Binary search buys $O(\log n)$ by demanding sorted, random-access storage.** Compare the target with the middle item, discard the impossible half, repeat. After $k$ comparisons at most $n/2^k$ candidates remain; requiring that to be at most one gives $n/2^k \le 1$, hence $2^k \ge n$ and $k \ge \log_2 n$. Worst case is $\lceil \log_2 n \rceil$ comparisons. For one million sorted document IDs that is about 20, because $2^{20} = 1{,}048{,}576$, against one million for a failed linear scan. It also answers *ordered* questions — "the first ID at least `734921`" — which a hash table cannot.
- **A hash probe is expected $O(1)$, and that word is load-bearing.** Hash the key, map it to a bucket, check the candidate entries in that bucket. With a well-distributed hash and a controlled load factor the expected bucket population is constant. It is not a worst-case guarantee: if many keys collide, one bucket can hold $n$ entries and lookup degrades to $O(n)$. Hashing also costs time proportional to key length — probing a cached 64-bit identifier is not the same physical operation as hashing a 2 MB string. And it destroys order, so it cannot directly answer "all IDs from 700000 through 800000".
- **The concrete contrast.** Among 1,000,000 chunk records, a request for chunk ID `734921` costs an unsorted array scan up to 734,922 equality checks, a sorted array at most 20 binary-search steps, and a hash map at load factor 0.75 one hash plus one or a few entry inspections.
- **Construction cost changes the verdict, and this is precompute vs compute-on-read again.** For one lookup against unsorted data, sorting first costs $O(n\log n)$ then $O(\log n)$ — more total work than a single $O(n)$ scan. For $q$ repeated lookups, sort-then-search costs $O(n\log n + q\log n)$ while repeated scanning costs $O(qn)$, so the upfront index pays as $q$ grows. A hash table costs expected $O(n)$ to build plus bucket memory, then expected $O(1)$ per point lookup. Persistent search systems build indexes precisely because one index serves many queries.
- **Intersecting two sorted lists is the inverted index's core loop.** Each term is a sorted postings list of document IDs; `vector AND database` needs the IDs in both. With lengths $m$ and $n$, two cursors: if $A[i] = B[j]$ emit and advance both; if $A[i] < B[j]$ advance $i$; otherwise advance $j$; stop when either list ends.
- **The $O(m+n)$ bound is a proof by accounting, not an intuition.** Every iteration advances at least one cursor and no cursor moves backward, so charge each iteration to an advance: $i$ advances at most $m$ times, $j$ at most $n$, giving at most $m+n$ charges. Auxiliary space beyond the output is $O(1)$. Worked example: $A = [2,4,8,16,32]$, $B = [1,2,8,9,32,40]$ yields $[2,8,32]$, and no document ID is ever revisited.
- **The alternative is probing, and skew decides between them.** Iterate the shorter list and binary-search each item in the longer one: $O(\min(m,n)\log\max(m,n))$. For $m = n = 1{,}000{,}000$ the merge costs about 2,000,000 cursor advances while repeated binary search does about 20,000,000 comparisons and jumps around memory. For $m = 10$ and $n = 10{,}000{,}000$ the merge can traverse nearly ten million entries while ten binary searches take about $10\log_2 10{,}000{,}000 \approx 233$ comparisons. Extreme skew favours probing the long list.
- **With three or more terms, intersect the rarest first.** An intersection can never be larger than its smallest input. Given postings lengths 20, 50,000 and 2,000,000: starting with the two long lists scans roughly 2,050,000 entries and produces a large intermediate result, whereas starting with the 20-entry list leaves at most 20 candidates for everything that follows. This is the algorithmic reason document frequency is a query-planning statistic.
- **$O(m+n)$ is an upper bound, not an instruction to decode everything.** When one cursor falls far behind, **galloping** (exponential search, then a binary search of the bracketed range) or skip data can jump forward. Those help on unequal or clustered lists without changing the fundamentals: sorted order is what makes monotone progress possible.
- **Intersection cost is not output cost.** If both lists contain the same ten million IDs, producing or scoring ten million results costs at least $\Omega(10{,}000{,}000)$ — no skipping technique avoids work proportional to required output. Separate input traversal, output materialisation and downstream scoring instead of quoting one bound for the query.
- **The memory hierarchy is why the above is not the whole story.** Registers, then small CPU caches, larger caches, main RAM, local SSD, remote or object storage: capacity rises down the list and so does latency, dramatically. Hardware moves *blocks*, not values — a cache miss fetches a whole cache line, commonly 64 bytes, and storage reads pages or extents. So cost depends on whether nearby touches reuse the block already fetched.
- **This is why sequential access beats random access.** A sequential scan has spatial locality: neighbouring elements arrive in the same cache line, hardware prefetchers recognise the stride and fetch ahead, and the CPU pipelines and vectorises comparisons. Random access to unrelated addresses defeats all three — each lookup may wait on a new cache line, translation, page or storage request, and most bytes of each fetched block go unused.
- **Worked numbers for the gap.** Scanning 100 million 32-bit document IDs is 400 MB; at 20 GB/s effective bandwidth the transfer floor is $0.4/20 = 0.02$ seconds. Now do 100 million random probes over a working set that does not fit cache: even at only 80 ns per RAM miss, serialised latency is $100{,}000{,}000 \times 80\text{ ns} = 8$ seconds. Real processors overlap some misses, but a roughly 400-fold gap is why a linear scan can beat an algorithm making far fewer, scattered accesses.
- **Re-read the first three algorithms in that light.** Binary search uses only $O(\log n)$ comparisons but its middle-of-subrange jumps touch distant cache lines, so on small arrays a branchless sequential scan wins. A hash table promises expected constant probes yet buckets and collision chains mean pointer chasing. The two-cursor postings intersection is the hardware-friendly one: compact arrays read forward once, so $O(m+n)$ work is delivered near memory bandwidth.
- **Representation controls locality.** An array stores equal-sized items contiguously, so one cache line carries many useful IDs. A linked list puts nodes wherever the allocator did, and each node's pointer must be resolved before the next address is even known, which defeats prefetch. Object-heavy JavaScript records add indirection over typed arrays. Compression can therefore *increase* speed: if gap encoding halves postings bytes and decoding is cheap, fewer lines and pages move and the CPU finishes sooner.
- **Storage magnifies all of it.** Reading a 128 MB contiguous range from GCS or SSD amortises request setup and reaches high throughput; thousands of tiny random reads pay latency and per-request overhead every time. B-trees use wide, page-sized nodes to cut storage accesses, and external sorting converts random work into sequential runs — both arrive later in this course.

**Rules to remember**

- Scan is $O(n)$ with no preconditions; binary search is $O(\log n)$ but needs sorted random access; hash probe is *expected* $O(1)$, worst case $O(n)$.
- Always state the contract, not just the bound: scans take arbitrary predicates, sorted arrays take range and successor queries, hash tables take point lookups only.
- Amortise construction over $q$ queries. One lookup favours a scan; many lookups favour an index.
- Two-cursor intersection of sorted lists is $O(m+n)$ time, $O(1)$ extra space, by the advance-accounting argument.
- Binary-search probing wins on skew: $O(\min(m,n)\log\max(m,n))$ beats $m+n$ when one list is tiny.
- Intersect the rarest postings list first; an intersection is never larger than its smallest input.
- A block is the unit of transfer. Estimate bytes moved and likely misses alongside Big-O.
- Sequential access beats random access by roughly two orders of magnitude — but not always, and the exception matters as much as the rule.

**Common pitfalls**

- **Calling a hash probe "$O(1)$" full stop.** That hides the load-factor and distribution assumptions, and the $O(n)$ worst case under adversarial or clustered keys.
- **Ignoring key length.** Hashing a 2 MB string is not a constant-time operation in any useful sense, even though the table's bound says constant.
- **Sorting for a single query.** $O(n\log n)$ to save $O(n)$ is a loss. The index only pays back across queries.
- **Assuming the merge bound always beats the probing bound.** At $m = 10$, $n = 10{,}000{,}000$ it is about 233 comparisons versus ten million steps.
- **Intersecting the two largest postings lists first.** It scans millions of entries to build an intermediate result the rare term was about to destroy.
- **Quoting intersection cost as the query cost.** Ten million matches cost $\Omega(10{,}000{,}000)$ to materialise and score no matter how clever the traversal.
- **Trusting Big-O on small $n$.** Constants, branch prediction and locality dominate there; benchmark rather than assert.
- **Treating "sequential is faster" as absolute.** A 400 MB scan to find one key loses to a hash index whose few pages are already cached.

**How to approach the questions**

1. Read for the *contract* first. If the question needs a range, a successor, or an ordered walk, a hash table is wrong however fast its probe is.
2. Count queries. A single lookup and a million lookups against the same data have opposite correct answers, and the query count is usually one clause in the scenario.
3. For any intersection question, get $m$ and $n$ out of the text and compare $m+n$ against $\min(m,n)\log_2\max(m,n)$ numerically. Skew is what the question is testing.
4. Separate expected from worst case explicitly — distractors quote one when the stem asked for the other.
5. When a scenario contrasts "fewer operations" with "slower in practice", it is a locality question: estimate bytes moved and count likely cache or storage misses.
6. Watch for absolute claims. "Binary search is always faster than scanning" and "sequential always wins" are both false, and the exception is usually the point of the question.
