1. Precompute Or Scan

DE 401 asked Precompute vs Compute-on-Read and Hot vs Cold Storage Tiering as judgment calls. This lesson supplies the arithmetic underneath them. One million chunk records, one point lookup at a time — drag how many lookups the system will ever serve and watch which plan is cheapest. Like alphabetising a filing cabinet: absurd for one document, obvious by the hundredth.

The crossover is the whole point, and it is not a constant to memorise — it moves with n, with how expensive one comparison is, and with how long the index stays valid. A persistent search system sits far to the right of it, which is why it pays construction cost without arguing. A one-off analytics question over a cold export sits far to the left, and building an index for it is strictly wasted work.

2. Scan Search Or Probe

Three ways to find chunk ID 734921, and three different contracts. Drag the collection size, then break the hash table's assumption and watch its guarantee change from expected to worst case. Like finding a house: walk the street, halve the street numbers, or already know which door.

One more thing the bounds hide: hashing costs time proportional to key length. Probing a cached 64-bit identifier and hashing a 2 MB string are not the same physical operation, however identically they are written as O(1). Experts quote the guarantee precisely — expected or worst case, and per what unit of key.

3. Two Cursors Stepping

An AND query over an inverted index is this loop and nothing else. Step it and watch the accounting proof happen: every iteration advances at least one cursor, no cursor ever moves backward, so the total is at most m + n. Like two people reading sorted guest lists aloud — whoever calls the smaller name reads on.

The O(m + n) bound is an upper bound, not an instruction to decode both lists. When one cursor falls far behind, galloping — exponential search forward, then a binary search of the bracketed range — or stored skip data can jump ahead. Those help on unequal or clustered lists without touching the fundamental requirement: sorted order is what makes monotone progress possible at all.

4. Skew Picks The Plan

Two bounds, and which one is smaller depends entirely on how unequal the lists are. Drag the short list against a fixed ten-million-entry long one, then reorder a three-term query and watch the intermediate result collapse. Like checking ten names against the phone book versus reading the phone book from A to Z.

This is the algorithmic reason document frequency is a query-planning statistic and not merely a scoring one: an intersection can never be larger than its smallest input, so the rarest term bounds everything downstream of it. Every query planner in the rest of the track keeps postings lengths precisely so it can make this choice before touching data.

5. Bytes Or Latency

Hardware moves blocks, not values: a cache miss fetches a whole 64-byte line. So cost is not how many values you touch but whether nearby touches reuse the block already fetched. Drag the number of lookups, then destroy the layout and watch a sequential loop stop being sequential. Like a supermarket: one trolley run down every aisle, or a separate drive home per item.

Storage magnifies every line of this. A 128 MB contiguous range from SSD or object storage amortises request setup and reaches high throughput; thousands of tiny random reads pay latency and request overhead each time. It is also why compression can make you faster, not just smaller: if gap encoding halves postings bytes and decoding is cheap, fewer lines and pages move and the CPU finishes sooner despite the extra arithmetic. The governing rule for the whole course — arrange computation so each expensive block fetched supplies as much useful work as possible.
