**The big idea**: **Time Complexity of Linear Scan vs Binary Search vs Hash Probe** gave you three costs for finding one item; **Big-O of Intersecting Two Sorted Lists** gave you the two-cursor merge at $O(m+n)$; **Memory Hierarchy: Why Sequential Access Beats Random Access** explained why that merge runs near memory bandwidth while scattered probes stall. This lesson spends all three at once. An inverted index needs two different kinds of structure — a **dictionary** that finds a term quickly, and a **postings** representation that stores an ordered, growing set of document IDs — and they are not the same problem. Choosing either by slogan fails predictably: hash tables collapse under poor load control, linked lists waste the memory hierarchy, and arrays make reads cheap by demanding disciplined writes. Four questions settle it — point lookup, ordered traversal, update frequency, physical layout.

**Key concepts**

- **A hash table is an array plus an address function.** For $M$ buckets, compute a deterministic hash $h(k)$ and reduce it to a bucket index, commonly $h(k) \bmod M$. The mechanism is that arithmetic *replaces* search: you compute where a key must live instead of looking for it. It works only if the hash spreads the *actual* key distribution approximately uniformly — otherwise the computed address is worthless and lookup is back to examining much of the $n$ stored keys.
- **Collisions are structural, not a bug.** The key space is larger than $M$, so distinct keys must share buckets. **Separate chaining** keeps a per-bucket collection: hash once, then scan that bucket. **Open addressing** stores every entry directly in the bucket array and follows a probe sequence until it finds the key or an empty slot. Linear probing checks consecutive slots — excellent locality, exactly what lesson 01 rewarded — but contiguous occupied clusters grow, and later probes walk them. Double hashing spreads probes better and jumps around memory, paying cache misses to avoid clustering.
- **Load factor $\alpha = n/M$ is the dial that decides whether "$O(1)$" is even true.** Under uniform hashing with chaining, an unsuccessful lookup examines roughly $\alpha$ entries after reaching its bucket, so expected work is $O(1+\alpha)$ — one hash plus the chain. With 750,000 terms in 1,000,000 buckets, $\alpha = 0.75$ and most chains are short. Put the same terms in 10,000 buckets and $\alpha = 75$: the identical line of code now scans dozens of entries per "hash lookup". Open addressing requires $\alpha < 1$ and degrades sharply as the table fills, because the empty slot that *terminates* a probe becomes rare.
- **Resizing keeps $\alpha$ bounded, and geometric growth makes it amortized $O(1)$.** Crossing the threshold allocates a larger bucket array and reinserts every entry under the new modulus — $O(n)$ at that instant. But with doubling, total rehash work across $n$ inserts is $1 + 2 + 4 + \cdots < 2n$, a geometric series bounded by twice the final size, so the whole build is $O(n)$ and one insert is amortized $O(1)$ even though a single one can be expensive.
- **Worked collision example.** Keys hashing to 42, 18 and 50 in an eight-bucket table all reduce to bucket 2 ($42 = 5\cdot 8 + 2$, $18 = 2\cdot 8 + 2$, $50 = 6\cdot 8 + 2$). Chaining stores three entries under bucket 2, so a *missing* key mapping there costs three comparisons before the answer is "no". Linear probing puts them in slots 2, 3, 4; a lookup starting at 2 follows that cluster until it matches or hits an empty slot.
- **Hash tables have an adversarial worst case and no order.** A flawed or attacker-controlled distribution can drive every key into one bucket: $O(n)$ lookup. Runtimes randomize string hashes to resist chosen-key collision attacks; a stable on-disk index instead needs *stable* hashing, so it must use a strong function and validate load. They also trade memory for speed — spare buckets, stored hashes, pointers and alignment can exceed the key payload. Excellent for exact term-to-postings lookup; no lexicographic order, no prefixes, no ranges.
- **Linked lists as postings: sequential access and cheap append.** Each node holds a document ID and a `next` pointer; the list holds a head and usually a tail. With the tail known, append is $O(1)$ — allocate, set the old tail's `next`, update the tail — and nothing already stored moves, which is exactly what incremental ingestion wants. Term `retrieval` with postings 3 → 11 → 19 accepts document 27 by changing two pointers, whatever its length.
- **Traversal is logically sequential, and binary search is simply unavailable.** Reading the $i$th posting costs $i$ pointer hops; no arithmetic jumps to node $i$. An ordered scan is $O(n)$ worst case, though it can stop once the current ID exceeds the target. Binary search fails not on comparisons but on addressing: locating the midpoint is itself a linear walk, which destroys the $\log n$ you came for. Intersecting 3 → 11 → 19 with 2 → 3 → 19 → 25 still emits 3 and 19 by last lesson's two-cursor logic — it just runs at pointer-chasing speed, not bandwidth speed.
- **The physical weakness is last lesson's memory hierarchy, made concrete.** Nodes are allocated individually and can be scattered, and each pointer must *arrive* before the processor knows the next address, so prefetching cannot run ahead. A 64-byte cache line may deliver one useful 4-byte ID plus pointer and allocator overhead, and a node carrying a 32-bit ID and a 64-bit pointer costs about 16 bytes after alignment — four times its payload. Pointers also block vectorized decoding of a dense block of gaps.
- **Arrays vs linked lists for postings storage: address arithmetic is the whole difference.** With base $b$ and width $w$ bytes, element $i$ sits at $b + iw$, so random access is $O(1)$, binary search is $O(\log n)$, two-cursor intersection is $O(m+n)$ *streamed near memory bandwidth*, and consecutive values compress as gaps in blocks that SIMD can decode. One million 32-bit document IDs pack into about 4 MB; the linked representation at 16 bytes per node needs about 16 MB before allocator overhead, and touches scattered cache lines to read it.
- **Dynamic arrays recover cheap append by the same geometric argument.** Keep capacity above length; append writes into spare capacity; on overflow, allocate a geometrically larger block, copy, then append. One resizing append is $O(n)$, amortized $O(1)$ — the price is latency spikes and holding both buffers at once.
- **Middle insertion reverses the ranking, and the usual claim about it is false.** Inserting ID 500 into a sorted million-element array may shift roughly half a million IDs, $O(n)$. A linked list splices in $O(1)$ **only after** the predecessor is known, and finding it is $O(n)$: "linked-list insertion is constant time" silently assumes a pointer to the right place. For postings arriving in increasing document-ID order both append cheaply and the array wins every read. Deletion is symmetric — shift, or use tombstones and a deletion bitset applied at a later merge.
- **The hybrid is the real answer.** Build into a mutable in-memory dynamic array, freeze and compress it into an immutable contiguous segment, and create new segments for later documents — cheap ingestion and fast serving stop fighting over one structure.
- **Hash map vs sorted structure: when order matters is a question about the query contract.** A hash map gives expected $O(1)$ exact lookup and no meaningful iteration order. A sorted array of key-value entries gives exact lookup by binary search in $O(\log n)$ and range lookup in $O(\log n + k)$ — two boundary searches plus $k$ outputs. Over a one-million-term dictionary, exact lookup of `retrieval` is one hash probe or about 20 comparisons, since $2^{20} \approx 10^6$. Autocomplete for prefix `retr` is a lower-bound search plus a scan while the prefix holds — about 20 comparisons plus 80 outputs if 80 terms match — whereas the hash layout must examine roughly one million keys, because it has no notion of "the next key".
- **Order also buys merging.** Two sorted dictionaries combine in one linear two-cursor pass preserving key order and identifying equal terms — which is why immutable index segments are sorted: merging a new segment into an old one becomes sequential I/O. A hash table would have to probe or rebuild, and emits nothing ordered without a later sort. Balanced search trees hold the mutable ordered middle at $O(\log n)$ per operation, paying pointers and weaker locality.

**Rules to remember**

- Expected $O(1+\alpha)$, not $O(1)$: quote the load factor or you have not quoted the cost.
- Geometric growth is what makes an $O(n)$ resize amortize to $O(1)$ per insert. Constant growth does not.
- Open addressing needs $\alpha < 1$; chaining tolerates $\alpha > 1$ and degrades linearly.
- A collision is normal; only a *degenerate* distribution — every key in one bucket — is the $O(n)$ case.
- Tail-pointer append is $O(1)$; reaching element $i$ is $O(i)$; binary search on a linked list is worthless.
- Arrays give $b + iw$ addressing, binary search, block compression and bandwidth-speed intersection.
- Linked splice is $O(1)$ *given the predecessor*; finding the predecessor is the real cost.
- Hash answers `get(key)`. Order answers `lower_bound`, prefix, range, ordered iteration and merge.
- List the required operations before naming a structure — that is the whole decision procedure.

**Common pitfalls**

- **Calling a hash probe $O(1)$ with no mention of load factor or hash quality.** The same code is a constant-time probe at $\alpha = 0.75$ and a 75-entry scan at $\alpha = 75$.
- **Believing amortized $O(1)$ means every insert is fast.** The resize really does cost $O(n)$; the *total* is what is bounded — good for throughput, not for a p99 latency target.
- **Reading "linked-list insertion is $O(1)$" as an argument against arrays.** It assumes the position is known; for postings you must search for it first.
- **Comparing structures only by Big-O.** Array and linked intersection are both $O(m+n)$; one streams 4 MB, the other chases 16 MB of scattered nodes.
- **Serving prefix or range queries from the hash dictionary.** A hash map over sorted input still cannot enumerate a prefix without scanning every key: that is an $O(n)$ scan pretending to be an index.
- **Forcing one structure to do both jobs.** A mutable linked postings list is a mediocre ingester and a bad server; buffer-then-freeze beats it at both. And its pointers do not survive a process, so it is flattened at serialization anyway.

**How to approach the questions**

1. For any "hash lookup cost" question, find $n$ and $M$, compute $\alpha$, answer $O(1+\alpha)$ — then check whether *expected* or *worst* case was asked, because they differ by a factor of $n$.
2. For chaining-versus-probing questions, ask what happens as the table fills: chains lengthen gracefully, probe sequences sharply, because they depend on empty slots existing.
3. When a stem says "insertion is constant time", locate the assumption. If the position must be searched for, the true cost is $O(n)$ whatever the structure.
4. Convert layout claims into bytes and cache lines: 4 bytes of payload in a 16-byte node, 4 MB versus 16 MB, one dependent miss per node.
5. For "which structure" questions, write the operation list — point lookup, prefix, range, ordered merge, append rate, update pattern — and let it decide. Distractors offer a structure that answers a *different* contract.
6. Watch for the amortized/worst-case swap and the expected/worst-case swap: the two commonest wrong options here.
