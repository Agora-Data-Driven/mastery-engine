1. From Cost To Structure

Time Complexity of Linear Scan vs Binary Search vs Hash Probe priced three ways to find one term. Drag the dictionary size and watch those prices separate — then read what this lesson spends them on. Like knowing the price of a taxi, a bus and a bike: the numbers only decide anything once you say where you are going.

lesson 01 — the cost model
  • linear scan O(n), binary search O(log n), hash probe expected O(1)
  • two sorted postings lists intersect in O(m+n) with two cursors
  • sequential access streams; scattered access stalls on one miss at a time
lesson 02 — the structures
  • the dictionary: a hash table, and whether its "O(1)" survives its load factor
  • the postings: linked nodes (cheap append) or a packed array (cheap everything else)
  • and when order itself is part of the query, not decoration

An inverted index needs both answers at once, and they are different questions. The dictionary is asked "where is term retrieval" millions of times; a postings list is asked to grow cheaply and then be walked forward at bandwidth. One structure that is fair at both loses to two that are each excellent at one.

2. The Load Factor Dial

Hold the dictionary at 750,000 terms and move the bucket array underneath it. The code never changes; the cost of "a hash lookup" changes by a factor of forty. Like a coat check with a fixed number of hooks: the same ticket takes a second or a minute depending on how many coats share a hook.

This is why tables resize: crossing a threshold reallocates and reinserts under a new modulus, O(n) at that moment. Double the capacity each time and the total rehash work over n inserts is 1 + 2 + 4 + … < 2n — a geometric series bounded by twice the final size — so insertion is amortized O(1) even though one insert can be the expensive one. Grow by a fixed amount instead and you rehash n/c times at O(n) each, which is quadratic.

3. Chained Or Probed

Three keys, one bucket, two ways to survive it. Insert them one at a time and switch the strategy underneath. Like three parcels for the same pigeonhole: hang a bag off that hole, or push each parcel into the next free hole along.

Neither strategy is a repair for a bad hash — a collision is the normal case, because the key space is larger than M. What separates them is physical: linear probing walks consecutive slots and is cache-friendly, exactly what lesson 01 rewarded, but its occupied clusters grow and every later probe walks them. Double hashing spreads probes better and jumps around memory — it pays cache misses to buy shorter probe sequences.

4. Nodes Or Bytes

The same postings list, twice: 4 bytes per document ID packed end to end, or 16 bytes per node scattered by the allocator. Pick the operation and drag the list length. Like a shopping list on one sheet of paper versus one word per sticky note taped around the house.

So the real index does neither one purely: accumulate into a mutable dynamic array, freeze it into an immutable contiguous segment, start a new segment for later documents. Append stays amortized O(1), serving reads contiguous bytes, and deletions become a separate bitset applied at the next merge. Forcing one structure to be both the ingester and the server makes it mediocre at both.

5. Order As Contract

One million terms, two dictionaries holding exactly the same pairs — one hashed, one sorted. Tap a query and drag how many terms match. Like a phone book versus a pile of business cards: both find one name; only one answers "everyone whose name starts with Mc".

The expert test is to list the required operations before choosing a structure. If the contract is only get(key), hashing is compelling. If it includes lower_bound, prefix enumeration, range scan, ordered merge or nearest key, order is data and not decoration — and paying O(log n) for exact lookup can be the cheaper system, because it avoids an O(n) scan or a second index maintained for every ordered query.
