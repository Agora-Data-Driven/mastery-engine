**The big idea**: **Hash Map vs Sorted Structure: When Order Matters** left you at two extremes — a hash table that answers a point lookup in O(1) and knows nothing about order, and a sorted structure that knows everything and charges to keep it. Retrieval lives between them. Once you have walked the postings (**Linked Lists as Postings: Sequential Access and Cheap Append**) and intersected them (**Big-O of Intersecting Two Sorted Lists**), you hold millions of scored documents — and you do not want them ordered. You want the best 10, 100 or 1,000. A **binary heap** maintains exactly that much order and no more: enough to name the current weakest winner, nothing about how the losers compare. That restraint turns an O(n log n) job into O(n log k), holds memory at O(k), and works on a stream that never fits in RAM — the **Memory Hierarchy: Why Sequential Access Beats Random Access** argument applied to what you *retain*.

**Key concepts**

- **A binary min-heap is a complete binary tree with one invariant.** Every node's key is no greater than either child's; "complete" means every level is full except possibly the last, which fills left to right. The root is therefore the global minimum — following any path away from it can never decrease the key. It does *not* promise sibling order: `[2, 5, 4, 12, 9, 7]` is a valid min-heap (2 below 5 and 4; 5 below 12 and 9; 4 below 7) yet is not sorted, because 5 sits before 4. Ancestor order only — and a promise you never make is one you never pay to maintain.
- **The tree is an array, and the pointers are arithmetic.** Zero-based, node $i$ has parent $\lfloor(i-1)/2\rfloor$, left child $2i+1$ and right child $2i+2$ where those exist. Completeness makes the arithmetic legal — no gaps, so array index equals level-order position. No node objects, no pointer chasing: one contiguous block, the sequential-access property you already know is worth having.
- **Insert = append, then sift up. O(log n).** Appending into the next slot preserves completeness but may violate the property against the parent, so swap upward while the new key is smaller. Insert 3 into `[2, 5, 4, 12, 9, 7]`: append → `[2, 5, 4, 12, 9, 7, 3]`; the newcomer is at index 6, parent $\lfloor 5/2 \rfloor = 2$ holding 4; 3 < 4, swap → `[2, 5, 3, 12, 9, 7, 4]`; its parent is index 0 holding 2, smaller, so stop. Only the ancestor chain moved, and a complete tree of $n$ nodes has height $\lfloor\log_2 n\rfloor$ — one swap per level, so $O(\log n)$.
- **Extract-min = promote the last element, then sift down. O(log n).** Shifting every element left would cost $O(n)$, so instead move the final element into the root, shrink by one, and swap it with its **smaller** child while it exceeds that child. From `[2, 5, 3, 12, 9, 7, 4]`: remove 2, move 4 to the root → `[4, 5, 3, 12, 9, 7]`; the children of index 0 are 5 and 3, so swap with 3 → `[3, 5, 4, 12, 9, 7]`. The smaller child is not cosmetic — taking the larger one leaves that key above its smaller sibling and breaks the invariant you were repairing.
- **Peek is O(1) because the minimum is the root; finding an arbitrary key is O(n).** The heap property cannot say whether key 8 lies under the child holding 3 or the one holding 5, so search degenerates to a scan. A heap is a **priority queue**, not a membership index — that job belongs to the hash table. A max-heap reverses the comparison so the maximum is at the root; the mechanics and costs are identical.
- **Construction has two costs, and the cheaper one needs all the data up front.** Inserting $n$ elements one at a time is $O(n\log n)$. Bottom-up **heapify** — sift down every internal node, last back to root — is $O(n)$: most nodes sit near the leaves and travel a step or two while only the few near the root travel the full height, so $\sum_h \frac{n}{2^{h+1}}\,h = n\sum_h \frac{h}{2^{h+1}} = n$. Streaming arrivals ⇒ insertion; a batch in memory ⇒ heapify.
- **Maintaining top-k with a bounded min-heap: the root IS the admission threshold.** Cap the heap at size $k$ and hold the current winners in it; the root is the smallest score among them. For each candidate `(score, document)`: if fewer than $k$ are held, insert; otherwise compare with the root — no greater, discard; greater, replace the root and sift down. The invariant: after any prefix of the stream the heap holds exactly the $k$ largest items in that prefix. By induction — true at the start; while underfull, keeping the newcomer preserves it; once full, the root is the weakest winner, so anything at or below it cannot belong to the top $k$ and anything above it must, and evicting the root removes exactly the displaced weakest winner.
- **Worked stream, $k=3$, scores `[8, 2, 5, 10, 7, 1]`.** The first three fill the heap: `{2,5,8}`, root 2. Then 10 > 2 → `{5,8,10}`, root 5. Then 7 > 5 → `{7,8,10}`, root 7. Then 1 is not greater than 7 and is discarded. The correct top three — but heap-ordered, not descending.
- **The cost, term by term.** The first $k$ cost at most $O(k\log k)$ by insertion, or $O(k)$ if buffered and heapified; each of the remaining $n-k$ pays one $O(1)$ root comparison; only winners pay the $O(\log k)$ replacement. Worst case $O(n\log k)$ time, $O(k)$ memory. At $k=100$, $n=10{,}000{,}000$: heap height under 7, 100 entries resident.
- **Why a *min*-heap when you want the largest values?** The algorithm needs the *weakest* retained item on demand, not the strongest. A max-heap puts the best winner at the root, which says nothing about the cutoff — finding the weakest would cost $O(k)$ every time. Symmetrically, the $k$ smallest want a bounded max-heap.
- **Ties need an explicit deterministic rule.** Break equal scores on a stable secondary key — compare `(score, -doc_id)` tuples in the heap *and* in the output. Without it, traversal order or shard timing decides which equal-score candidate survives, and pagination stops being reproducible.
- **Distributed search repeats the pattern.** Each shard keeps its local top $k$ instead of shipping every score, and a coordinator merges the candidates into the global top $k$. That is *sufficient* for pure score ordering: a document outside its own shard's top $k$ has at least $k$ documents in that shard alone above it. The judgment changes once a later stage applies diversity, quotas or a different reranker — local score order no longer proves global eligibility, and shards must overfetch.
- **Heap-based top-k vs full sort: the cost comparison in units.** A comparison sort of all candidates is $O(n\log n)$ and stores or rearranges all $n$ records — you paid to order every loser against every other loser. With $n=1{,}000{,}000$ and $k=10$: full sort is on the order of $n\log_2 n \approx 20$ million comparison units, the bounded heap at most $n\log_2 k \approx 3.3$ million. At $k=n$ the bounds meet ($\log k = \log n$) and the heap offers no selection advantage.
- **The heap does not return a sorted top-k list.** Only the root is guaranteed. Sort the $k$ winners in $O(k\log k)$, or extract the minimum repeatedly: combined $O(n\log k + k\log k)$, dominated by the first term whenever $n \gg k$.
- **Full sorting is still correct and sometimes better.** If the consumer needs every result in order, sorting is necessary work. If $n$ is small, library sort is simpler and highly optimised. If $k$ is a large fraction of $n$, the heap's branches and swaps can lose to cache-friendly sorting despite similar asymptotics — and on numeric data a vectorized partial selection can beat it.
- **Quickselect is the third option.** It partitions an in-memory array around the $k$th boundary in expected $O(n)$, then sorts only the winning $k$ — often best for one batch already resident in mutable memory, but it rearranges and retains the whole input and has a quadratic worst case without careful pivoting. The bounded heap is **online**: it never sees a future candidate and handles streams larger than RAM. Ten million scored chunk IDs from a streaming iterator feeding a 100-candidate reranker is its case exactly; exporting every scored record in order is not, and there full sorting is honest.

**Rules to remember**

- A heap promises ancestor order only. Siblings are unconstrained, so never read a heap array as sorted.
- Parent $\lfloor(i-1)/2\rfloor$, children $2i+1$ and $2i+2$, zero-based; completeness is what makes that arithmetic valid.
- Insert appends then sifts up; extract-min promotes the last element then sifts down against the **smaller** child. Both $O(\log n)$; peek $O(1)$; search $O(n)$.
- Heapify a batch in $O(n)$; insert a stream in $O(n\log n)$.
- For the $k$ largest use a bounded **min**-heap — the root is the admission threshold. For the $k$ smallest, a bounded max-heap.
- Bounded-heap top-k: $O(n\log k)$ time, $O(k)$ memory, one pass, online. Full sort is $O(n\log n)$ and retains all $n$; the gap vanishes at $k=n$.
- Winners come out heap-ordered, not ranked — add $O(k\log k)$ for rank order — and ties need a stable secondary key in the heap and the output.

**Common pitfalls**

- **Reading a heap array as a sorted list.** Only the root is guaranteed; `{7,8,10}` may be held in any heap-valid arrangement.
- **Reaching for a max-heap to keep the largest values.** It puts the wrong end at the root, so every admission test becomes an $O(k)$ hunt for the weakest winner.
- **Getting the comparator backwards.** A flipped comparison silently retains the bottom $k$ — no crash, just wrong results. Asserting parent ≤ child for every $i>0$ is an $O(n)$ check worth running after any custom implementation.
- **Letting the heap grow past $k$.** Unbounded gives $O(n\log n)$ time and $O(n)$ memory: the sort you were avoiding.
- **Shifting the array on extract-min** instead of promoting the last element. $O(n)$ per removal, and the cost argument is gone.
- **Using a heap for lookups or ranges, or claiming it always wins.** Arbitrary search is $O(n)$, ordered traversal means draining it, and at $k$ near $n$ or against a vectorized partial sort it loses.
- **Assuming local top-k survives any downstream stage.** Proven only for pure score ordering; diversity, quotas or a different reranker require overfetch.
- **Reporting $O(n\log k)$ as though every candidate pays $\log k$.** Most pay one comparison; only winners pay the replacement.

**How to approach the questions**

1. Ask what the consumer needs — the whole order, a boundary, or the best $k$. That decides between full sort, quickselect and a bounded heap more often than any constant factor.
2. For any trace, write the array out and apply the index arithmetic literally. Most wrong answers sift against the wrong child or parent.
3. Check the heap direction against the goal: "$k$ largest" ⇒ min-heap. Distractors reliably offer the reverse.
4. On cost questions put real numbers in — $n\log_2 n$ against $n\log_2 k$, memory $n$ against $k$ — then ask whether $k$ is close enough to $n$ for the gap to disappear.
5. Treat "stream", "iterator" or "larger than memory" as decisive: they eliminate quickselect and full sort whatever the asymptotics say.
6. If the question asks about the *output*, add the $O(k\log k)$ step; and separate the construction cases — batch ⇒ heapify $O(n)$, arrivals ⇒ insertion $O(n\log n)$.
