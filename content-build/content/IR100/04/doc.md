Search dictionaries need more than exact lookup: autocomplete needs prefixes, range scans need order, and on-disk indexes must minimize page reads rather than merely comparisons. Ordered trees and string-specific automata solve those contracts with different physical tradeoffs. Their common theme is paying slightly more than expected constant-time hashing so that key order becomes usable structure.
That structure is valuable only when its ordering semantics remain consistent.

## Balanced Search Trees vs Hash Indexes: Range vs Point Lookups

A binary search tree stores a key at each node, with smaller keys in the left subtree and larger keys in the right. Lookup compares the target with the current key and chooses one subtree. If tree height is $h$, lookup, insertion, and deletion cost $O(h)$. An ordinary tree can become a chain: inserting already sorted keys 1, 2, 3, 4, 5 creates height $n-1$ and $O(n)$ operations.

A **balanced search tree** maintains height $O(\log n)$ through structural rules and rotations. AVL trees tightly constrain subtree-height differences; red-black trees enforce coloring rules that keep the longest root-to-leaf path within a constant factor of the shortest. The precise rules differ, but both repair imbalance after updates with local rotations while preserving sorted order. Thus point lookup, insertion, deletion, predecessor, successor, and boundary search are worst-case $O(\log n)$.

A hash index instead computes a bucket and offers expected $O(1)$ exact lookup under good distribution and load control. For `get("retrieval")`, hashing normally beats a pointer-based tree. But the hash layout deliberately scrambles key order. To answer keys in `[cloud, cluster]`, a hash table must examine all $n$ keys and test the range, $O(n+k)$ for $k$ outputs. A balanced tree finds the lower bound in $O(\log n)$ and follows in-order successors for $k$ results, $O(\log n+k)$.

Worked example: a million-term dictionary receives `terms from "retrieval" through "retriever"`. A red-black tree needs about 20 to 40 node comparisons to find the first key, then visits only matching successors. A hash table scans roughly one million entries even if seven terms match. Conversely, one million independent exact membership probes favor the hash table's expected constant bucket work over repeated tree paths.

Order enables additional operations: nearest key, floor and ceiling, sorted iteration, prefix range once prefix bounds are computed, and merge-like traversal. Balanced trees also provide worst-case logarithmic behavior, whereas a collision-heavy hash table can degrade to linear work. Their costs are extra comparisons, node pointers or metadata, rotations on writes, and weak locality when nodes are separately allocated.

Judgment begins with the operation set. Use hashing for a memory-resident workload dominated by exact point access with no ordered questions. Use a balanced tree when mutations and ordered queries both matter or worst-case latency is important. A sorted array can beat both for an immutable batch because it has excellent locality and $O(\log n)$ lookup, but middle updates cost $O(n)$. Many systems use a hash table for one exact-access path and a separate ordered index for ranges; that duplication is justified only when both workloads are important enough to pay extra memory and update coordination.

The comparator is part of the index contract. Byte order, locale-aware collation, case folding, and numeric-versus-text comparison can produce different trees and range boundaries. If insertion uses one normalization and lookup uses another, a present key can become unreachable even though balancing is perfect. Persist the comparator and normalization version with an ordered index, and rebuild when those semantics change; structural correctness cannot compensate for inconsistent ordering.

## B-tree Intuition: Wide Nodes for Block Storage

A binary tree minimizes comparisons per node but not storage reads. Database and filesystem indexes operate over pages, commonly several kilobytes. Fetching a page costs far more than comparing keys already inside it, so a storage-oriented tree should pack many separator keys and child pointers into each fetched page. A **B-tree** is a balanced multiway search tree designed around this fact.

An internal node with sorted separators $[k_1,k_2,\ldots,k_r]$ and $r+1$ child pointers divides key space into ranges. Search within the node, often by binary search, then follow exactly one child. All leaves remain at the same depth. Splits and merges preserve occupancy and balance as keys are inserted or removed, so height is logarithmic in base equal to the branching factor rather than base two.

Suppose an 8 KB internal page fits 256 key-pointer entries. A binary tree holding one billion keys has height near $\log_2 10^9\approx30$. A B-tree with effective fan-out 256 needs about $\log_{256}10^9 = \log_2 10^9/8\approx3.7$, roughly four page levels. If the root and upper level remain cached, a lookup may require only two storage reads. Comparing dozens of separators in RAM is far cheaper than 30 random page fetches.

Worked insertion: a leaf page is full and a new key belongs there. The page splits into two roughly half-full leaves; a separator identifying the new right leaf is inserted into the parent. If the parent overflows, the split propagates upward. A root split creates a new root and increases tree height by one. Unlike a binary-tree rotation, the unit of rearrangement is a page-sized node.

In a classic B-tree, records or values may appear in internal and leaf nodes. A **B+ tree**, common in databases, stores actual row pointers or records only at leaves; internal nodes contain routing separators. Leaves are linked in key order. Point lookup descends to one leaf, while a range scan finds its first leaf and walks sequential leaf pages. The linked leaves turn a potentially random tree traversal into high-throughput ordered I/O after the boundary is found.

Node occupancy is a real tradeoff. Completely full pages maximize fan-out but leave no insertion room, causing frequent splits. Implementations maintain minimum occupancy and reserve space according to workload. Sequential inserts can create a hot rightmost leaf; random inserts distribute writes but fragment locality. Concurrency, write-ahead logging, and latch protocols complicate production B-trees, but the stable principle is simple: align nodes with the transfer unit and maximize useful branching per expensive read.

B-trees are not inverted indexes. A database B-tree orders complete keys or key tuples and excels at equality, range, and ordered scans. An inverted index maps terms to postings containing all matching document IDs; it answers full-text containment without scanning every row key. A B-tree over document text would order whole strings, not create term-level access. Experts choose the index whose key granularity matches the predicate.

## Tries and FSTs for Prefix Lookup and Autocomplete

A **trie** stores strings one symbol per edge. Paths from the root spell prefixes; terminal markers identify complete keys. To look up a key of length $L$, follow its $L$ symbols, giving $O(L)$ time independent of the number of stored terms, assuming outgoing-edge lookup is efficient. To enumerate a prefix, follow the prefix path and traverse terminal descendants.

For keys `car`, `card`, `care`, and `cat`, the root edge `c` and next edge `a` are shared. Node `r` is terminal for `car`; its children `d` and `e` produce `card` and `care`; sibling `t` produces `cat`. Autocomplete for `car` navigates three edges and enumerates the three terminal completions. A hash table would need a separate prefix index or a scan, while a sorted array could binary-search the prefix boundary and scan matches.

The naive trie can be memory-hungry. Every character may allocate a node containing maps or pointer arrays, and sparse outgoing edges waste space. **Path compression** collapses nonbranching chains into multi-character edge labels, producing a radix tree. Compact encodings store edges in arrays rather than heap objects. These changes preserve prefix mechanics while improving locality.

A **finite-state automaton** can share suffix structure as well as prefixes. A trie for `mop` and `top` shares nothing before their common suffix because paths diverge at the first character. In a minimized deterministic acyclic finite-state automaton, equivalent suffix states can merge. A **finite-state transducer** (FST) adds outputs to transitions or final states, allowing a key path to yield a term ID, postings offset, or weight. Search engines use compact FST dictionaries because sorted term sets contain abundant shared prefixes and suffix-equivalent tails.

Mechanically, FST lookup starts at one state, consumes one input symbol per transition, accumulates any transition outputs, and succeeds only at a final state after all symbols are consumed. Prefix enumeration reaches the prefix state, then explores outgoing paths. Weighted variants can store information enabling high-value completions to be returned early, although maintaining an exact dynamic top-completion policy adds metadata and complexity.

Worked comparison for one million terms and query prefix `retr`. A hash dictionary may scan all million keys. A sorted array finds the lower boundary in about 20 comparisons and scans $k$ matches. A trie or FST consumes four prefix symbols, then enumerates the $k$ reachable completions, roughly $O(L+k)$ plus traversal overhead. The FST can occupy far less memory than an object-heavy trie because it merges equivalent states and uses compact serialized arrays.

The compression advantage creates an update cost. A mutable trie accepts insertion by adding a path in $O(L)$, but a minimal serialized FST depends on global state equivalence and is usually built from sorted keys as an immutable artifact. Frequent changes are handled through small mutable overlays or new immutable segments, followed by merging, rather than editing a large FST in place.

Judgment: use a hash map for exact term lookup when memory and point speed dominate; a sorted array when the dictionary is immutable and ranges suffice; a trie for mutable prefix-heavy workloads; and an FST for compact, read-heavy term dictionaries and autocomplete. Unicode adds a design choice: edges may represent bytes, code points, or normalized tokens. Whatever representation is chosen must match the analyzer's normalization, or visually equivalent strings follow different paths. Prefix speed cannot repair inconsistent key semantics.
