**The big idea**: **Hash Tables: Buckets, Collisions, and Load Factor** bought you expected constant-time exact lookup, and **Hash Map vs Sorted Structure: When Order Matters** already named the price — hashing deliberately scrambles key order. This lesson is what you build when order is the thing you need. Search dictionaries need more than exact lookup: autocomplete needs prefixes, range scans need order, and an on-disk index must minimise *page reads* rather than comparisons — **Memory Hierarchy: Why Sequential Access Beats Random Access** restated as a requirement on a data structure. A **balanced search tree** keeps sorted order under mutation, so ranges and neighbours stay cheap. A **B-tree** re-cuts that tree until one node is one storage block, trading comparisons (cheap) for page fetches (expensive). A **trie** or **FST** indexes strings by their symbols, so a prefix becomes a walk rather than a search. The theme: you pay slightly more than an expected-constant hash probe so that key order becomes usable structure — and that structure is worth nothing if its ordering semantics are inconsistent.

**Key concepts**

- **A binary search tree costs $O(h)$, and $h$ is not automatically $\log n$.** Smaller keys left, larger right; lookup compares and descends one subtree, so lookup, insertion and deletion all cost $O(h)$. Insert the sorted keys 1, 2, 3, 4, 5 and each lands right of the last: height $n-1$, every operation $O(n)$. That degenerate tree is the linked list from lesson 02 with extra pointers.
- **Balanced search trees pin the height at $O(\log n)$ with rotations.** AVL trees tightly constrain the height difference between sibling subtrees; red-black trees enforce colouring rules keeping the longest root-to-leaf path within a constant factor of the shortest. The rules differ; the behaviour does not — both repair imbalance after an update with *local* rotations that preserve sorted order. Point lookup, insertion, deletion, predecessor, successor and boundary search are all worst-case $O(\log n)$.
- **Point versus range is where hash indexes break.** For `get("retrieval")` a hash index computes a bucket and finishes in expected $O(1)$ under good distribution and load control; a pointer-chasing tree cannot beat that. But for all keys in `[cloud, cluster]` a hash table must examine and test all $n$ keys: $O(n+k)$ for $k$ outputs. A balanced tree finds the lower bound in $O(\log n)$, then follows in-order successors — $O(\log n + k)$.
- **Worked numbers.** A million-term dictionary is asked for `terms from "retrieval" through "retriever"`, seven of which match. A red-black tree needs about 20 to 40 node comparisons to reach the first key, then visits only the matching successors; that range is $\log_2 10^6 \approx 19.9$ at best and about $2\log_2(n+1) \approx 40$ in the worst case its rules permit. The hash table scans roughly one million entries for the same seven. Flip the workload to one million exact membership probes and the hash table's expected constant bucket work wins instead.
- **Order buys a whole operation set, not just ranges.** Nearest key, floor and ceiling, sorted iteration, prefix range once the bounds are computed, and merge-like traversal — the sorted-list intersection you already costed. Balanced trees also give *worst-case* logarithmic behaviour where a collision-heavy hash table degrades to linear. Costs: extra comparisons, node pointers, rotations on writes, weak locality.
- **A sorted array is the third answer, often the right one.** For an immutable batch it has excellent locality and $O(\log n)$ lookup, beating both — but a middle insert costs $O(n)$. Many systems run a hash table for exact access *and* a separate ordered index for ranges; pay for that duplication only when both workloads earn it.
- **The comparator is part of the index contract.** Byte order, locale-aware collation, case folding and numeric-versus-text comparison produce different trees and different range boundaries. Insert under one normalisation and look up under another and a present key becomes unreachable, the balancing perfectly correct throughout. Persist the comparator and normalisation version with an ordered index; rebuild when those semantics change.
- **The B-tree intuition: make the node the size of the thing you fetch.** A binary tree minimises comparisons per node, the wrong quantity when block storage hands you pages of several kilobytes. Fetching a page costs far more than comparing keys inside it, so a storage-oriented tree packs many separators and child pointers into every fetched page. A B-tree is a balanced multiway search tree built on that: an internal node holds sorted separators $[k_1,\dots,k_r]$ and $r+1$ child pointers, you binary-search *within* the node, then follow one child. All leaves stay at the same depth.
- **The fan-out derivation is the whole argument for wide nodes.** An 8 KB internal page holding 256 key-pointer entries gives fan-out 256. For one billion keys a binary tree has height $\log_2 10^9 \approx 30$; the B-tree's is $\log_{256}10^9 = \log_2 10^9 / \log_2 256 = 29.9/8 \approx 3.7$ — about four levels of pages. Cache the root and the level below and a lookup may cost **two** storage reads. Dozens of in-RAM separator comparisons instead of 30 random page fetches is the entire trade: block storage economics, not comparison counting.
- **Splits are the page-sized version of a rotation.** A full leaf page receives a key that belongs in it: it splits into two roughly half-full leaves, and a separator naming the new right leaf goes into the parent. If the parent overflows it splits too, propagating upward; a root split creates a new root and raises the height by one. The unit of rearrangement is a page-sized node, not a rotation.
- **B+ trees put the payload only at the leaves and link them.** Internal nodes carry routing separators; records or row pointers live at the leaves, chained in key order. A point lookup descends to one leaf; a range scan finds its first leaf and walks sequential leaf pages, turning a random traversal into high-throughput ordered I/O once the boundary is found.
- **Occupancy is a real dial.** Full pages maximise fan-out but leave no insertion room, so splits become frequent; implementations hold a minimum occupancy and reserve space per workload. Sequential inserts create a hot rightmost leaf; random inserts spread writes but fragment locality.
- **A B-tree is not an inverted index.** It orders complete keys or key tuples and excels at equality, range and ordered scans; an inverted index maps a term to postings of matching document IDs. A B-tree over document text orders whole strings and gives no term-level access. Match key granularity to the predicate.
- **Tries make prefix lookup a walk: $O(L)$, independent of how many terms are stored.** One symbol per edge; paths from the root spell prefixes; terminal markers identify complete keys. For `car`, `card`, `care` and `cat`, edges `c` and `a` are shared; node `r` is terminal for `car`, its children `d` and `e` give `card` and `care`, sibling `t` gives `cat`. Autocomplete for `car` walks three edges and enumerates three completions. A hash table would need a separate prefix index or a full scan.
- **Naive tries are memory-hungry, and the fixes preserve the mechanics.** Every character may allocate a node holding a map or pointer array, and sparse edges waste space. **Path compression** collapses non-branching chains into multi-character edge labels — a radix tree — and compact encodings store edges in arrays, not heap objects. Prefix behaviour is unchanged; locality improves.
- **FSTs share suffixes as well as prefixes, and can carry outputs.** A trie for `mop` and `top` shares nothing: the paths diverge at the first character. In a minimised deterministic acyclic automaton the equivalent suffix states merge — seven trie nodes collapse to four, since the states after `m` and after `t` both accept exactly `op`. A **finite-state transducer** adds outputs to transitions or final states, so a key path yields a term ID, postings offset or weight. Lookup consumes one symbol per transition, accumulating outputs, and succeeds only at a final state once all symbols are consumed.
- **Worked comparison, one million terms, prefix `retr`.** A hash dictionary may scan all million keys. A sorted array binary-searches the boundary in about 20 comparisons and scans $k$ matches. A trie or FST consumes four prefix symbols and enumerates the $k$ reachable completions — roughly $O(L+k)$ plus traversal overhead — and the FST holds far less memory than an object-heavy trie, because sorted term sets are rich in shared prefixes *and* suffix-equivalent tails.
- **The compression advantage is paid for at write time.** A mutable trie inserts a path in $O(L)$, but a minimal serialised FST depends on *global* state equivalence and is built from sorted keys as an immutable artifact. Changes land in small mutable overlays or new immutable segments, later merged — never by editing a large FST in place.

**Rules to remember**

- Unbalanced BST cost is $O(h)$ and $h$ can be $n-1$; balancing converts that into a worst-case $O(\log n)$ guarantee.
- Hash index: expected $O(1)$ point lookup, $O(n+k)$ range. Balanced tree: $O(\log n)$ point, $O(\log n + k)$ range.
- Choose from the operation set, not the data: memory-resident and no ordered questions means hash; mutations plus ordered queries, or a worst-case latency target, means an ordered tree.
- Height in a B-tree is logarithmic in base *fan-out*: $\log_{256}10^9 \approx 3.7$ versus $\log_2 10^9 \approx 30$.
- Splits propagate upward, and only a root split changes the height.
- B+ tree: separators inside, records at linked leaves, so ranges become sequential leaf-page I/O.
- Trie/FST lookup is $O(L)$ in the key length, independent of how many terms are stored; prefix enumeration adds $O(k)$.
- A minimal FST is an immutable build over sorted keys; mutability comes from overlays and segment merges.
- Whatever the structure, the comparator or symbol normalisation is part of the contract and must match the analyser.

**Common pitfalls**

- Treating "balanced" as if it bought locality. It bounds *comparisons*, not page fetches; separately allocated nodes are the random access the memory hierarchy punishes.
- Answering a range from a hash index: $O(n+k)$, a full scan however few keys match.
- Reading fan-out as a comparison saving. A B-tree does *more* comparisons; it does far fewer page reads, and only the reads are billed.
- Confusing a B-tree with an inverted index: different key granularity.
- Assuming a full page is an efficient page: 100% occupancy guarantees a split on the next insert.
- Expecting a trie to share the tails of `mop` and `top`. Prefix sharing only; suffix sharing needs minimisation.
- Treating an FST as a drop-in mutable dictionary. Minimality is global, so in-place edits are unavailable.
- Assuming structural correctness rescues inconsistent ordering. A key inserted under one normalisation and probed under another is unreachable in a perfectly balanced tree.

**How to approach the questions**

1. Read the *operation set* first — point, range, prefix, neighbour, ordered scan — then pick the structure. Most distractors are correct for a different operation.
2. Given a page size and an entry size, compute the fan-out and take $\log_{\text{fan-out}} n$. When the choices differ by an order of magnitude, that division by $\log_2(\text{fan-out})$ decides it.
3. Separate expected from worst case: hash is expected $O(1)$ and degrades with collisions; balanced trees are worst-case $O(\log n)$. Latency questions turn on that.
4. For prefix questions, count symbols consumed ($L$) and completions enumerated ($k$) — never the dictionary size.
5. When a scenario mentions insert order, suspect an unbalanced tree's height or a hot rightmost B-tree leaf.
6. If case folding, collation or Unicode normalisation appears, the answer is about the comparator contract, not the structure.
