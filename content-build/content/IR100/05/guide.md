**The big idea**: **Memory Hierarchy: Why Sequential Access Beats Random Access** established that storage pays you for long contiguous reads and charges you for scattered ones. **Binary Heap Mechanics: Insert and Extract-Min** and **Maintaining Top-k with a Bounded Min-Heap** gave you a structure that answers "what is the smallest thing I have not taken yet?" in logarithmic time while holding almost nothing. **Big-O of Intersecting Two Sorted Lists** showed that sorted inputs let cursors walk each other in a single pass. And **Linked Lists as Postings: Sequential Access and Cheap Append**, **Arrays vs Linked Lists for Postings Storage** and **Hash Map vs Sorted Structure: When Order Matters** described the artifact all of this has to produce. This lesson bolts those pieces into one machine. An index builder must reorder more data than memory can hold: tokens arrive grouped by document, but an inverted index must group them by term and then by document ID. External merge sort resolves that physical mismatch using sequential I/O, bounded memory, and a merge whose output is already in index order — the foundational batch primitive behind search segments, warehouse sort stages, and many compaction jobs.

**Key concepts**

- **Phase one is run generation, and it costs exactly $2N$.** Read up to $M$ records — whatever the memory budget genuinely holds — sort them in RAM, write the sorted block out as an immutable **run**, repeat until the input is consumed. Every input byte is read once and written once, so the phase is one full read plus one full write. With $N = 1$ TB and 8 GB of usable sort memory, simple run generation produces $\lceil 1024/8 \rceil = 128$ runs. Each run satisfies order internally; their key ranges overlap freely, which is exactly what the merge phase exists to fix.
- **Phase two is merging, and it costs $2N$ per level.** Read the run heads, emit the smallest remaining record, advance only that run. If every run can be open at once, one pass finishes it. Otherwise merge a bounded number — the **fan-in** $F$ — at a time into longer runs, and repeat. For $R$ initial runs the number of merge levels is $\lceil\log_F R\rceil$, because each level divides the run count by $F$. Total storage traffic is therefore $2N + 2N\lceil\log_F R\rceil = 2N(1 + \lceil\log_F R\rceil)$.
- **Worked: 128 runs at fan-in 16 is about 6 TB.** $\lceil\log_{16}128\rceil = 2$ merge levels, so 1 TB is read and written during run generation and then read and written twice more — $2 + 2 + 2 = 6$ TB of total I/O. Raising the fan-in to 128 permits a single merge level and about 4 TB, but demands 128 input buffers and 128 open streams. **The largest possible fan-in is not automatically best**: split a fixed buffer pool 128 ways and every read becomes small, or you exceed file-descriptor limits.
- **Correctness rests on one invariant.** Each run is sorted, so the smallest un-emitted record globally must be one of the current run heads. Emitting the smallest head and advancing only that run preserves the invariant; once all runs are exhausted, every record has been emitted in nondecreasing order. That sentence is the whole proof.
- **Replacement selection makes initial runs longer than memory.** Maintain a heap of records; after emitting the minimum, admit the next input record into the current run if it is at least the last output, otherwise freeze it for the next run. Under random input, runs average roughly **twice** the number of records that fit memory — 128 runs become about 64, which can remove a merge level outright. The cost is a more complicated builder and harder parallel run generation, so straightforward chunk-sort runs are often preferable.
- **Memory accounting must include more than record payload.** Sort implementations need pointer arrays and temporary merge buffers; variable-length strings carry offsets; the runtime and decoder need working space; and the budget must leave headroom for OS caching, monitoring agents and concurrent readers sharing the worker. Size an "8 GB run" from raw fields alone on an 8 GB worker and allocation failure arrives *during the sort*, after the read. **More, smaller valid runs are cheaper than repeatedly crashing on an oversized one.**
- **The k-way merge is where the heap from lesson 03 earns its keep.** Merging two runs needs two cursors and $O(N)$ time. For $K$ runs, scanning all $K$ heads for the next minimum costs $O(K)$ per emitted record — $O(NK)$ overall. A min-heap holding one candidate per run reduces each choice to $O(\log K)$, giving $O(N\log K)$ time and $O(K)$ heap memory, plus one I/O buffer per run and an output buffer. Heapify costs $O(K)$; each of $N$ records is extracted once and, except for a run's final record, causes one insertion.
- **The loop, precisely.** Seed the heap with each nonempty run's first record as `(key, run_id, record)`. Extract the smallest entry and write its record; read the next record from that same `run_id`; insert it if the run is not exhausted; repeat until the heap is empty. Heap size never exceeds $K$.
- **Worked: $A=[2,8,20]$, $B=[1,8,9]$, $C=[3,7,30]$.** Initial heads are `(2,A)`, `(1,B)`, `(3,C)`. Emit 1 and replace B's head with 8; emit 2 and replace A's with 8; emit 3 and replace C's with 7; then emit 7, 8 from A, 8 from B, 9, 20, 30 by the tie-break. The result is sorted and **only three heads ever compete**.
- **Equal keys require a total comparator.** Include `run_id` or a stable secondary key in the heap comparison, or some priority-queue implementations order equal items inconsistently. For index construction, sort by `(term, doc_id, position)`, not merely by term: that makes all postings for a term consecutive, document IDs ordered, positions ordered inside a document, and duplicate tuples adjacent so they can be detected in one pass.
- **The heap does not dominate physical cost in every regime.** At $K=128$, $\log_2 K = 7$ comparisons per record is modest next to reading and decoding it. At extremely large $K$, comparison cost, tiny per-run buffers and random alternation among streams reduce throughput. That is the real argument for multi-level merging: trade one more full I/O pass for efficient buffering and manageable resource use.
- **Why index construction is a sorting problem.** Tokenizing document 42 yields records such as `(vector,42,5)`, `(index,42,6)` and `(vector,42,19)` — a stream naturally ordered by document processing, not by term. An inverted index needs every occurrence of a term adjacent, with increasing document IDs and increasing positions inside each. Sorting occurrence tuples by `(term, doc_id, position)` performs exactly that transformation. One sequential pass over the sorted tuples then groups equal terms, gap-encodes the increasing IDs and positions, and writes dictionary entries pointing at each completed postings list.
- **Worked micro-example.** Document 1 contains `blue vector`, document 2 contains `blue index`, document 3 contains `vector index`. Tokenization emits, in document order, `(blue,1,1), (vector,1,2), (blue,2,1), (index,2,2), (vector,3,1), (index,3,2)`. After sorting: `(blue,1,1), (blue,2,1), (index,2,2), (index,3,2), (vector,1,2), (vector,3,1)`. Stream that once and you have `blue:[1,2]`, `index:[2,3]` and `vector:[1,3]` with positions attached — **no corpus-wide random insertion anywhere**.
- **The tempting alternative fails at scale.** A giant in-memory map from term to a growing postings list works only while vocabulary, postings buffers and object overhead fit RAM. Spilling individual lists independently creates huge numbers of small random writes and a difficult consistency problem. Sorting converts those scattered updates into immutable sequential runs and one ordered output stream. **Blocked index construction** is the external-sort recipe applied directly: parse a memory-sized document block, accumulate occurrence tuples, sort them, write a run or partial index, repeat, then merge runs by term and document ID — and the final merge can build the term dictionary and postings file simultaneously, because term boundaries arrive in order.
- **Sorting creates the compression.** Increasing document IDs become small gaps; increasing positions within a document do the same; and a repeated term key need not be stored on every occurrence once grouping has happened. The construction order is chosen for the **serving** representation — sequential query traversal plus a binary-searchable or FST-backed dictionary — not for aesthetic ordering.
- **Dynamic indexes merge forever instead of sorting once.** Re-sorting the entire corpus after every document is absurd. Instead build small immutable sorted segments for new data, serve across them, and merge segments in the background: an ongoing sequence of external merges that trades write amplification for a bounded query-time segment count. Deletions live in tombstone bitsets until a merge removes them physically.

**Rules to remember**

- Total I/O $= 2N(1 + \lceil\log_F R\rceil)$ with $R = \lceil N/M\rceil$. Every merge level is one full read plus one full write of the dataset.
- Fan-in cuts levels logarithmically but divides your buffer pool linearly. There is a maximum *useful* $F$, and it is rarely the maximum possible one.
- Heap-based k-way merge is $O(N\log K)$ time and $O(K)$ memory; rescanning the heads is $O(NK)$.
- Make the comparator total: `(term, doc_id, position)`, with `run_id` as the tiebreak inside the heap.
- Run files are immutable, checksummed, deterministically named, and committed only after a complete write — so a failed job reuses valid runs instead of restarting from raw input.
- Grouping at scale is sorting in disguise: SQL `GROUP BY`, distributed shuffle, LSM compaction and inverted-index construction all route equal keys together and then reduce them.

**Common pitfalls**

- **Budgeting memory from payload size alone.** Pointer arrays, string offsets, decoder space and OS cache are not free, and the crash arrives mid-sort rather than at startup.
- **Maximising fan-in reflexively.** 128 streams with tiny buffers can be slower than two levels with large ones, and can exhaust file descriptors.
- **Sorting by term only.** Postings then arrive in arbitrary document order, gap encoding breaks because gaps go negative, and duplicates are no longer adjacent.
- **Assuming the heap is the bottleneck.** At $K=128$ it is 7 comparisons against a full decode; the I/O pattern is what you tune.
- **Emulating local random writes into one object.** Object stores want whole-object or range operations: write the merged object under a temporary name and publish a manifest only after validation.
- **Restarting from raw input after a failure** instead of reusing runs that were committed intact.
- **Partitioning the final output by key range carelessly**, so identical keys split across outputs whose format cannot express a continuation.

**How to approach the questions**

1. Translate every scenario into $N$, $M$, $R$, $F$. Most cost questions are $2N(1 + \lceil\log_F R\rceil)$ wearing different clothes.
2. When something "does not fit", ask *which* budget: per-run sort memory $M$, or per-merge memory (an $O(K)$ heap plus one buffer per stream). They are different numbers and distractors swap them.
3. For "which is faster", find what changes the number of full passes. Fan-in and run length change passes; heap micro-tuning almost never does.
4. If an option involves random access, in-place mutation of a stored object, or a corpus-wide in-memory map, it is usually wrong — and wrong for the same reason each time.
5. For index-construction questions, write the tuples out in document order and then sorted. The answer is nearly always visible in that two-line comparison.
6. Read tie-break and stability wording carefully. "Sort by term" versus "sort by `(term, doc_id, position)`" is a deliberate trap, and so is "stable sort" when the key already encodes the full deterministic order.
