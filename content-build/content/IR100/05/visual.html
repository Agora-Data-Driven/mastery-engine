1. From Heap To Disk

Everything in this lesson is four things you already have, bolted together. Drag the dataset past the memory budget and watch the familiar in-memory sort break into runs — then tap each row to see which earlier idea takes over. Like tidying a library: one trolley of books you can alphabetise on the table, a whole floor you must do shelf by shelf and then walk the shelves together.

The one genuinely new idea is that order survives a write. A sorted run on disk keeps its guarantee for free, so the expensive comparison work is done once, in memory, at a size you chose — and every later pass is a cursor walk over sequential bytes. Nothing here ever seeks backwards.

2. Runs And Merge Levels

One terabyte, two dials. Run size decides how many runs you make; fan-in decides how many times you have to read them all again. Every merge level is a full read and a full write of the whole dataset. Like a knockout tournament: more matches per round means fewer rounds, but every round still puts every player back on the pitch.

Judgment lives in the buffer number, not in the level count. Large sequential reads and writes amortise object-store requests and saturate disks, so a fan-in that shrinks each buffer to kilobytes can lose to an extra level with generous ones. Runs should also be checksummed, deterministically named, and committed only after a complete write — then a failed job resumes from valid runs instead of re-reading the raw input.

3. Stepping The Merge

Three sorted runs, one min-heap, nine emissions. Step it and watch the invariant hold: the smallest record left anywhere in the world is always one of the three heads. Like three queues at passport control where you always wave through whoever holds the lowest number.

The heap does not dominate physical cost in every regime. At K = 128, log2 K = 7 comparisons per record is modest next to reading and decoding it — but at extremely large K, comparisons, tiny per-run buffers and random alternation among streams all bite at once. That is the real argument for multi-level merging: trade one more full pass for buffering you can live with.

4. Tuples Become Postings

Three tiny documents, six occurrence tuples. Switch the sort key and watch the inverted index appear — or fail to. The transformation an index builder needs is a sort, and the sort key is not "term". Like a class photo list: sorted by who walked in you can count nobody; sorted by surname then first name, every family is together and in order.

The alternative is a giant in-memory map from term to a growing postings list — fine until vocabulary, buffers and object overhead outgrow RAM, at which point spilling individual lists makes an enormous number of small random writes and a nasty consistency problem. Blocked index construction is just this recipe at scale: parse a memory-sized block, accumulate tuples, sort, write a run, repeat, merge by term and document ID — and the final merge can write dictionary and postings at once, because term boundaries arrive in order.

5. Sizing A Safe Run

An 8 GB worker does not give you an 8 GB run. Set the budget you declare, then set how much the things you forgot actually multiply it by — and watch where the failure lands. Like packing a suitcase to the airline's exact weight limit and then remembering the suitcase itself weighs something.

Production builders set a conservative explicit budget, spill before reaching it, and measure peak resident memory against realistic skew rather than against average records. The instinct to squeeze one more gigabyte into a run is exactly backwards: the merge bill grows with the logarithm of the run count, and the crash bill grows with the number of retries.
