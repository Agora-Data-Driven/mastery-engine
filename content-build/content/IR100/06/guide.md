**The big idea**: an adjacency list is a postings list for geometry. **Linked Lists as Postings: Sequential Access and Cheap Append** and **Arrays vs Linked Lists for Postings Storage** taught you to keep, per term, only the documents that actually contain it, and **Memory Hierarchy: Why Sequential Access Beats Random Access** taught you to pack that list flat so a walk over it reads whole cache lines. A proximity graph keeps, per vector, only the few vectors actually near it, in exactly that layout. What changes is the query: a postings list gets *intersected* (**Big-O of Intersecting Two Sorted Lists**), a proximity graph gets *walked*. Dense retrieval turns vectors into a geometric search problem, and a graph index turns geometry into navigation — store a small neighbor set per vector, enter somewhere, move toward the query. The tension running through the lesson: sparse storage and fast local movement versus the risk that purely local choices cannot reach the globally nearest region.

**Key concepts**

- **A graph $G=(V,E)$ is vertices plus edges; in a retrieval graph a vertex is usually a document or chunk vector and an edge joins vectors considered neighbors.** Edges may be **directed**, where $u\to v$ does not imply $v\to u$, or **undirected**, where the connection is symmetric. A relation built by taking each vector's nearest $M$ candidates is naturally directed: A can hold B among its closest neighbors while A is not among B's. Assuming symmetry you did not build makes you expect a return edge the traversal has no way to take.
- **Graph representations: the adjacency matrix is $O(n^2)$ space for $O(1)$ edge tests.** For $|V|=n$ it is an $n\times n$ table whose cell says whether an edge exists. At $n=10^6$, one bit per possible edge is $10^{12}$ bits — about **125 GB** — before weights or overhead. A proximity graph with 32 outgoing neighbors per vertex has only about **32 million** edges, so that matrix spends essentially all 125 GB on a trillion *absent* edges.
- **Adjacency lists in practice: store, per vertex, only its outgoing neighbors — $O(|V|+|E|)$ space.** Enumerating a vertex's neighbors costs $O(\deg(v))$. Testing one specific edge costs $O(\deg(v))$ with a plain array, expected $O(1)$ hashed, or $O(\log \deg(v))$ sorted and binary-searched — the same three-way choice as **Time Complexity of Linear Scan vs Binary Search vs Hash Probe**, one level up. Retrieval traversal almost only ever *enumerates*, so compact arrays beat per-vertex hash tables here.
- **The worked five-vertex graph.** `A: [B, D]`, `B: [A, C, D]`, `C: [B]`, `D: [A, B, E]`, `E: [D]` — **ten directed adjacency entries** (degrees `[2,3,1,3,1]`); undirected, each logical edge appears twice, once per endpoint. A breadth-first traversal from A keeps a queue and visits A, then B and D, then C and E, never twice, at $O(|V|+|E|)$ for the reachable component: each vertex enqueued once, each adjacency entry examined once.
- **Physical layout decides the constant, and CSR is the layout that wins.** An object per vertex holding a JS array is convenient to build but pays object and pointer overhead per vertex. A compressed sparse row layout uses one `offsets` array and one flat `neighbors` array, with the neighbors of vertex $i$ at `neighbors[offsets[i] .. offsets[i+1])`. For degrees `[2,3,1,3,1]` the offsets are `[0,2,5,6,9,10]` — one entry more than there are vertices, ending at the edge count. Contiguous 32-bit IDs, good cache behaviour, serialises straight to disk. Weights live in a parallel array.
- **Mutability is the price.** Flat arrays are excellent for read-heavy traversal and expensive to edit, since inserting into the middle shifts everything after it — so builders reserve fixed neighbor capacity or rebuild immutable segments, and deletion tombstones until compaction. All of it needs **stable integer vertex IDs** plus an external document-ID map.
- **Greedy nearest-neighbor graph traversal: enter, score the neighbors, move to the best, repeat while it improves.** Given query vector $q$ and vertex vectors $x_v$, start at entry $c$, compute $d(q,x_c)$, enumerate $c$'s neighbors, move to the one with smallest query distance *if it beats $c$*, and stop when none improves. With cosine-normalised embeddings, maximising dot product is equivalent to maximising cosine similarity — the comparison flips direction, the mechanism does not.
- **The worked 2-D traversal.** Query $q=(9,9)$. Entry A $(0,0)$ is at $\sqrt{162}\approx 12.73$. A's neighbors are B $(4,3)$ at $\sqrt{61}\approx 7.81$ and C $(2,5)$ at $\sqrt{65}\approx 8.06$ — move to B. B's are D $(7,7)$ at $\sqrt{8}\approx 2.83$ and E $(6,4)$ at $\sqrt{34}\approx 5.83$ — move to D. D reaches F $(9,8)$ at distance **1** — move to F. No F neighbor improves, so return F: four neighborhoods scored, not the corpus.
- **Keep a `visited` set, or a cycle re-does work forever.** Following only the single best current node keeps memory proportional to the visited IDs. The broader **best-first** variant keeps a candidate priority queue ordered by query distance plus a result set, expands the best unexpanded candidate, and carries on after one path stalls — the **Maintaining Top-k with a Bounded Min-Heap** machinery, reused. More distance computations, more recall.
- **Why it is approximate, and where the win comes from.** The walk never proves an unseen vertex is farther than the current result. Exact linear k-nearest-neighbor search computes $n$ query distances at dimension $d$: $O(nd)$. Graph search scores only the neighbors of visited vertices: roughly $O(vMd)$ for $v$ visited vertices of degree $M$. **The advantage exists exactly when $vM \ll n$**, and dies as the budget grows to corpus scale.
- **Bytes matter as much as arithmetic.** A 768-dimensional float32 vector is **3,072 bytes**, so evaluating 10,000 scattered vectors moves about **30 MB** before graph metadata. Batching neighbor vectors contiguously and using SIMD dot products raises throughput. Graph navigation cuts the *number* of vectors touched; quantisation (later) cuts the bytes per touch.
- **Local minima in greedy search: a vertex closer to the query than all its stored neighbors, but not the global nearest.** Greedy stops because every legal one-edge move looks worse. The failure belongs to **the graph, not the distance metric** — the arithmetic was right at every step.
- **The number-line derivation.** Query at 10. Entry A at 0 (distance 10) connects to B at 6 (distance 4). B connects back to A and to C at 4 (distance 6). The true nearest, D at 9.8, is reachable only through C. Greedy moves A → B because $10 \to 4$ improves. From B, A is at 10 and C at 6, both worse than 4, so it halts at B. Reaching D means first moving *away*, 4 → 6, and pure greedy forbids that step.
- **Disconnected components are the extreme case**: no edge sequence reaches the true region at all. Poor neighbor selection also creates dense clusters with few bridges — a geometric community that traps walks. High dimensions intensify this: distance contrast weakens and neighbor relations get noisy.
- **The local-scale fixes, and their ceiling.** More degree adds escape routes but costs memory and one distance computation per extra neighbor at every expansion. Broader best-first crosses a valley by keeping alternatives. Restarts and multiple entry points sample different basins. All of them spend work *at the same scale* as the trap.
- **Why layered graphs help: scale matching.** A **layered graph** puts a small upper graph — a subset of vertices with longer-range connections — above a dense base layer holding everything with local links. Search starts at the sparse top, where each greedy move covers a large geometric distance; when no upper neighbor improves, it descends at that vertex and refines with shorter links. Highways for the cross-city leg, local streets near the door. Worked layout: ten base clusters along a line, each densely linked internally. A base-only walk entering cluster 1 needs many hops and can be trapped by weak bridges before cluster 9; an upper layer keeping one representative per cluster jumps **1 → 5 → 8**, descends, and walks locally to 9.8. Local edges are useful once near the query and inefficient for crossing the corpus; long links are the reverse. Combining scales gives reach *and* precision.
- **Layering is not a guarantee.** Poor upper links can still route into the wrong region, and weak base connectivity is not repaired by descending. More layers, degree, candidate breadth and construction effort improve navigability and cost memory and latency, so recall must be *measured* against exact neighbors on representative queries.

**Rules to remember**

- Matrix: $O(n^2)$ space, $O(1)$ edge tests. List: $O(|V|+|E|)$ space, $O(\deg(v))$ enumeration. Sparse retrieval graphs want lists.
- Nearest-$M$ relations are directed by default; undirected costs two entries per edge.
- CSR: `offsets` has $|V|+1$ entries and ends at $|E|$; neighbors of $i$ are `neighbors[offsets[i] .. offsets[i+1])`.
- BFS over an adjacency list is $O(|V|+|E|)$ on the *reachable* component — that word is doing real work.
- Greedy moves only when a neighbor strictly improves the query distance, and always keeps a visited set.
- Exact scan $O(nd)$ versus graph $O(vMd)$: the graph wins only while $vM \ll n$.
- A local minimum needs a *worsening* step to escape; breadth, restarts, bridges or an upper layer supply it.
- Degree is a dial with cost on both sides: too low disconnects, too high inflates memory and per-expansion work.

**Common pitfalls**

- **Assuming the neighbor relation is symmetric.** Nearest-$M$ construction is directed; the missing return edge silently changes reachability.
- **Storing a matrix "for fast edge lookups"** on a graph that only enumerates neighbors — 125 GB at a million vertices to answer a question nobody asks.
- **Hashing every vertex's neighbor set.** Expected $O(1)$ membership, but traversal *enumerates* — you traded a cache-friendly array for pointer chasing.
- **Off-by-one in CSR offsets.** The array is length $|V|+1$; forgetting the terminator loses the last vertex's neighbors.
- **Blaming the distance metric for a stop at a local minimum.** The metric was correct at every step; the graph offered no improving edge.
- **Reading "greedy found F" as "F is nearest".** Nothing was proved about unvisited vertices.
- **Counting only arithmetic.** 10,000 scattered 768-d float32 vectors is ~30 MB of movement; layout often dominates the FLOPs.
- **"Just increase the ANN parameter."** Not a diagnosis, and three of the four failure causes below ignore it.

**How to approach the questions**

1. For representation questions, ask what the workload *does*: enumerate neighbors (list) or test arbitrary edges (matrix). Then check sparsity, $|E|$ against $n^2$, which usually settles it.
2. Count adjacency entries directly: directed, one per stored neighbor; undirected, two per logical edge. The five-vertex example has ten.
3. For CSR, rebuild `offsets` from the degree list by prefix sum and check the length is $|V|+1$.
4. For a traversal trace, compute the distances and apply the strict-improvement rule move by move. Most distractors are the path you get by relaxing that rule, or by forgetting `visited`.
5. For cost comparisons, write $vMd$ against $nd$ and see which side the numbers put you on.
6. When a search returns the wrong vector, run the four-way diagnosis: was the true component **unreachable** (construction), did greedy stop at a **local minimum** (breadth, restarts, bridges), did the **candidate budget** end early (search parameters), or were the **distances distorted** by the representation? The remedies differ, and naming the mechanism is the answer.
7. Watch absolute claims. "Layers guarantee the nearest neighbor" and "higher degree is always better" are both false and both appear as confident distractors.
