**The big idea**: IR 100 handed you every part of this machine separately. **Big-O of Intersecting Two Sorted Lists** costed the two-cursor merge at $O(m+n)$; **Memory Hierarchy: Why Sequential Access Beats Random Access** explained why that merge is the right shape for real storage; **Hash Tables: Buckets, Collisions, and Load Factor** and **Tries and FSTs for Prefix Lookup and Autocomplete** gave you two ways to resolve a key; **Arrays vs Linked Lists for Postings Storage** already used the word *postings*; and **Why Index Construction Is a Sorting Problem** told you how a build ends. This lesson assembles them into one artifact. Lexical retrieval begins by *reversing the corpus*: documents arrive as sequences of terms, but a query needs to ask which documents contain a term without scanning every document. The inverted index performs that reversal, storing only the term-document relationships actually observed, in an order that makes Boolean intersection — and later, scoring — efficient. It is not a search-specific database; it is a sparse matrix held as the nonzero entries of each row.

**Key concepts**

- **Term-Document Incidence is the conceptual contract.** With $V$ terms and $N$ documents, the incidence matrix $A$ has $A_{t,d} = 1$ when term $t$ occurs in document $d$ and $0$ otherwise. For d1 `vector search`, d2 `database search`, d3 `vector database`, the rows are `vector = [1,0,1]`, `search = [1,1,0]`, `database = [0,1,1]`. A Boolean AND is then a row-wise logical AND: `[1,0,1] AND [0,1,1] = [0,0,1]`, returning d3. The model is clean and generalises straight to counts or weights instead of bits.
- **Why Matrices Do Not Scale: almost every cell is a zero you paid for.** Take $N = 10^8$ documents and $V = 10^7$ distinct terms. The dense matrix needs $NV = 10^{15}$ cells; at one bit each that is $10^{15}/8 = 1.25 \times 10^{14}$ bytes, about **125 TB** of a structure whose content is overwhelmingly "no". Now count what is actually true: if each of the 100 million documents contains 300 distinct indexed terms, the nonzero pairs number $10^8 \times 300 = 3 \times 10^{10}$ — 30 billion. Large, but $10^{15} / (3\times10^{10}) \approx 33{,}000$ times fewer entries, and compression later shrinks their ordered document IDs further.
- **Scanning a dense row is also the wrong cost curve.** If `quokka` occurs in 20 documents, reading its 100-million-bit row spends essentially all its work proving absence, while a sparse representation stores those 20 document IDs directly. Query cost should scale with **occurrences, not corpus size**.
- **Dense bitmaps are not useless — density decides.** For a frequent Boolean attribute such as `language=en` or `published=true`, one bit per document is compact, intersections process whole machine words or SIMD vectors, and compressed formats exploit long runs. Sparse postings for terms with few matches; bitmaps for dense filter sets under repeated bitwise operations. The matrix stays the contract either way — a postings list is just the column indexes where one row is nonzero.
- **The Inverted Index has exactly two components: Dictionary and Postings.** The **dictionary** maps each normalised term to metadata plus a pointer or byte offset; the **postings list** holds the ordered document IDs where that term occurs. With d1=1, d2=2, d3=3 the whole index is `database -> [2, 3]`, `search -> [1, 2]`, `vector -> [1, 3]`. "Inverted" is relative to the forward representation, document to terms. Postings alone cannot reconstruct the text, so engines keep stored fields or a document store beside them.
- **Construction is IR 100's sorting problem wearing new labels.** Analyse each document into normalised tokens, emit occurrence tuples `(term, doc_id, position)`, sort by that tuple, group equal terms. For d1 `vector search` the emissions are `(vector,1,1)` and `(search,1,2)`. Once sorted, equal terms and increasing document IDs are adjacent, so the builder streams postings to disk and records each list's byte offset in the dictionary.
- **Document frequency and collection frequency are different numbers.** $df_t$ counts the documents containing $t$ — it is 2 for every term in the toy corpus — while collection frequency counts total occurrences. A document repeating `vector` ten times contributes **one** to document frequency and **ten** to collection frequency.
- **Payload is optional and every field is paid for.** A richer posting is `vector -> [(doc=1, tf=1, pos=[1]), (doc=3, tf=1, pos=[1])]`. Sorted document IDs enable intersection and gap compression; positions enable phrases; term frequency enables ranking. Each costs storage and decode time, so an index omits what the product never uses.
- **The dictionary is small; the postings are not.** One entry per *term*, not per term-document pair — but a noisy corpus mints millions of one-off strings, so normalisation and quality filtering are memory decisions as well as relevance ones. Implementation follows IR 100: a hash table for exact lookup, a sorted array or FST for compact storage and prefix enumeration.
- **Query and index must be analysed the same way.** Looking up `vector` means analysing the query with the indexing analyser, finding normalised `vector` in the dictionary, seeking to its offset, decoding `[1,3]`, then fetching or scoring. If the two normalisations differ, a logically present term misses, because the lookup key differs.
- **Boolean Query Processing by Intersecting Postings is the two-cursor merge.** Compare the two current document IDs; emit on equality and advance both, otherwise advance the cursor on the smaller ID. With lengths $m$ and $n$ the work is $O(m+n)$ with constant state. On `vector -> [1,3,7,10,14]` and `database -> [2,3,6,10,12,14]`: 1 vs 2 advance `vector`; 3 vs 2 advance `database`; **match 3**; 7 vs 6 advance `database`; 7 vs 10 advance `vector`; **match 10**; then **match 14**. Result `[3,10,14]`.
- **OR and NOT reuse the same walk.** OR emits the union: on equality emit once and advance both, otherwise emit the smaller and advance it. NOT needs a universe — `vector AND NOT database` subtracts, giving `[1,7]`. Materialising a rare term's complement over all document IDs is ruinous, so negation is applied as *exclusion while traversing a positive candidate list*.
- **Multi-term AND composes because intersection only shrinks.** Intersect a pair, then intersect that result with the third list; the intermediate is already sorted and compatible with the next merge. A multiway implementation advancing several cursors toward the current maximum ID obeys the same principle.
- **Skipping helps imbalance, not volume.** Skip pointers or exponential advances jump a lagging cursor, and modern codecs store block maximum IDs so a decoder skips whole blocks without expanding every integer. But skipping has overhead and cannot avoid *output* work: two dense, equal lists still produce many matches. Representation can switch too — two dense bitmaps intersect faster word-wise than cursor-merging millions of IDs.
- **Boolean retrieval is a set, not a ranking.** AND returns the documents satisfying a logical condition with no inherent order. A ranked engine may use "should" semantics where matching more terms raises a score without being required.
- **Query Optimization: Processing Rarest Terms First.** Document frequency predicts postings length, and an AND result can never contain more documents than the shortest list — so start there. Given `the` $df = 80{,}000{,}000$, `database` $df = 2{,}000{,}000$, `vectorized` $df = 5{,}000$: intersecting `the` with `database` first scans roughly **82 million** postings and builds a large intermediate that `vectorized` then discards almost entirely. Starting with `vectorized` yields at most **5,000** candidates to probe against the others. The final Boolean set is commutative; execution cost is not.
- **Pick the join style from the size ratio, not from habit.** Similarly sized lists merge sequentially. A tiny list against an enormous one is better served by iterating the tiny candidates and seeking or galloping within the large list — binary search inside the postings, exactly IR 100's cost model. Worked plan for `neural vector database` with frequencies 500,000, 200,000 and 2,000,000: order `vector`, `neural`, `database`; if the first intersection returns 700 IDs, everything downstream works on 700 candidates.

**Rules to remember**

- The incidence matrix is the semantics; postings are the storage. One row's nonzero column indexes *are* its postings.
- Dense costs $NV$ regardless of content; sparse costs one entry per observed pair. $10^{15}$ versus $3\times10^{10}$ is the whole argument.
- Postings are stored in increasing document ID order; intersection and gap compression both depend on it.
- Document frequency counts documents; collection frequency counts occurrences.
- Intersection of two sorted lists is $O(m+n)$ with constant state — never $O(mn)$.
- AND intersects, OR unions, NOT excludes against a positive candidate list.
- Rarest term first for AND. The result cannot exceed the shortest list.
- Rarest-first does **not** transfer to OR: every list contributes results either way.
- Query-time and index-time analysis must match, or the lookup key does not exist.

**Common pitfalls**

- **Treating the inverted index as a different kind of database.** It is the sparse form of a matrix you can write down. Lose that view and term frequency, positions and weights look like unrelated features rather than payload on a nonzero entry.
- **Arguing sparsity from corpus size rather than per-document term counts.** The number that matters is distinct terms per document — 300, not 10 million.
- **Concluding bitmaps are always wrong.** For dense filters like `language=en` under repeated bitwise operations they win.
- **Confusing $df$ with collection frequency.** Ten occurrences in one document is $df = 1$.
- **Expecting NOT to be symmetric with AND.** The complement of a rare term is nearly the whole corpus; negation must be applied while traversing something positive.
- **Reading Boolean AND as a ranking.** It returns a set; order comes from a scorer not yet introduced.
- **Assuming rarest-first is unconditionally optimal.** It loses if the rare term's postings are expensive to reach remotely while a slightly larger list is already cached, or if the term is optional rather than required.
- **Trusting stale term statistics.** If an analyser change made a term common but metadata still calls it rare, the plan is built on a lie. Segment-level frequencies complicate this further: a term can be dense in one specialised segment and absent elsewhere, so aggregate or plan per segment.
- **Editing the index in place.** Updates normally create immutable segments merged in the background, with tombstones for deletions. The index is a *derived serving artifact*: keep stable document IDs and analyser versions so it can be rebuilt, and republish rather than repair.

**How to approach the questions**

1. For any scaling claim, compute both numbers. Dense is $N \times V$; sparse is documents times distinct terms per document. The ratio answers before any prose does.
2. When a question describes an intersection, ask what the cursors do on inequality. Advancing the *smaller* ID is the invariant, and distractors advance the larger or advance both.
3. For ordering questions, sort the terms by $df$ and check the bound: the answer set cannot exceed the shortest list. Then check whether the operator is really AND — the argument evaporates under OR and under negation.
4. Watch for a size *ratio* clue. Similar lengths mean merge; a 5,000-versus-80,000,000 gap means probe or gallop, usually hidden in one clause.
5. Separate semantics from cost. "Does the result change?" and "does the work change?" have different answers for query ordering, for bitmaps versus postings, and for skip pointers.
6. If a scenario mentions phrases or adjacency, the Boolean stage only produces *candidates* — positions decide, and that is a later lesson.
7. Be suspicious of absolutes. "Always use postings", "always start with the rarest term" and "matrices are useless" each fail on a case named above.
