1. From Merge To Postings

Big-O of Intersecting Two Sorted Lists and Memory Hierarchy: Why Sequential Access Beats Random Access already costed this machine out in IR 100. Flip the label on the same two arrays and you have Boolean retrieval. Then drag a term's document frequency and see what the dense matrix would have charged instead. Like a stocktake: counting the twenty crates you have beats ticking "none" against every item in the catalogue.

The invariant to carry forward: query cost should scale with occurrences, not with corpus size. The dense row does identical work for every term in the vocabulary — which is why the incidence matrix is a contract to reason with and never a structure to store.

2. The Matrix Does Not Fit

The term-document incidence matrix is the semantics of Boolean retrieval — tap two term rows and combine them. Then scale the same idea up and watch it become 125 TB of mostly "no". Like a school register with a column for every pupil on Earth: perfectly correct, and unprintable.

Keep the matrix as the conceptual contract and never as the storage. A postings list is exactly the column indexes where one row is nonzero — so adding term frequency, positions or weights enriches those nonzero entries without changing the reversal at all.

3. Build The Dictionary

Indexing is IR 100’s sorting problem wearing new labels: emit one tuple per occurrence, sort, group. Step through it on the three-document corpus, then choose how much payload each posting carries. Like alphabetising a pile of index cards — the sort is what puts every mention of a word next to every other one.

The dictionary holds one entry per term, not per term-document pair, so it stays small enough to keep hot — a hash table for exact lookup, a sorted array or FST where compact storage and prefix enumeration matter. A noisy corpus is what breaks that: millions of one-off strings make normalisation a memory decision as much as a relevance one.

4. Two Cursors Stepping

One comparison at a time on the worked lists. Pick an operator and step: the rule never changes — emit on equality, otherwise advance the cursor sitting on the smaller document ID. Like two fingers running down two sorted guest lists, always moving the one that is behind.

Solid outline = cursor here  ·  dashed + faded = already passed  ·  bold green = emitted to the result

Skip pointers, exponential advances and block-maximum IDs can jump a lagging cursor when the lists are badly imbalanced — but skipping carries overhead and cannot avoid output work: two dense, equal lists still match on nearly every step. Note too what this panel never produces: an order. Boolean AND returns a set; ranking is a different question, and a ranked engine may use "should" semantics where matching more terms merely raises a score.

5. Rarest Term First

Same three terms, same answer set, wildly different bills. Reorder the plan with the ▲ buttons, then change how each pair is joined. Like packing a suitcase: put the bulkiest thing in first and you repack everything; start with the smallest and it never gets in the way.

Document frequency is the stable first approximation, not a latency model. A cost-based optimiser also weighs where the postings live, whether they are cached, how they compress and what the operator means — a rare term fetched from remote storage can lose to a slightly larger list already in memory. And the whole argument is AND-only: under OR every list contributes results, so ordering moves heap use and deduplication, never eligibility.
