**The big idea**: **The Inverted Index: Dictionary and Postings** gave you the structure that answers a query, and **Boolean Query Processing by Intersecting Postings** with **Query Optimization: Processing Rarest Terms First** made that answer cheap, while **Term-Document Incidence and Why Matrices Do Not Scale** explained why the postings list had to exist at all. Every one of those mechanisms begins with a *lookup key*, and not one of them says where the keys come from. That is this lesson. An inverted index can retrieve only the keys its analyzer creates: splitting `Cloud Run`, folding case, removing `the`, or reducing `policies` to `polici` changes which surface forms become the same lookup key and which distinctions disappear permanently. Text analysis is therefore relevance modelling performed at index-construction time — every normalization buys matches while risking false equivalence — and query analysis must reproduce the same contract, or the two halves of the lookup never meet.

**Key concepts**

- **Tokenization Choices and Their Retrieval Consequences: the tokenizer fixes the vocabulary, so it fixes what is findable.** Tokenization segments an input character sequence into indexable units and assigns positions and offsets. Whitespace splitting is a useful toy that fails on punctuation, scripts without spaces, URLs, product names and code. On `C++ guide for node.js in Asia-Pacific` a whitespace tokenizer yields `C++`, `guide`, `for`, `node.js`, `in`, `Asia-Pacific`; a punctuation-splitting tokenizer yields `C`, `guide`, `for`, `node`, `js`, `in`, `Asia`, `Pacific` — destroying the exact identifiers `C++` and `node.js` while improving matches for `Pacific`. Neither output is inherently correct; correctness depends on query behaviour.
- **Token boundaries trade exact lookup against component retrieval.** Treating `state-of-the-art` as one token supports an exact lookup but misses a query for `state art` unless extra forms are indexed; splitting it supports component retrieval but changes phrase positions and may overmatch unrelated uses. The common escape emits several tokens at the same or carefully managed positions — preserve `node.js` and also emit `node` and `js` — which raises recall and index size together.
- **Worked comparison.** Documents contain `CloudRun`, `Cloud Run` and `cloud-run`. An analyzer that only whitespace-splits produces, after lowercasing, three incompatible forms: `cloudrun`, `cloud` + `run`, and `cloud-run` — so a `cloud run` query reaches exactly one of the three documents. A domain analyzer that preserves the originals *and* emits normalized `cloud` and `run` subtokens reaches all three, at the price of more postings and a noisier generic `run` query.
- **Language and domain choose the segmenter.** Chinese and Japanese normally lack spaces between every word, so dictionary or statistical segmentation is needed; character n-grams avoid committing to one segmentation but create more postings and less precise matches. Thai has its own boundary challenges. Code needs domain rules: `getUserProfile`, `get_user_profile` and `get-user-profile` can emit the complete identifier plus subtokens `get`, `user`, `profile`; version strings such as `v1.2.3`, IPv4 addresses, emails and URLs may deserve structured tokens. Numeric policy is a real dial: retaining every timestamp and UUID explodes the vocabulary with one-off terms, dropping all numbers loses error codes.
- **Positions and offsets are outputs, not incidental metadata.** Positions later support phrase queries; offsets highlight matching spans and must refer to the original character sequence even after normalization. A tokenizer emitting subtokens must place them deliberately, or it invents phrases nobody wrote.
- **When Stemming Helps Recall and Hurts Precision: a stem is an equivalence key, not a word.** Stemming applies heuristic rules to reduce related word forms to a common stem: a Porter-style English stemmer maps `connect`, `connected`, `connecting` and `connection` toward `connect`, and `policy` and `policies` toward `polici`. The stem need not be a valid word. Applied at both index and query time, it lets a query for `connect` match a document containing only `connected`, because the morphological variants now share one postings list. Without it those surface forms are separate terms unless the query expands them explicitly.
- **The same merging costs precision.** **Overstemming** collapses distinct concepts onto one key — organization names and technical identifiers are especially vulnerable. **Understemming** is the opposite failure: genuinely related forms stay separate, such as irregular `go` and `went`.
- **Worked corpus, with the arithmetic.** d1 says `connection timeout`, d2 says `connected clients`, d3 says `connective tissue`; the query is `client connection`. Unstemmed, `clients` is not `client` and `connected` is not `connection`, so only d1 is retrieved: against a networking judgment of {d1, d2} that is precision $1.0$, recall $0.5$. Porter-style stemming retrieves d1 and d2 — precision and recall both $1.0$. A broad stem that merges every `connect*` form also admits d3: recall stays $1.0$, precision falls to $2/3$ — and in a biomedical collection where only d1 is relevant, to $1/3$. Identical machinery, opposite verdict, decided entirely by the collection.
- **Stemming changes document frequency, so it changes ranking.** Over that three-document corpus the query key's df moves with the analyzer: unstemmed `connection` has df $= 1$, so $\text{idf} = \log_{10}(3/1) = 0.477$; Porter's `connect` has df $= 2 \Rightarrow \log_{10}(1.5) = 0.176$; the broad stem has df $= 3 \Rightarrow \log_{10}(1) = 0$ — the term has stopped discriminating between documents at all. Scores from stemmed and unstemmed indexes are therefore not comparable, and an analyzer migration means reindexing and re-evaluation, not enabling a query-side option.
- **Lemmatization is the linguistic alternative, and neither solves synonymy.** Lemmatization maps inflected words to dictionary lemmas — `was` to `be`, `mice` to `mouse` — avoiding some crude suffix errors at higher cost and with a dependence on language and part of speech. Neither technique makes `car` match `automobile`; that needs expansion or semantic retrieval. The practical answer is multi-field: an unstemmed field for product codes, citations and names, a stemmed field for prose, and separate scoring weights.
- **Stop Words: Space Savings vs Phrase-Query Damage.** Stop words are very frequent function words such as `the`, `of` and `to`. In a 100-million-document corpus where `the` occurs in 80 million documents, its inverse document frequency is $\log_{10}(100/80) = 0.097$ — next to nothing beside a term in 1,000 documents at $\log_{10}(10^5) = 5$. Dropping it removes 80 million postings and the work of decoding them. But modern compression makes dense postings cheap per document and engines can skip low-impact common terms, so the saving may not justify what it costs.
- **Removal is irreversible for anything that depends on those terms.** If the index drops `to` and `be`, the phrase `to be or not to be` cannot be verified from positions, because the required postings do not exist. `The Who`, `The Hague`, code symbols and legal phrases show that frequent words can be decisive in context — and a stop list is language- and domain-specific: `can` is a container noun as well as grammar, and `os` is not noise in a corpus about operating systems.
- **Position increments are the subtle half.** Take `state of the art` with `of` and `the` removed. If the retained tokens are renumbered `state:1, art:2`, the index has invented the exact phrase `"state art"`. Correct position increments preserve the gaps — `state:1, art:4` — so the phrase query fails at slop zero, which is the right answer, though the removed words still cannot be verified individually. The middle path is to omit them from the general body field while keeping an exact phrase field that retains everything.
- **Normalization: Case, Accents, and Equivalence Classes.** Normalization maps surface strings into equivalence classes before dictionary lookup. Lowercasing makes `Cloud`, `CLOUD` and `cloud` one key. Unicode normalization resolves code-point sequences that render identically — composed `é` versus `e` plus a combining acute — which must not become different terms by accident. Case folding is broader and more language-aware than ASCII lowercasing, and case can carry meaning: `US` versus `us`, `Apple` versus `apple`, identifiers in case-sensitive code.
- **Accent folding and compatibility folding buy recall and can erase meaning.** `café` toward `cafe` helps users who omit diacritics and can merge distinct words in languages where accents change meaning. NFKC maps compatibility characters such as full-width Latin to common forms, and can erase distinctions that matter in mathematical or technical text. Worked example: `Résumé`, `resume` and `RESUME` all fold to `resume`, maximising recall — but if the query means the French noun and the English verb is common, precision falls. Indexing the exact token *alongside* the folded one lets exact matches be weighted up while folded matches stay candidates.
- **Order and idempotence are part of the design.** Each transformation should be idempotent — applying it twice yields the same token — and Unicode normalization belongs before case and accent handling, because ad hoc byte replacement never sees the decomposed form. Equivalence extends past characters to punctuation folding, possessive removal and URL canonicalization. Normalization must be identical at index and query time; store the analyzer configuration version with the index, and during migration either analyze per segment version or rebuild and cut over atomically.

**Rules to remember**

- The analyzer is a contract: whatever runs at index time must run at query time, or the lookup silently misses.
- A term the tokenizer never emitted can never be retrieved, at any ranking quality.
- Stemming raises recall by merging postings and lowers precision by merging concepts. Overstemming merges too much, understemming too little.
- Any equivalence change alters document frequency, so it alters ranking. Reindex; do not compare scores across analyzers.
- Removing stop words destroys phrase, name and citation queries that need them. Position increments limit the damage but never restore the terms.
- Normalize Unicode first, then case, then accents, and keep every step idempotent. Normalized terms are lookup keys, never replacements for the source text.
- The general answer to a precision/recall conflict is a second field, not a more aggressive global rule.

**Common pitfalls**

- **Assuming one tokenization is "correct".** Both outputs on `node.js` are defensible; only the query workload decides.
- **Applying an English regular expression to multilingual text.** Recall goes uneven by language and looks like a ranking bug.
- **Turning stemming on at query time only.** The index still holds unstemmed keys, so the two sides disagree and matches vanish.
- **Judging an analyzer by a mean metric.** Averages hide total failures on acronyms and proper nouns — measure per query class.
- **Renumbering positions after stop-word removal.** It manufactures phrases that were never written, which is worse than missing them.
- **Applying a generic stop list after normalization.** `US` has already become `us`, and it is about to be deleted as a pronoun.
- **Folding accents globally because it helped one query set.** In languages where accents change meaning it merges different words permanently.
- **Changing an analyzer without reindexing.** Old and new segments answer under different rules: systematic, silent misses.

**How to approach the questions**

1. Ask first *which strings become the same key* under the change. Almost every answer follows.
2. Sort the effect into recall or precision before choosing an option — merging keys buys recall and spends precision; splitting keys does the reverse.
3. When a scenario mentions a phrase, a name, an acronym or a code symbol, check whether the analyzer still has the postings to verify it. Stop-word removal and aggressive folding are the usual culprits.
4. Watch for the index-time versus query-time mismatch. If only one side changed, the answer is "nothing matches", regardless of how sensible the change was.
5. For anything involving score or rarity, remember that merging forms raises df and lowers the term's discriminating power.
6. Prefer answers that add a field or a variant token over answers imposing one global rule.
7. Treat "and then we reindexed" as a load-bearing clause. If it is missing from a migration scenario, that is the defect being tested.
