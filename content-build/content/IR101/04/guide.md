**The big idea**: **The Inverted Index: Dictionary and Postings** handed you a finished structure, and **Boolean Query Processing by Intersecting Postings**, **Query Optimization: Processing Rarest Terms First** and **Skip Pointers: Faster Intersection for Extra Storage** all quietly assumed it was already there — sorted, complete, and holding still. **Positional Indexes and Their Size Cost** made it much bigger, and **Tokenization Choices and Their Retrieval Consequences** decided what its keys would be. This lesson is the part none of that could do: an inverted index is too large to assemble as one in-memory term map, and a production corpus does not stop changing after its first build. So construction creates *sorted immutable pieces under a memory bound*, and update policy decides when to *merge* those pieces or *replace* the whole index. These are not maintenance details. They govern freshness, query fan-out, write amplification, recovery, and whether a failed build can safely resume.

**Key concepts**

- **Blocked Index Construction: Build Runs, Merge Runs — bound the memory, then sort your way out.** Blocked sort-based indexing partitions the input into blocks that fit a controlled memory budget. Per block: parse documents through the *versioned* analyzer; emit occurrence records `(term, doc_id, position)`; sort by term, then document ID, then position; group into a partial dictionary and postings lists; write an immutable sorted run. Without the block boundary there is no bound at all — random insertion into one giant postings structure, and the build dies on the first corpus that outgrows RAM.
- **Merge runs: the final index is one sequential pass over immutable files.** Take the worked three-run example. `run A: cloud->[1,4], vector->[2]`; `run B: database->[5], vector->[3,6]`; `run C: cloud->[8], search->[7], vector->[9]`. A three-way term merge emits `cloud -> [1,4,8]`, `database -> [5]`, `search -> [7]`, `vector -> [2,3,6,9]`. Equal terms from different runs meet in the merge and their *already sorted* postings are merged into one list; only the current term heads and postings buffers are ever active. The final writer records dictionary offsets and encodes document and position gaps.
- **The cost, derived.** If total emitted occurrences are $T$ and a block holds $M$, you get roughly $\lceil T/M \rceil$ runs. Sorting one run costs $O(M \log M)$, so all runs together cost $(T/M) \cdot O(M \log M) = O(T \log M)$ — cheaper than the $O(T\log T)$ of one impossible global sort, because the $\log$ is over the *block*, not the corpus. Numerically, $T = 10^9$ with $M = 5\times10^7$ gives 20 runs and $\log_2 M \approx 25.6$ against $\log_2 T \approx 30$. The external merge then processes every occurrence through one or more levels, I/O proportional to the dataset per level, memory still bounded.
- **Local aggregation shrinks the run before it is written.** If `vector` occurs five times in one document, the block combines those occurrences into one posting carrying five positions. Duplicate documents and repeated ingestion are a *different* problem: resolve them with stable source IDs and build policy, never by hoping the merge recognises semantic duplicates.
- **Parallel builds need deterministic IDs and one analyzer version.** Workers own disjoint document-ID ranges or input partitions. Let one assign IDs from a local counter, or run a different tokenizer, and the merge produces collisions or inconsistent keys. A manifest records each run's input scope, checksum, record counts, minimum and maximum term, analyzer version, and completion state.
- **Recovery is a property of immutability.** Write a run under a temporary name, validate counts and checksum, then add it to the manifest. A retry of the same deterministic block either reuses the committed run or replaces the uncommitted temporary artifact. Publish only after all expected blocks and validation gates pass, and reconcile source, indexed, rejected, vocabulary, postings and byte counts before cutover — a syntactically valid index can still omit an entire input block.
- **Merge-Based Dynamic Index Updates (Logarithmic Merge): a binary counter made of indexes.** Rebuilding the whole corpus per arrival is wasteful, so keep a hierarchy of immutable indexes with geometrically growing capacities: level 0 holds up to $B$, level 1 up to $2B$, level 2 up to $4B$. New documents form a small sorted level-0 segment; if L0 is occupied, merge the two size-$B$ segments into one size-$2B$ segment at L1; if L1 is occupied, merge again and carry. With $B = 1{,}000$: batch 1 leaves 1,000 at L0; batch 2 collides at L0 and merges into 2,000 at L1; batch 3 occupies L0 and leaves L1 alone; batch 4 makes 2,000 at L1, collides, and carries into 4,000 at L2.
- **Why that shape wins.** After $N$ base batches at most one segment sits per level, so there are $O(\log N)$ segments, and a document is rewritten at most once per level as merges carry it upward — $O(\log N)$ write amplification in the simple model, instead of rewriting the corpus on every batch.
- **What it costs on the read side.** Queries search *all* live segments and merge the results: term lookup probes each segment dictionary, then Boolean or ranked results combine document IDs and scores. Logarithmically many levels bounds this, but every extra segment adds seeks, probes, duplicate resolution and per-segment statistics. Background merging trades write I/O for lower query fan-out.
- **Versions and tombstones are what make updates and deletes correct.** A newer segment can hold a replacement for a stable document ID while the old content still exists below, so queries must prefer the newest version or consult a live-doc/version map. A delete writes a **tombstone** that suppresses older postings; the record disappears physically only when a merge includes both the tombstone and the obsolete data. Until then, tombstones and superseded postings consume space and query work.
- **Merging segments, and committing safely.** Walk both term dictionaries in order; for equal terms merge the sorted postings, resolving duplicate document IDs by generation; terms on one side only pass through. Because output is new and immutable, readers keep using the old segments until the new one is validated and a manifest *atomically* replaces the old set. Concurrency needs generation IDs: a merge snapshots its inputs, later arrivals land in another segment and are not lost, and at commit you verify the inputs are still live. Garbage-collect only when no reader references the old segments.
- **Rebuild vs Merge: Index Update Strategy Tradeoffs — a cost and correctness decision, not a maturity ladder.** A **full rebuild** reads the authoritative corpus and constructs a new index from scratch: one coherent artifact under one analyzer and schema version, deletes and fragmentation physically gone, drift self-healed because output is derived again from source, validation and rollback simplified by build-version aliases. Its weaknesses are latency, compute, temporary storage and freshness — a ten-hour build cannot reflect events arriving during it without a snapshot plus catch-up delta, and rebuilding a petabyte for a 0.01% change is severe write amplification.
- **Incremental merge is the mirror image.** Low update latency, work proportional to changes plus merge amplification, a natural fit for continual ingestion — paid for in operational state: segments, tombstones, version precedence, backlog, mixed analyzer generations. Bugs and missed deletes persist until reconciliation.
- **The worked decision.** A 10-million-document research corpus changing 5,000 documents daily is a 0.05% delta: a nightly full rebuild rewrites all 10 million for it, so small daily segments plus scheduled merging win, with a monthly rebuild or source-to-index reconciliation to bound drift. Invert the numbers — a 50,000-document policy corpus, changed weekly, building in four minutes — and full replacement is simpler, self-healing and probably cheaper than permanent merge machinery.
- **Compare costs explicitly, then add what arithmetic misses.** With corpus size $S$, daily changed bytes $\Delta$ and merge write amplification $W$, incremental daily write cost is roughly $W\Delta$ and rebuild is roughly $S$ plus temporary output. Then add query read amplification, operational labour and incident risk; when $S$ is small enough that rebuild is routine, simplicity has measurable value.

**Rules to remember**

- Blocks bound memory; runs are immutable and sorted; the merge is sequential, never random insertion.
- Roughly $\lceil T/M \rceil$ runs, $O(T \log M)$ sort work, memory bounded by $M$. Bigger blocks mean fewer runs and less merge work, but higher peak memory and a costlier retry.
- Deterministic document IDs plus one analyzer version are preconditions for parallel builds, not niceties.
- Commit through a manifest: temp name, validate counts and checksum, then publish. Never expose a directory mid-replacement.
- Logarithmic merge: capacities $B, 2B, 4B, \dots$; $O(\log N)$ segments; $O(\log N)$ write amplification; a batch can cascade like adding one to a binary counter.
- Every live segment is searched on every query. Merging trades write I/O for read fan-out; the knobs are size ratio, level versus tier, merge concurrency and throttling.
- A delete is a tombstone until a merge sees both it and the data it suppresses.
- Analyzer or schema changes force reprocessing — a merge cannot invent positions that old postings never stored.
- Large deletion waves (say 40% removed) favour rebuild; small frequent deletes favour tombstones plus normal compaction.
- Atomic cutover is required either way: alias switch after shadow validation, or a new segment manifest after the output is durable.

**Common pitfalls**

- **Treating a bigger block as free.** It cuts run count and merge work while raising peak memory and retry cost. Budget for token strings, positions, sort pointers, runtime overhead and output buffers — and cap or safely spill unusually long documents rather than crashing the block.
- **Assuming the merge will deduplicate.** It resolves *sorted postings*, not semantic duplicates. Repeated ingestion without stable source IDs indexes the same document twice.
- **Believing "the index built" means "the index is right".** A missing input block leaves a perfectly valid index. Reconcile the counts.
- **Reading logarithmically many segments as free queries.** Bounded is not zero: each segment adds probes, seeks, duplicate resolution and its own statistics.
- **Forgetting tombstones cost space and work until compaction.** Deleted-but-not-merged data is still read past on every query.
- **Merging across analyzer generations.** Mixed tokenization or stemming means inconsistent keys and term statistics — a retrieval bug that looks like a ranking bug.
- **Calling incremental the mature choice.** For a small corpus that rebuilds in minutes, permanent merge machinery is the expensive option.
- **Replacing files in place.** Mixed dictionaries and postings offsets corrupt reads. Publish a new version, switch atomically.

**How to approach the questions**

1. Ask first whether the scenario is *construction* (one bounded build, blocks and runs) or *update policy* (a live index absorbing change). The vocabulary overlaps and the right answers do not.
2. For sizing questions, reach for $\lceil T/M \rceil$ and $O(T \log M)$, and state both sides of the block-size dial — fewer runs versus higher peak memory.
3. For logarithmic merge, run the binary counter by hand with $B = 1{,}000$; the cascade at batch 4 is where distractors live.
4. Separate write amplification from read amplification: aggressive merging lowers the second and raises the first, delayed merging the reverse.
5. When a question involves deletes, ask whether a merge has yet seen both the tombstone and the data. Until then the bytes are still there.
6. For rebuild-versus-merge, compute $W\Delta$ against $S$ — then check for a *trigger* that overrides the arithmetic: analyzer or schema change, a high deleted-byte ratio, unexplained count drift, or cumulative merge cost approaching replacement cost.
7. Prefer the hybrid answer when offered: incremental segments for freshness, merges to control fan-out, periodic reconciliation or rebuild to prove the index still matches source truth.
