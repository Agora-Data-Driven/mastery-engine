**The big idea**: **The Inverted Index: Dictionary and Postings** gave you the artifact; **Boolean Query Processing by Intersecting Postings** made it a two-cursor walk over strictly increasing document IDs; **Positional Indexes and Their Size Cost** multiplied the bytes; **Skip Pointers: Faster Intersection for Extra Storage** bought jumps with storage; **Blocked Index Construction: Build Runs, Merge Runs** and **Merge-Based Dynamic Index Updates (Logarithmic Merge)** wrote it all out in sorted runs. This lesson pays the bill. Those billions of document IDs and positions sit *directly on the query path*, so compression is a speed feature as much as a storage one: fewer bytes fit in cache, cross a storage boundary faster, and stay memory-resident. The technique is three moves — exploit the sorted order you already guaranteed, turn large absolute IDs into small gaps, and encode small positive integers with a representation whose decode cost is predictable.

**Key concepts**

- **A gap is a subtraction; decoding is a prefix sum.** Document IDs are strictly increasing within a segment, so store $g_1 = d_1$ and $g_i = d_i - d_{i-1}$ for $i > 1$. IDs `[1000, 1003, 1007, 1012]` become gaps `[1000, 3, 4, 5]`; decoding walks forward — 1000, then $1000+3=1003$, $1003+4=1007$, $1007+5=1012$. It is lossless as long as order and the initial base survive.
- **Why it pays is a distribution argument you can derive.** Absolute IDs grow with corpus size and need 32 or 64 bits; gaps depend only on postings *density*. A term in $df$ of $N$ documents has gaps summing to at most $N$, so the mean gap is at most $N/df$ — one document in ten gives mean gap 10, magnitude $\lceil \log_2 11 \rceil = 4$ bits, **whether the corpus holds ten thousand documents or a billion** (where an absolute ID already costs 30 bits).
- **Worked cost.** Four 32-bit IDs are 128 bits; under variable-byte, 1000 takes two bytes while 3, 4 and 5 take one each — five bytes, **40 bits**, ignoring a small block header. Frequent terms cost fewer bits *per posting*, rare terms simply have fewer postings, so total size reflects both document frequency and bits per gap.
- **Positions delta-encode the same way and reset per document.** Positions `[2, 10, 20]` become `[2, 8, 10]`, and the next document starts a fresh base. Term frequency tells the decoder how many position gaps belong to the current posting — without it the stream cannot be parsed. Any monotone sequence, such as offsets into the postings file, behaves identically.
- **Sorted order is not a convenience, it is the format.** An out-of-order ID produces a *negative* gap, unrepresentable in most postings codes and fatal to monotone traversal. Duplicate IDs must be combined into one posting carrying several positions; a zero document gap may be representable, but it violates the one-posting-per-term-document contract.
- **Large gaps stay large.** Gap encoding exposes local scale; it does not promise small integers. Block formats respond with a bit width per block, exceptions for outliers, or mixed schemes. Segment boundaries also reset the document-ID base, so many small segments compress worse than one globally ordered list while being far more updateable — the tradeoff logarithmic merge already made.
- **Compression and skipping are one design problem.** To jump into a delta stream the decoder needs a known absolute base at a block boundary *plus* a byte offset, so blocks carry metadata — last document ID, count, compressed length — and skipping to a block avoids decoding every preceding gap. That is what keeps skip pointers usable after compression.
- **Corruption's blast radius is "everything after".** One damaged gap shifts every later prefix sum, so formats bound it with block checksums and restart points, and build tests check monotonicity and decoded counts.
- **Document-ID assignment is a compression lever with a correctness ceiling.** Give topically or temporally related documents nearby IDs and many postings become locally dense; random IDs destroy that locality. But assignment must stay stable across rebuilds and must not make authorization or deletion brittle — compression is secondary to identity correctness. Segment-local remapping raises density behind a stable external ID, at the cost of a mapping table to weigh against the bytes saved.
- **Variable-byte encoding spends seven payload bits per byte and one marker bit.** Under the common terminal-high-bit convention, values 0–127 need one byte, 128–16,383 need two, and values up to $2^{21}-1$ need three; polarity varies, so a format must document it. Encode by writing the integer in base 128: 5 is a single group; $130 = 1 \times 128 + 2$, so the groups are 1 and 2, the first marked continuing and the second terminal.
- **The byte count is a formula, and it steps.** With $b$ the bit length of $v$, $\text{bytes}(v) = \max(1, \lceil b/7 \rceil)$. So 1000 has $b=10 \Rightarrow 2$ bytes; 16,383 has $b=14 \Rightarrow 2$; 16,384 has $b=15 \Rightarrow 3$. Storage changes stepwise at 128, 16,384, and so on — never smoothly. Gaps `[1000,3,4,5]` are five bytes against sixteen fixed-width.
- **The decoder is a four-step loop.** Read a byte; accumulate its seven payload bits; if terminal, emit, else continue; for postings, add the gap to the previous ID.
- **What variable-byte buys, and what it costs.** It buys simplicity, byte alignment, no bit-level seek, and tolerance of mixed magnitudes — an outlier takes more bytes without widening its neighbours. It costs branchy decoding and one marker bit in eight, so tiny gaps burn eight bits to carry three or four. Block codecs bit-pack at a shared width and decode with SIMD, usually beating it on ratio *and* throughput; variable-byte survives where simplicity or random restart matter more.
- **Pin the conventions; random access needs blocks.** A decoder expecting terminal-high-bit cannot read continuation-high-bit data, so formats carry magic/version metadata and golden byte-level test vectors. And seeking into a raw stream is poor — byte position $p$ may land mid-integer, and preceding gaps determine absolute IDs — hence block indexes recording a compressed offset plus an absolute or previous ID, then sequential decode inside the block.
- **Postings compression and Parquet encodings run one principle:** a cheap reversible transform that exposes low entropy, then bits spent by residual magnitude or repetition. Delta-encoded document IDs are the idea behind Parquet `DELTA_BINARY_PACKED` timestamps; dictionary-encoded column values mirror mapping terms into compact integer IDs; RLE pays on repeated small codes either side. Worked parallel: postings IDs `[1000,1003,1007,1012]` become gaps `[1000,3,4,5]` then variable-byte or block packing, and the same sorted timestamps in a Parquet page take the same delta transform and bit packing — while a `status` column of four strings becomes 2-bit dictionary indexes with RLE over equal-index runs.
- **The access path is the real difference.** Search traverses postings *during an interactive query*, intersecting, skipping blocks, accumulating scores — so decode latency and jumping without expanding everything are critical. Parquet analytics reads column pages into vectorized batches and applies predicates; reaching one value inside a page is not central. Grain differs too: postings are partitioned by term and hold monotone IDs with optional nested positions, while Parquet stores columns within row groups and needs repetition and definition levels. Row-group statistics prune before page decode; postings dictionaries and skip metadata identify the relevant lists and blocks.
- **General-purpose codecs sit in different places.** Snappy or Zstd may compress Parquet pages *after* type-aware encoding, whereas search leans on specialized integer codecs because decoding lies in the scoring loop and a whole-stream codec destroys skip granularity. Sortedness helps both: document order is required for intersection *and* creates small gaps, while sorting a Parquet column tightens min/max statistics, creates runs and shrinks deltas.
- **Worked judgment: latency, not ratio.** A denser codec saving 20% loses if it doubles decode CPU on hot postings. So a hot term list read thousands of times a minute and frequently skipped by block wants a block integer codec with restart points and SIMD decoding, even if Zstd could make it smaller; a cold archival Parquet column read monthly justifies stronger Zstd, because storage savings amortize one slower decode. Benchmark real distributions, cache state, intersections and skips, and track compressed bytes per value and decode throughput.

**Rules to remember**

- Gap encode only what is sorted; decode with running prefix sums from a known base.
- Gaps scale with density ($\approx N/df$), not with corpus size — the entire argument.
- Term frequency delimits a posting's position gaps; drop it and the stream is unparseable.
- Variable-byte cost: $\max(1, \lceil b/7 \rceil)$ bytes, stepping at 128 and 16,384.
- One marker bit per byte is variable-byte's fixed tax; bit packing avoids it at the price of a shared width.
- Random access needs block metadata — absolute base plus compressed offset. Raw streams have none.
- Ratio is a means; the metric is work avoided per unit of CPU under the real read pattern.
- Delta, dictionary and run-length are shared vocabulary with Parquet; the access path is what differs, and a codec that must expand a whole stream to reach one posting is disqualified for search.

**Common pitfalls**

- **Believing gap encoding guarantees small numbers.** It exposes local scale only. A rare term still has huge gaps, and one outlier inflates a fixed-width block unless exceptions exist — so average gap alone is the wrong statistic.
- **Forgetting the base.** Segment boundaries reset it, and a block with no stored absolute ID needs everything before it decoded.
- **Letting duplicates or out-of-order IDs through.** They produce zero or negative gaps: at best a contract violation, at worst unrepresentable.
- **Assuming a variable-byte stream supports seeking.** Byte offset $p$ can land inside an integer, and even a clean landing yields a gap, not a document ID.
- **Mixing terminal-bit conventions.** The bytes decode to plausible garbage rather than failing loudly — hence version metadata and golden vectors.
- **Optimising ratio in isolation.** A 20% smaller list that doubles decode CPU is a regression on hot postings; whole-stream compression that kills skipping is worse still.
- **Treating Parquet and postings as one problem because the encodings share names.** Same transforms, different access path, grain and objective — a warehouse buys scan throughput and billed bytes, a search engine buys tail latency and cache residency.
- **Reordering document IDs purely for compression.** They must stay stable across rebuilds and must not make deletion brittle.

**How to approach the questions**

1. For any sizing question, compute both numbers: fixed-width bits versus gap bits times postings count. `[1000,3,4,5]` at 40 bits against 128 is the pattern.
2. For a variable-byte byte count, take the bit length and divide by seven, rounding up. Values sitting exactly at 127/128 or 16,383/16,384 are where the distractors live.
3. When a scenario says "random access" or "skip", ask what metadata sits at the block boundary. No absolute base or offset means sequential decode, whatever the codec.
4. If a claim compares two codecs, check whether it mentions decode CPU and cache state; a ratio-only argument is incomplete by construction. And for dense-versus-rare comparisons, separate bits per posting from number of postings — both move, usually in opposite directions.
5. On Parquet parallels, agree on the transform, then find the clause about *when the data is read*. Interactive selective decode versus vectorized batch scan decides nearly every such question.
6. Be suspicious of absolutes. "Always use variable-byte" and "compression always helps latency" each fail on a case above.
