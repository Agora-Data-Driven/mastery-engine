**The big idea**: **The Crawl Frontier: Prioritization and Queue Management** chose what to fetch next, **Politeness: Rate Limits, robots.txt, and Crawl Delay** chose how hard to push, **Crawler Traps and URL Canonicalization** stopped one page being fetched a thousand ways, and **Sitemaps, Feeds, and Change Notifications**, **Search APIs as an Acquisition Channel** and **Seed Selection and Crawl Scope Policy** decided where the URLs came from at all. All six end in the same place: bytes. Retrieval does not run on bytes. It runs on trustworthy text with structure and provenance, and nothing downstream repairs what this stage destroys — a perfect ranker cannot recover meaning erased by a broken PDF extractor, and an LLM will confidently quote a navigation menu if boilerplate dominates its chunks. Extraction is therefore a data-quality stage in its own right: typed inputs, versioned parsers, measurable failure signals, and an explicit decision per artifact to accept, retry, quarantine, or discard.

**Key concepts**

- **Main-content extraction identifies the DOM region carrying the page's primary semantic content; boilerplate removal strips the repeated site chrome around it.** The mechanism combines features. Text-dense blocks with long sentences and low link density are likely content; blocks dominated by short anchors are likely navigation. Semantic elements such as `<main>` and `<article>`, headings, paragraph counts, CSS classes and templates repeated across pages add signal. Readability-style algorithms score DOM subtrees, select a high-scoring ancestor, then clean unlikely descendants.
- **Link density is the workhorse feature, and it is just a ratio.** For a block, $\mathrm{LD} = (\text{characters inside anchors}) / (\text{total characters})$. A 300-link navigation tree at ~2 words a link is ~600 words that are *all* anchor text, so $\mathrm{LD} \approx 1.0$; article prose gives $\mathrm{LD} \approx 0.02$. One number, a fifty-fold separation, no markup conventions assumed.
- **Worked page.** A documentation page holds 1,200 words of article text, a 300-link navigation tree, 100 footer words and a 50-word cookie banner. Naive `document.body.innerText` produces perhaps 3,000 tokens, the navigation labels repeated on every crawled page. A main-content extractor selects the `<main>` subtree and keeps title, headings, paragraphs, lists and code — roughly the 1,200 useful words. With the chrome at ~870 words, only 58% of what the naive path indexes is the document.
- **Boilerplate harms twice.** It dilutes relevance: common navigation terms enter *every* document, inflating document frequency and returning wrong pages. And it manufactures near-duplicates, because thousands of pages share most of their template text — chunking the full body generates identical menu chunks that consume embedding and retrieval capacity for nothing.
- **Template learning marks DOM paths repeated on most pages as boilerplate — but repetition is not proof of uselessness.** A safety warning or a version banner repeated site-wide may be essential context; a unique advertisement evades every repetition rule. Keep metadata for removed regions, or sample them in quality review, so the rule is audited rather than trusted.
- **Client-rendered pages break the assumption that the fetched HTML contains the text.** The response may be only an application shell, the content arriving after JavaScript execution or an API call. A headless browser can render it, at the cost of money, attack surface, nondeterminism and wait-policy complexity. Prefer stable content APIs or embedded structured data where authorized; render only sources that need it, under sandbox and resource limits. **Worked failure:** extraction returns `Enable JavaScript to continue` — 30 words — while the rendered page is a full API guide. Low text length plus a shell phrase should trigger a rendered fallback or quarantine, not a success flag.
- **HTML to clean text is a second decision, about which structure to preserve.** The target is a stable, readable intermediate — Markdown-like text plus a structural map — not an undifferentiated string. Preserve: title and heading hierarchy (they supply context to child passages); paragraph and list boundaries, with ordered-list numbering where sequence matters; table rows and headers, because a cell's meaning depends on its row-column association; code blocks and inline code, with whitespace where syntax depends on it; links as anchor text plus destination, especially citations; and alt text and captions that carry content. Remove the presentation, never the organization: scripts, styles, hidden elements, tracking text and decorative labels go, entities are decoded and line endings normalized, but source offsets are retained so citations map back to the page.
- **Worked conversion.** `<h2>Limits</h2><p>Maximum batch size is <code>100</code>.</p><ul><li>Retry 429 responses.</li><li>Do not retry 400 responses.</li></ul>` becomes a level-2 heading `Limits`, the sentence with `100` still marked as literal code, and two bulleted peers. Flatten it to `Limits Maximum batch size is 100 Retry 429 responses Do not retry 400 responses` and you lose which statements are list peers and that `100` is code, not prose.
- **Tables need their own care.** A rectangular table converts to Markdown or to row records with headers repeated semantically; merged cells may need preserved HTML or structured JSON. A pricing table should yield `tier=standard, requests_per_minute=1000`, not a bag of numbers.
- **Emit a deterministic content hash after normalization, and never overwrite provenance with cleaned text.** Store URL, fetch time, content type, raw hash, extractor version, language and structural offsets. When a new parser turns the same raw page into different output, version and hash are both on record, so downstream chunks and embeddings are invalidated *deliberately* — and extraction reruns without refetching.
- **PDF is a page-description format, not a semantic one.** It stores glyphs at coordinates; reading order, paragraphs, tables and even spaces may be absent. Extracting text from PDFs therefore starts by asking whether the page carries an embedded text layer. If it does, parse glyphs and infer lines and blocks from coordinates. If not, render page images and run OCR.
- **Worked two-column page.** Visual reading order is the left column top to bottom, then the right. A naive extractor sorts every glyph by vertical coordinate and alternates left and right lines, producing nonsense. Layout-aware parsing clusters text into columns and blocks *before* ordering them. Headers and footers repeated at similar coordinates can be dropped while page numbers are kept for citation.
- **OCR introduces recognition errors that are silent and structural.** `O` versus `0`, `l` versus `1`, hyphenated line breaks and low-resolution scans corrupt exactly the identifiers and numbers queries key on. Store OCR confidence per page or span, the engine and version, and the rendered page reference. A page at 0.62 confidence should be retried at higher resolution or quarantined; 0.96 is fine.
- **Office formats are ZIP packages of XML — use format-aware parsers, never string extraction from the archive.** DOCX has paragraphs, styles, tables, headers, footnotes, comments and tracked changes (decide whether to accept revisions or expose both). PPTX needs slide order, text boxes, speaker notes and shape geometry, because XML order can differ from visual order. XLSX has typed cells, formulas, displayed values, merged cells and hidden rows.
- **Worked spreadsheet.** Cell B2 holds the formula `=A2*1.1`, the cached value `110`, and the header `Adjusted Price`. Emitting only `110` loses the logic; emitting only the formula may not answer the business question. Record sheet, cell coordinates, headers, value *and* formula.
- **Security is mandatory, not a hardening pass.** Documents carry macros, external links, decompression bombs, malformed objects and parser exploits. Parse in isolated workers with CPU, memory, page, file-count and decompressed-size limits. Never execute macros or follow external resources, and MIME-sniff rather than trusting the extension.
- **Extraction quality is multidimensional, so the judgment runs off a quality record.** Useful signals: text yield per page and against file size, replacement-character ratio, language confidence, OCR confidence and the fraction of low-confidence spans, repetition (duplicate lines, headers, repeated page bodies), structural coverage (headings, tables, code, pages processed versus expected), link density for HTML, and parser warnings, timeouts, truncation or encrypted status.
- **Worked thresholds.** A 20-page English PDF where 19 pages parse, the median is 350 words per page, replacement characters are under 0.1% and OCR confidence is 0.96 — that passes, at a text yield near 6,650 words. Another yields 25 words total, 15% replacement characters, two processed pages: ~12 words per page, roughly 28× below the first, at 150× the corruption threshold. It fails automatic acceptance and must retry or quarantine.
- **Routing has four outcomes, and three are not "discard".** **Accept** when quality passes. **Retry with fallback** when another renderer, OCR engine, password path or parser may repair it. **Quarantine for review** when the document matters but confidence is uncertain. **Discard** only when content is provably empty, out of scope, unsupported after fallbacks, malicious, or below a documented threshold.

**Rules to remember**

- Bytes are not text. A parser returning a non-empty string is not evidence of successful extraction.
- Combine features — link density, text density, semantic elements; no single one generalizes. Repetition across a site is a *hypothesis* of boilerplate, not proof, so audit what the rule removed.
- Preserve the minimum structure the declared downstream features need, and err toward a reversible structured representation before lossy flattening. Cleaning removes presentation noise, never organization.
- Store raw artifacts and extractor version so better parsers regenerate text without refetching, and never call a PDF "empty" before distinguishing a scan from a genuinely blank artifact.
- A discard is a lineage event, not an absence: store source ID, reason code, attempts, metrics, decision time.
- Low-quality text must never join the same trusted path as verified extraction just because both are strings.

**Common pitfalls**

- **Indexing `document.body.innerText`.** It looks like it works, and it quietly injects the same navigation vocabulary into every document, inflating document frequency and making near-duplicate menu chunks.
- **Trusting the template detector absolutely.** Removing every block repeated site-wide also removes the safety warning and the version banner — and it never touches a unique advertisement.
- **Flattening structure to save effort.** Once list peers, table headers and code marks are gone, nothing downstream recovers them.
- **Sorting PDF glyphs by vertical coordinate.** On a two-column layout the output is interleaved nonsense that still reads as text to any check based on length alone.
- **Treating OCR output as authoritative.** Without stored confidence, a 0.62 page is indistinguishable from a 0.96 one downstream.
- **One global minimum word count.** A two-line release notice is valid; a 200-page manual yielding two lines is not; a code file fails a prose heuristic outright.
- **Silently discarding in a corpus that cannot afford it.** A web research corpus may drop low-value failures cheaply; a compliance corpus must quarantine and alert instead.

**How to approach the questions**

1. Ask what the *evidence* is, not what the output looks like. Most scenarios hinge on a signal that was available and ignored: text length, link density, replacement characters, OCR confidence, pages processed.
2. When a page yields suspiciously little text, separate the three causes: client-side rendering, a scan with no text layer, and a genuinely short document. They route differently.
3. For structure questions, read the *downstream use* clause. Bag-of-words search tolerates less layout than citation-grounded RAG; text-to-code retrieval needs exact code; table QA needs headers and cells.
4. For routing questions, check whether a fallback exists. If another renderer, engine or password path is untried, the answer is retry — not discard.
5. Watch for absolute claims. "Remove all repeated content", "always OCR", "discard anything under N words" are wrong as stated, and the right answer names the exception.
6. Prefer the option that preserves evidence — raw hashes, reason codes, extractor version. Options that destroy the ability to reprocess are almost always the distractor, and "extraction got worse last Tuesday" is really a question about a versioned parser.
