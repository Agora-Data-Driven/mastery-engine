The vector space model turns text retrieval into geometry. Once documents and queries share a coordinate system, ranking becomes a comparison of weighted directions rather than a brittle test for exact string equality. The model is simple enough to inspect term by term, yet it establishes ideas that still appear inside modern sparse and hybrid retrieval systems.

## Documents as Bag-of-Words Vectors

A bag-of-words representation treats a document as a collection of term occurrences while discarding word order. Begin with a vocabulary containing every indexed term, assign one coordinate to each term, and place a document's weight for that term in the matching coordinate. With the vocabulary `[database, index, query, vector]`, a document containing "database index index query" has the raw-count vector `[1, 2, 1, 0]`. A query containing "vector query" becomes `[0, 0, 1, 1]`. Both objects now inhabit the same four-dimensional space.

Real vocabularies may contain millions of terms, but each document uses only a small fraction of them. The vector is therefore sparse. An implementation does not allocate a million-element array per document; it stores nonzero entries such as `(term_id, weight)` pairs, usually through the inverted index. The posting for `query` identifies documents whose `query` coordinate is nonzero and carries information needed to calculate its weight. Sparsity makes the apparently enormous geometric model practical.

The coordinate value need not be a raw count. It can be binary presence, a saturated term-frequency value, a tf-idf weight, or another field-aware weight. Representation and comparison are separate decisions: the bag-of-words model defines the axes, while the weighting scheme decides how much evidence each active axis supplies. In a common configuration, coordinate `t` for document `d` is `w(t,d) = (1 + ln(tf(t,d))) * idf(t)`. A term occurring four times with idf 2.0 receives approximately `(1 + 1.386) * 2 = 4.772`, not the raw value 4.

Discarding order creates useful invariance. "vector search ranks documents" and "documents rank vector search" activate the same coordinates. For topical retrieval, both passages discuss the same ingredients, so this invariance often helps. It also lets an inverted index aggregate evidence independently by term. The price is lost structure: "dog bites person" and "person bites dog" have identical bags, while "not reliable" and "reliable" overlap strongly despite opposite implications. Phrase indexes, positional features, or later rerankers can restore some of this information when the application needs it.

Vocabulary construction is therefore a modeling choice rather than clerical preprocessing. Tokenization determines whether `PostgreSQL`, `postgres`, and `postgresql` share an axis. Stemming may merge `connect`, `connected`, and `connection`, improving recall but erasing distinctions. Stop-word removal saves coordinates and postings, yet removing `to` can damage a query such as "flights to Singapore." Character n-grams handle spelling variation and unseen words, but increase index size. Each transformation changes the geometry in which similarity will be measured.

Consider two support articles. Document A contains `timeout` three times and `database` once; document B contains `timeout` once and `browser` twice. For query `database timeout`, both documents share the timeout coordinate, but only A shares database. If database has greater idf because it occurs in fewer documents, A gains a strong second contribution. The result is not based on the surface length of either text. It follows from overlap along weighted vocabulary dimensions.

Bag-of-words also clarifies an important zero-evidence rule. A document with no query term has a dot product of zero with the query and cannot receive a positive lexical similarity under the basic model. Semantic relatedness without shared axes is invisible: a query for `car` will not match a document containing only `automobile` unless normalization, expansion, or another retrieval channel connects them. Engineers should recognize this as a boundary of the representation, not a bug in cosine similarity.

The model is attractive when inspectability matters. A score can be decomposed into contributions from `database`, `timeout`, and every other matched term. Operators can identify whether a rare identifier dominated, whether tokenization prevented a match, or whether a synonym was absent. This trace is valuable in debugging and evaluation, and it provides a reliable lexical foundation even when a learned reranker later makes the final ordering.

## Cosine Similarity as a Ranking Function

The dot product measures aligned weight. For query vector `q` and document vector `d`, it is `q dot d = sum_t q_t * d_t`. Only coordinates nonzero in both vectors contribute, which maps naturally to traversing postings for query terms. If `q = [1, 1, 0]`, document A is `[2, 1, 0]`, and document B is `[1, 4, 0]`, their dot products are 3 and 5. On this calculation alone, B ranks first.

Raw dot product favors vectors with large magnitudes. A long document has more opportunities to mention query terms and often accumulates larger weights, even when the query is a minor part of it. Cosine similarity corrects for magnitude by comparing direction:

`cos(q,d) = (q dot d) / (||q|| * ||d||)`

The Euclidean norm is `||d|| = sqrt(sum_t d_t^2)`. For the example, `||q|| = sqrt(2)`, `||A|| = sqrt(5)`, and `||B|| = sqrt(17)`. A's cosine is `3 / sqrt(10)`, about 0.949. B's is `5 / sqrt(34)`, about 0.857. The ranking reverses because A's term proportions point more directly toward the query, while B devotes disproportionate weight to its second coordinate.

Cosine ranges from zero to one for the nonnegative weights normally used in lexical retrieval. Zero means no shared positive coordinate. One means the vectors have the same direction, even if one is a scaled copy of the other. Thus `[1, 2]` and `[3, 6]` have cosine one. This scale invariance captures the intuition that repeating an entire document should not automatically change its topical direction.

Ranking usually does not require calculating every part of the formula at request time. For one query, `||q||` is constant across all candidate documents, so removing it preserves document order. Document norms can be computed during indexing and stored as compact values. The runtime scorer can accumulate the numerator from query-term postings and multiply by a stored inverse document norm. This separation matters because a ranking function may be mathematically neat but operationally poor if it demands scanning every vocabulary coordinate.

Weights shape the angle, so cosine does not rescue a bad weighting scheme. Suppose a common term has raw count 20 and a discriminative term has count 1. Without saturation and idf, the common coordinate can steer both query and document directions excessively. Applying log tf and idf first gives the geometry a retrieval-aware meaning; cosine then normalizes those weighted vectors. The usual pipeline is therefore tokenize, weight, calculate overlap, and normalize, not cosine over unexamined counts.

Cosine can be explained as a sum of evidence. A matched term contributes `q_t * d_t / (||q|| * ||d||)`. For query `vector database`, an explanation might show 0.42 from `vector` and 0.31 from `database`, producing 0.73. Such traces support relevance debugging. They also reveal problems such as a rare typo carrying nearly the entire score or a title boost making a coordinate unexpectedly large.

There are cases where cosine is not the best ranking rule. Very short queries make query-vector direction coarse. Exact identifiers may need filters or large boosts rather than smooth angular similarity. Field structure is awkward if all text is collapsed into one vector. Probabilistic functions such as BM25 often provide better calibrated length handling. The right judgment is empirical: use offline relevance judgments and online outcomes, and keep the scoring explanation detailed enough to diagnose changes.

## Document Length Normalization

Length normalization asks how much confidence to assign to matches in documents of different sizes. Without normalization, a 5,000-word manual can beat a focused 200-word answer because it repeats more query terms. With overly aggressive normalization, the concise answer can win even when the manual contains a more complete and genuinely useful discussion. Length is a confounder, but it can also carry information.

Cosine uses the vector norm rather than token count. This distinction is important. The norm depends on term weights and their distribution: ten repetitions of one term produce a different norm from ten distinct terms, especially after tf saturation and idf. If A has vector `[3, 0, 0]`, its norm is 3; if B has `[1, 1, 1]`, its norm is about 1.732. Both may contain three weighted units, but normalization treats their geometry differently.

Full cosine normalization divides by `||d||`. A tunable alternative uses `||d||^alpha`, where alpha lies between zero and one. Alpha zero gives no document normalization, alpha one gives full cosine, and alpha 0.5 is a compromise. If two documents have the same numerator 6 but norms 2 and 8, no normalization ties them. Full normalization produces scores 3 and 0.75. With alpha 0.5, scores are approximately 4.24 and 2.12. The parameter controls the penalty rather than assuming one universal strength.

Pivoted normalization takes another view: compare document length with the collection average and apply a linear adjustment around that pivot. A schematic denominator is `(1 - s) + s * length(d) / avg_length`, where `s` sets the slope. With `s = 0.2`, average length 500, and document length 1,000, the denominator is `0.8 + 0.4 = 1.2`. A document of length 250 gets `0.8 + 0.1 = 0.9`. The longer document is penalized and the shorter one modestly amplified.

The definition of length should match the field and tokenizer. Body token count, unique-term count, and weighted vector norm express different assumptions. A product title of 12 tokens is not unusually long merely because a body field averages 800. Normalizing them together can suppress useful title matches. Fielded systems commonly calculate a separate length statistic and average for title, body, tags, and other channels, then combine their scores.

Document type also changes the appropriate judgment. Long legal opinions or research papers may be relevant precisely because they cover a subject comprehensively. A support-answer collection may reward focus. Source-code files contain repeated syntax tokens that inflate raw length without proportional semantic breadth. Tables and generated logs can be enormous but have strong exact-match value. Segmenting long documents into passages is often better than trying to solve every mismatch with a single normalization exponent.

Normalization must be versioned with indexing. If stored norms were computed before a tokenizer change, combining them with new term weights creates incoherent scores. The index metadata should identify tokenizer, vocabulary statistics, weighting formula, field configuration, and norm calculation. During a rolling migration, segments built under different statistics may need isolated scoring or recalibration before results are merged.

Finally, tune length handling against measured relevance rather than aesthetic preference. Slice evaluation by document-length bucket and query class. Look for systematic failures: long relevant documents disappearing, short keyword-stuffed pages rising, or particular fields dominating. A parameter that improves mean ranking may hurt identifier queries or broad research queries. The vector space model makes the mechanism visible, but the application determines which tradeoff is correct.
