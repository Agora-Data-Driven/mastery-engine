Ranking every document that shares a query term is wasteful when the user will inspect only the first few results. Efficient top-k retrieval preserves the scoring model while avoiding work that cannot change the final heap. The central engineering problem is to organize traversal, maintain a competitive threshold, and use safe upper bounds to prove when candidates or postings can be skipped.

## Term-at-a-Time vs Document-at-a-Time Scoring

An inverted index gives one posting list per query term. A ranker must combine those lists into document scores, and two classic traversal strategies organize that work differently. Term-at-a-time, abbreviated TAAT, consumes one entire term's postings before moving to the next term. Document-at-a-time, abbreviated DAAT, advances lists together in increasing document-identifier order and completes one candidate document before considering the next.

For query `vector database`, suppose the postings are `vector: (2,1.5), (5,0.7), (9,1.0)` and `database: (2,0.8), (7,1.2), (9,0.6)`, where each pair contains a document identifier and score contribution. TAAT first adds vector contributions into an accumulator: document 2 gets 1.5, 5 gets 0.7, and 9 gets 1.0. It then processes database, raising document 2 to 2.3, creating document 7 at 1.2, and raising document 9 to 1.6. Finally, it selects the largest scores.

The TAAT accumulator may be a hash map, dense score array, or compressed structure. Its advantage is sequential access through one postings list at a time, which can be cache-friendly and easy to parallelize by term. Its cost is potentially large accumulator state. A broad query can touch millions of distinct documents even though only ten results are needed. Clearing a dense score array can itself be expensive, so implementations often track which slots were touched.

DAAT places an iterator at the head of every query-term list. The smallest current document identifier is the next candidate. In the example, both iterators begin at document 2, so the scorer sums 1.5 and 0.8, finalizes 2.3, and advances both lists. The current identifiers then become 5 and 7. Document 5 is finalized from vector alone, then 7 from database alone, and finally both meet at 9 for a score of 1.6.

DAAT naturally produces complete scores in document order. It can feed each completed score into a min-heap of size k. Before the heap is full, every candidate enters. Once full, the root is the current threshold: a new candidate must exceed it to enter the result set. Memory is bounded by the query iterators, heap, and small scoring state rather than the number of touched documents. Coordinated iterator movement also creates the foundation for WAND-style skipping.

The tradeoff is access behavior. DAAT repeatedly switches among postings lists, and naïve implementations pay branch and pointer costs. TAAT can exploit blockwise vectorized accumulation and process high-impact terms first, causing a useful threshold or pruning state to emerge. Neither traversal is universally faster. Query length, posting-list sizes, compression layout, cache behavior, scoring complexity, and available pruning rules determine the winner.

Intersection semantics also matter. Conjunctive retrieval requires every query term, so DAAT can leap lagging iterators toward the current maximum document identifier. Disjunctive retrieval allows any term and must consider the union, but top-k bounds may still avoid full scoring. Phrase and proximity features need positions after a document becomes a plausible candidate; decoding positions for every lexical match would defeat much of the efficiency gain.

Consider three postings lists of lengths 50, 50, and 5,000,000. A conjunctive query should usually drive traversal with a short list and seek into the long one. For a disjunctive query, the frequent term may create many weak candidates. Processing rare, high-idf terms early or using DAAT bounds can reduce wasted work. A planner should use collection statistics instead of choosing one traversal for all queries.

Correctness requires a stable score definition regardless of traversal order. Floating-point addition can create tiny differences, but TAAT and DAAT should otherwise rank the same fully evaluated candidates. Engineers should test optimized traversal against an exhaustive reference scorer on sampled queries, including ties, missing terms, deleted documents, and segment boundaries. Performance is valuable only after equivalence or explicitly accepted approximation has been demonstrated.

## Index Elimination and Champion Lists

Index elimination reduces the postings considered before or during scoring. The simplest form removes query terms with negligible discriminative value. If a query contains several content terms plus an extremely common term, ignoring the common term can save a long traversal while barely changing ranking. This is a heuristic: the eliminated term might matter for a phrase, entity name, or navigational query, so the policy should consider query structure rather than idf alone.

Another form keeps only documents likely to score highly for each term. A champion list for term `t` contains the r documents with the largest term-specific weights for `t`, often selected at indexing time. If the full posting contains one million documents but its champion list contains 1,000, an initial ranker can score a much smaller candidate pool. For query `vector database`, it takes the union of the vector and database champion lists and evaluates those candidates.

Champion lists move computation from request time to index construction. They are especially useful when term-local weights are stable and high values strongly predict final rank. They are less reliable when the final scorer includes large document-independent interactions, freshness, personalization, proximity, or field combinations that cannot be captured by a single term's ordering. A document mediocre for each individual term can be excellent because it matches all query terms.

The size r controls recall and cost. With r equal to 100, retrieval is fast but may miss competitive documents. With r equal to 100,000, recall improves while much of the saving disappears. Lists can use fixed r, a score cutoff, or a term-specific size. Rare terms may need their entire short posting, while frequent terms benefit from more aggressive restriction. Evaluation should measure recall of the exhaustive top k, not merely overlap of candidate sets.

Static quality can create global champion lists. Instead of selecting only by term weight, the index may combine term evidence with a query-independent score such as authority or document quality. A two-tier index stores high-quality postings in a first tier and the remainder in a fallback tier. The ranker searches the first tier, checks whether it has enough convincing results, and expands to the second if necessary. The fallback condition must be explicit; simply stopping after k first-tier matches can return weak results.

Suppose k is 10 and the first-tier search returns 10 documents, but the heap threshold is only 0.15 while omitted postings could contribute as much as 0.9. Stopping is unjustified. If a safe upper bound proves every omitted candidate scores at most 0.12, stopping is correct. Heuristic index elimination accepts some recall risk; bound-based elimination proves that skipped work cannot affect the answer. The system should label which guarantee it provides.

Elimination policies need special handling for short queries. For a one-term query, removing the only common term yields no candidates. A champion list then defines almost the entire retrieval behavior, so overly small r can hide relevant documents beyond the first page or after filters are applied. Filters are particularly important: if nine of ten champions fail an access-control or language filter, the ranker must expand rather than return one result.

Operational freshness matters as well. Champion lists can become stale when term weights, document quality, or deletion state changes. Segment-based indexes may build champions per segment, then merge candidates across segments. If segment score statistics are inconsistent, a small new segment can dominate or vanish. Store the list construction version and rebuild or invalidate derived structures with the scoring model.

Champion lists are best treated as candidate-generation tools with measured recall. Maintain an exhaustive scorer for evaluation, sample production queries, and compare top-k recall and latency by query class. Tail latency often improves more than mean latency because pathological frequent-term queries lose much of their candidate volume. The right configuration is the smallest candidate budget that meets an explicit relevance target.

## WAND and MaxScore: Skipping Non-Contenders

WAND and MaxScore use score upper bounds to avoid fully evaluating documents that cannot enter the current top k. For each query term, the index supplies an upper bound on that term's possible contribution. If `vector` can contribute at most 1.4 and `database` at most 0.9, any document matching both has score at most 2.3 under an additive scorer. Tighter bounds may be stored per postings block so local regions can be skipped more aggressively.

WAND, commonly expanded as Weak AND, operates over document-ordered iterators. Sort the iterators by their current document identifiers, then accumulate term upper bounds from the front until the sum exceeds the heap threshold. The document identifier at that point is the pivot. If every iterator contributing to the bound is positioned at the pivot, the pivot becomes a candidate for full scoring. Otherwise, iterators behind the pivot advance to it, skipping documents that cannot gather enough possible evidence.

Imagine k results have produced a threshold of 1.5. Three term iterators have current document identifiers 10, 14, and 14, with upper bounds 0.4, 0.7, and 0.8 in that order. At document 10, the first bound alone is insufficient. Adding the second reaches 1.1, still insufficient. Adding the third reaches 1.9, making 14 the pivot. The iterator at 10 advances toward 14. If it lands on 14, document 14 is scored from all matches; if it jumps beyond 14, the iterators are reordered and the test repeats.

The threshold is dynamic. Before the top-k heap fills, it is effectively negative infinity or zero for nonnegative scores, so pruning is weak. As competitive documents arrive, the threshold rises and more candidates become provably irrelevant. Query planning that encounters strong candidates early can therefore accelerate the rest of retrieval without changing the scoring formula.

MaxScore also divides query terms using upper bounds. Terms whose cumulative maximum contribution cannot help a candidate cross the threshold become nonessential. Essential postings drive candidate generation, while nonessential terms are consulted only when their remaining possible contribution might rescue a candidate. As the threshold rises, more terms can become nonessential. Compared with WAND's pivot process, MaxScore exposes a useful conceptual split between required traversal and optional score refinement.

Correct bounds are non-negotiable for exact retrieval. An underestimated maximum can skip a true winner. Bounds must account for every positive component used during first-stage scoring, including field boosts and term-dependent factors. If a later feature can add 0.5, either include its maximum in the bound or apply it only after a safely generated candidate set. Negative contributions and non-additive interactions require careful derivations rather than copying an additive WAND implementation.

Block-Max WAND stores upper bounds for blocks within a posting list rather than one loose maximum for the whole term. If a term's global maximum is 4.0 but the next block's maximum is 0.3, the local bound supports a large skip that the global value would forbid. Smaller blocks tighten bounds but consume more metadata and can increase decoding overhead. Block size is thus a space, CPU, and pruning tradeoff.

Filters complicate threshold growth. If access control rejects early high-scoring candidates, the heap fills slowly and pruning remains weak. Integrating selective filters into iterator traversal may help, but only if skipping retains correct bounds. Distributed retrieval adds another layer: each shard computes local top results, and a coordinator merges them. Local thresholds and statistics must support sufficient shard candidates, or a globally competitive document can be omitted before merging.

Optimization should be evaluated using postings decoded, candidates fully scored, block skips, heap updates, and end-to-end latency, not latency alone. Compare every exact optimization with exhaustive top-k output across adversarial and ordinary queries. WAND and MaxScore are powerful because they convert a performance hope into a proof: given valid upper bounds and a current threshold, skipped non-contenders cannot alter the final top k.
