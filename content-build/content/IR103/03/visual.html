1. Top-k Not All-k

Cosine Similarity as a Ranking Function, over Bag-of-Words Vectors weighted by tf-idf and fixed by Document Length Normalization, already gives every document a number. This lesson never changes that number. It asks how many of them you can decline to compute. Drag k, and flip the heap between full and still filling. Like an exam where only the top three get in: once you know the third-best mark, most papers need no marking at all.

The threshold is the whole hinge, and it is not free: it only exists because scores can be finalized in document order and fed to a min-heap of size k. That is why the traversal question in visual 2 comes before the skipping questions in visuals 4 and 5 — an algorithm that finishes one term at a time has no finished score to threshold on until the very end.

2. TAAT Versus DAAT

Same postings, same arithmetic, same final ranking — two ways of ordering the work. Pick a traversal and step it. Watch what the algorithm is holding in memory at each moment. Like adding up a stack of receipts: one column at a time down every page, or one whole page at a time.

step 0 of 7

Neither is universally faster. DAAT keeps switching between lists and naïve implementations pay branch and pointer costs; TAAT reads one list end to end, which is cache-friendly and vectorizes well. Query length, list sizes, compression layout and the pruning rules available decide it — with lists of 50, 50 and 5,000,000, a conjunctive query wants the short list driving and a seek into the long one. A planner should read collection statistics, not pick one traversal for everything.

3. Champion List Size

Index elimination cuts what is traversed before scoring. A champion list keeps only the r best-weighted documents per term, chosen at indexing time. Drag r, drop the very common term, turn a filter on. Like a shortlist drawn up before the interviews: cheap, and only as good as whoever drew it.

Champion lists move work from request time to index construction, so they go stale: term weights, document quality and deletion state all drift. Store the construction version and rebuild derived structures whenever the scoring model changes, and if champions are built per segment, make sure the segments' score statistics are comparable — otherwise a small new segment either dominates the merged candidate set or vanishes from it.

4. The WAND Pivot

Three iterators, three upper bounds, one threshold. Sort by current document identifier, add bounds from the front, and stop the instant the running sum can beat θ. Drag the threshold and watch the pivot move. Like queue-jumping at a weigh-in: nobody who cannot possibly make the weight even gets on the scale.

Correct bounds are non-negotiable. A bound must cover every positive component of first-stage scoring — field boosts included. If a later feature can add 0.5, either fold its maximum into the bound or apply it only after a safely generated candidate set. An underestimated maximum skips a true winner, and that is a correctness bug, not a slow query.

5. Essential Or Skippable

Same threshold, two ways of spending it. MaxScore splits the query into terms that must drive traversal and terms that only refine a score; Block-Max stores a bound per block so a quiet stretch of a loud term can be jumped. Like packing for a weight limit: some items you must carry, others you only pick up if there is room left.

Two things break threshold growth in production, and both make pruning weak rather than wrong. Filters that reject early high scorers keep the heap under-filled, so θ stays low; integrating them into traversal only helps if the bounds stay correct. Distributed retrieval merges shard-local top-k at a coordinator, so each shard must return enough candidates or a globally competitive document is dropped before the merge ever sees it. Judge these systems on postings decoded, candidates fully scored, block skips and heap updates — not on latency alone.
