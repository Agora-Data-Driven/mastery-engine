**The big idea**: **Learned Embeddings: Meaning as Geometry** promised that an encoder turns a variable-length token sequence into one fixed-dimensional vector, so a paraphrase scores high without sharing a word — the failure **The Vocabulary Mismatch Problem** diagnosed and the one **LSA as a Bridge: SVD on the Term-Document Matrix** could only half-fix, since a global decomposition must be refactored whenever the corpus moves. This lesson is the architecture that makes that promise *servable*. One structural decision does all the work: a query tower and a document tower encode **separately**, so every document vector can be computed before any query arrives and request-time work collapses to one query encoding plus cheap vector comparisons. Everything else follows from that separation — how token states get pooled into the one vector, which similarity function you compare with, and the quality ceiling you accept in exchange for the speed.

**Key concepts**

- **The dual-tower architecture is two encoders that never see each other's input.** A bi-encoder has a query tower and a document tower; each maps its own token sequence to one fixed-dimensional vector alone, and retrieval scores a pair with a cheap function, commonly the dot product: `score(q, d) = f_query(q) · f_document(d)`. The towers can share all parameters, share a base model with different instructions, or use distinct parameters. Shared weights reduce model count and encourage one common language space; asymmetric towers better represent a short question versus a long passage but complicate training and deployment. **Compatibility matters more than architectural symmetry** — both outputs must inhabit a space whose comparison was trained for the task.
- **The factorization is the source of scale, and it is the shape of a dual-tower recommender.** A user tower produces a user vector, an item tower precomputes item vectors, the dot product retrieves candidates; here the query is the user-side context and a passage is the item. With one million document vectors already stored, request-time work is **one** query encoding plus vector comparisons or index traversal — not one transformer pass over one million query-document pairs. That is the whole difference between a retriever and a scorer.
- **Worked ranking.** Let `q = [0.8, 0.6]` with precomputed `d1 = [0.7, 0.7]`, `d2 = [-0.2, 0.9]`, `d3 = [0.9, -0.1]`. Dot products: $0.8(0.7)+0.6(0.7)=0.98$, $-0.16+0.54=0.38$, $0.72-0.06=0.66$. Ranking: d1, d3, d2. Only `q` changed this request — those three document vectors are reused for every query that ever arrives.
- **Precomputation creates an artifact lifecycle, not just a cache.** Each vector needs a document and chunk ID, model version, preprocessing version, source revision, dimensions and ACL metadata. When text changes its vector must change; when the encoder changes, index and query service move through a **coordinated migration**, because vectors from unrelated spaces produce meaningless scores even when the dimensions happen to match — nothing errors, the scores are simply noise.
- **Independent encoding is also the ceiling.** The document representation cannot emphasise different words for different queries, because it was computed before the query existed. A passage covering installation, upgrades and deletion compresses all three subjects into one vector, so for `remove the agent` the model cannot perform token-by-token interaction between `remove` and `deletion` at scoring time. That makes the bi-encoder an excellent candidate generator and not always the best final judge; engineers manage the bottleneck with focused chunks, task-appropriate training, useful titles and a later reranking stage.
- **Batching changes throughput, never the score.** If one accelerator encodes 32 passages in 40 ms, batch throughput is $32/0.040 = 800$ passages per second, though the first passage waits roughly for the whole batch. Offline indexing favours large batches and high utilisation; an interactive query service favours small dynamic batches, a bounded queue and tail-latency protection, so record examples per second *and* percentile latency. Benchmark encoding latency separately from vector-search latency: optimising the index cannot fix an overloaded query-model endpoint. The towers may also take different maximum lengths — a query capped at 32 tokens while a passage uses 256 — but that asymmetry is an evaluated model contract, not a serving shortcut.
- **Sentence embeddings are a pooling rule applied to token embeddings.** Transformer layers produce one contextual vector per input token; a sentence embedding pools those states into one vector for the whole query, sentence or chunk. Mean pooling averages eligible states, special-token pooling selects a designated state, learned pooling assigns content-dependent weights. With unmasked states `h1 = [1,0]`, `h2 = [0.6,0.8]`, `h3 = [0.2,1]`, mean pooling gives $[(1+0.6+0.2)/3,\ (0+0.8+1)/3] = [0.6, 0.6]$ — cheap to index, and no longer able to expose which token supplied which signal.
- **Padding is the silent pooling bug.** Wrongly include five padding vectors of `[0,0]` and the same text pools to $1.8/8 = [0.225, 0.225]$. Cosine direction happens to survive in this artificial case, but real padding states are not guaranteed to be zero and dot-product magnitude changes regardless. Production pooling must match the model's training and documentation — validate by encoding the same text alone and inside a padded batch, where the vector should be effectively unchanged.
- **Single-vector storage is arithmetic you should be able to do in your head.** A 768-dimensional float32 vector is $768 \times 4 = 3{,}072$ bytes, so ten million chunks need about **30.72 GB** of raw vectors before index overhead. That compactness is what makes approximate search and simple serving possible.
- **Token embeddings keep many vectors per document and score by late interaction.** One common conceptual score sums, for every query token, its maximum similarity to any document token. With similarities `[0.9, 0.2, 0.1]` for query token qa and `[0.1, 0.4, 0.8]` for qb, the max-per-query-token sum is $0.9 + 0.8 = 1.7$: each query concept finds its own supporting token, where a single pooled vector might blur the two alignments.
- **That fidelity is paid for in memory and comparisons.** A chunk retaining 128 token vectors of 128 float32 dimensions is $128 \times 128 \times 4 = 65{,}536$ bytes, against 512 bytes for one 128-dimensional vector — 128× — and scoring performs far more comparisons. Hence compression, pruning, specialised indexing, and the standard multi-stage design: a single-vector retriever finds a manageable candidate set, a richer interaction model scores it afterwards. The decisive evidence is end-to-end quality per unit of latency and memory, never the label *sentence* or *token*.
- **The three similarity metrics, algebraically.** Dot product combines alignment and magnitude, $x \cdot y = \|x\|\,\|y\|\cos\theta$; cosine divides it out, $\cos(x,y) = (x \cdot y)/(\|x\|\,\|y\|)$, so it measures direction only; Euclidean distance measures straight-line separation, $d(x,y)^2 = \|x-y\|^2$.
- **They are not interchangeable for arbitrary vectors.** Let `q = [1,0]`, `a = [2,0]`, `b = [0.8,0.6]`. Dot products are 2 and 0.8, so dot prefers **a**. Cosines are 1 and 0.8, so cosine also prefers **a**. Euclidean distances are 1 and $\sqrt{0.04+0.36} = \sqrt{0.4} \approx 0.632$, so Euclidean prefers **b**. Same vectors, opposite answer — magnitude did it.
- **Normalise and all three collapse to one ordering.** With unit vectors $\cos(x,y) = x \cdot y$, and expanding the square gives $\|x-y\|^2 = \|x\|^2 + \|y\|^2 - 2\,x\cdot y = 2 - 2\,x \cdot y$, strictly decreasing in the dot product. So maximising dot, maximising cosine and minimising Euclidean distance yield **the same ranking** — useful when an index supports one metric more efficiently. Sanity-check it above: `b` is already unit length, which is why its distance was $\sqrt{2 - 2(0.8)} = \sqrt{0.4}$.
- **Normalisation is a modelling choice with consequences either way.** If the training objective used normalised embeddings, serving should normalise identically. If magnitude encodes confidence, popularity or learned relevance, normalising at retrieval throws that away; an unnormalised dot-product system, conversely, can favour large-norm documents whose direction is less relevant. Inspect norm distributions rather than guessing.
- **Metric name, normalisation step and score direction are versioned interface fields.** An index built for Euclidean distance but queried as though higher scores are better inverts the results, and some APIs return a distance where others return a similarity. Watch the numerical edges too: a zero vector has **no defined cosine**, empty or fully truncated inputs produce pathological embeddings, and quantisation perturbs close scores — validate norms, route invalid records rather than indexing them, and let ranking tests tolerate tiny numeric differences.

**Rules to remember**

- The towers never see each other's input. That fact explains the speed, the artifact lifecycle and the quality ceiling.
- Document vectors are precomputed; only the query is encoded per request. Changing the encoder invalidates every stored vector.
- Compatibility of the two output spaces beats symmetry of the two architectures.
- Pooling must match training: mean, special-token or learned, with padding masked out.
- One vector per chunk is cheap and blurs; many vectors per chunk are precise and expensive. 3,072 bytes versus 65,536 bytes per chunk is the shape of the trade.
- For unit vectors, max dot = max cosine = min Euclidean. For arbitrary vectors, none of those follow.
- $\|x-y\|^2 = 2 - 2\,x\cdot y$ only when both are unit length. Drop that condition and the equivalence goes with it.
- Start with the metric the model was trained and evaluated under. Trying three metrics on unlabelled examples is not model adaptation.

**Common pitfalls**

- **Expecting query-specific emphasis from a document vector.** It was computed before the query existed. If the scenario needs `remove` to interact with `deletion`, that is a reranker's job, not the bi-encoder's.
- **Mixing vectors from two encoder versions.** The dimensions match, nothing throws, and every score is meaningless. Migration is coordinated across index and query service.
- **Averaging padding into the pooled vector.** The document still indexes successfully while the whole neighbourhood degrades quietly — the same class of failure as a silent truncation regression.
- **Assuming cosine and dot product agree.** They agree only for unit-length vectors; the `[2,0]` versus `[0.8,0.6]` example flips as soon as magnitude varies.
- **Normalising by reflex.** If magnitude carried confidence or popularity, you just deleted it — and if training normalised and you do not, you broke the contract the other way.
- **Querying a distance index as if higher were better.** The ranking inverts, quietly, and looks like a bad model.
- **Indexing a zero or near-empty vector.** Cosine is undefined at zero norm; validate and route those records instead.
- **Benchmarking the index when the encoder is the bottleneck.** Measure the two latencies separately or you tune the wrong half.
- **Buying multi-vector fidelity without pricing it.** 128× the bytes must be repaid in end-to-end quality per unit latency.

**How to approach the questions**

1. Ask *when* each side is encoded. Most dual-tower questions resolve the moment you notice that the document vector predates the query.
2. For any similarity comparison, check whether the vectors are unit length **before** deciding which metrics agree. If any magnitude differs from 1, expect the three to disagree and compute them.
3. Do the arithmetic — these are two-dimensional examples on purpose. A dot product, a mean pool, `dims × 4 bytes`: seconds of work that eliminate most distractors outright.
4. When a scenario changes the encoder, the pooling rule, the maximum length or the normalisation, ask what stored artifact just became invalid.
5. Distinguish *throughput* claims from *score* claims. Batching, dynamic batching and length caps move latency and cost; none of them changes the number a pair scores.
6. For sentence-versus-token questions, name the currency: bytes per chunk and comparisons per query, against recall on detail-sensitive text.
7. Treat "just switch the metric" as a warning sign — reproduce the training contract first, then measure.
