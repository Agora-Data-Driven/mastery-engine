**The big idea**: **Learned Embeddings: Meaning as Geometry** turned relevance into proximity, **Dual-Tower Architecture: Encode Separately, Compare by Dot Product** moved the document tower offline so serving is nothing but similarity comparisons, and **Similarity Metrics: Cosine vs Dot Product vs Euclidean** fixed what "nearest" means. All three quietly assumed you can *find* the nearest vectors. Dense vectors solve semantic matching only if nearby candidates can be found inside a latency and memory budget, so production systems deliberately trade a small, *measured* amount of recall for much less work. IVF, HNSW and product quantization make three different approximations, and none of their knobs mean anything except against a measured exact baseline.

**Key concepts**

- **Why Exact k-NN Does Not Scale: the cost is proportional to $N \cdot d$, and both factors are large.** Exact k-nearest-neighbor search computes a distance or similarity between the query and *every* indexed vector, then retains the best k; selection adds work, but the dense comparisons dominate. With ten million 768-dimensional float vectors, one brute-force query is $10{,}000{,}000 \times 768 = 7.68$ **billion coordinate multiplications**, and float32 storage is $10{,}000{,}000 \times 768 \times 4$ bytes = **30.72 GB** before IDs and index structures. Matrix multiplication is superbly optimised and accelerators make exact search viable at moderate scale — but cost and latency grow *directly* with the corpus, and that is what eventually breaks.
- **Exact search does not disappear; it becomes the instrument.** It establishes ground-truth neighbors for an evaluation subset and detects whether an approximate index is losing relevant candidates. It is also the right *production* choice for tens of thousands of vectors, heavily filtered partitions, offline jobs, or hardware that batches many queries. Approximation has overhead and complexity of its own, so **no fixed corpus size automatically requires it**.
- **ANN recall@k is agreement with exact search — not relevance.** Among the exact top-k neighbors, what fraction did the approximate search return? That is *index* recall. An index can reproduce an embedder's neighbors perfectly while the embedder ranks irrelevant content, so 1.0 here says nothing about whether the user was served.
- **A baseline is only comparable if it is frozen.** Take representative query vectors, compute exact results, then sweep index parameters, reporting p50/p95 latency, throughput, memory, build time, update behaviour and ANN recall. Freeze the corpus snapshot, model version, metric and tie-breaking rule; a few thousand held-out queries stay affordable offline even when serving the corpus exactly does not. If filters define the eligible set, compute exact neighbors *inside that same set*.
- **IVF: k-Means Partitioning of the Vector Space — your k-means, used as a router.** An inverted file vector index trains k-means on representative vectors to learn centroids, assigns each document vector to its nearest centroid, and stores posting lists of vector IDs and payloads. At query time it finds the nearest centroids and scans only their lists. Worked: 1,000,000 vectors spread evenly over 1,000 cells gives ~1,000 per list, so `nprobe = 10` examines roughly **10,000 candidates — about one percent of the corpus** — plus 1,000 centroid comparisons. Real distributions are rarely even, and clusters can be badly skewed.
- **`nprobe` exists to repair the boundary failure, IVF's characteristic miss.** If query q lies almost equally between centroids A and B, q is assigned to A while its true closest vector may sit in B's list. Probing one cell is fast and brittle; probing both repairs that miss, at proportionally more comparisons.
- **The number of lists is the build-time dial, and it is wrong in both directions.** Too few leave large scans; too many give tiny cells, expensive centroid selection, sparse training and maintenance complexity. Centroids must be trained on vectors representative of production languages, domains and model versions — a distribution shift creates overloaded or semantically poor cells, and enough drift justifies retraining. Monitor list-size imbalance, probe counts, recall by segment, and the fraction of results removed by post-filtering.
- **HNSW: Layered Greedy Graph Search — shortcuts instead of partitions.** Hierarchical navigable small world indexing builds a proximity graph: each vector is a node connected to selected nearby nodes. Upper layers hold progressively fewer nodes and give long jumps; the bottom layer holds every node and supplies local navigation. Search enters at an upper layer, greedily moves to a closer neighbor, descends, and maintains a candidate frontier near the query. Concretely: from node A the query is closer to A's neighbor F, then to F's neighbor M; at the next layer M leads to the target neighborhood. Edges act as shortcuts — the navigable-links idea from a well-connected network.
- **Three parameters, only one tunable after the build.** `M` controls roughly how many neighbor connections each node keeps: more links improve navigability and recall, and cost memory and build work. `efConstruction` is the breadth used while finding a new node's neighbors — higher means a better graph, slower construction. `efSearch` is the query-time candidate frontier: raising it improves recall and costs latency. The first two are baked into the graph, which is why `efSearch` is the dial in every sweep table.
- **Greedy traversal can settle for a local neighborhood that is not globally best.** Hierarchical entry and a wider frontier reduce that risk without eliminating it; weakly connected regions, aggressive settings and unusual filtered subsets all cause misses. In exchange HNSW gives strong low-latency recall with no centroid-training phase — and pays in graph memory *beyond* the raw vectors, expensive construction, deletion and churn maintenance, and metadata filtering that can send traversal through many disallowed nodes.
- **Product Quantization: Compressing Vectors — split the vector, then store codeword IDs.** Split a 768-dimensional vector into 96 groups of 8 dimensions and train a separate k-means codebook of 256 centroids *per subspace*. Selecting one of 256 codewords costs $\log_2 256 = 8$ bits, so each group needs one byte: **96 bytes instead of $768 \times 4 = 3{,}072$, a 32-fold reduction** before overhead. The Cartesian product of the 96 codebooks represents $256^{96}$ reconstructions while storing only $96 \times 256$ centroids. The price is distortion: every subvector is replaced by its nearest codeword.
- **Asymmetric distance computation keeps the query uncompressed.** For each subspace, build a lookup table of distances between the query subvector and every codeword — $96 \times 256 = 24{,}576$ partial scores, computed once per query. A database code is then scored by summing the 96 entries its bytes address: 96 lookups and 95 additions, no per-vector floating-point arithmetic at all.
- **PQ's own dials, and its usual partner.** More subspaces or larger codebooks reduce distortion but enlarge codes, tables or training work. Poorly balanced dimensions waste capacity — rotations such as optimized product quantization redistribute variance more favourably. PQ most often rides on IVF: IVF narrows the searched cells, PQ compresses and rapidly scores their contents, and the best candidates are then **reranked** against original full-precision vectors stored elsewhere.
- **The Recall-Latency-Memory Triangle: three resources, no universal best setting.** More IVF cells probed or a wider HNSW frontier improves recall and costs latency and compute. More HNSW links improve navigation and cost memory. Stronger PQ compression saves memory and bandwidth and introduces distance error that lowers recall. A sweep makes it concrete:

| efSearch | ANN recall@10 | p95 latency |
|---:|---:|---:|
| 20 | 0.91 | 8 ms |
| 80 | 0.975 | 21 ms |
| 200 | 0.992 | 48 ms |

  With a 25 ms candidate-stage budget, **80 is the defensible operating point**. Choosing 200 buys 0.017 recall and breaks the objective; 20 may be right for an autocomplete path with a stricter budget.

- **Memory is never just the vectors, and ANN recall is never the objective.** A nominal 30 GB collection needs far more resident memory once HNSW edges, posting lists, metadata, replicas and transient build capacity are counted. And lifting ANN recall from 0.98 to 0.995 may produce **no measurable relevance gain** if the lost neighbors were redundant — or matter greatly when each query has one relevant document.
- **Candidate width ties the index to the rest of the funnel.** If a reranker needs 100 candidates, ask whether ANN search reliably supplies *useful documents* within those 100, not whether the first ten approximate neighbors equal the exact first ten. Over-fetching 300 before filters protects the final width and consumes reranking capacity.

**Rules to remember**

- Exact search costs work proportional to $N \cdot d$ per query and $4Nd$ bytes at float32: 10M × 768 is 7.68 billion multiplies and 30.72 GB.
- ANN recall@k is agreement with exact vector search; relevance recall is whether useful documents arrive. Different numbers, and they can move in opposite directions.
- Freeze the baseline — corpus snapshot, model version, metric, tie-breaking — and compute exact neighbors under the *same* filters.
- IVF: `nprobe` is the query-time dial; list count and centroid training are build-time. Boundary queries are its failure mode.
- HNSW: `M` and `efConstruction` are build-time; `efSearch` is the only query-time dial.
- PQ code size is subspaces × log2(codebook size) bits: 96 × 8 = 96 bytes against 3,072, a 32× reduction.
- ADC never decompresses: build the table once per query, then lookups and adds.
- IVF + PQ + rerank is the standard shape — narrow, score cheaply, re-score survivors in full precision.
- Choose the operating point from the stage's service objective, not the largest recall in the table.

**Common pitfalls**

- **Assuming a corpus size mandates approximation.** Small corpora, filtered partitions, offline jobs and batching hardware are legitimately exact, with no training, build or drift.
- **Confusing ANN recall with relevance recall.** An index reproducing the embedder's neighbors perfectly still returns irrelevant documents if the embedder is wrong.
- **Benchmarking without filters,** or scoring filtered ANN output against an unfiltered exact list. The first hides the worst case; the second records correct behaviour as a failure.
- **Training IVF centroids on an unrepresentative sample** — one language, one domain, the previous model version. The symptom is recall varying by segment rather than falling overall.
- **Treating `M` or `efConstruction` as query-time knobs.** They are properties of the built graph; changing them means a rebuild.
- **Trusting PQ distances as final.** Quantization error is real distance error; rerank survivors in full precision.
- **Reading mean latency instead of p95,** or sizing memory from raw vectors alone. Edges, posting lists, metadata and replicas are the rest of the bill.
- **Chasing the top of the recall column.** 0.992 at 48 ms simply fails a 25 ms budget.

**How to approach the questions**

1. Ask which dial moves and *when*. Query-time (`nprobe`, `efSearch`) versus build-time (`M`, `efConstruction`, list count, codebook size) separates most distractors on its own.
2. Recompute any cost claim. N times d for compute, times 4 for float32 bytes; for PQ, subspaces times bits per subspace.
3. When a question mentions recall, decide *which* recall. Agreement with exact neighbors is an index question; useful documents reaching the candidate set is a funnel question.
4. Read the budget before the table. The right operating point is the highest recall that fits the stage's latency objective, never the highest available.
5. For "recall got worse in production", suspect the distribution — stale centroids, a new model version, a filtered subset, updates degrading the graph — before the parameters.
6. Watch for absolutes. "HNSW is faster than IVF", "you must use an ANN index" are conditional, and the question hides the condition in one clause about corpus size, filters or memory.
