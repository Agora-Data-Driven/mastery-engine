Chunking is the first irreversible decision in a retrieval-augmented system: it fixes the unit of indexing, and therefore the ceiling on what any downstream retriever, reranker, or LLM can ever see. A hybrid retriever with perfect BM25 tuning and a state-of-the-art reranker still fails if the fact the user needs was split across two chunks or drowned inside one bloated chunk. Because re-chunking means re-embedding and re-indexing the whole corpus, these choices are expensive to revisit, so they deserve deliberate engineering rather than a library default.

## Chunk Size and Overlap: The Core Tradeoffs

A chunk is the atomic unit your index stores: one BM25 posting target, one embedding vector, one candidate the retriever can return. Sizes are measured in tokens, not characters, because both embedding models and LLM context windows meter in tokens; a common working range is 200 to 800 tokens.

The central tension is **precision versus completeness**. Recall from linear algebra that an embedding model compresses a chunk into a single vector, and that vector behaves like a weighted blend of the meanings inside the text. A 1,500-token chunk covering refund policy, shipping times, and warranty claims produces a vector near the centroid of those three topics, far from the query vector for any one of them. Cosine similarity against a focused query drops for every topic the chunk contains: this is **embedding dilution**. Small chunks keep each vector sharp, so retrieval is precise. But small chunks fragment meaning: a 100-token chunk may contain "It must be submitted within 30 days" with no indication of what "it" is, because the referent lived two sentences earlier. Pronouns, definitions, and multi-step arguments get severed from their context, and the LLM receives shards it cannot interpret. Large chunks invert the failure: each retrieved hit carries full context, but the vectors are blurry, relevant chunks rank lower, and every retrieved chunk spends more of the generation context window on text that is mostly irrelevant.

**Overlap** is the standard hedge against boundary damage. A sliding window of size $s$ tokens with overlap $o$ advances with stride $s - o$: each chunk repeats the last $o$ tokens of its predecessor, so a fact that straddles one boundary appears intact in at least one chunk. The cost is index inflation. The number of chunks grows by the factor $\frac{s}{s-o}$: a 10,000-token document at 500-token chunks with no overlap yields 20 chunks; with 100-token overlap the stride is 400, yielding 25 chunks, a 25% increase in vectors to embed, store, and search. Overlap of 10 to 20 percent of chunk size is the usual range; 50 percent overlap doubles the index for marginal additional protection.

Worked example: a 2,000-token policy document, chunk size 500, overlap 100. Chunk 1 spans tokens 0 to 500, chunk 2 spans 400 to 900, chunk 3 spans 800 to 1300, and so on. A sentence occupying tokens 480 to 520 is cut in chunk 1 but whole in chunk 2. Without overlap, that sentence exists nowhere intact in the index, and no retriever setting can recover it.

Overlap has a second-order failure mode: **near-duplicate crowding**. Two adjacent chunks sharing 20 percent of their text often earn nearly identical scores for a query that hits the shared region, so both occupy top-k slots and one of your limited retrieval slots is wasted on redundancy. Production systems deduplicate near-identical hits before assembling context.

The expert move is to stop assuming the retrieval unit must equal the generation unit. In **small-to-big retrieval** (also called parent-document retrieval), you embed small, precise child chunks for matching, but when a child matches, you return its larger parent section to the LLM. You get sharp vectors and complete context simultaneously, at the price of extra storage and a parent-lookup step. Judgment guide: short factoid queries over homogeneous text tolerate small chunks; synthesis-heavy questions over dense documents favor larger chunks or small-to-big. One silent landmine: every embedding model has a maximum input length (many embedding models cap around 512 tokens, others accept 8,000 or more), and text beyond the cap is typically truncated without error, so a chunk longer than the cap has a tail that is permanently invisible to vector search even though it sits in your index.

## Structure-Aware and Semantic Chunking

Fixed-size splitting treats a document as an undifferentiated token stream, so it happily cuts mid-sentence, mid-table, or mid-function. Two families of methods respect meaning instead.

**Structure-aware chunking** splits along boundaries the document already declares. The workhorse is recursive splitting with a separator hierarchy: try to split on the strongest separator first (blank lines between paragraphs), and only if a piece still exceeds the size limit, fall back to weaker separators (single newlines, then sentence boundaries, then words). The result is chunks that are as large as allowed but almost never cut inside a semantic unit. Format-specific structure does better still: Markdown splits on heading levels, HTML on DOM elements, source code on function and class boundaries, and PDFs on layout blocks. Some elements should be **atomic**: a table split mid-row indexes as gibberish in both halves; a code function split mid-body loses its signature or its return. Structure-aware splitters treat tables, code blocks, and lists as indivisible units, oversized or not.

**Semantic chunking** manufactures boundaries where none are marked. The mechanism: split the text into sentences, embed each sentence (or a small sliding window of sentences to stabilize the signal), and compute the cosine distance between each adjacent pair, where distance is $1 - \cos\theta = 1 - \frac{a \cdot b}{\lVert a \rVert \lVert b \rVert}$, exactly the complement of the cosine similarity you already use for retrieval. While consecutive sentences discuss one topic, adjacent embeddings stay close and distances stay small; when the topic shifts, the distance spikes. Place a chunk boundary wherever the distance exceeds a threshold, commonly a percentile of the distance distribution for that document. Worked example: adjacent-sentence distances of 0.11, 0.09, 0.14, 0.58, 0.12, 0.10 with a 95th-percentile threshold of about 0.40 yields exactly one boundary, before the sentence that produced 0.58, splitting the passage into its two actual topics. Lowering the threshold percentile (say from 95th to 80th) fires on smaller shifts and produces more, smaller chunks.

The judgment layer: semantic chunking costs an embedding call per sentence at index time, produces variable-length chunks that still need minimum and maximum caps, and in published comparisons often beats naive fixed-size splitting only modestly while rarely beating good structure-aware splitting on documents that have structure. Experts reach for it when structure is absent or unreliable: meeting transcripts, chat logs, OCR output, and scraped text with mangled markup. For a Markdown knowledge base or a codebase, header-based and syntax-based splitting is cheaper, deterministic, and usually at least as good. Determinism matters operationally: structure-aware splits are reproducible across re-index runs, while semantic boundaries shift if the embedding model changes, which complicates incremental re-indexing.

## Contextual Chunk Enrichment: Titles, Headers, Summaries

Splitting destroys global context by construction. The chunk "The termination notice period is 60 days" is useless in an index of 400 contracts: which party, which agreement? A chunk reading "Returns are accepted within 30 days" from the page for one product will match return-policy queries about every product. The chunk text no longer says what the document knew. Enrichment repairs this by injecting document-level context into each chunk **at index time**, so that both the embedding and the BM25 terms carry it.

The cheapest and highest-yield form is **breadcrumb prepending**: prefix each chunk with its document title and the heading path that contains it, for example `Acme MSA 2025 > 9. Termination > 9.2 Notice`. Now the query "Acme termination notice period" matches lexically on "Acme" and "termination" via BM25 and semantically via the embedding, where before it matched neither. Headers you preserved during structure-aware splitting are exactly the material for these breadcrumbs, which is one reason the two techniques compose. A related pattern prepends a short document-level summary or key entities (product name, client, date range) to every chunk from that document.

The heavyweight form is **LLM-generated contextual enrichment**, popularized as contextual retrieval (Anthropic, 2024): for each chunk, an LLM receives the full document plus the chunk and writes 50 to 100 tokens situating the chunk, for example "This clause is from the Acme master services agreement and specifies the notice period the customer must give to terminate for convenience." That context is prepended to the chunk before embedding and before BM25 indexing. Anthropic reported that contextual embeddings cut top-20 retrieval failure rates by roughly 35 percent on their benchmarks, and combining contextual embeddings with contextual BM25 cut failures by roughly 49 percent; treat the exact numbers as benchmark-specific, but the direction is well replicated. The obvious objection is cost, one LLM call per chunk with the whole document in the prompt, and the standard answer is prompt caching: the document is a stable prefix reused across all of its chunks' calls, so you pay full input price roughly once per document rather than once per chunk.

Two engineering details separate clean implementations from messy ones. First, decide what the enriched text is **for**: the prefix exists to improve matching, so index the enriched text, but store the original chunk boundaries so that generation and citation can use clean source text (a duplicated breadcrumb on every chunk also wastes generation-window tokens). Second, enrichment is derived data with an invalidation problem: when a document is edited, its chunks' contexts can silently go stale, so re-enrichment must be part of the re-index path, which makes LLM enrichment much more attractive for mostly-static corpora than for rapidly churning ones.

Failure modes and judgment: an LLM writing context can hallucinate, and a hallucinated enrichment is worse than none because it injects confident falsehoods into the index itself, where they attract queries the chunk cannot answer; spot-check enrichments and constrain the prompt to describe, not infer. Titles and breadcrumbs are nearly free, deterministic, and should be your default everywhere. Escalate to LLM enrichment when chunks are strongly context-dependent (contracts, codebases, support threads where "it" and "the customer" abound), the corpus is large enough that retrieval failures are your measured bottleneck, and the re-index budget tolerates it.
