1. The Funnel's Ceiling

IR 202 handed you a funnel you can tune end to end — BM25 and vectors fused by Reciprocal Rank Fusion, then a cross-encoder for the precision stage. Every one of those stages ranks chunks somebody else cut. Turn the funnel up, then move the overlap. Like a world-class librarian: they can find any book on the shelves, and none that was never shelved.

This is why chunking is the first irreversible decision in the stack. Re-ranking is a config change; re-chunking means re-embedding and re-indexing the whole corpus. The funnel slider is cheap to move and the overlap slider is not — which is exactly backwards from how much each one can cost you.

2. Size Versus Overlap

The core tradeoff has two dials and they pull against each other: a sharp vector wants a small chunk, an interpretable passage wants a large one, and overlap buys safety by inflating the index. Like a photo crop: tight enough to be about one thing, wide enough that you can tell what it is.

The judgment: short factoid queries over homogeneous text tolerate small chunks; synthesis-heavy questions over dense documents want larger chunks or small-to-big. And note which dial you are actually allowed to move — every embedding model has a maximum input length, and text past it is truncated without an error. Many cap around 512 tokens; a 900-token chunk under such a model has a tail that is permanently invisible to vector search while sitting happily in your index.

3. Where To Cut

Fixed-size splitting treats a document as an undifferentiated token stream, so it cuts mid-sentence, mid-table and mid-function. Run the same contract through four splitters and watch which units survive. Like slicing a cake with your eyes shut versus following the icing lines.

The separator hierarchy behind recursive splitting is ¶¶ blank line → ↵ newline → . sentence → ␣ word: take the strongest separator that fits, drop to a weaker one only when a piece still exceeds the limit. That produces chunks as large as allowed that almost never cut inside a semantic unit — and its blind spot is that a table or a function is not made of paragraphs. Structure-aware splitters treat those as indivisible, oversized or not.

4. The Distance Spike

Semantic chunking manufactures boundaries where none are marked: embed every sentence, measure the cosine distance to the next one, and cut where it spikes. Move the threshold percentile and watch the chunks multiply. Like listening for the pause where a speaker changes subject.

Distance is 1 − cosθ = 1 − (a·b)/(‖a‖‖b‖) — the exact complement of the cosine similarity you already use for retrieval, so this needs no new machinery, only an embedding call per sentence at index time. In published comparisons it beats naive fixed-size splitting only modestly and rarely beats good structure-aware splitting on documents that have structure. The 95th percentile of these six distances lands near 0.47; the lesson quotes ≈0.40 as the rule of thumb, and either way exactly one spike clears it — which is the point.

5. Breadcrumbs And Context

Splitting destroys global context by construction: "The termination notice period is 60 days" is useless in an index of 400 contracts. Contextual enrichment injects the document's knowledge back into every chunk, at index time, before both the embedding and the BM25 terms. Like writing the case name at the top of every loose page in a file.

Two engineering details separate clean implementations from messy ones. Index the enriched text, but store the original chunk boundaries so generation and citation use clean source text — a duplicated breadcrumb on every chunk also wastes generation-window tokens. And enrichment is derived data with an invalidation problem: edit the document and its chunks' contexts go stale silently, so re-enrichment must be part of the re-index path. A hallucinated enrichment is worse than none, because it injects a confident falsehood into the index itself, where it attracts queries the chunk cannot answer.
