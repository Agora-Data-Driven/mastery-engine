**The big idea**: **Chunk Size and Overlap: The Core Tradeoffs**, **Structure-Aware and Semantic Chunking** and **Contextual Chunk Enrichment: Titles, Headers, Summaries** built a corpus that can be found; **Selecting and Ordering Retrieved Context**, **Citation-Grounded Extraction: Attributing Spans to Sources**, **Metadata Filters in Context Assembly** and **Context Window Budgeting: Relevance Density over Volume** decided what to do with the results once they arrived. All of them treat the user's query as a fixed input that fires once and is never touched. Once retrieval feeds a language model that assumption dissolves: the query becomes raw material the system can rewrite, expand, decompose, retry, and route to a database instead of a document index. This lesson is that query-side machinery — the cheap single-shot transforms, the agentic search loop with its stop policy, multi-hop decomposition, conversational rewriting, self-correcting loops, and text-to-SQL as a retrieval tool. They differ in mechanism and are identical in economics: each buys recall or robustness with the same currency, extra model calls and latency.

**Key concepts**

- **A query rewrite is one small model call that transforms the user's text into a better search query before retrieval runs.** Users type `renewal terms` when the corpus talks about `subscription renewal policy`, misspell product names, and omit context the previous screen made obvious. The rewriter normalizes vocabulary toward the corpus, expands abbreviations and adds implied constraints. It is the highest-leverage transform here because retrieval quality is *query-bound* — nothing downstream recovers a query that never matched — and the call costs **100 to 300 ms** with a small model.
- **Expansion generalizes the idea: generate several paraphrases, retrieve with each in parallel, fuse the lists with RRF** as in IR 202. Recall rises because different phrasings catch different documents; cost rises multiplicatively with the variant count, so **two to four** is the practical range.
- **HyDE — hypothetical document embeddings — inverts the direction.** Instead of embedding the question, ask the model to write a short hypothetical answer, embed *that*, and search for real documents near it. It works because answer-shaped text clusters near real answers in embedding space even when the hypothetical answer's facts are wrong: a generated passage about `orthostatic hypotension when standing` sits near genuine medical pages and pulls the right neighbourhood. The failure is symmetric — on a niche factual lookup the model hallucinates confidently and the embedding drags retrieval toward the hallucination. HyDE earns its generation cost on conceptual how-to queries and loses it on precise entity lookups.
- **All three are stateless and pre-retrieval, so they are trivial to A/B** — and the original query is always logged as the fallback.
- **Retrieval as a tool: the model gets `search(query, filters, top_k)` and usually `read(document_id)`, and calls them in a loop.** It searches, inspects snippets, reads promising documents, then decides whether to answer or search again with a better query — a deliberative process that can recover from a bad first query, which single-shot RAG cannot do.
- **The hard part is not searching, it is stopping.** A decide-to-stop policy weighs **coverage** (does the evidence address every facet), **marginal utility** (did the last two searches return documents already seen) and **budget** (a hard cap on tool calls and latency). Without an explicit cap agents loop, rephrasing the same failing query while latency and spend climb. A typical production cap is **three to five searches**, then the model must answer with what it has or declare insufficiency.
- **The cost profile decides where agentic retrieval belongs.** One iteration is one model call plus one retrieval, roughly **one to three seconds**; three iterations push time-to-answer toward **ten seconds before generation starts**. Route with a cheap classifier: multiple entities, constraints or comparison structure go agentic, simple factual questions go single-shot.
- **Tool design carries the reliability.** Stable document IDs in snippets so `read` is cheap; filters in the schema so the model can scope searches; caching of identical searches within a session; and the full trace recorded, since the search sequence is the primary debugging artifact.
- **Query decomposition and multi-hop retrieval exist for compositional questions.** `Which company founded by a Google alumnus raised the largest Series B in 2019` is in no single document. Three mechanisms cover most systems: **single-pass decomposition** (a numbered plan of sub-queries up front, executed, then synthesised), **iterative retrieval** (reasoning and retrieval interleave — read, emit the next sub-query, repeat), and **recursive resolution** (hop one's answer fills the template for hop two).
- **The failure accounting is multiplicative.** If each hop retrieves its fact with probability 0.9, a three-hop chain succeeds with probability $0.9^3 = 0.729$ — about **0.73** before any reasoning error; a fourth hop gives 0.66. Worse, errors propagate semantically: a wrong entity from hop one poisons hop two's query and the chain walks confidently off a cliff. Decomposition itself can split the question along the wrong joints. Cap chain depth, prefer the fewest hops that work, and evaluate per-hop retrieval success separately from final answer accuracy — the fixes differ.
- **Conversational query rewriting across turns repairs context-dependent follow-ups.** After `Tell me about the Team plan`, the turn `How much does it cost?` is unanswerable by search — the bare query retrieves generic pricing text. The mechanism is **contextualize-then-retrieve**: one model call rewrites the latest turn into a standalone query using recent history *including the assistant's previous answer*, which usually holds the entities being discussed. `How much does it cost?` becomes `Team plan pricing`, and that standalone form is what retrieval runs on, what is logged, and what is evaluated.
- **Three conversational failure modes, each with a fix.** *Over-anchoring*: the user changes topic and the rewrite drags in stale entities, so the instruction must include `if the turn is already standalone, return it unchanged`. *Error lock-in*: a wrong previous answer injects its wrong entities into every later rewrite, so confidence-degraded answers are excluded from rewrite context. *History bloat*: keep the last few turns or a running summary, never the full transcript. One small model call per turn makes this nearly always worth it in chat.
- **Self-correcting RAG inserts explicit checks where single-pass RAG fails silently** — weak retrieval producing a confident, fluent, wrong answer. **Retrieval grading**: a model or small classifier judges whether the documents are relevant and sufficient; a failing grade triggers a rewrite and re-retrieval, the corrective pattern from CRAG-style systems. **Generation reflection**: after drafting, check every claim against the context, flag unsupported sentences, regenerate or abstain. A third check asks whether the draft addresses the question at all. Reflect, re-retrieve, refine — with a budget.
- **Every gate needs a fall-through policy, and abstention is a legitimate output.** One or two re-retrievals at most, then caveats or abstention: for a support product, `I could not verify this from our documentation` beats a fabricated policy detail. Each check is a model call, so a fully checked pipeline runs **two to four times** the latency and token cost of single-pass RAG — so skip reflection when retrieval scores are strong and the question is simple. The checks are model judgments and err in both directions, approving bad evidence and rejecting good, which is why they are gates with budgets rather than loops without end. Log which corrective path fired; that distribution is the health metric of the retrieval layer underneath.
- **Text-to-SQL makes the database another retrieval tool for structured data.** `What was churn in Q3 by plan?` is answered by rows, not by any chunk. The model generates SQL from the question plus schema context, the system executes it read-only, and the rows become context. Three mechanisms decide success: **schema linking** (retrieve the relevant schema subset rather than dumping thousands of columns), **few-shot exemplars** (a handful of question-to-SQL pairs in the house style beats zero-shot by a wide margin), and **value grounding** (the filter `Team plan` must map to a real `plan_id`, via a lookup or a curated list of dimension values).
- **Guardrails are not optional, because model output is never executed raw.** Read-only role, allow-listed tables, row limits, query timeouts, estimated bytes scanned before running, a result-size cap, and a parse that rejects anything that is not a single SELECT. Failure modes are specific: hallucinated columns; wrong join grain producing fanout duplicates, the hazard from DE 102's grain lessons; empty results misread as `zero churn` instead of `wrong query`; and ambiguous questions needing a clarification loop, not a guess.
- **Quality is bounded by schema documentation, not model cleverness.** Column descriptions and metric definitions — in effect a semantic layer — matter more than a better model, and governed metrics are better served by curated semantic-layer queries than free-form generation. Keep the SQL and returned rows in the trace: they are the audit artifact. In hybrid systems an orchestrator routes each question to document retrieval, to SQL, or to both, and the agentic loop chooses the tool.

**Rules to remember**

- Rewriting first, expansion when recall is measurably short, HyDE for conceptual traffic only — and keep the original query as the fallback.
- An agentic loop without a hard cap is a latency bug waiting to fire: three to five searches, then answer or declare insufficiency.
- Multi-hop success is the product of per-hop successes; a wrong hop corrupts later queries as well as the answer, so grade hops separately from final accuracy.
- In conversation, retrieval runs on the *standalone* rewrite; an already-standalone turn is returned unchanged.
- Gates have budgets: one or two re-retrievals, then caveats or abstention.
- Generated SQL is parsed and executed read-only — single SELECT, with limits and timeouts.

**Common pitfalls**

- **Applying HyDE everywhere.** On precise entity lookups the hypothetical answer is a hallucination and steers retrieval toward it.
- **An agentic loop with no stop policy.** It rephrases the same failing query; the symptom is a slow answer, not an error.
- **Sending easy questions down the agentic path** and paying ~10 s before generation starts.
- **Decomposing a question one retrieval would have answered.** Every hop is another model call and another multiplicative failure term.
- **Rewriting a follow-up that was already standalone** — over-anchoring, which drags stale entities in on a topic change.
- **Feeding a wrong previous answer into the rewrite context.** That is error lock-in: one bad turn poisons every later query.
- **Treating a self-correction gate as infallible.** It is a model judgment and needs a fall-through.
- **Reading an empty SQL result as a real zero.** `zero churn` and `wrong query` look identical in the rows.

**How to approach the questions**

1. Ask what the technique *costs*. Nearly every judgment question here resolves to "extra model calls and latency, bought for recall or robustness" — then ask whether the traffic deserves it.
2. Check whether the transform is stateless and pre-retrieval (rewriting, expansion, HyDE) or history-dependent (conversational rewriting); distractors swap them.
3. For HyDE, read the query type in the stem: conceptual how-to versus precise entity lookup flips the answer.
4. For agentic scenarios, find the stop condition. If the scenario has none, that is the defect, whatever else it describes.
5. For multi-hop, do the arithmetic — per-hop probabilities multiply — and separate a retrieval miss from a propagated wrong entity.
6. For self-correcting designs, ask what happens when the gate fails twice. A correct answer names caveats or abstention, never an unbounded loop.
7. For text-to-SQL, separate the three mechanisms (schema linking, exemplars, value grounding) from the guardrails (read-only, allow-list, limits, single-SELECT parse). A stem usually breaks exactly one of them.
