**The big idea**: **Context Window Budgeting: Relevance Density over Volume** taught you to spend a token allowance deliberately, **Selecting and Ordering Retrieved Context** decided what went into it, **Retrieval as a Tool: Search, Read, Decide-to-Stop** bought extra recall with extra model calls, **Context Precision and Context Recall** measured whether that spending bought anything, and **Tenant Isolation in Shared Indexes** made the pipeline safe to share. Every one of those decisions has a price, and the user experiences the sum of all of them. A RAG answer is a chain of model calls; this lesson is the ledger for that chain. Three ideas do the work: the **RAG latency budget** allocates milliseconds stage by stage from a target backwards, **caching layers** buy back time and money wherever work legitimately repeats, and the **long context vs retrieval** question has a definite cost shape rather than a matter of taste. None of it is guesswork — every stage has a measured distribution, every cache has an invalidation contract, and the arithmetic decides.

**Key concepts**

- **End-to-end latency decomposes, and streaming splits it into two halves that matter differently.** The chain is an optional rewrite, retrieval, reranking, context assembly, then generation — and generation itself splits into **time-to-first-token** and **decode**. Streaming hides decode behind progressive rendering, so the user reads while the model writes; everything *before* the first token is dead time. The pre-generation block is the latency frontier engineering actually controls, and it must fit in roughly two seconds or the product feels stalled no matter how fast tokens then stream.
- **A representative budget for an 8-second target with streaming.** Rewrite 0.2 s or skipped; parallel retrieval legs 0.3–0.5 s, since BM25 and the ANN service run concurrently; reranking 0.5–1.5 s depending on depth; assembly effectively free; time-to-first-token 0.5–1.5 s; decode 2–5 s depending on answer length.
- **Budget backwards from the objective, and measure p50 and p95 in production.** Benchmark numbers lie about queueing. A healthy measured system: rewrite 120 ms p50 / 280 ms p95 (budget 300 ms); parallel retrieval 180 / 450 (budget 500 ms); rerank at depth 50, 380 / 900 (budget 1,000 ms); time-to-first-token 600 / 1,400 (budget 1,500 ms); decode 2.8 s / 5.5 s, user-tolerated because it streams. Summed, the p95 column is **three to four seconds of dead time before streaming begins**, and that is the figure the SLO must absorb.
- **The chain's p95 is not the sum of the stage p95s.** Stages do not all hit their worst case on the same request, so the true tail sits below the sum — under independence, well below it. But load correlates: a busy moment slows every stage at once, so the sum of p95s is the safe approximation to budget with, and the measured end-to-end p95 is what you verify against.
- **Parallelize whatever the dependency graph allows.** Retrieval legs run concurrently; the raw-query embedding can run alongside the rewrite as a hedge, so a slow rewriter never blocks retrieval entirely.
- **Decode is pure multiplication: output tokens × per-token latency.** 400 tokens at 15 ms per token is 6 s, and no amount of retrieval tuning touches it. The controls are output caps, prompts that demand concision, streaming, and routing simple query classes to a smaller, faster model to generate with.
- **Every stage needs a deadline with an evaluated fallback.** Reranker timeout serves the fused order; model timeout retries once then degrades gracefully; queues are bounded so overload sheds load rather than compounding it.
- **The cost ledger runs in parallel, and input tokens dominate.** Ten chunks of 500 tokens is 5,000 input tokens per query; at 100,000 queries a day that is **500 million input tokens daily**. Add reranker accelerator-seconds and output tokens, and track cost per answered query next to p95. Quality work that doubles input tokens is a pricing decision, not only a relevance one.
- **Two levers move cost without touching users.** Context assembly discipline — eight focused chunks instead of fifteen loose ones is a direct input-token cut — and query-class routing, since about a third of traffic is simple enough for a smaller, cheaper generator with no measurable quality loss *on that class*. Both stay invisible only when the evaluation layer verifies the savings did not come out of answer quality.
- **Three caching layers sit at different points, with different savings and liabilities.** The **embedding** cache maps normalized query text to its vector, saving tens of milliseconds and one model call; normalization (lowercasing, whitespace collapsing) is what makes repetitions actually collide. The **result** cache maps query + filters + ACL context to the fused or reranked candidate list, erasing the two slowest pre-generation stages at once — usually the highest-value layer. The **answer** cache maps query + context hash to the final answer, saving everything, and is correspondingly the most dangerous: valid only for non-personal, non-time-sensitive answers.
- **Every cache key must carry the versions that can invalidate it.** Embedding keys include the model version, because vectors from different models are incompatible. Result keys include the index generation, or a re-index silently serves stale candidates, and the tenant plus ACL hash, or the cache becomes the cross-tenant leak the security lesson warned about. Answer keys include corpus generation and prompt version, with a TTL as backstop. Never cached at all: personalized answers, answers from revoked documents, and time-dependent facts such as status pages.
- **Semantic caching keys by embedding similarity rather than exact text.** Hit rates jump, but the cache now answers questions that are merely *similar*, and similar is not equal: a user asks about the Team plan and gets the Enterprise answer because the embeddings were close. Treat it as experimental — high thresholds, low-stakes classes only, the score logged on every hit, and a kill switch back to exact-match keys.
- **The economics justify the discipline.** At 100,000 queries a day, a 35% result-cache hit rate eliminates roughly **35,000** retrieval-plus-rerank executions, and a 20% answer-cache rate eliminates **20,000** full generations. Savings land in both the bill and the p95, because hits skip the slowest stages entirely. Caching is the cheapest capacity available — and each layer is a consistency liability.
- **Long context vs retrieval, on variable cost.** A long-context call pays input price for the entire stuffed slice on *every* query: 100,000 tokens of context × 100,000 queries a day is **10 billion input tokens daily**, against roughly 5,000 focused tokens on the retrieval path — a twenty-fold difference that grows with corpus size. Retrieval pays the corpus cost **once**, at ingest, through embedding and indexing; long context pays it per query, forever.
- **Latency tells the same story.** Prefilling a hundred thousand tokens takes seconds before the first token appears, which reclassifies long-context calls as batch jobs rather than interactive ones; the retrieval path reaches first token in about a second. Accelerated processing does not change the shape: prefill grows with the slice while the retrieval path is essentially flat in corpus size, so the gap widens as the corpus grows.
- **Quality is subtler, and must be measured rather than assumed.** The lost-in-the-middle effect means models underuse the middle of long contexts, and needle tests show recall of a specific fact degrading as context grows. Retrieval's focused context is an *attention-precision* optimization: fewer, better chunks beat more, noisier ones. But long context genuinely wins for whole-corpus reasoning and cross-document synthesis, for corpora small enough to fit entirely, and for eliminating retrieval's own failure modes — chunking damage and the recall ceiling — by not having them. Freshness tilts further: a stuffed context is a snapshot, re-stuffed at every corpus change, while retrieval reads the live index. Prefix caching blurs this for repeated large contexts without changing the arithmetic for dynamic corpora.

**Rules to remember**

- Streaming hides decode, never the pre-generation block. Optimize what happens before the first token.
- Budget backwards from a target; measure p50 and p95 in production, not on a benchmark.
- Budget with the sum of stage p95s; verify against the measured end-to-end p95, which is lower.
- Decode time = output tokens × per-token latency. Cap the output or route to a faster model.
- Every stage gets a deadline and an evaluated fallback; queues are bounded.
- Input tokens are the dominant variable cost. Cost per answered query is a first-class metric.
- Cache keys carry model version, index generation, tenant + ACL hash, corpus and prompt version.
- Never cache personalized, revoked-source, or time-dependent answers.
- Hit rate and staleness complaints are read together, never separately.
- Retrieval pays the corpus cost once at ingest; long context pays it on every query.

**Common pitfalls**

- **Optimizing decode when the complaint is "it feels slow."** With streaming on, the felt delay is the pre-generation block; shaving a second off decode changes nothing a user notices.
- **Treating the chain's p95 as one stage's problem.** The tail is assembled from every stage; a rerank at depth 200 can blow the budget while every dashboard still looks green.
- **Reading benchmark latencies as production latencies.** Benchmarks omit queueing, which is exactly where the p95 lives.
- **Caching without versioning the key.** A re-index or a prompt change turns a cache into a machine for serving confidently stale answers; an ACL-blind result key turns it into a cross-tenant leak.
- **Celebrating a rising cache hit rate on its own.** Rising hits alongside rising stale-answer reports is a failure mode wearing a success metric.
- **Shipping semantic caching at a loose threshold.** Near-duplicate is not duplicate, and the Team-versus-Enterprise answer is wrong in a way no latency graph shows.
- **Buying quality with input tokens and never pricing it.** Fifteen chunks instead of eight is a permanent bill increase the relevance review never sees.
- **Assuming a bigger window retires retrieval.** It moves the break-even point; it does not repeal the arithmetic.

**How to approach the questions**

1. Locate the stage first. "Slow to start" is pre-generation; "slow to finish" is decode, and the fix there is token count, not retrieval.
2. When a budget is given, add the stage p95s and compare with the target before choosing — the arithmetic usually eliminates two options outright.
3. For any cache question, ask what changed since the entry was written. The answer names a version component that belongs in the key.
4. Separate savings from liability: which stages does this layer skip, and what can go stale or leak because of it?
5. For long-context questions, run the five checks — corpus size relative to the window, point lookup versus corpus synthesis, query rate × per-query context cost, freshness requirement, and what needle tests and the golden set say on *your* data.
6. Watch for stems where a per-query cost is quietly multiplied by a large query rate; that multiplication is usually the whole question.
7. Prefer the hybrid answer when workloads differ: interactive Q&A over a two-million-chunk corpus retrieves, a nightly compliance pass over one customer's contracts goes long-context in batch, and an agent may retrieve a dossier then synthesize it in one long-context call.
